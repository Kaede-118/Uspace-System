## 一、结论

**在营业执照与 ICP 备案未就位的阶段，用樱花 frp 免费版做内网穿透对外提供服务，
暂不购买云服务器。**

三条理由：

1. **成本** —— 免费版 0 元；对照香港轻量服务器首年 100-200 元 + 域名
2. **免备案** —— 走境外节点，不需要 ICP 备案（境内节点则要）
3. **访问不带端口** —— 樱花支持 HTTP/HTTPS 隧道，由服务商在 80/443 上按域名分流，
   因此访问 `https://你的域名` 是标准形态，不是 `:12345` 那种高位端口

代价如实记录在第七节 —— 延迟、稳定性、数据经第三方、合规、以及「服务跑在自己机器上」
带来的运维负担。**本文不是「这条路更好」的论证，而是「这条路的账已经算清楚、决定走它」的记录。**

## 二、被否掉的选项（写清楚，将来不必重新调研）

| 选项 | 否掉的理由 |
|---|---|
| **改本机端口到 80/443** | ① **端口数字 ≠ 服务数量** —— 现在是两个服务（Vite:5173 + Spring Boot:8080），改成 443 还是两个端口，一条都不省；要只映射一个，得让两个服务**同源**（见第五节）。② **443 是 HTTPS 端口** —— 本机跑的是明文 HTTP，挂上去会 TLS 握手失败。③ **Windows 上 <1024 端口要管理员权限**，且 443 常被代理/IIS/Docker 占用。④ 对生产毫无帮助 —— 生产形态是 nginx 一个端口托管前端 + 反代 `/api`，**后端仍在 8080** |
| **自建 frp（自己买 VPS 跑 frps）** | 照样得租一台有公网 IP 的服务器，与「云服务器直跑」差价只有几十元/年，再加电费反而更贵。详见 `Docker化与云部署草案.md` 2.1 |
| **自签证书** | 浏览器亮红警告（「您的连接不是私密连接」），而这是**要输密码、要传付款凭证**的页面，顾客直接就跑。不可接受 |
| **HTTP 明文隧道** | 浏览器标「不安全」；且 `Service Worker` 要求 secure context，**PWA 直接不可用**（见 `CLAUDE.md`「客户端形态」） |
| **樱花隧道里的「HTTP 用户名 / HTTP 密码」字段** | ⚠️ **不要填**。它会加一层 HTTP Basic Auth，而 Basic 与 JWT **用的是同一个 `Authorization` 头** —— 两者必然互相覆盖。表现为页面能打开、数据全不出来（401），且前端代码拿不到这一层、无从处理。该字段是给「临时把某个后台给同事看一眼」设计的，不适合任何有 API 调用的应用 |

> ⚠️ **一处曾经的误判要记下来**：初稿认为「公共免费 frp 给不了 80/443」，
> 那是把 **TCP 隧道**的端口限制当成了 frp 的普遍限制。**HTTP/HTTPS 隧道走的是另一套机制**
> —— 服务商自己在 80/443 上监听、按域名（Host / SNI）分流到各用户，
> 因此「不带端口」是能拿到的。这个区别值得记住。

## 四、樱花 frp 的实际情况（2026-10-08 调研）

### 4.1 免费版参数

| | 普通用户（免费） | 青铜 VIP ￥10/月 | 白银 VIP ￥20/月 |
|---|---|---|---|
| 隧道数量 | **2 条** | 10 条 | 10 条 |
| 隧道限速 | 10 Mbps | 24 Mbps | 36 Mbps |
| 每月流量 | **5 GiB** | 5 + 108 GiB | 5 + 158 GiB |
| 解锁节点 | 普通节点 | 青铜节点 | 青铜、白银节点 |

**另有「每日签到领流量」，实测约 3 GiB/天（4 天得 12 GiB）→ 合每月约 90 GiB。**
加上基础 5 GiB，免费版实际可用流量约 95 GiB/月。

**够不够**：本系统流量大头是付款截图（单张上限 2 MB，见 `uspace.upload.max-image-bytes`），
粗估一天 5 位顾客约 20 MB/天 → 约 600 MB/月，管理员看后台翻倍到 1.2 GB 左右。
**95 GiB 远超所需，流量不是约束。**

**所以 VIP 不必买** —— 多出来的东西（10 条隧道、上百 GiB、更高带宽）本场景一样用不上。

### 4.2 节点与备案

节点分两类（面板实测，2026-10-08）：

- **内地节点 16 个** —— 浙江、济南、江苏、长沙、石家庄、东莞、重庆、福建、成都等，
  多为「三网 DNS 分流」的 PLUS / 三线线路，**延迟低**。全部标注「建站」
- **境外节点 6 个** —— 韩国1、越南1、日本1、日本2、新加坡1、中国台湾CHT1。
  **全部标注「只推荐海外用户使用」**（台湾那条是「线路无优化，只推荐非内地用户使用」）

⚠️ **这是本方案的核心矛盾**：

| | 内地节点 | 境外节点 |
|---|---|---|
| 线路 | 三网分流，延迟低 ✅ | **樱花自己标注「只推荐海外用户使用」** |
| 备案 | **建站前要过「用户信息 → 验证备案」** ❌ | 免 ✅ |
| 免费子域名 + 证书 | 有（nyat.app） | **不给** ❌ |

**两个门槛各堵一头**：内地节点要过「验证备案」；海外节点不给子域名（也就拿不到免费证书）。

### 4.3 自动 HTTPS 与证书

**机制**（官方文档 `doc.natfrp.com/frpc/auto-https.html`）：frpc 在**本机侧**承接 TLS，
「脱壳」后再用明文 HTTP 连本地服务。**因此本机服务保持 HTTP 即可**，不必自己跑 HTTPS。

⚠️ **但 `auto` 模式默认给的不是真证书**：

| 怎么设 | 拿到什么 | 浏览器表现 |
|---|---|---|
| `auto`，**没做子域绑定** | frpc 用节点域名当 CN **生成自签证书** | 🔴 报警告（HSTS 下可能直接打不开）|
| `auto` + **已做子域绑定** | 从服务端**自动加载樱花签发的证书** | ✅ 正常 |

**子域绑定**（免费 `nyat.app` 子域名 + 樱花签发证书）的流程：

```
1. 管理面板 → 子域绑定 → 申请一个 nyat.app 子域名
2. 绑定到已开启自动 HTTPS 的隧道，自动 HTTPS 设为「自动」
3. 为 Web 应用创建 CNAME 记录作为访问地址
4. 重启隧道，frpc 会从服务端自动加载证书
   日志出现「已从服务器为 xxx.nyat.app 加载证书」
5. 首次可能提示「Nyat APP SSL 证书签发中」，保持隧道开启，通常几分钟后签发成功
```

⚠️ 子域绑定提供的域名**已开启 HSTS Preloading** —— 好处是强制 HTTPS，
代价是**证书一有问题页面直接打不开、没有「继续访问」的按钮**。

⚠️ **用自己的域名时证书要自备**：`auto_https` 支持填自己的域名，逻辑是读 frpc 工作目录下的
`<域名>.crt` / `<域名>.key`，**加载失败则退回自签证书**。

⚠️ **实测（2026-10-09）：Windows 上那个工作目录是
`%PROGRAMDATA%\SakuraFrpService\FrpcWorkingDirectory\`** —— 比官方文档的说法多一层子目录。
判断依据：隧道启用自动 HTTPS 后，frpc 自动生成的自签证书就落在这里
（文件名就是 `<域名>.crt` / `<域名>.key`，Subject 为 `SakuraFrp Automatic TLS sn.xxxx`）。
换真证书时**覆盖**这两个文件、重启隧道即可。

### 4.4 四个坑

1. **禁忌证** —— 穿透对象**本身已是 HTTPS** 时不要开自动 HTTPS（会 TLS 套 TLS，
   Nginx 报 `400 Bad Request`）。本文方案的 Vite 是 HTTP，不踩这条。
   ⚠️ 官方文档特意警告「已遇到上百例因乱开自动 HTTPS 开关造成隧道访问不了」
2. **「HTTP 用户名 / HTTP 密码」不要填** —— 理由见第二节最后一行
3. **内地节点的「验证备案」是创建隧道的前置条件** —— 页面提示：
   「使用该节点建站时，需要到 用户信息->验证备案 页面完成验证才能创建 HTTP(S) 隧道」
4. **绑定域名最多 3 个** —— 本方案只用 1 个（前后端同源），无影响

## 五、tunnel 模式（已落地，2026-10-08）

**要只映射一条隧道，就得让前端与后端同源。** 做法是让 Vite 代理 `/api`，
请求链路变成：

```
顾客浏览器 →（frp 隧道）→ Vite :5173 ─┬─ /            前端 SPA
                                      ├─ /api/…       代理 → Spring Boot :8080
                                      └─ /uploads/…   代理 → Spring Boot :8080
```

### 5.1 四处改动

```
frontend/vite.config.js    defineConfig 改为函数形式，mode === 'tunnel' 时才挂 /api 代理
                           ⚠️ 同时放行隧道域名（server.allowedHosts，见 5.4）
frontend/.env.tunnel       新增：VITE_API_BASE_URL=（空串 → axios 走相对路径）
frontend/package.json      新增 script: "dev:tunnel": "vite --mode tunnel"
```

### 5.2 为什么做成独立模式，而不是把 `/api` 代理常开

`vite.config.js` 里原本写着一条**刻意的决策**：「`/api` 不配 proxy，
开发期一路顺畅，上线换 nginx 时才发现预检或响应头没配对」。

**常开就永久失去这条收益。** 独立模式下：

| | `npm run dev`（日常） | `npm run dev:tunnel`（穿透） |
|---|---|---|
| `/api/billing/rules` 返回 | `index.html`（SPA fallback） | 真实 JSON |
| 说明 | 没代理，前端仍直连 8080，**CORS 问题照常暴露** | 代理生效，前后端同源 |
| 行为变化 | **0**（一个字节都没变） | 新增能力 |

**已实测验证**（2026-10-08）：两个模式分别起在 5198 / 5199 端口，`/api` 的返回
一为 HTML、一为 JSON，隔离确认无误。

### 5.3 为什么不用 nginx 那一层

生产环境这一层由 nginx 承担（托管 dist + 反代 `/api`），**同样是同源、同样只需一个端口**。
穿透演示时用 Vite 代这一层，是同一个思路的两种落地 —— 省掉「先 build 再配 nginx」的步骤。

> ⚠️ **代价**：跑的是 dev server，性能不如构建产物。对演示够用；
> 若将来穿透形态要长期服役，应改为 `npm run build` + 一个静态服务器 + 反代。

### 5.4 第四处改动：放行隧道域名（2026-10-09 实测补）

**Vite 4.0+ 有 `allowedHosts` 防护（防 DNS rebinding 攻击），默认只接受
`localhost` 与 IP 的 Host 头 —— 带域名的请求一律 403**，响应体直接写着
`Blocked request. This host "xxx" is not allowed.`。

而穿透正是按域名转发的，于是出现一个**极难排查**的现场 —— 每一环单独看都是对的：

| 检查项 | 结果 |
|---|---|
| 本地 5173 直连 | ✅ 200 |
| DNS 解析 | ✅ 正常 |
| frpc 与节点连接 | ✅ 已建立 |
| 服务器返回的证书 | ✅ 正是本机 frpc 那张（**证明请求确实到达了 frpc**）|
| 经域名访问 | ❌ **403** |

**只有把 403 的响应体读出来才看得见答案** —— 否则容易一路怀疑隧道、DNS、证书，
绕一大圈。修法（写在 `isTunnel` 分支里）：

```js
server.allowedHosts = ['nsfwonly.fans']   // 精确白名单，不是 true
```

⚠️ **换域名时这里与后端 `uspace.web.base-url` 要一起改** —— 它们是同一件事的两端。

⚠️ **必须用 `npm run dev:tunnel` 启动才生效**（它写在 `isTunnel` 分支里，
与 5.2 的纪律一致：日常 `npm run dev` 行为一个字节不变）。
⚠️ 顺带一提，用 `npm run dev` 时**不只是域名被拒**：`/api` 代理也没挂，
前端所有接口请求会拿到 SPA 的 index.html 而不是 JSON —— 两个症状同时出现时，
先确认启的是哪个模式。

## 六、配置步骤

### 6.1 樱花面板

| 项 | 填什么 |
|---|---|
| 节点 | 境外：台湾 CHT1 或 日本2；内地：任一标「建站」的 PLUS 节点（需先过验证备案）|
| 隧道类型 | **HTTPS**（或 HTTP）|
| 本地 IP | 留空（即 `127.0.0.1`）|
| **本地端口** | **`5173`** |
| 绑定域名 | 子域绑定给的 `xxx.nyat.app`，或自己的域名 |
| HTTP 用户名 / 密码 | **留空**（理由见第二节）|
| 自动 HTTPS | `自动`（配合子域绑定）；自备证书时填自己的域名 |

### 6.2 本机

```bash
cd frontend
npm run dev:tunnel      # ⚠️ 必须用这个，不是 npm run dev
```

### 6.3 后端配置（⚠️ 容易漏）

`backend/src/main/resources/application.properties`

```properties
uspace.web.base-url=https://你的域名
```

**这一项决定所有「发给别人的链接」长什么样**，两处用到它：

- **包场邀请链接** —— 包场人发到群里，被邀请者点开
- **QQ 群里的 `fwweb` 指令** —— 机器人给出的网页端地址

不改的话链接还是 `http://localhost:5173` —— **顾客点开只会打开他自己手机上的 localhost**，
且他不会知道为什么。改完**后端要重启**才生效。

> `CLAUDE.md` 里对这条已有一模一样的记录（原为「局域网调试」写的）：
> 「后端跑在店里的电脑上、顾客手机在别处，发 localhost 出去只会在对方自己的手机上打开」

### 6.4 域名

**买 `.com`**（`.cn` 在没执照、不备案的阶段更麻烦，见下）：

- **别用 `.xyz` / `.top` / `.club` 这类便宜后缀** —— 将来要备案时可能不在工信部批复名单里
  （`.io` / `.dev` / `.app` 明确不在）
- **在阿里云 / 腾讯云买**，别在海外注册商买（备案要求注册商是境内机构）
- **下单前看续费价** —— 真正决定成本的是续费价，不是首年价
- ⚠️ **持有者信息填真实的、将来要做备案主体的那个人** —— 拿到执照后要**过户一次**
  （个人 → 个体户），同平台内的「持有者信息修改」，一般 1-3 天

## 七、已知代价（如实记录）

| 代价 | 具体是什么 |
|---|---|
| **延迟** | 链路是「顾客手机（广州）→ 境外节点 → **回连店里**」，**出国再回国**。广州↔台湾/日本约 30-80ms，穿透绕两趟 ≈ 150-400ms。**用户接受「1 秒以内」的标准，这个量级在范围内**；但首次加载页面（下载整个 SPA）约 1-2 秒、上传付款截图（最大 2 MB）受**店里上行带宽**限制约 2-5 秒 |
| **稳定性** | **三个单点**：樱花节点（免费版共享、限速 10 Mbps、可能降速）、你自己的机器（断电/断网/路由器死机）、店里的宽带（家庭宽带协议普遍写明「不得用于经营性对外服务」）。**全都自己扛，无人值守门店出故障时现场没人能处理** |
| **安全** | **frps 是流量的终点**，能看到全部明文请求内容 —— 而本系统跑的是**登录密码、JWT token、付款截图（含付款人昵称与金额）、QQ 号**。第三方服务商是谁、节点在哪儿，都不在你的控制内 |
| **合规** | 用境外节点规避备案，而本系统是**明摆着的经营性网站**（下单、收钱、传付款凭证）。实际被抽查概率不高，但被举报是另一回事 |
| **运维** | 机器要 24 小时开机；**开发机 = 生产机**（改代码要重启、跑测试占满 CPU、晚上不能关机），而开发期恰是改动最频繁的时期 |

> **PWA 不在代价之列** —— 走 HTTPS 隧道时 secure context 成立，Service Worker 可用 ✅
> （这正是必须用 HTTPS 隧道而非 HTTP 明文隧道的原因之一）

## 八、待办与未决（涉及时先与用户确认）

### 8.1 三件待办

1. **⚠️ 晚高峰实测（唯一真正的未知数）** —— 普通节点是共享的，而**营业高峰 20:00-23:00
   恰是节点最挤的时候**，下午测的数字不算数。实测要在**店门口、用手机流量**，
   记三个数：打开首页几秒、点「开门计时」几秒回、传一张图几秒
2. **证书方案落地（进行中）** —— 已定：走**阿里云免费 DV 证书**（域名在阿里云，
   控制台可用「自动 DNS 验证」自助签发，无需手动加 TXT 记录）。
   ⚠️ 免费证书有效期 **3 个月**、**到期不支持续期**，要在到期前重新申请并覆盖
   `FrpcWorkingDirectory` 里的两个文件，否则第 91 天网站打不开。
   （早先设想的 Let's Encrypt + DNS-01 仍是可选路线，但域名已在阿里云时，
   上面那条更省事 —— 不必自己跑 ACME 客户端。）
3. **去看内地节点的「用户信息 → 验证备案」页面要求什么** —— 这是**可能改变整个结论**的一件事：
   - 若验证的是**你自己的备案号** → 内地节点这条路暂时堵死（等执照 + 备案）
   - 若只是承诺/确认，或验证的是**樱花自己的域名** → 那 `nyat.app` 子域名就能用上，
     **内地节点 + 免费子域名 + 免费真证书 + 低延迟，方案完美落地**
   - ⚠️ 关键判断依据：**备案是「域名」维度的事** —— `nyat.app` 的备案主体是樱花而非用户，
     用他们给的子域名，用户理论上不需要办备案。**以面板实际要求为准**
