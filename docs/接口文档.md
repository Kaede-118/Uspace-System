## 一、通用约定

### 1.1 基地址

| 环境 | 地址 |
| --- | --- |
| 本地开发 | `http://localhost:8080` |

所有接口以 `/api` 开头。开发期 CORS 已放开所有来源（见 `SecurityConfig`），
前端脚手架尚未创建，端口未定 —— 换端口时不必额外配置。

> ⚠️ 生产环境应当把 CORS 来源收紧为实际的前端域名。

### 1.2 认证

**除下面列出的匿名接口外，一律需要携带凭证。**

```
Authorization: Bearer <token>
```

- `token` 由 `POST /api/auth/login` 返回，前端存 `localStorage`
- 有效期 **7 天**（`uspace.auth.expire-days`），到期需重新登录
- **没有 refresh token** —— 单 token 方案，过期就重新登录

**匿名可访问的接口**（共 5 个，精确匹配，不做前缀通配）：

| 路径 | 说明 |
| --- | --- |
| `POST /api/user/register` | 注册 |
| `POST /api/auth/login` | 登录 |
| `GET /api/store/status` | 门店营业状态（相当于店门口挂的牌子，要求先注册才能看是把新顾客挡在门外） |
| `POST /api/payments/notify/wxpay` | 微信支付回调（鉴权改由**验签**承担） |
| `POST /api/payments/notify/alipay` | 支付宝回调（同上） |

**凭证失效的三种情形**，前端拦截器应统一处理为「跳登录页」：

| 业务码 | HTTP | 含义 |
| --- | --- | --- |
| `UNAUTHORIZED` | 401 | 没带凭证 |
| `TOKEN_INVALID` | 401 | 凭证损坏，或因**改密 / 封禁**被撤销 |
| `TOKEN_EXPIRED` | 401 | 已过期 |

### 1.3 统一返回体

**所有响应都是同一结构，包括 401、403、404、500 这些错误出口。**
前端因此只需写一次统一的错误处理，不必为「万一某个接口挂掉返回的是 HTML 错误页」做兼容。

```json
// 成功
{ "code": 0, "message": null, "data": { } }

// 失败
{ "code": 40901, "message": "该用户名已被使用", "data": null }
```

- `code` 为 **0** 表示成功，**不用 200** —— HTTP 状态码已经表达了「请求成功」，
  body 里再放一个同名不同义的 200 只会让人混淆
- 失败时 `code` 是**五位业务码**，前三位与 HTTP 状态码对齐（如 `40901` 对应 409）
- **HTTP 状态码用真实的**，不是一律 200 —— axios 拦截器靠它统一识别登录态失效，
  网关与监控也靠它统计错误率

> **例外**：两个支付回调端点的响应体**不是这个结构**，而是支付平台自己的协议
> （微信 `{"code":"SUCCESS"}`、支付宝纯文本 `success`）。理由见第九章。

### 1.4 错误码

完整的错误码表见[附录 A](#附录-a完整错误码表)。几条通用的：

| 业务码 | HTTP | 场景 |
| --- | --- | --- |
| `PARAM_INVALID` | 400 | 参数校验失败、格式错误、类型不匹配 |
| `UNAUTHORIZED` / `TOKEN_INVALID` / `TOKEN_EXPIRED` | 401 | 见 1.2 |
| `BAD_CREDENTIALS` | 401 | 用户名或密码错误（**用户不存在也复用它**，避免被枚举账号） |
| `FORBIDDEN` | 403 | 角色不足（普通用户访问了 `/api/admin/**`） |
| `ACCOUNT_DISABLED` | 403 | 账号被禁用 |
| `NOT_FOUND` | 404 | 资源不存在（含未匹配到任何接口的路径） |
| `INTERNAL_ERROR` | 500 | 服务端异常兜底（堆栈只进日志，不外泄） |

**参数校验失败时**，`message` 是各字段错误的拼接，用 `；` 分隔 ——
用户一次就能看到全部问题，而不是改一个提交一次。

### 1.5 分页

**请求参数**：`page`（页码，从 1 开始，默认 1）、`size`（每页条数，默认 10，**最多 100**）。

**返回体**：

```json
{
  "total": 42,      // 总记录数（满足条件的全部，不是当前页的条数）
  "current": 1,     // 当前页码，从 1 开始
  "size": 10,       // 每页条数
  "records": []     // 当前页的记录列表
}
```

> **`size` 传超过 100 会被拒绝**（400），不是静默截断。
> 唯一的例外是 `GET /api/access-records/me`，它的 `page`/`size` 没有校验注解，
> 超限时由 MyBatis-Plus 的分页插件截断。

排序规则由各接口自行规定，**但都带第二排序键**（通常是 `id`）——
否则同一时刻创建的行在翻页时顺序不确定，会出现重复或漏行。

### 1.6 时间格式

**请求体与响应体里的 `LocalDateTime`，统一是 `yyyy-MM-dd HH:mm:ss`。**

```json
{ "startAt": "2026-09-29 14:00:00" }
```

> ⚠️ **查询参数（`?from=...`）是另一套机制**：它走 Spring 的类型转换，不经过 Jackson，
> 所以只有**显式标注了格式**的参数才能接收带空格的日期串。
> 目前只有 `GET /api/admin/access-records` 的 `from` / `to` 标了。
> 其余接口的时间筛选用请求体或在 Service 内部取当前时刻。

**时区**：全程用本地时间（Asia/Shanghai），不存 UTC ——
计费规则按本地时钟定义（日场 10:00–22:00），存 UTC 反而多一层换算与出错机会。

## 二、认证（模块 2）

### POST /api/auth/login

登录。凭据错误返回 401，账号被禁用返回 403。

**请求体**

| 字段 | 类型 | 必填 | 校验 |
| --- | --- | --- | --- |
| `username` | string | 是 | 非空 |
| `password` | string | 是 | 非空（**刻意不做长度校验** —— 老用户的密码可能不满足现行规则） |

**返回 `data`**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `token` | string | 访问凭证，后续以 `Authorization: Bearer <token>` 携带 |
| `tokenType` | string | 固定 `Bearer` |
| `expiresIn` | number | 有效期（**秒**） |
| `user` | object | 登录用户的资料，字段同 `UserProfileVo`（见第三章） |

**错误码**：`BAD_CREDENTIALS`(40103)、`ACCOUNT_DISABLED`(40301)

```json
// 响应示例
{
  "code": 0,
  "message": null,
  "data": {
    "token": "eyJhbGciOiJIUzI1NiJ9...",
    "tokenType": "Bearer",
    "expiresIn": 604800,
    "user": { "id": 145, "username": "zhangsan", "nickname": "张三", "role": "USER", "totalPaid": 0, "createdAt": "2026-09-28 15:23:55" }
  }
}
```

### POST /api/auth/logout

登出。**服务端不做任何事**，只记一条日志便于审计 —— JWT 无状态，没有会话可销毁。
真正的登出是前端删掉 `localStorage` 里的凭证。仍要求携带有效凭证。

**返回 `data`**：null

> **刻意不用「版本号 +1」实现登出**：那会让该用户**所有设备**一起下线，
> 那是「强制下线」的语义，应当留给封禁与改密使用。

## 三、用户（模块 1）

### POST /api/user/qq-verify

签发一个 QQ 验证码。**匿名可访问**（注册之前没有凭证）。

> ⚠️ **两个接口都走 POST + 请求体，`/status` 虽然是纯查询也不破例** ——
> 它们要带 `challengeId`，而那是**能换取账号绑定的凭证**（谁拿到它，
> 谁就能在验证有效期内用那个 QQ 注册）。放进 URL 查询参数会落进访问日志、
> 浏览器历史与反向代理日志，看到日志的人就能抢先注册。

**请求体**

| 字段 | 类型 | 必填 | 校验 |
| --- | --- | --- | --- |
| `qq` | string | 是 | 5~12 位数字 |

**返回 `data`**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `challengeId` | string | **给浏览器的凭证**，轮询与提交注册都要带上。留在页面里（sessionStorage 即可） |
| `code` | string | **给用户的 6 位码**，复制了发到 QQ 群里。⚠️ **它不是凭证** —— 群里所有人都看得见它，但只有持有那个 QQ 的人查得到自己那条记录 |
| `expiresAt` | string | 有效期截止时刻 |
| `ttlSeconds` | number | 剩余秒数，供前端做倒计时（别拿客户端时间减 `expiresAt`，机器时钟偏几分钟就会显示成负数） |

**错误码**：`PARAM_INVALID`(40000)、`QQ_VERIFY_TOO_MANY`(40936，待验证请求数超上限)

> 💡 **同一个 QQ 重复调会覆盖上一次**（含已验证状态）。这是刻意的：
> 不覆盖的话，攻击者可以先给受害者的 QQ 签发一条、自己攥着 `challengeId`；
> 受害者随后自己取码验证通过，攻击者拿自己那个就能用这个 QQ 注册。

### POST /api/user/qq-verify/status

查询群内确认的结果。**匿名，供注册页轮询。**

**请求体**

| 字段 | 类型 | 必填 |
| --- | --- | --- |
| `qq` | string | 是 |
| `challengeId` | string | 是 |

**返回 `data`**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `verified` | boolean | 群里确认了没有。⚠️ **刻意是布尔而不是字符串状态** —— 前端写 `status === 'VERIFED'` 打错一个字母就永远不相等，页面永远停在「等待确认」且控制台里一行报错都没有 |
| `expiresAt` | string | 有效期截止时刻（确认通过后会被顺延） |

**错误码**：`QQ_VERIFY_NOT_FOUND`(40413) —— 挑战不存在 / 已过期 / 凭证对不上，
**三者共用同一个码**：对调用方的处置动作完全一样（重新取一次码），
分开反而会泄露「这个 challengeId 曾经存在过」。

### POST /api/user/register

注册新用户。**匿名可访问。**

> ⚠️ **注册成功只返回用户资料、不返回登录凭证**，前端需要再调一次登录。
> 这是模块边界使然：模块 1 不依赖模块 2。

> ⚠️ **QQ 号是必填项，而且必须先在群里完成验证**（2026-10-01 起）。
> 完整流程是四步：
>
> 1. `POST /api/user/qq-verify`（匿名）—— 取一个 6 位验证码，拿到 `challengeId` 与 `code`
> 2. 用户把 `code` 发到 QQ 群
> 3. `POST /api/user/qq-verify/status`（匿名，轮询）—— 机器人在群里看到后回执给后端，
>    这一步返回 `verified: true`
> 4. 注册时把 `challengeId` 一起提交 —— 服务端消费掉它，确认「这个 QQ 是本人的」
>
> **为什么要这么麻烦**：店里没有店员，顾客是谁、该收多少钱全靠系统；
> 模块 11 的播报与群查询又都按 `sys_user.qq` 认人。
> 「不绑 QQ 也能进店」等于留一个**出了事找不到主的顾客**；
> 而「随手填一个号」会让群里的播报认错人。

**请求体**

| 字段 | 类型 | 必填 | 校验 |
| --- | --- | --- | --- |
| `username` | string | 是 | 3~20 字符，只能包含字母、数字与下划线 |
| `password` | string | 是 | 8~32 位 |
| `qq` | string | **是** | 5~12 位数字；**必须唯一**，且必须已通过群内验证 |
| `challengeId` | string | **是** | 上一步签发的验证凭证。**用完即焚**，同一个不能注册第二个账号 |
| `nickname` | string | 否 | ≤50 字符。留空时按「QQ 号 → 用户名」兜底，不会真的为空 |
| `phone` | string | 否 | 手机号格式 |
| `preference` | string | 否 | ≤64 字符。逗号分隔的设备类型 code，如 `PAIPAI,TAISHOU` |

**错误码**：`USERNAME_EXISTS`(40901)、`QQ_ALREADY_BOUND`(40902)、
`QQ_VERIFY_REQUIRED`(40935，凭证缺失 / 过期 / 该 QQ 尚未在群里确认)、`PARAM_INVALID`(40000)

**返回 `data`**：`UserProfileVo`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | number | 用户 ID |
| `username` | string | 登录名，注册后不可改 |
| `nickname` | string | 昵称 |
| `phone` | string | 可为空 |
| `qq` | string | 注册时必填；**绑定后本人改不了**（改资料时会返回 40937），要换号得找管理员 |
| `preference` | string | 逗号分隔的设备类型 code，可为空 |
| `role` | string | `USER` / `ADMIN` |
| `totalPaid` | number | 累计实付总额（**终生累计**，不等于「本月累计消费」） |
| `createdAt` | string | 注册时间 |

**错误码**：`USERNAME_EXISTS`(40901)、`QQ_ALREADY_BOUND`(40902)、`PARAM_INVALID`(40000)

### GET /api/user/me

查询当前登录用户的资料。**身份从凭证取**，路径里不出现用户 ID。

**返回 `data`**：`UserProfileVo`

**错误码**：`USER_NOT_FOUND`(40401)

### PUT /api/user/me

修改当前登录用户的资料。

> ⚠️ **PUT 是全量替换语义**：未提交的字段视为清空。
> 前端应把当前所有值一并带上，而不是只传改动的那个。
> 用户名不在可改范围内。

**请求体**

| 字段 | 类型 | 必填 | 校验 |
| --- | --- | --- | --- |
| `nickname` | string | 否 | ≤50 字符。传 null 表示清空，服务端会按 QQ 号 → 用户名重新兜底 |

## 四、空间与包场（模块 3）

### GET /api/store/status

查询当前营业状态与门店信息。**匿名可访问** —— 用户端首页用它。

> 门店名称、地址与「此刻是否营业」是面向公众的信息，相当于店门口挂的牌子。
> 响应里**不含停业原因与包场人信息** —— 那是运营内部信息，那道边界在 VO 上。

**返回 `data`**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `status` | string | `OPEN`（营业中）/ `BOOKED`（已被包场）/ `CLOSED`（暂停营业） |
| `statusText` | string | 中文文案，可直接展示：`营业中` / `当前时段已被包场，仅限受邀者入场` / `暂停营业` |
| `statusEndAt` | string | 状态结束时刻：停业时为恢复营业时刻，包场时为包场结束时刻，`OPEN` 时为 null |
| `store` | object | 门店信息，字段见下 |

`store` 内嵌 `StoreVo`：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | number | 门店 ID |
| `name` | string | 门店名称 |
| `address` | string | 可为空 |
| `description` | string | 可为空 |
| `updatedAt` | string | 最后更新时间 |

**错误码**：`STORE_NOT_FOUND`(40402)

> **前端提示**：`BOOKED` 与 `CLOSED` 都拒绝新下单，但对用户的意义不同 ——
> `CLOSED` 是「今天不营业」，`BOOKED` 是「这个时段被人包了」。
> `statusEndAt` 告诉用户「什么时候恢复」，应当展示出来。

### GET /api/store/bookings

查询**包场时间表**：尚未结束的已付款包场。**匿名可访问**。

> 与 `/status` 的分工：`/status` 回答「**现在**能不能进」，
> 本接口回答「**接下来**哪些时段不能进」。首页的「近期包场安排」卡片用它 ——
> 用户当场进不去时，看到时间表上那一行亮着就知道原因，而不是以为门坏了。

**查询参数**

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `limit` | number | 否 | 最多几条，默认 10，最大 20；超范围时截到边界值而不报错 |

**返回 `data`**：数组，按开始时间**升序**（从近到远）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `startAt` | string | 包场开始时刻 |
| `endAt` | string | 包场结束时刻 |
| `ongoing` | boolean | 此刻是否正在进行中。**由后端算好**，前端不要拿两个时间自己比 |

> **为什么 `ongoing` 不交给前端算**：客户端时钟不可信（用户可能改过手机时间），
> 而且「进行中」的判定口径要与准入规则一致，只能有一处定义。
>
> **响应里没有包场人、没有包场编号、没有价格** —— 普通顾客只需要知道
> 「这个时段进不去、什么时候能进」，不需要知道是谁包的场。
> 那道边界在 VO 上：`BookingScheduleVo` **连 `hostUserId` 这个字段都没有**。

> **为什么包场不写成公告**：包场是「未来的安排」，公告是「已发生的事」；
> 混在一条流里用户分不清哪条是通知、哪条是日程。而且日程会随改期变动，
> 消息流只增不改，改期后旧的那条永远对不上。

**错误码**：无（门店不存在时返回空数组）

### GET /api/store/free-periods

查询**近期免费活动**：尚未结束的活动（**含正在进行的那一场**）。**匿名可访问**。

> 与 `/bookings` 的分工：那个回答「接下来哪些时段**进不去**」，
> 本接口回答「接下来哪些时段**不收钱**」。两者可以同时成立
>（活动期间恰好也是某场包场的时段），前端各显示各的，不要合并。
>
> 正在进行的那一场也在列表里 —— 「今晚 20:00–次日 02:00 免费」这条
> 在 21:00 打开首页时正是最该看见的。

**查询参数**

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `limit` | number | 否 | 最多几条，默认 3，最大 20；越界时截到边界值而不报错 |

**返回 `data`**：数组，按开始时间**升序**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | number | 活动 ID |
| `startAt` | string | 免费开始时刻（**含**） |
| `endAt` | string | 免费结束时刻（**不含**） |
| `reason` | string | 活动名称，可为空 |

> **刻意没有 `ongoing` 字段**（包场时间表有）：那边要「比包场开始早 15 分钟就亮」
> 这条运营规则，只能由后端算；而这里的「是否正在进行」就是纯粹的
> 「起止之间」，前端按客户端时钟算一个展示标签即可 ——
> **它不参与任何金额判定**，真正的「此刻免不免单」在服务端的计费侧。

**错误码**：无（没有活动时返回空数组）

> 正是因为它们是同一件事的两面：「哪段时间不营业」与「哪段时间不收钱」。

办活动就是要让人看见省了多少，剪掉的话账单上什么都看不出来。

| `reason` | string | 否 | ≤255 字符，如「跨年活动」 |

> 重叠校验按**半开区间** `[startAt, endAt)` 判：`18:00–20:00` 与 `20:00–22:00`
> 可以背靠背排，不算重叠。**跨天也可以**（如跨年活动 `2026-12-31 20:00:00`
> 到 `2027-01-01 02:00:00`），区间本身不与自然日绑定。

> `BookingVo` **不含 `inviteToken`** —— 那是包场人分享给朋友的凭证，
> 放进后台列表接口就成了一个泄露路径。它只在付款成功时生成，且拿不到就等于进不去。

**错误码**：`STORE_NOT_FOUND`(40402)

### POST /api/admin/bookings

创建包场（**排期，不收款**）。**仅 ADMIN。**

> 新场次处于 `PENDING_PAYMENT`：**时段已被占住，但准入尚未生效**。
> 付款后才产生排他性 —— 没付款的包场不该把散客挡在门外。
> **收款见第九章**：线上通道走 `POST /api/payments`，扫码转账走
> `POST /api/payment-proofs` —— 两者的 `targetType` 都传 `BOOKING`。

**请求体**

| 字段 | 类型 | 必填 | 校验 |
| --- | --- | --- | --- |
| `hostUserId` | number | 是 | 该用户必须存在 |
| `startAt` | string | 是 | **可以是过去时刻**（2026-10-04 放开）—— 排过去的场次用于测试与补录，提示由运营后台提交时的确认层承担 |
| `endAt` | string | 是 | 必须晚于 `startAt` |
| `price` | number | 是 | ≥ 0（**允许 0 元**，用于内部占用等场景） |
| `remark` | string | 否 | ≤255 字符 |

**返回 `data`**：`BookingVo`

**错误码**：`BOOKING_TIME_INVALID`(40910)、
`STORE_NOT_FOUND`(40402)、`USER_NOT_FOUND`(40401，附加消息「包场人不存在」)、
`BOOKING_OVERLAP`(40912)、`BOOKING_CLOSURE_OVERLAP`(40913)

> ⚠️ 2026-10-04 起**不再返回** `BOOKING_START_IN_PAST`(40911)：后端放开了
> 「开始时刻不能是过去」这条校验，提示改由运营后台在提交时弹一次确认层。
> 错误码本身保留（它是文档化的接口契约，删掉会让 40911 成为空号）。

### PUT /api/admin/bookings/{id}

修改包场排期（改期与改价）。**仅 ADMIN。**

> **只有待付款的包场可以修改**。
> **请求体不含 `hostUserId`** —— 换包场人应当取消原场、另建一场，
> 而不是把已存在的付款/令牌信息悄悄挪给别人。

**请求体**

| 字段 | 类型 | 必填 | 校验 |
| --- | --- | --- | --- |
| `startAt` | string | 是 | 非空 |
| `endAt` | string | 是 | 必须晚于 `startAt` |
| `price` | number | 是 | ≥ 0 |
| `remark` | string | 否 | ≤255 字符。null 或空串表示清除 |

**返回 `data`**：null

**错误码**：`BOOKING_TIME_INVALID`(40910)、`BOOKING_NOT_FOUND`(40404)、
`BOOKING_NOT_EDITABLE`(40914)、`BOOKING_OVERLAP`(40912)、`BOOKING_CLOSURE_OVERLAP`(40913)

### DELETE /api/admin/bookings/{id}

取消包场（**逻辑删除**）。**仅 ADMIN。** 只有待付款的可以取消。

> 已付款的要**撤销并退款**，走下面的 `POST /{id}/revoke` —— 两个动作的后果不同
> （一个没有钱的事，一个要动钱），所以是两个端点、两个错误码。

**返回 `data`**：null

### POST /api/admin/bookings/{id}/revoke

**撤销一场已付款的包场并退款。仅 ADMIN。**

> **两种退款方式**（`refundMode`）：
> - `MANUAL` **人工退** —— 管理员已经在线下把钱转给顾客了，这里只是登记
> - `ONLINE` **原路退回** —— 调支付网关的退款接口，钱沿原支付通道退回
>
> 两种都要有：**线上退款不是随时能用的** —— 它要求这笔包场当初是走线上通道付的
> （扫码转账来的钱没有平台交易号），也要求商户号开通了退款权限。
> 只做线上，遇到这两种情况就没有出路；只做人工，则把「垫钱 + 手工记账」变成常态。
>
> ⚠️ **投产时实际只有 `MANUAL` 这一条可用** —— 扫码转账是唯一的收款方式，
> 而这笔钱根本没经过支付平台，没有可退的流水。`ONLINE` 是给将来接入线上通道预留的。

**请求体**

| 字段 | 类型 | 必填 | 校验 |
| --- | --- | --- | --- |
| `refundMode` | string | 是 | `MANUAL` / `ONLINE` |

> **金额不由调用方传**：包场是一口价，撤销就是整场作废，退款恒为全额。
> 能传就能传错，而这里错一分钱都要跟顾客解释。

**返回 `data`**：`BookingVo`（状态为 `REFUNDED`，含五个退款字段）

**错误码**：`BOOKING_NOT_REFUNDABLE`(40934，不是已付款状态，含「已被别人撤过」)、
`BOOKING_NOT_FOUND`(40404)、`PARAM_INVALID`(40000，退款方式非法)、
`PAYMENT_GATEWAY_UNAVAILABLE`(50201，**原路退回失败，状态已回滚**)

> **执行顺序是「先占位、再退钱」**：先用带 `WHERE status = 'PAID'` 的 SQL
> 把状态翻成已退款（并发时只有一个能成功），再去调支付平台；
> 平台失败就回滚状态。反过来做的话，两个管理员同时点会让两笔退款请求
> 都到达平台 —— **钱退两次，而本地只记一次**。
> 代价是有一个几百毫秒的窗口，状态显示「已退款」而钱还没到；
> 这一步失败会当场回滚并报错。**宁可退不成，也不能记成退成了。**

> **撤销后时段重新释放**（`occupiesSlot` 不含 `REFUNDED`），邀请令牌随之失效 ——
> 令牌还在行上，但准入与邀请页都只认 `PAID`。

**错误码**：`BOOKING_NOT_FOUND`(40404)、`BOOKING_NOT_EDITABLE`(40914)

### GET /api/bookings/host

分页查询**我作为包场人**的场次（含待付款的）。**需登录。**

包场人要靠这个列表找到待付款的场、点进付款入口 —— 所以它按
`biz_booking.host_user_id` 查，**不是**按参与者表查：参与者表里的 `HOST` 行
是付款成功那一刻才写入的，改读它就会漏掉所有待付款的场次，包场人也就
点不到付款入口。

**请求参数**：分页参数

**返回 `data`**：`PageResult<BookingVo>`（字段同后台列表）

### GET /api/bookings/joined

分页查询**我作为被邀请者**参与的场次。**需登录。**

与上面那个列表的区别只有角色一个变量：本接口按参与者表的
`role='PARTICIPANT'` 查，所以自己发起的场次不会在两个列表里各出现一次。

**请求参数**：分页参数

**返回 `data`**：`PageResult<BookingVo>`

### GET /api/bookings/{id}/invite-link

取某场包场的邀请链接（**只有包场人本人**）。**需登录。**

这是包场人把链接分享出去的唯一入口 —— 令牌在付款成功那一刻就生成了，
在此之前没有任何接口能把它交给包场人。

> **`url` 的域名取自服务端配置**（`uspace.web.base-url`），不从 `Origin` 请求头拼
> —— 那个头由客户端填写，伪造它就能让接口吐出一条指向任意域名的分享链接。
> **前端应当优先用 `location.origin + path` 自己拼**：开发期后端配的多半是
> localhost，那条链接粘到微信里打不开。

**路径参数**：`id` —— 包场 ID

**返回 `data`**：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `bookingId` | number | 包场 ID |
| `bookingNo` | string | 包场单号，便于口头核对「我发的是哪一场」 |
| `inviteToken` | string | 43 位令牌。前端要自己拼带额外参数的链接时用它 |
| `path` | string | 前端路由路径，如 `/invite/xxxxx` |
| `url` | string | 完整链接，域名来自配置 |
| `startAt` / `endAt` | string | 包场时段 |

**错误码**：

| 业务码 | HTTP | 含义与前端处置 |
| --- | --- | --- |
| `BOOKING_NOT_FOUND` | 404 | **不是本人的场次，或包场不存在** —— 两种情形刻意不区分：403 等于承认这场包场存在，可以靠状态码的差异枚举别人的单号 |
| `BOOKING_NOT_PAID` | 409 | **包场尚未付款**，令牌还没生成。前端应引导包场人去付款，而不是让他检查手机 |

### GET /api/bookings/invite/{token}

凭邀请令牌查看包场信息与**参与者名单**（被邀请者点开分享链接时调用）。**需登录。**

**只读，不产生任何副作用** —— 所以它**不会**把调用者记进名单。这是刻意的：
GET 会被浏览器预取、被刷新、被爬虫重复请求，让这些动作决定「谁进了名单」
是不对的。真正的加入是落地页加载完成后单独发的那次 POST（见下一个接口），
用户的感受完全一样（点开链接就进去了）。

> **令牌的有效性由包场时段界定**，不单独设过期时间 ——
> 时段一过，那场包场的排他性自然消失，令牌也就没有意义了。
> 只能查到**已付款**的场：令牌是付款那一刻才生成的。

**路径参数**：`token` —— 43 位 URL-safe 字符串

**返回 `data`**：`BookingInviteVo` —— 字段与 `BookingVo` 完全相同，另加一个名单：

| `participants[]` 字段 | 类型 | 说明 |
| --- | --- | --- |
| `userId` | number | 参与人用户 ID |
| `nickname` | string | 昵称 |
| `avatar` | string | 头像的站内相对路径，可为空 |
| `role` | string | `HOST` 发起人 / `PARTICIPANT` 参与者 |
| `roleText` | string | 角色的中文文案，可直接展示 |

> **发起人固定排在最前**，其后按加入时刻升序。
> **名单里只有昵称与头像**：拿到链接的人能看到参与者都有谁，这是分享链接的
> 固有语义（群邀请页都是这样）；但**看不到任何人的手机号、QQ 号与消费金额** ——
> 那些是本店的经营信息，不该随一条转发出去的链接外泄。

**错误码**：`NOT_FOUND`(40400)（令牌无效或已失效）

### POST /api/bookings/invite/{token}/join

凭邀请令牌加入包场（**落地页加载后自动调用**，用户无感）。**需登录。**

重复调用不是错误 —— 刷新页面、从聊天记录里再点一次都会走到这里。
接口返回「你已经进入过了」，而不是报错。

> **为什么让 GET 保持只读、另开一个 POST**：HTTP 语义上 GET 本就该是安全的，
> 而浏览器预取、爬虫抓取都会重复请求它。把它变成写操作，等于让这些
> 无关的动作决定谁进了名单。

**路径参数**：`token` —— 邀请令牌

**返回 `data`**：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `joined` | boolean | 本次是否新加入 |
| `alreadyJoined` | boolean | 之前是否已经在名单里 |
| `participantCount` | number | 加入之后的参与者人数（**含包场人**） |

> `joined` 与 `alreadyJoined` 恒为一真一假。前端据此决定是「欢迎」
> 还是「你已经在名单里了」，而不是弹一个错误框。
>
> 两人同时点同一条链接时，后到的那个会撞上唯一键 —— 那不是异常，
> 正是「你已经加入过了」这个答案。

**错误码**：`NOT_FOUND`(40400)（令牌无效或已失效，**此时不会写入任何参与者行**）

## 五、设备（模块 4）

> **本模块是纯展示的资产台账，不进主链路**：机台**不绑定订单**（用户下单时不选机台，
> 计费也不看他玩了哪台），机台状况也**不影响准入** —— 能不能进店只由停业与包场决定。
> 哪怕全店机器都标成「维护中」，系统照样放人进门；真要拦住顾客，得排一条停业区间。
>
> **「维护中」的机台照样陈列、不隐藏**：陈列的目的就是让顾客看到「这台在修」，
> 藏起来反而会让人以为机器搬走了。
>
> **用户端两处展示共用同一个接口**：门店信息页的概况（几台正常、几台待维护）
> 与「店内设施」页的完整陈列，都读 `GET /api/devices`，
> 概况的台数统计由前端从同一份数据里自行完成 —— 分成两个接口会出现
> 「首页说 6 台、设施页说 5 台」这类自相矛盾。

### GET /api/devices

查询店内机台陈列，按类型分组。**匿名可访问**（店里有什么机器是顾客走进店门
就能亲眼看到的事）。

返回**全部机台**，含维护中的。

**返回 `data`**：`DeviceGroupVo[]`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `typeCode` | string\|null | 类型代码，如 `PAIPAI`。类型已被删除时为空 |
| `typeName` | string | 类型名称，如「拍拍机」。前端用作分组标题 |
| `devices` | array | 该类型下的机台，按展示顺序排列 |

`devices[]` 每项为 `DeviceDisplayVo`：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | number | 机台 ID |
| `name` | string | 机台名称，如「拍拍机 1 号」 |
| `deviceNo` | string\|null | 资产编号，可与现场贴纸核对 |
| `location` | string\|null | 位置描述，如「靠窗第二台」 |
| `status` | string | 状况：`NORMAL` / `NEEDS_REPAIR` / `MAINTAINING` |
| `statusLabel` | string | 状况的中文说明，如「待维护」 |
| `usable` | boolean | 该状况下是否可用（**「待维护」算可用**，只有「维护中」不可用） |

> **不含 `remark`（备注）** —— 那是运营内务（「等屏幕配件到货」「某顾客反映左键不灵」），
> 边界落在 `DeviceDisplayVo` 这个类型上，不靠前端记着别显示。
>
> **`usable` 由后端算好**：判断口径（待维护算可用）只该有一处定义，
> 让每个前端各自比对字符串，早晚会漂移成「网页能玩、套壳 App 说不能玩」。

**示例**：

```json
{
  "code": 0, "message": null,
  "data": [
    { "typeCode": "PAIPAI", "typeName": "拍拍机", "devices": [
      { "id": 1, "name": "拍拍机 1 号", "deviceNo": "PP-01", "location": "靠窗第一台",
        "status": "NORMAL", "statusLabel": "良好", "usable": true },
      { "id": 4, "name": "拍拍机 4 号", "deviceNo": "PP-04", "location": "靠墙第四台",
        "status": "NEEDS_REPAIR", "statusLabel": "待维护", "usable": true }
    ]},
    { "typeCode": "TAISHOU", "typeName": "抬手乐", "devices": [
      { "id": 6, "name": "抬手乐 2 号", "deviceNo": "TS-02", "location": "进门右手边",
        "status": "MAINTAINING", "statusLabel": "维护中", "usable": false }
    ]}
  ]
}
```

**错误码**：`STORE_NOT_FOUND`(40402)（未执行建表脚本）

### GET /api/devices/types

查询可选的设备类型列表（**仅启用中的**）。**匿名可访问。**

两个消费方共用：顾客在个人资料里选**游玩偏好**（勾的就是 `code`）、
管理员新增机台时选类型。返回顺序即排序权重。

> **与陈列的口径不同，别混**：陈列组装查的是**全量类型**（含停用），
> 否则停用类型下的机台会整批消失；本接口只给启用中的，
> 因为它的用途是「还能选哪些」。停用 = 不再新增使用，不是删掉。

**返回 `data`**：`EquipmentTypeVo[]` —— 每项 `{ id, code, name }`

### GET /api/admin/devices

查询全部机台（**含运营内部字段**）。**仅 ADMIN。**

与用户端陈列取的是同一批数据，多出 `remark`（备注）、`sort`（排序权重），
`typeCode` / `typeName` 也一并给出（免得前端再查一次字典）。

> **不分页**：机台是「店里有几台机器」，十几到几十条封顶，
> 与停业记录那种会逐年累积的数据不同。含维护中的机台 ——
> 后台恰恰要靠它来找到「哪几台要修」。

**返回 `data`**：`DeviceVo[]`

### POST /api/admin/devices

新增机台。**仅 ADMIN。**

**请求体**：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `name` | string | 是 | 机台名称，≤ 50 字 |
| `typeId` | number | 是 | 设备类型 ID |
| `deviceNo` | string | 否 | 资产编号，≤ 32 字。同门店内不重复；**不填则不受此限** —— 多台还没贴编号的机器可以共存 |
| `location` | string | 否 | 位置描述，≤ 64 字 |
| `status` | string | 否 | 状况，**不填默认「良好」** |
| `sort` | number | 否 | 展示顺序，不填按 0。越小越靠前 |
| `remark` | string | 否 | 备注，仅运营可见，≤ 255 字 |

**返回 `data`**：`DeviceVo`

**错误码**：`STORE_NOT_FOUND`(40402)、`EQUIPMENT_TYPE_NOT_FOUND`(40409)、
`DEVICE_NO_EXISTS`(40927)、`DEVICE_STATUS_INVALID`(40928)

### PUT /api/admin/devices/{id}

修改机台。**仅 ADMIN。** 语义是**全量替换**：字段传 `null` 即清空该项。

> **`status` 是这条规则唯一的例外**：传 `null` 时**保持原值**，
> 不会被一次普通改名顺手改回「良好」。设备状况表达的是管理员正盯着看的那个事实，
> 而不是可以随便清空的描述字段。要单独改状况请用下一个接口。

**请求体**：字段同新增

**返回 `data`**：`DeviceVo`

**错误码**：`DEVICE_NOT_FOUND`(40408)、`EQUIPMENT_TYPE_NOT_FOUND`(40409)、
`DEVICE_NO_EXISTS`(40927)、`DEVICE_STATUS_INVALID`(40928)

### PUT /api/admin/devices/{id}/status

**只修改机台状况**。**仅 ADMIN。**

运营里最高频的动作（机器坏了点一下、修好了再点一下），单独成一个接口：
**只更新状况一列**，不碰名称、位置、备注等其他字段 ——
走全量替换意味着前端要先把整条记录读出来再整个传回去，
中间若有别人改了名称，这次提交会**静默覆盖**对方的改动。

改成与当前相同的状况**不算错误**，重复点两下的结果与点一下相同。

**请求体**：`{ "status": "MAINTAINING" }`

**返回 `data`**：`null`

**错误码**：`DEVICE_NOT_FOUND`(40408)、`DEVICE_STATUS_INVALID`(40928)

### DELETE /api/admin/devices/{id}

删除机台（**逻辑删除**），用于机器退役、搬走。**仅 ADMIN。**

> **退役走删除而不是加一个「已报废」状况**：一台机器一旦退役就不再陈列，
> 与「暂时不能玩」是两回事 —— 混进状况枚举里，会让「店里还有几台能玩」
> 这个数需要额外过滤才对，陈列页也要专门记住跳过它。
>
> 逻辑删除后记录仍在库里，事后能查到「这台机器原来在哪个位置」。

**返回 `data`**：`null`

**错误码**：`DEVICE_NOT_FOUND`(40408)

## 六、门禁（模块 5）

> **本模块的接口面向应急场景与联调**：顾客手机没电、忘记密码、
> 临时给维修人员开门。**正常流程下密码由「点击开门」自动下发**（见第八章），
> 不需要人工调这些接口。

### POST /api/admin/lock/passcodes

下发一个限时密码。**仅 ADMIN。**

**通通锁的两条硬约束**（都不是可以绕过的注意事项）：

1. **自定义密码只能设为限时密码** —— 不给有效期会被拒绝，
   不能设成永不过期的一次性码
2. **远程下发（`addType=2`）要求锁接入网关、或本身就是 Wi-Fi 锁** ——
   纯蓝牙锁拿不到远程指令

**请求体**

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `lockId` | number | 是 | 锁 ID |
| `keyboardPwd` | string | 否 | **留空则由服务端随机生成 6 位数字**，生成结果在响应里返回 |
| `keyboardPwdName` | string | 否 | 密码名称，便于后台识别用途，如「维修人员」 |
| `startTime` | string | 是 | 生效时间 |
| `endTime` | string | 是 | 失效时间，到期自动失效，无需再调删除接口 |
| `addType` | number | 否 | 默认 **2**。`1`=先在 APP 内用蓝牙添加再同步到云端（非远程）；`2`=经网关或 Wi-Fi 锁**远程直接下发**（无人值守场景必须用这个）；`3`=NB-IoT 锁，需等网络唤醒 |

**返回 `data`**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `keyboardPwd` | string | 下发成功的限时密码 |

**错误码**：
- `BUSINESS_REJECTED`(40900) —— 通通锁返回 `-4043`「该锁不支持此操作」，
  最常见是拿纯蓝牙锁去远程下发。**这是接入方式配置问题，重试无用**，故走 409 而非 502
- `LOCK_CLOUD_UNAVAILABLE`(50200) —— 其余失败情形

附加消息为通通锁的 `errmsg`。

### POST /api/admin/lock/passcodes/revoke

撤销（提前失效）一个已下发的密码。**仅 ADMIN。**

> **幂等**：密码本就不存在时同样返回成功，可安全重复调用。
> 走 POST 而非 `DELETE` 带请求体，是为了**不让密码进访问日志与浏览器历史**。

**请求体**

| 字段 | 类型 | 必填 |
| --- | --- | --- |
| `lockId` | number | 是 |
| `keyboardPwd` | string | 是 |

**返回 `data`**：null

**错误码**：`BUSINESS_REJECTED`(40900)、`LOCK_CLOUD_UNAVAILABLE`(50200)

### GET /api/admin/lock/status

查询门锁的在线状态。**仅 ADMIN。**

后台展示「锁是否可用」用它，也是排查「同步开门记录为空」时的辅助手段。

**请求参数**

| 参数 | 位置 | 类型 | 必填 |
| --- | --- | --- | --- |
| `lockId` | query | number | 是 |

**返回 `data`**：`ONLINE` / `OFFLINE` / `UNKNOWN`

> **本接口不返回失败分支** —— 查不到状态本身就是有效答案（`UNKNOWN`），
> 不必当成错误。前端按三态展示即可。

## 七、进出记录（模块 6）

> **本模块是旁路的记录与审计**，供人工复核（用户忘记点「结束使用」时与监控比对）、
> 争议追溯与 QQ 播报参考。**它不参与计费链路** —— 计费起点是订单的 `startTime`
> （用户点击「开门」的时刻），无需等门锁记录回来对齐。
>
> **只记开门，不记离场**：封闭空间出门是机械推杠（消防要求内部免密自由开门），
> 不产生门锁记录；离场时刻落在订单的 `endTime` 上。
> 因此本表是 **append-only，不提供修改与删除接口**。

### GET /api/admin/access-records

分页查询开门记录。**仅 ADMIN。**

典型用途：用户忘记点「结束使用」时，管理员按时间范围查出这段期间的开门记录，
与监控录像比对后手工修正订单时长。

**请求参数**

| 参数 | 位置 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- | --- |
| `userId` | query | number | 否 | 按开门人过滤，不传表示不限 |
| `from` | query | string | 否 | 时间范围起点（**含**）。**格式必须是 `yyyy-MM-dd HH:mm:ss`** |
| `to` | query | string | 否 | 时间范围终点（**不含**），格式同上 |
| `page` / `size` | query | number | 否 | 分页参数 |

> ⚠️ `from` / `to` 是本项目**唯二需要显式传格式**的查询参数 ——
> 查询参数走 Spring 类型转换，不经过 Jackson，不显式声明格式的话，
> 带空格的日期串会在进入方法之前就被拒掉（400）。

**返回 `data`**：`PageResult<AccessRecordVo>`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | number | 记录 ID |
| `orderId` | number | 关联订单 ID，**可为空**（补录未指定订单、或记录由门锁云同步而来时为空） |
| `userId` | number | 开门人用户 ID，**可为空**（指纹/钥匙开门、或密码非本系统下发时为空） |
| `storeId` | number | 门店 ID |
| `lockId` | number | 门锁 ID |
| `passcode` | string | 本次开门所用密码，可为空 |
| `openType` | number | 开门方式，通通锁原样返回的枚举值 |
| `openTime` | string | 开门时刻 |
| `source` | string | 记录来源：`MOCK` / `TTLOCK` / `ADMIN` |
| `sourceLabel` | string | 来源中文名：`模拟门锁` / `门锁云` / `管理员补录` |
| `createdAt` | string | **记录落库时刻**（与 `openTime` 是两回事 —— 补录的 `openTime` 在过去，`createdAt` 是现在） |

**错误码**：`STORE_NOT_FOUND`(40402)

### POST /api/admin/access-records/sync

从门锁云同步开门记录。**仅 ADMIN。**

> ⚠️ **按需手动触发，请勿轮询。** 每次调用消耗门锁云配额（**免费额度 30,000 次/月**，
> 是整个系统的硬约束）。正常同步消耗 1 次；**拉取结果为空时会再探活一次**，
> 变成 2 次。

**同步是幂等的**，判重键是 `(lock_id, open_time)`，重复同步不会产生重复记录。

> **失败不会伪装成「0 条」**：门锁云查询失败时返回的是空列表而非异常，
> 若直接采信就会把「云端没拉到」当成「确实没有开门记录」。
> 因此结果为空时必须再探活确认锁在线（`ONLINE` 才下结论），
> 否则返回 502 而不是「成功、0 条」。

**请求体**

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `lockId` | number | 是 | 锁 ID |
| `from` | string | 是 | 区间起点（**含**） |
| `to` | string | 是 | 区间终点（**不含**）；必须晚于 `from`，且**跨度不超过 31 天** |

**返回 `data`**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `lockId` | number | 本次同步的锁 ID |
| `from` / `to` | string | 本次同步的区间 |
| `fetched` | number | 门锁云返回且落在区间内的条数 = `inserted` + `skipped` |
| `inserted` | number | 本次实际写入数据库的条数 |
| `skipped` | number | 因库中已存在同一 `(lockId, openTime)` 而跳过的条数 |
| `discarded` | number | 因缺少开门时刻而被丢弃的条数 |
| `cloudCalls` | number | **本次消耗的门锁云调用次数**（正常 1；拉取为空时 +1 次探活） |

**错误码**：
- `ACCESS_TIME_INVALID`(40916) —— 附加消息区分「结束时间必须晚于开始时间」
  与「单次同步跨度不能超过 31 天，请分多次同步」
- `STORE_NOT_FOUND`(40402)
- `LOCK_CLOUD_UNAVAILABLE`(50200) —— **锁离线或云端不可达，且无法确认「确实没有记录」**

### POST /api/admin/access-records

手工补录一条开门记录。**仅 ADMIN。**

用于系统或门锁故障期间、开门没留下记录的场景。
**来源固定记为 `ADMIN`，请求方无法指定。**

**请求体**

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `lockId` | number | 是 | 锁 ID |
| `openTime` | string | 是 | 开门时刻。**不能晚于当前时刻**，但可以是任意早的时刻 |
| `userId` | number | 否 | 开门人用户 ID，无法确定时留空 |
| `orderId` | number | 否 | 关联订单 ID，对不上则留空 |
| `passcode` | string | 否 | 本次开门所用密码，无法确定时留空 |

**返回 `data`**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `record` | object | 落库后的开门记录（**无论本次新建还是已存在都返回**），字段同 `AccessRecordVo` |
| `created` | boolean | `true` = 本次新写入了一条；`false` = 该锁在该时刻已有记录，本次未写入 |

**错误码**：`ACCESS_TIME_INVALID`(40916)、`STORE_NOT_FOUND`(40402)、`PARAM_INVALID`(40000)

### GET /api/access-records/me

分页查询**我自己**的开门记录。**需登录。**

`/me` 路径里不出现用户 ID，身份从凭证取。

**请求参数**：`page` / `size`（**本接口的分页参数没有校验注解**，超限由分页插件截断）

**返回 `data`**：`PageResult<AccessRecordVo>`

### POST /api/admin/access-records/mock-open

**模拟一次开门并落库**（仅演示与联调用）。**仅 ADMIN。**

> ⚠️ **本接口在 `uspace.lock.provider=mock` 时才存在**（缺省即为 mock）。

> 不会在生产环境留一个「能凭空造开门记录」的口子。

**特殊行为**：请求未带密码时，会**先自动下发一个 3 小时有效的限时密码**再用它开门
（模拟门锁要求「密码必须已下发」才能开门）。

**请求体**

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `lockId` | number | 是 | 锁 ID |
| `passcode` | string | 否 | 留空则自动下发一个（有效期 3 小时） |
| `userId` | number | 否 | 可为 null |

## 八、订单（模块 8）

### 计费规则（模块 7，匿名）

> **放在本章是因为模块 7 只有一个对外端点**，且它服务的正是订单与结账 ——
> 为它单开一章会把后面所有章节重编号，得不偿失。

`GET /api/billing/rules`

**价目表**。给用户端「计费规则」页（`/pricing`）与「我的」页面的优惠文案用。
**匿名可访问** —— 与门店名、营业状态同理：价格是走到店门口就该看得见的信息。

⚠️ **页面上的价格数字一律取自这个接口，前端不要写死**：单价、封顶、宽限、
优惠门槛全是配置项（`uspace.billing.*`）。前端抄一份等于把计费规则复制了一份，
调价之后两处必然对不上 —— 而那种不一致**不会有任何报错**。

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "unitMinutes": 30,
    "graceMinutes": 5,
    "dayStart": "10:00",
    "dayEnd": "22:00",
    "dayUnitPrice": 4,
    "nightUnitPrice": 3.5,
    "dayCap": 40,
    "nightCap": 35,
    "dayPricePerHour": 8.00,
    "nightPricePerHour": 7.00,
    "discountEnabled": true,
    "discountThreshold": 200,
    "discountDayUnitPrice": 3.5,
    "discountNightUnitPrice": 3,
    "discountDayCap": 35,
    "discountNightCap": 30,
    "discountDayPricePerHour": 7.00,
    "discountNightPricePerHour": 6.00
  }
}
```

**两套口径，选错了不会报错、只会显示一个错价格**：

| 口径 | 字段 | 用在哪 |
| --- | --- | --- |
| **元 / 计费单位** | `dayUnitPrice`、`nightUnitPrice`、优惠后两个同名段 | 价格阶梯表（第 n 档 = n × 单价） |
| **元 / 小时** | `*PricePerHour` | 页面展示与「我的」的优惠文案 |

⚠️ **有两个「7 元/小时」不要搞混**：优惠后的**日间**价是 7 元/小时，
而**夜间原价**也是 7 元/小时 —— 数字一样、含义不同，页面上要分行写。

> `discountEnabled=false` 时，优惠那几个字段**照样返回值**（它们是配置里写着的数），
> 由前端决定展不展示 —— 后端替前端做决定的话，
> 「活动停了但页面还写着优惠价」这类不一致就没人拦得住了。

### 状态机（前端要按它决定按钮的形态）

```
（点击开门 → 创建订单即进入）IN_USE ──结束使用──> PENDING_PAYMENT ──支付到账──> PAID
                                  └──── 结算为 0 元时直通 ────┘
```

**只有三态，只有两跳。**

- **没有 `CREATED` 中转态**：点一次「开门」就同时完成「创建订单 + 下发密码 + 开始计费」，
  不存在「订单已创建但没开门」的挂起状态
- **没有「取消订单」接口**：误点一下不想进店，点「结束使用」即可 ——
  五分钟内落在免费档，0 元自动结清
- **0 元订单直接跳到 `PAID`**：0 元单没有可支付的通道，卡在待支付只会让用户
  看到一个「0 元去支付」的按钮

### 结账流程（用户端的按钮顺序）

| 用户动作 | 调用 | 结果 |
| --- | --- | --- |
| 点「结账」 | `GET /api/orders/{id}/preview` | 看到当前时长与金额，**计时不停** |
| 点「停止计时」 | `POST /api/orders/{id}/settle` | 定格、转待支付（0 元则直通已支付） |
| 点「去支付」 | `GET /api/payments/channels`、`GET /api/payments/qr` | 拿到本店收哪几种钱、收款码贴出来 |
| 扫码付款后传图 | `POST /api/payment-proofs/image` → `POST /api/payment-proofs` | **订单当场转已支付**（订单属「提交即交付」） |
| 管理员复核 | `POST /api/admin/payment-proofs/{id}/confirm` | 留个结论 —— 订单这类，钱在提交那刻就算收到了 |

> **走上线通道时是另一条路**：`POST /api/payments` → 拉起微信 / 支付宝 →
> 平台回调（见第九章）→ 订单转已支付。两条路的终点是同一个状态。

> **第一步的预览页就是那个确认环节。** 用户看完时长、金额、是否封顶，
> 点「停止计时」即视为确认离场 —— **没有二次确认弹窗，也没有反悔路径**，
> 停止即定格。想继续玩只能重新开门、重新计费。
>
> **预览不产生任何副作用**：计时继续走、订单状态不变、门锁密码不撤销、
> 不消耗门锁云额度。金额随时长增长，前端应持续轮询（约 10 秒一次）——
> 屏幕上的数字始终是新的，「确认」才是对当下一刻的确认。

### POST /api/orders

**点击「开门」：创建订单、下发限时密码、开始计费 —— 一次调用完成。** 需登录。

> **用户端只点这一次。** 前端可以加二次确认弹窗
> （「确认开门？将开始计费」），那是前端的事，后端只有这一个入口。

**准入判断顺序是固定的：停业 → 包场 → 普通。**

**包场的准入窗口比包场本身更早开始**，命中后按「身份 × 时刻」分档：

| 当前时刻 | 非参与者 | 参与者（包场人 / 加入过名单的被邀请者） |
| --- | --- | --- |
| 开始前 15 分钟以上 | 放行 | 放行 |
| 开始前 15 分钟 ~ 前 5 分钟 | 拒绝 | **拒绝** |
| 开始前 5 分钟内 | 拒绝 | 放行 |
| 包场进行中 | 拒绝 | 放行 |
| 结束后 | 放行 | 放行 |

> 提前挡人的理由是「一局游戏打不完就要被清场」：开始前 15 分钟放进来的人
> 必然会被中途打断，不如一开始就挡住。参与者的 5 分钟提前量用于进店放东西、
> 做开场准备。两个提前量可由服务端配置调整。
>
> **「谁是参与者」由参与者表说了算**（`biz_booking_participant`）：被邀请者
> 点开邀请链接时就被记了进去，下单时不必再带令牌 —— 查表就知道他是谁。
> 包场人同样占着一行（`HOST`），另有 `host_user_id` 作为历史数据的兜底。

**请求体**

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `inviteToken` | string | 否 | ≤64 字符。**兜底路径**：只在「落地页那次自动加入没成功」时才需要 |

> **正常情况下不必带这个字段。** 被邀请者点开邀请链接时，落地页会自动调
> `POST /api/bookings/invite/{token}/join` 把他记进参与者表，之后下单靠查表
> 就能认出他 —— 他在包场时段内**不带令牌下单也能成功**。
>
> 留着这个字段，是为了兜住那一次加入失败的情形：网络抖动，或者用户还没等
> 落地页加载完就点了「开门」。这时带上令牌仍然进得去。
>
> **包场人本人任何时候都不需要令牌** —— 系统按 `host_user_id` 就认得出来。

**返回 `data`**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `orderId` | number | 订单 ID，后续所有操作都用它 |
| `orderNo` | string | 订单号，对外展示与客服核对用 |
| `passcode` | string | **门锁密码**，6 位数字，用户拿它在门口输 |
| `passcodeStart` | string | 密码生效时间 |
| `passcodeEnd` | string | **密码失效时间**。应当展示给用户（「密码有效至 XX:XX」） |
| `startTime` | string | 计费起点 |
| `renewed` | boolean | 本次是否做了续期（新建订单时恒为 `false`） |
| `regenerated` | boolean | 续期时是否换了新密码（新建订单时恒为 `false`） |
| `message` | string | **给用户看的一句话提示**，可直接展示 |

**错误码**：

| 业务码 | HTTP | 含义与前端处置 |
| --- | --- | --- |
| `STORE_CLOSED` | 409 | 当前停业，暂不支持下单 |
| `BOOKING_ACCESS_DENIED` | 409 | 该时段已被包场，仅限包场人与被邀请者进入 |
| `BOOKING_PREPARING` | 409 | **包场即将开始，暂停接待新顾客** —— 与上一条的区别是包场还没开始，提示语可以写「稍后再来」而不是「今天进不去」 |
| `BOOKING_NOT_STARTED` | 409 | **包场尚未开始，参与者暂不能入场** —— 只发给参与者，属于「再等等就行」，前端可提示具体还要等几分钟 |
| `ORDER_ALREADY_ACTIVE` | 409 | **你已有进行中的订单** —— 前端应转而调「查看密码」，而不是当作错误弹窗 |
| `ORDER_UNPAID_EXISTS` | 409 | **你有一笔未支付的订单** —— 前端应引导到「去支付」，而不是「查看密码」 |
| `LOCK_CLOUD_UNAVAILABLE` | 502 | 门锁云调用失败（**此时订单不会创建**，可直接重试） |
| `STORE_NOT_FOUND` / `LOCK_NOT_CONFIGURED` | 404 | 系统未初始化，联系管理员 |
| `PARAM_INVALID` | 400 | 邀请令牌格式不对（超过 64 字符） |

> **上一单未结清时会拒绝新单，且两种情形给的是不同的码** —— 这是刻意的，
> 因为用户看到之后该做的事完全不同：
>
> | 码 | 用户此刻的处境 | 前端处置 |
> | --- | --- | --- |
> | `ORDER_ALREADY_ACTIVE` | 人还在店里玩 | 跳「查看密码」 |
> | `ORDER_UNPAID_EXISTS` | 玩完了、账单还欠着 | 跳「去支付」 |
>
> 合并成一个码的话，前端只能给一句模糊的提示，而用户不知道自己该点「结束使用」
> 还是「去支付」。两者都是**正常的业务分支，不是故障**：响应消息里带着那笔订单的
> 订单号，前端照着引导即可，不要弹「操作失败」。

### GET /api/orders/current

查询当前进行中的订单。**需登录。**

**前端首页靠它决定「开门」按钮的语义**：没有进行中的订单就是「开门并开始计费」，
有就是「查看密码」。没有这个接口，前端只能靠试错 ——
先调一遍开门、拿到 `ORDER_ALREADY_ACTIVE` 再改调查看密码。

**只返回 `IN_USE` 的订单，不含待支付的** —— 待支付的单已经结算、门锁密码也撤销了，
把它算作「当前订单」会让用户看到一个点不动的「查看密码」。
首页要显示「你有 N 笔未付款」时，另调
`GET /api/orders/me?status=PENDING_PAYMENT&size=1`。

> 也就是说首页需要**两个独立的数据源**：本接口答「我在不在玩」，
> 订单列表答「我有没有欠费」。

**返回 `data`**：`OrderVo`，**没有进行中的订单时 `data` 为 `null`**（不是错误）

### GET /api/orders/{id}/passcode

查看门锁密码，**已过期时自动续期**。**需登录。**

用于「玩到一半出门买水、回来还要进门」的场景。

> **续期不换密码**：密码数字不变，只把有效期往后推。
> 用户截图里的那串数字始终有效，锁上也不会越积越多密码。

**返回 `data`**：`OrderOpenVo`（字段同 `POST /api/orders`），其中：

- `renewed` = `true` 表示本次做了续期
- `regenerated` = `true` 表示**密码变了**（续期失败降级为重新下发的极端情形）——
  此时必须以本次返回的 `passcode` 为准，旧密码已作废

**错误码**：`ORDER_NOT_FOUND`(40405)（不存在或不属于你）、
`ORDER_STATUS_INVALID`(40918)（订单不在使用中）、`LOCK_CLOUD_UNAVAILABLE`(50200)

### GET /api/orders/{id}/preview

**结账预览**：算出「此刻停止计时的话要付多少」。**需登录。**

> **纯查询，没有副作用** —— 计时照走、订单状态不变、门锁密码不撤销、
> 不消耗门锁云额度。用户看完这一屏再点「停止计时」才算真的结束。
>
> **这一屏就是确认环节**：展示的「时长 + 金额 + 是否封顶」已经足够用户做决定，
> 点「停止计时」即视为确认离场，不再有二次确认弹窗，也没有反悔路径。

**前端应持续轮询本接口**（约 10 秒一次）：金额随时长增长，屏幕上的数字要一直是新的。
比对 `previewAt` 丢弃乱序到达的旧响应；用户点完「停止计时」后立刻停掉轮询 ——
此时会收到 409，那个 409 **不是错误**，而是「本页使命结束」，据此刷新订单状态即可。

**返回 `data`**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `orderId` / `orderNo` | number / string | 订单标识 |
| `startTime` | string | 计费起点（点击开门的时刻） |
| `previewAt` | string | **本次计算的截止时刻**。显示「更新于 …」用它，丢弃乱序响应也用它 |
| `stayMinutes` | number | **在店时长**（分钟），含包场时段 |
| `billingStart` | string | 实际参与计费的起点，含义同「结束使用」 |
| `freeByBooking` | boolean | 是否因包场而减免了时长 |
| `cappedNow` | boolean | **当前账单是否已到封顶价**（此后不会因时长增长而变贵） |
| `willAutoSettle` | boolean | 停止后是否**无需支付**、直接结清 |
| `statusAfterStop` / `statusAfterStopText` | string | 停止后将进入的状态（`PENDING_PAYMENT` / `PAID`） |
| `nextChangeInSeconds` | number \| null | 距**下一次账单变化**的剩余秒数；`null` 表示当前段内不会再变 |
| `nextChangeText` | string | 下一次变化的说明，**不含时间**。与上者同为 `null` 表示此刻没有可预告的 |
| `bill` | object | **分段账单**，结构与「结束使用」完全一致 |

> **`nextChange*` 是「现在停还是再玩一会儿」的依据**，首页的进行中卡片与结账页共用。
> 前端拼成「还有 12:30 进入下一档 ¥20.00」——**时间由前端每秒重绘，文案由后端给**。
> 三种取值：
>
> | `nextChangeText` | `nextChangeInSeconds` | 含义 |
> | --- | --- | --- |
> | `进入下一档 ¥20.00` | 到档位边界的秒数 | 段内跳档 |
> | `跨入夜场，按夜场重新计价` | 到时段边界的秒数 | **先跨时段**，而不是等那个到不了的档位 |
> | `当前已到封顶价` / `当前时段月卡免费` | `null` | 段内不会再变，**只显示文字、不要显示倒计时** |
>
> ⚠️ **不要让前端拿 `bill.segments` 自己推算下一次跳档**：档位边界里的
> 「30 分钟一档」与「5 分钟宽限」都是配置项，前端算等于把计费规则复制一份 ——
> 改配置时前端静默算错，且不报任何错。
>
> ⚠️ **用剩余秒数而不是绝对时刻**：绝对时刻会带上客户端与服务端的时钟偏差，
> 用户手机时间不准时倒计时会算出荒谬的值。

> ⚠️ **`stayMinutes` 与 `bill.totalMinutes` 不是一回事**：后者是剪掉包场时段后的
> **计费时长**，整段落在包场里时是 0，而在店时长可能有好几个小时。
> 账单页两个都要展示（「在店 3 小时 20 分，其中计费 1 小时 20 分」）——
> 只显示计费时长会让包场用户以为系统算错了。
>
> ⚠️ **`cappedNow` 为 `true` 时措辞不要写成「继续玩也不会更贵」**：
> 它只对当前时刻的账单成立，跨过日场与夜场的边界（22:00）会产生新的一段、
> 从那一刻起重新计费。安全说法是「**当前已到封顶价**」。
>
> ⚠️ **`willAutoSettle` 与预览金额都不是承诺**：5 分 59 秒预览是 0 元，
> 6 分 01 秒停止就是 4 元。用户点「停止计时」后，**必须以那次
> `POST /{id}/settle` 的返回为准**决定下一步（去支付 / 直接结束），
> 不能沿用预览页的金额与状态。

**错误码**：`ORDER_NOT_FOUND`(40405)（不存在或不属于你）、
`ORDER_STATUS_INVALID`(40918)（订单不在使用中 —— 已结束的订单看详情即可，
那里的金额是真实的结算结果，比预估更准）

### POST /api/orders/{id}/settle

**结束使用**：算出账单并转待支付。**需登录。**

**返回 `data`**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `orderId` / `orderNo` | number / string | 订单标识 |
| `startTime` | string | 计费起点（点击开门的时刻） |
| `endTime` | string | 离场时刻 |
| `billingStart` | string | **实际参与计费的起点**。通常等于 `startTime`，但若这段时间内有已付款的包场，包场时段不计费，此值会晚于 `startTime` |
| `freeByBooking` | boolean | 本次是否因包场而减免了时长。**为 true 时账单页应说明「包场时段不计费」** |
| `status` / `statusText` | string | 结算后的状态 |
| `bill` | object | **分段账单**，见下 |

`bill` 的结构（前端账单页按它渲染）：

```json
{
  "startTime": "2026-09-28 13:23:55",
  "endTime": "2026-09-28 15:25:18",
  "totalMinutes": 121,
  "segments": [
    {
      "period": "DAY",            // DAY 日场 / NIGHT 夜场
      "startTime": "2026-09-28 13:23:55",
      "endTime": "2026-09-28 15:25:18",
      "minutes": 121,
      "units": 4,                 // 计费档数
      "unitPrice": 4,             // 本段单价（元/档）
      "capAmount": 40,            // 本段封顶
      "rawAmount": 16,            // 封顶前金额
      "amount": 16,               // 本段实收
      "capped": false             // 是否触发封顶
    }
  ],
  "totalAmount": 16,              // 实收合计（各段已分别封顶）
  "monthSpentBefore": 0,          // 结算前的当月累计实付额 —— 用来解释「为什么走了/没走优惠价」
  "discounted": false,            // 本单是否按月度优惠价计费
  "discountAmount": 0             // 本单优惠金额（说明性，已含在 totalAmount 中）
}
```

> ⚠️ **三个金额字段的口径**：`amount` / `totalAmount` 存的都是**实收**
> （已封顶、已含优惠），`discountAmount` **只是说明性字段** ——
> **不可再用「合计 − 优惠」减第二次**。
>
> ⚠️ **`unitPrice` 与 `capAmount` 必须逐段展示**：日夜场不同价、优惠与否又不同价，
> 只显示总价的话，用户看到「合计 40 而单价 4」会以为算错了。

**错误码**：`ORDER_NOT_FOUND`(40405)、`ORDER_STATUS_INVALID`(40918)（已经结束过了）

> ⚠️ **订单不一定是你点的结束**：包场开始时，仍在店内的非参与者订单会被系统
> **自动结算**（见「点击开门」一节的准入窗口）。计费截止到**包场开始时刻**，
> 不是系统执行结算的那一刻 —— 前端看到订单「自己转了待支付」属于预期行为。
> 金额直接取接口返回的 `endTime` 与账单，**不要用「当前时刻 − 开始时刻」自己算**，
> 那样在自动结算的订单上会多算几十秒到几分钟。

### GET /api/orders/me

分页查询我的订单。**需登录。**

**请求参数**：分页参数 + `status`（可选，按状态筛选）

**返回 `data`**：`PageResult<OrderVo>`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` / `orderNo` | number / string | 订单标识 |
| `storeId` | number | 门店 ID |
| `bookingId` | number | 关联的包场 ID，未命中包场时为 null |
| `startTime` / `endTime` | string | 计费起点 / 离场时刻（使用中时 `endTime` 为 null） |

| `dayMinutes` / `dayAmount` | number | 日场时长与实收 |
| `nightMinutes` / `nightAmount` | number | 夜场时长与实收 |

| `discountAmount` | number | 本单优惠金额（说明性，已含在合计中） |

| `payableAmount` | number | **应付金额**。发起支付时用它 |

> 两个动作的返回体里出现。放进通用视图的话，任何一次订单查询都会把密码带出来 ——
> 包括后台列表页、也包括用户翻自己的历史订单。

> ⚠️ **列表接口不带分段账单**（没有 `bill` 字段）。分段明细只出现在两个**详情**
> 接口里 —— 一页 20 条订单各带一份账单会让响应体白大出许多，老订单还要逐条重算。
> 要看「几档 × 单价」，进订单详情。

### GET /api/orders/{id}

查询我的订单详情。**需登录。**

**返回 `data`**：`OrderVo` —— 字段与列表接口相同，**另加两个账单字段**：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `bill` | object / **null** | **分段账单**，结构与「结束使用」返回的 `bill` 完全一致（见该节的 JSON 示例）。数据来自结算时落库的快照；快照机制（2026-10-03）之前结算的老订单按当前规则重算，**只有金额与落库完全一致才返回** |
| `freeByBooking` | boolean / null | 是否因包场减免了计费时长（账单上用一句「包场时段不计费」解释「计费时长 < 在店时长」）。与 `bill` 同来同去 |

> ⚠️ **`bill` 可能为 null，页面必须准备回落展示**（日场/夜场汇总行）：
> 使用中的订单没有账单（费用在走，要看估算去结账预览）、老订单重算与落库金额
> 对不上时也没有（活动被删改、包场被撤销、价格调整过都会造成对不上）——
> 对不上就不展示，宁可少一块，也不给一份与实收金额矛盾的假明细。

**错误码**：`ORDER_NOT_FOUND`(40405) —— **非本人的订单一律返回 404 而不是 403**，
否则「403 说明这个订单存在，只是不归你」可以被用来枚举订单号。

### POST /api/admin/orders/{id}/adjust

**人工调整订单时长并重算金额。** 仅 ADMIN。

> **典型场景**：顾客玩完直接走了，忘了点「结束使用」，订单一直挂在使用中。
> 管理员查监控确认他 21:30 离场，把离场时刻改过来、让账单能出来收款。

**允许调整的状态**：`IN_USE` 与 `PENDING_PAYMENT`。

> **使用中的订单调整后会自动转待支付** —— 不转的话，一条永远不会被点结束的
> 订单就永远收不到钱。
>
> **已支付的订单不允许调整**（`ORDER_NOT_ADJUSTABLE`）—— 调整必然改变金额，
> 已入账的就要走退款与对账，那是人工运营流程。

**请求体**

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `endTime` | string | 是 | 核实后的离场时刻。必须晚于开门时刻，且不能是未来 |
| `reason` | string | 是 | ≤255 字符。**必填**，会永久留痕 —— 写「用户忘记结束，监控核实 21:30 已离场」这样的记录，事后无论是顾客质疑还是运营复盘都说得清 |

**返回 `data`**：`OrderSettleVo`（重算后的账单，字段同「结束使用」）

**错误码**：`ORDER_NOT_FOUND`(40405)、`ORDER_NOT_ADJUSTABLE`(40920)、
`ORDER_STATUS_INVALID`(40918)（时间不合法：早于开门时刻，或是未来）

### GET /api/payments/channels

**列出某类收款当前可用的支付通道 —— 收银台选项的唯一来源，前端不要写死。**
需登录。

> 一个通道能不能出现，取决于两件只有服务端知道的事：**本店收不收这种钱**
> （`uspace.payment.enabled-channels`）、**这类收款受不受理它**。
> 前端自己再判一遍就会出现「选项就在那里、点了却报错」。

**请求参数**

| 参数 | 位置 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- | --- |
| `targetType` | query | string | 是 | `ORDER` / `BOOKING` / `MONTHLY_CARD` / `PRODUCT` |

**返回 `data`**：数组，元素结构如下

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `channel` | string | 通道名，提交支付时原样回传 |
| `label` | string | **面向用户**的支付方式名（如「扫码转账」「微信支付」）—— 用户不需要知道 JSAPI 与 H5 的区别 |
| `needProof` | boolean | 这条通道**是否需要用户上传付款凭证**。`true` 走上传面板，`false` 走线上支付流程 |
| `online` | boolean | 是否线上通道，决定「要不要向平台发起支付、要不要轮询查单」 |

> **`needProof` 与 `online` 在当前取值下互补，但语义不同，两个都要留着。**
> 将来若加一条「现金」通道（管理员线下收款），它**既非线上、也不需要凭证** ——
> 那时只有一个字段就不够用了。

**通道由前端按浏览器环境预选，但用户仍可改。** 微信内打不开支付宝、
支付宝内打不开微信（双方互相屏蔽外链），预选错了必然出现「选了却调不起来」的死路。
判断依据是 User-Agent：

| UA 含 | 环境 | 预选 |
| --- | --- | --- |
| `MicroMessenger` | 微信内置浏览器 | `WXPAY_JSAPI` |
| `AlipayClient` | 支付宝内置浏览器 | `ALIPAY_WAP` |
| 其余 | 微信外的手机浏览器 | `WXPAY_H5` 与 `ALIPAY_WAP` 并列给出 |

> 预选结果**不由后端返回** —— 它依赖 User-Agent，只有前端拿得到。

### GET /api/payments/qr

**列出启用中的收款码**，供扫码转账的收银台展示。需登录。

**返回 `data`**：数组

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | number | 收款码 ID。提交付款凭证时用 `payQrId` 回传它 |
| `channel` / `channelLabel` | string | `WXPAY` / `ALIPAY` 与其中文名 |
| `name` | string | 显示名（如「老板微信」） |
| `imageUrl` | string | 收款码图片的站内路径，直接给 `<img :src>` |

> **门店一张码都没配时返回空列表** —— 那是真实的运营状态（刚部署完还没配），
> 前端应提示「请联系管理员配置收款方式」，而不是白屏。
>
> **只返回启用中的码**：把停用的也列出去，顾客会扫到一张不再使用的码。
> 后台那个列表（本章末尾的 `GET /api/admin/pay-qrs`）口径相反，是刻意的。

### POST /api/payments

**统一发起支付。** 需登录。

> **为什么是一个统一入口，而不是 `/api/orders/{id}/payment`**：
> 本系统要收钱的东西不止订单一种（还有包场），它们走同一套支付通道与回调链路。
> 把入口收在「支付」这个动作上，加一类收款不必新开路径。

**请求体**

| 字段 | 类型 | 必填 | 取值 |
| --- | --- | --- | --- |
| `targetType` | string | 是 | `ORDER` / `BOOKING` / `MONTHLY_CARD` / `PRODUCT` |
| `targetId` | number | 是 | 对应类型的单据 ID |
| `channel` | string | 是 | 四条通道之一，取值请从 `GET /api/payments/channels` 拿 |

> **传 `QR_UPLOAD` 会返回一个不含任何支付参数的「成功」**（只有单号、通道与金额）——
> 它不调用支付网关，`prepayId` / `h5Url` / `formHtml` / `mockPayUrl` 都是空的。
> 前端拿到它应当转入上传付款凭证的界面（`POST /api/payment-proofs`），
> 而不是等某个拉起参数。
>
> 投产时这正是主路径：`enabled-channels` 里只有 `QR_UPLOAD`，收银台也就只给这一个选项。

**返回 `data`**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `outTradeNo` | string | 商户订单号（= 订单号或包场单号）。用于「主动查单」与客服核对 |
| `targetType` / `targetId` | string / number | 回显 |
| `channel` / `channelLabel` | string | 通道名与中文说明 |
| `amount` | number | 应付金额（元） |
| `prepayId` | string | **仅 JSAPI**：预支付会话标识，用 `WeixinJSBridge.invoke('getBrandWCPayRequest', …)` 调起 |
| `h5Url` | string | **仅 H5**：`location.href = h5Url` 拉起微信 App |
| `formHtml` | string | **仅 WAP**：一段自动提交的表单 HTML，插入页面即可拉起支付宝 App |
| `mockPayUrl` | string | **仅模拟模式非空**，见下 |
| `expireHint` | string | 有效期提示文案，可直接展示 |

> ⚠️ **应当在用户点「去支付」时才调这个接口**，不要在订单结算完就调 ——
> JSAPI 的凭据有效期 **2 小时**、H5 的链接更是只有 **5 分钟**，
> 提前下单只会让它在用户还没决定付款时就过期。

> ⚠️ **H5 的 `h5Url` 严禁篡改、拆分或截断**，且**只有 5 分钟有效期** ——
> 拿到后应当立刻跳转，不要缓存、不要等待。

**关于 `mockPayUrl`**：当前 `uspace.payment.provider=mock`（毕设阶段无支付商户号），
它**非空**表示处于模拟模式。前端识别到非空时，**不要真的跳转 `h5Url` 或提交表单**，
而是弹出自己的「模拟收银台」，由它去调 `POST /api/payments/mock/pay`。

**错误码**：`ORDER_NOT_FOUND`(40405)、`BOOKING_NOT_FOUND`(40404)、
`ORDER_STATUS_INVALID`(40918)、`BUSINESS_REJECTED`(40900)（包场不需要支付）、
`PAYMENT_GATEWAY_UNAVAILABLE`(50201)

### GET /api/payments/{outTradeNo}

**查询支付状态，必要时向支付平台补偿。** 需登录。

> **用途是「我付过了但订单还是待支付」** —— 支付成功而回调丢失在生产环境
> 是必然事件，这个接口是它的兜底。查到平台已收款而本地未更新时，
> 会走与回调完全相同的处理逻辑补上，所以**调一次就能修好**。

**请求参数**

| 参数 | 位置 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- | --- |
| `outTradeNo` | path | string | 是 | 商户订单号 |
| `channel` | query | string | 是 | 当时使用的通道，决定查哪个平台 |

**返回 `data`**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `outTradeNo` | string | 商户订单号 |
| `paid` | boolean | 是否已支付 |
| `status` / `statusText` | string | 目标当前状态 |
| `paymentMethod` / `paymentNo` / `paidAt` | string | 支付信息，未支付时为空 |
| `amount` | number | 应付金额 |
| `message` | string | **给用户看的一句话**，区分「已到账」「尚未到账」「平台已扣款但本地未更新」 |

> 最后那种情形（`message` 提示「请联系管理员核对」）最要紧 ——
> 用户最需要知道的是**不要再付一次**。

**错误码**：`NOT_FOUND`(40400)（单号不存在或不属于你 —— 两者返回同一个结果，
避免被用来枚举别人的单号）、`PARAM_INVALID`(40000)（没传 `channel`）、
`PAYMENT_GATEWAY_UNAVAILABLE`(50201)

### POST /api/payments/mock/pay

**模拟用户完成支付**（仅 `provider=mock` 时存在）。需登录。

> **它模拟的是「用户在微信/支付宝的收银台上点完成支付」这个动作，
> 而不是「把订单改成已支付」** —— 触发的是**完整的回调链路**
> （签名 → 验签 → 幂等 → 金额核对 → 状态流转），不是直接改状态。
> 若模拟支付直接改状态，那条链路上的分支在演示时就永远走不到。

**请求体**

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `outTradeNo` | string | 是 | 订单号（`OD` 前缀）或包场单号（`BK` 前缀） |

**返回 `data`**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `paid` | boolean | 模拟的支付动作是否完成（相当于「用户确实付了钱」） |
| `notified` | boolean | **回调是否真的投递到了后端**。为 `false` 通常是配置了 `notify-drop-rate` 用于演示「回调丢失」，此时订单仍是待支付，调一次查单接口就能补上 |
| `message` | string | 给演示者看的说明 |

> ⚠️ **需要登录，且校验支付单归属** —— 少了这一步，任何登录用户只要知道
> 别人的订单号，就能把别人的订单标记成已支付。

### POST /api/payments/notify/wxpay · POST /api/payments/notify/alipay

**支付平台的回调端点。这两个是给支付服务器调的，不是给前端调的。**

- **匿名可访问**（支付平台不带 JWT），但鉴权改由**验签**承担，验签不过一律拒绝处理
- 两个端点**不能合并成一个**：微信是「RSA 验签 + AES-GCM 解密」，
  支付宝是「表单参数 + RSA2 验签」，协议完全不同
- **响应体不是本系统的 `ApiResult`**，而是平台自己的协议：
  - 微信：`{"code":"SUCCESS","message":"成功"}`，失败时 HTTP 5xx + `{"code":"FAIL"}`
  - 支付宝：纯文本 `success` / `failure`

**应答规则**：

| 情形 | 应答 | 理由 |
| --- | --- | --- |
| 处理成功 / 重复回调 / 单号不存在 | 成功 | 重推无意义 |
| 金额不符 / 状态冲突 / 验签失败 | 失败 + 错误日志 | 让平台持续重推，同时引起人工注意 |

**幂等有四道**：状态预检 → 条件 UPDATE 的受影响行数 →
用户累计消费用相对更新 → 商户订单号上的唯一索引。

### POST /api/payment-proofs

**提交付款凭证** —— 扫码转账的收款入口。需登录。

> **四类收款共用这一个入口**（订单 / 包场 / 月卡 / 商品），靠 `targetType` +
> `targetId` 指明是哪一笔 —— 与 `POST /api/payments` 是同款设计。

**请求体**

| 字段 | 类型 | 必填 | 校验 |
| --- | --- | --- | --- |
| `targetType` | string | 是 | `ORDER` / `BOOKING` / `MONTHLY_CARD` / `PRODUCT` |
| `targetId` | number | 是 | 对应类型的单据 ID |
| `proofUrl` | string | 是 | ≤255 字符。**必须是 `/api/payment-proofs/image` 返回的那个路径** —— 前缀会被校验，填外链或别的种类的图会被拒 |
| `paymentNo` | string | 否 | ≤64 字符。从付款详情页抄来的交易流水号，**强烈建议填** |
| `ocrPaymentNo` | string | 否 | 上传接口返回的识别单号，**原样回传** |
| `ocrAmount` | number | 否 | 上传接口返回的识别金额，**原样回传** |
| `ocrText` | string | 否 | 上传接口返回的识别原文，**原样回传** |
| `payQrId` | number | 否 | 扫的是哪张收款码。店里有多个收款账号时回传它，钱进了谁的口袋事后才追溯得到 |

> **提交时没有金额参数** —— 凭证金额取自收款目标本身，不由请求体决定。

> **三个 `ocr*` 字段是上传接口返回的那三个，原样回传即可**，服务端不再重新识别
>（识别按次计费，而免费额度只有 1000 次/月，一单两次会让额度当月翻倍耗尽）。
> 它们与 `paymentNo` 是两回事：`paymentNo` 是用户确认后的值（他可能改过），
> 而这三个是**机器当初读出了什么** —— 分列存着，后台才分得清
> 「这个号是认出来的还是人填的」。
>
> ⚠️ 它们的定位是**辅助线索**：后台拿识别出的金额与单号跟用户提交的比对，
> 帮管理员快速看出哪几条对不上。系统里**没有任何自动判断依赖它们** ——
> 复核永远是人做的，管理员看的始终是那张截图。也正因如此，
> 超长或不合理的值由服务端截断、丢弃，**不会因为辅助信息没对上格式而让提交失败**。

**返回 `data`**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `targetType` / `targetId` | string / number | 回显 |
| `verifyStatus` / `verifyStatusLabel` | string | 凭证状态名与中文（`SUBMITTED` 待复核 / `CONFIRMED` 已核对 / `REJECTED` 未通过） |
| `delivered` | boolean | **本次提交是否已经让这笔收款完成交付**，见下 |
| `message` | string | 给用户看的一句话，由后端拼好，直接展示 |

> ⚠️ **`delivered` 必须用后端返回的，前端不要按 `targetType` 自己判**：
> - `true`（订单 / 商品）—— 提交那一刻就落账了，界面应当说「支付完成」
> - `false`（包场 / 月卡）—— 还在等复核，界面应当说「等待管理员确认」
>
> 哪一类「提交即交付」是业务规则；前端再判一遍就会与后端漂移，
> 而漂移的表现是「页面说已交付、实际没交付」，不报任何错。

**错误码**：`PAYMENT_PROOF_IMAGE_INVALID`(40002)（截图路径不合法）、
`PAYMENT_PROOF_TARGET_INVALID`(40941)（这笔当前状态不支持提交）、
`PAYMENT_PROOF_REJECTED`(40939)（该凭证已被驳回，需联系管理员）、
`PAYMENT_ALREADY_PAID`(40942)（线上通道付的款没有凭证可言）

**几条分支**（都不是异常，是常态）：

| 情形 | 结果 |
| --- | --- |
| 目标已支付 + 凭证待复核 | 只更新凭证（换图 / 改流水号），**不重复落账** |
| 目标已支付 + 凭证已核对 | 幂等返回，不覆盖 —— 覆盖会把一条已核对的凭证打回待复核 |
| 目标已支付 + 凭证未通过 | 拒绝，并附上驳回原因 |
| 同一流水号被多笔凭证引用 | **不拦提交**，但相关凭证全部被标记风险，并排到后台列表最前 |

### GET /api/payment-proofs/rejected

**查我被驳回、还没重交的付款凭证。** 需登录。

用户端首页的提醒条与订单详情页的标记都读它。**补的是「先交付后复核」那道缺口**：
订单与商品在提交凭证那一刻就落账了，而管理员事后驳回**不回退订单状态**
（回退要连带退库存、减累计消费、恢复欠费拦截，三件事每一件都得人判断），
所以用户端看到的仍是「已支付」。没有这个接口，那个结论就永远到不了当事人那里。

**返回 `data`**：数组。一条都没有时是**空数组**而不是 404 ——
首页每次加载都会调它，「没有待处理的事」是最常见的正常状态。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `proofId` | number | 凭证 ID |
| `targetType` / `targetTypeLabel` | string | `ORDER` / `BOOKING` / `MONTHLY_CARD` / `PRODUCT` 与其中文名 |
| `targetId` | number | 目标 ID，前端据此跳到具体那一笔 |
| `orderNo` | string | 商户订单号 |
| `amount` | number | 提交时的应付额 |
| `reason` | string | 管理员填写的驳回原因（**必填**） |
| `rejectedAt` | string | 驳回时刻 |

> **「还没重交」不需要额外判断**：重交走 upsert，会把状态翻回待复核并清掉原因，
> 所以 `REJECTED` 本身就意味着「还等着他处理」。用户重交之后这条自动消失，
> **前端不必做任何「已处理」的本地标记**。
>
> ✅ **驳回会把订单标成 `REJECTED`（凭证未通过）** —— 订单与商品是「提交即交付」，
> 驳回时 `PaymentProofService` 会把那一步退回去：订单转 `REJECTED`
> 并清掉支付四列、商品退回购买单（**不还库存** —— 货多半已被取走，
> 还回去是记假账）、累计消费冲减。退完之后用户重新上传走的就是
> 正常的落账路径，不必另开一条重交通道。
>
> ⚠️ **订单退的是 `REJECTED` 而不是 `PENDING_PAYMENT`**：后者一个状态要承载
> 两件处置方式完全不同的事 ——「他还没付钱」（去支付）与「他付过了、
> 只是凭证没通过」（重新上传一张截图）。合并的话，用户看到「待支付 ¥8.00」
> 极可能再扫一次码、**真的付第二遍**。
>
> ⚠️ 连带效果：**那笔未结清的单子会挡住他开新单**（下单前的欠费校验把
> `REJECTED` 也算作未了结）—— 这是刻意的，有被驳回的账在，他就是潜在的欠费者。
> 下单接口对这两种情形返回**不同的错误码**：`ORDER_UNPAID_EXISTS`(40931)
> 与 `ORDER_PROOF_REJECTED`(40947)，因为用户该做的事不同。

### POST /api/payment-proofs/image

**上传付款截图，并顺带识别一次。** 需登录。`multipart/form-data`，字段名 `file`。

**返回 `data`**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `proofUrl` | string | 截图的站内路径，提交凭证时原样回传 |
| `ocrPaymentNo` | string? | 识别出的交易单号，可空。前端用它**预填**流水号输入框 |
| `ocrAmount` | number? | 识别出的金额（元），可空 |
| `ocrText` | string? | 识别出的原文，可空。仅供复核参考 |

> **只落盘、只返回路径，不写任何数据库**：用户传完图要核对流水号、
> 可能还要改一遍再交。把它与提交合成一个接口的话，
> 「传了图又放弃」会留下一条状态不明的凭证记录。

> **三个 `ocr*` 字段可能全为空** —— 没配识别引擎（`uspace.ocr.provider=mock`，
> 默认值）时恒为空，配了引擎也可能认不出用户传的这张图。它们由前端原样带回
> 提交接口（见上一节），服务端不再重新识别。
>
> **识别失败不会让上传失败**：网络不通、配额耗尽、凭据失效，一律按「没识别出」
> 处理，上面三个字段留空、`proofUrl` 照常返回。用户手填单号那条路一直都在。

> **同一用户两次成功上传之间有冷却（2026-10-10 加）**：默认 10 秒
> （`uspace.payment.proof-image-cooldown`）。识别在上传那一刻做一次，
> 而 OCR 每月免费额度有限 —— 冷却挡的是连点与脚本。
> **只有成功上传才计时**：文件不合法在识别之前被挡下、不消耗额度，
> 所以不计入冷却。网页端与群里传图共用这一道。

**错误码**：`UPLOAD_FILE_INVALID`(40001)、`UPLOAD_FILE_TOO_LARGE`(41300)、
`PAYMENT_PROOF_COOLDOWN`(42900，同一用户上传太频繁)

### GET /api/admin/payment-proofs

**后台分页查询付款凭证。仅 ADMIN。**

**请求参数**：`page`（默认 1）、`size`（默认 10，最大 100）、
`verifyStatus`（可选，`SUBMITTED` / `CONFIRMED` / `REJECTED`）

> **排序是刻意设计的**：有风险标记的 → 待复核的 → 新的在前。
> 不传 `verifyStatus` 时返回全部，后台默认视图就靠它 —— 一打开先看到最该处理的。

**返回 `data`**：`PageResult<AdminProofVo>`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | number | 凭证 ID，复核时用它 |
| `targetType` / `targetTypeLabel` | string | 收款类型与其中文名 |
| `targetId` / `orderNo` | number / string | 目标 ID 与商户单号 |
| `userId` / `userNickname` | number / string | 提交人 |
| `amount` | number | **提交时的应付额快照**（不是用户说付了多少） |
| `proofUrl` | string | 付款截图，直接给 `<img :src>` |
| `paymentNo` | string | 用户填的交易流水号，可空 |
| `ocrPaymentNo` / `ocrAmount` / `ocrText` | string / number / string | OCR 识别结果，可空。`ocrPaymentNo` 与用户填的 `paymentNo` **分列显示** —— 两者不一致说明用户改过单号、或机器读错了，都值得看一眼。没配识别引擎时三列全空 |
| `payQrName` | string | 扫的是哪张收款码（显示当前名字，锚点仍是 `pay_qr_id`） |
| `verifyStatus` / `verifyStatusLabel` | string | 复核状态 |
| `riskFlag` / `risk` | string / boolean | 风险标记原始值（如 `DUPLICATE_PAYMENT_NO`）与布尔 |
| `delivered` | boolean | **这类的钱在提交那刻就算收到了** —— 见下 |
| `createdAt` / `confirmedAt` / `confirmedBy` / `rejectReason` | — | 提交时刻、复核信息与驳回原因 |

> ⚠️ **`delivered` 为 true 的条目，驳回不代表事情结束。** 订单与商品在提交那一刻
> 就已经落账（订单已 PAID、库存已扣、累计消费已加），而系统**不做自动回退** ——
> 那涉及改状态、退库存、减累计消费三件事，每一件都需要人来判断。
> 后台必须把这类条目显著标出来，否则管理员点完「未通过」会以为结束了，
> 实际上还欠一步人工处置。

### POST /api/admin/payment-proofs/{id}/confirm

**复核通过。仅 ADMIN。**

无请求体 —— 要填的东西一样都没有，不为对称造一个空对象。

> **「通过」的含义取决于收款类型**：订单与商品是**纯登记**（钱在提交那一刻
> 就算收到了）；包场与月卡是**此刻才交付**（邀请令牌与月卡都产生在这一步），
> 所以这一步必须成功。

**返回 `data`**：null

**错误码**：`PAYMENT_PROOF_NOT_FOUND`(40415)、
`PAYMENT_PROOF_STATUS_INVALID`(40940)（这条已被别人处理过）

### POST /api/admin/payment-proofs/{id}/reject

**复核不通过。仅 ADMIN。**

**请求体**

| 字段 | 类型 | 必填 | 校验 |
| --- | --- | --- | --- |
| `reason` | string | 是 | ≤200 字符。**会展示给用户**，所以不能空着 —— 空着的话他只能反复试 |

**返回 `data`**：null

> ⚠️ **驳回不会回退已经发生的交付**（见上）。系统能做的是把事实喊出来：
> 记一条 warn 日志，并让列表里的 `delivered` 标记提示管理员还有一步要做。

**错误码**：同 `confirm`

### GET /api/admin/pay-qrs

**列出本店全部收款码（含停用的）。仅 ADMIN。**

> **含停用的是一个刻意的选择**：只列启用中的话，管理员停用一张码之后
> 就再也找不回它了，而「临时停用、过阵子再开」正是最常见的用法。

**返回 `data`**：数组 —— `id` / `channel` / `channelLabel` / `name` / `imageUrl` /
`enabled` / `sort` / `updatedAt`

### POST /api/admin/pay-qrs

**新增一张收款码。仅 ADMIN。**

**请求体**

| 字段 | 类型 | 必填 | 校验 |
| --- | --- | --- | --- |
| `channel` | string | 是 | `WXPAY`（微信）/ `ALIPAY`（支付宝） |
| `name` | string | 是 | ≤50 字符，显示名 |
| `imageUrl` | string | 是 | ≤255 字符，**必须是 `/api/admin/pay-qrs/image` 返回的路径** |
| `enabled` | number | 是 | 1 启用 / 0 停用。**必填** —— 建出来到底能不能用，不给默认值 |
| `sort` | number | 否 | 排序，不传按 0 |

**返回 `data`**：新增后的收款码

**错误码**：`PARAM_INVALID`(40000)（渠道取值非法、图片路径非法）、
`STORE_NOT_FOUND`(40402)（门店还没初始化）

### PUT /api/admin/pay-qrs/{id}

**修改一张收款码（全量替换）。仅 ADMIN。**

没传的字段就是清空，唯一的例外是 `sort`（不传按 0 处理）。
**启停也在这里一起改** —— 它是这张码编辑表单里的一个字段，
不像机台状况那样需要单开接口。

**错误码**：`PAY_QR_NOT_FOUND`(40414)、`PARAM_INVALID`(40000)

### DELETE /api/admin/pay-qrs/{id}

**删除一张收款码（逻辑删除）。仅 ADMIN。**

> **走逻辑删除而不是物理删除**：历史付款凭证上记着 `pay_qr_id`，
> 物理删掉之后那个号就查不出对应的是哪张码了，
> 对账时说不清「这笔钱当时扫的是哪个账号」。

**错误码**：`PAY_QR_NOT_FOUND`(40414)

### POST /api/admin/pay-qrs/image

**上传收款码图片。仅 ADMIN。** `multipart/form-data`，字段名 `file`。

**返回 `data`**：`{ imageUrl }` —— 图片的站内路径

> **只落盘、不写数据库** —— 与商品封面是同一套语义：管理员拿到路径填进表单，
> 随新增 / 修改一起提交。
>
> **不裁剪、不缩放，输出 PNG**：二维码常是透明底，转成 JPEG 后透明区变黑，
> 就扫不出来了。

### POST /api/admin/reconcile-batches

**上传账单并执行对账。仅 ADMIN。** `multipart/form-data`，字段名 `file`。

**支持的账单格式**（**由表头自动识别，不需要传渠道参数**）：

| 格式 | 来源 | 特点 |
| --- | --- | --- |
| 微信 | App 里导出 | xlsx |
| 支付宝 | 导出为 CSV | 无 BOM 的 GBK |
| 系统标准模板 | 管理员手工整理 | 六列：`交易时间,交易单号,金额(元),收/支,交易状态,备注`（后两列可省） |

**一次上传就是一个批次，没有「先预览再确认」** —— 对账不改任何业务状态，
传错一份已经对过的账单会走「已被认领」那一支、零差异。响应里直接带着解析结果
（账单多少笔、合计多少、覆盖哪段时间），管理员据此就能看出自己有没有传错文件。

**返回 `data`**：一个批次对象

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | number | 批次 ID（**`batchId` 这个名字只出现在文档里**，接口返回的是 `id`） |
| `channel` / `channelLabel` | string | `WXPAY` / `ALIPAY` / `STANDARD` 与其中文名。**由表头认出来的** |
| `fileName` | string | 上传时的原始文件名 |
| `periodStart` / `periodEnd` | string | **账单内容里**最早的 / 最晚的交易时间（不采信文件名） |
| `windowStart` / `windowEnd` | string | 系统侧凭证的比对窗口，见下 |
| `billCount` / `billAmount` | number | 账单侧解析出的笔数与金额合计 |
| `billExcludedCount` | number | **未参与对账**的笔数：收支方向不是「收入」的，以及交易类型不在白名单里的（个人收款账单里的转账、红包、别处买东西的退款）。**只计数不参与匹配**。要与 `billCount` 并列看才完整 —— 账单上写着收了多少、系统只认了多少，差额全在这里 |
| `billSkippedCount` | number | 账单侧因「已被之前的批次认领」而跳过的笔数 |
| `billUnclaimedCount` / `billUnclaimedAmount` | number | **总账：账单侧未被任何有效凭证认领的笔数与金额** —— 为 0 就是「账对平了」，不必再翻逐笔差异。口径 = `BILL_ONLY`（一条凭证都没有）＋ `REJECTED_IN_BILL`（有凭证但被驳回）；**金额不符与重复认领不算**（那两类钱确实到了，只进差异列表）。⚠️ **可空**：`null` 表示该批次建于本功能之前、没统计过，与 0 是两回事 |
| `proofCount` / `proofAmount` | number | 系统侧参与比对的凭证数与金额 |
| `proofSkippedCount` | number | 已被之前批次认领、本次跳过的凭证数 |
| `matchedCount` / `matchedAmount` | number | 匹配成功的笔数与金额 |
| `diffCount` | number | 本次写入的差异条数 |
| `unhandledCount` | number | 这个批次还有几条差异没处理 |
| `hasBillFile` | boolean | 账单原文件在不在（**为 false 不代表对账失败**） |
| `createdBy` / `createdByName` / `createdAt` | — | 执行对账的管理员与时刻 |

> **`windowStart` / `windowEnd` 是「为什么这条凭证没被算进来」的答案**：
> 系统只比对落在这个区间内提交的凭证。区间由账单里的交易时间往前放宽 1 天、
> 往后放宽 2 天算得（两个都是配置项），**两端不对称是刻意的** ——
> 上界要覆盖「当天玩完忘了传、隔天才想起来」。
>
> **重复上传同一份账单不会产生重复差异**：已经对过的跳过、已经处理过的差异
> 不重复记。结果是安静的「匹配 0 笔、跳过 N 笔、0 条差异」——
> 那两个「跳过」的数就是为了让这句话有据可依。

**错误码**：`RECONCILE_BILL_ENCODING`(40003)、`RECONCILE_BILL_FORMAT`(40004)、
`RECONCILE_BILL_EMPTY`(40005)、`UPLOAD_FILE_TOO_LARGE`(41300)

### GET /api/admin/reconcile-batches

**后台分页查询对账批次。仅 ADMIN。**

**请求参数**：`page`（默认 1）、`size`（默认 10，最大 100）

> **分页参数用 `page` + `size`** —— 本项目里月卡与商品那两个模块用的是
> `pageNum` + `pageSize`。传错**不报错**，只会永远返回第一页。

**返回 `data`**：`PageResult<批次对象>`（字段同上）。排序固定为「新的在前」。

### GET /api/admin/reconcile-batches/{id}

**取一个批次的详情。仅 ADMIN。**

**返回 `data`**：批次对象，**比列表多一个 `diffTypeCounts`** ——
各类型差异的条数，键是枚举名。⚠️ **某个类型一条都没有时那个键不存在**，
前端取值要用 `?? 0`。

**错误码**：`RECONCILE_BATCH_NOT_FOUND`(40416)

### GET /api/admin/reconcile-batches/{id}/diffs

**分页查询某个批次的差异明细。仅 ADMIN。**

**请求参数**：`page`（默认 1）、`size`（默认 20，最大 100）、
`diffType`（可选，认不出的取值返回空列表）、`handled`（可选，`0` / `1`）

**返回 `data`**：`PageResult<差异对象>`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` / `batchId` | number | |
| `diffType` / `diffTypeLabel` / `diffTypeHint` | string | 类型名、中文短标签、**一句话说明「这意味着什么、该做什么」** |
| `proofId` | number \| null | 相关凭证；`BILL_ONLY` 时为空（**这一类说的正是「系统里没有凭证认领这笔钱」**） |
| `paymentNo` | string \| null | **归一化后**的交易单号；`NO_PAYMENT_NO` 时为空 |
| `orderNo` / `targetType` / `targetTypeLabel` | string \| null | 凭证明细，管理员凭它直接去订单页找人 |
| `billAmount` / `billTime` / `billSummary` | — | 账单侧金额、时刻、商品或交易对方摘要；账单侧无记录时为空 |
| `proofAmount` | number \| null | 系统侧凭证金额；`BILL_ONLY` 时为空 |
| `handled` / `handleNote` / `handledBy` / `handledByName` / `handledAt` | — | 处理状态与结论 |

> **排序是刻意设计的**：待处理的 → 类型优先级（最紧急的在前）→ 新的在前。
> 六类的优先级顺序见 `ReconcileDiffType`。

### GET /api/admin/reconcile-batches/{id}/file

**下载账单原文件。仅 ADMIN。**

**返回**：文件流（`application/octet-stream` +
`Content-Disposition: attachment`），**不是 JSON**。

> ⚠️ **不能用 `<a href>` 直接打开这个地址**：那样不会带上 `Authorization` 头，
> 拿到的是 401。前端必须走 `responseType: 'blob'`，再用
> `URL.createObjectURL` 触发下载。
>
> **账单刻意不落在公开的 `/uploads/` 下**：那个目录是匿名可访问的
>（头像与截图要用 `<img src>` 加载，浏览器不为图片请求带 token），
> 而账单里含全部交易对手、备注、金额与时间。它只能通过这个带鉴权的接口取。

**错误码**：`RECONCILE_BATCH_NOT_FOUND`(40416)、`RECONCILE_BILL_FILE_MISSING`(40418)

### POST /api/admin/reconcile-diffs/{id}/handle

**标记一条对账差异已处理。仅 ADMIN。**

**请求体**：`{ "note": "已联系顾客补交凭证" }` —— **`note` 选填**（≤200 字）

> **这一步不改动任何业务数据** —— 订单状态、付款凭证、批次都不会变，
> 只是记下「管理员看过了、结论是什么」。
>
> 备注选填是刻意的：它是管理员**写给自己的备忘**，
> 而凭证驳回的原因是**给顾客的结论**（那个必填）。强制填的话，
> 管理员会对几十条同类差异逐个打上「已处理」三个字，然后这个功能就没人用了。
>
> **不提供「取消已处理」**：标错了的条目仍然筛得出来、看得见。

**返回 `data`**：`null`

**错误码**：`RECONCILE_DIFF_NOT_FOUND`(40417)、`RECONCILE_DIFF_HANDLED`(40943)

## 十、月卡（模块 9）

### 购买流程

```
POST /api/cards/purchases   →  拿到购买单与单号（此时还没有卡）

线上通道：
POST /api/payments          →  发起支付，targetType 传 MONTHLY_CARD
POST /api/payments/mock/pay →  （模拟模式）完成付款

扫码转账（投产时的路径）：
POST /api/payment-proofs    →  提交付款截图，targetType 同样传 MONTHLY_CARD
POST /api/admin/payment-proofs/{id}/confirm
                            →  管理员复核通过后，卡才发出来

GET  /api/cards/me          →  卡包里出现生效中的卡
```

> **月卡属于「等复核」那一类**（不是「提交即交付」）：凭证提交后卡不会立刻出现，
> 要等管理员确认 —— 它交付的是一张 30 天的卡，发出去就收不回来。
> 提交接口返回的 `delivered` 字段会说清楚是哪一种。

**付款复用支付模块的统一入口**，不新增支付接口 —— 回调、验签、幂等全部沿用。

### GET /api/cards/types

列出在售卡种与价格。需要登录。

```json
{
  "code": 0,
  "data": [
    {
      "cardType": "ALL_DAY",
      "label": "全天月卡",
      "price": 600,
      "coverageLabel": "全天",
      "periodText": "不限时段",
      "validDays": 30
    },
    {
      "cardType": "NIGHT",
      "label": "夜间月卡",
      "price": 320,
      "coverageLabel": "仅夜场",
      "periodText": "22:00 – 次日 10:00",
      "validDays": 30
    }
  ]
}
```

`price` 来自后端配置，前端不参与定价。

### POST /api/cards/purchases

发起购买月卡。创建一笔**待支付购买单** —— 此时还没有卡，付款成功后才会生成。

**请求**

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `cardType` | string | 是 | `ALL_DAY` 全天 / `NIGHT` 夜间 |

**响应**

```json
{
  "code": 0,
  "data": {
    "id": 28,
    "orderNo": "MC202609290920327700",
    "cardType": "ALL_DAY",
    "cardTypeLabel": "全天月卡",
    "price": 600,
    "status": "PENDING_PAYMENT",
    "statusLabel": "待支付",
    "createdAt": "2026-09-29 09:20:32",
    "expireAt": "2026-09-29 09:50:32"
  }
}
```

发起支付时：`targetId` 传 `id`，`targetType` 传 `MONTHLY_CARD`，
返回的 `outTradeNo` 就是这里的 `orderNo`。

**失败**

| 码 | 场景 |
|---|---|
| 40924 | 已有生效中的月卡 —— 续费要在旧卡到期之后 |
| 40925 | 已有一笔未超时的待支付单 —— 前端引导回收银台，或先取消 |
| 409 | 月卡暂停开放（总开关关闭），已售出的卡不受影响 |

超过存活时长（默认 30 分钟）的待支付单，会在用户下次购卡时被自动关闭 ——
用户完全无感，不必先去清理。

### POST /api/cards/purchases/{id}/cancel

取消一笔待支付的购买单。**这不是退款** —— 那笔钱从来没付过。

非本人的单返回 404 而不是 403：403 等于承认「这个单存在，只是不归你」，
可以被用来枚举单号。

| 码 | 场景 |
|---|---|
| 40407 | 单子不存在，或不属于本人 |
| 40926 | 单子不是待支付状态（已付款的关不掉） |

### GET /api/cards/me

我的卡包。一次给出三样，前端不必连发三个请求：

```json
{
  "code": 0,
  "data": {
    "active": {
      "id": 31,
      "cardNo": "MC202609290920429922",
      "cardType": "ALL_DAY",
      "cardTypeLabel": "全天月卡",
      "price": 600,
      "status": "ACTIVE",
      "statusLabel": "生效中",
      "startDate": "2026-09-29",
      "endDate": "2026-10-28",
      "paidAt": "2026-09-29 09:20:43",
      "paymentMethod": "WXPAY_H5",
      "coverageLabel": "全天",
      "remainingDays": 30
    },
    "pending": null,
    "history": []
  }
}
```

- **`active`**：此刻生效的卡，没有则为 `null`。`remainingDays` 只有它才有值（含首尾）
- **`pending`**：待支付的购买单，前端据此显示「去支付」
- **`history`**：已过期与已退款的卡，倒序

**三者互不重叠**，前端按字段名分渲染即可 —— 不必自己拿状态和日期去判断某张卡该放哪边，
那样等于在客户端再实现一遍免单判定的口径。

### GET /api/admin/cards

月卡分页列表。**需要管理员身份。**

| 参数 | 说明 |
|---|---|
| `pageNum` / `pageSize` | 分页，默认 1 / 10 |
| `userId` | 按持卡人筛选，可空 |
| `status` | `ACTIVE` / `EXPIRED` / `REFUNDED`，可空 |
| `cardType` | `ALL_DAY` / `NIGHT`，可空 |

> **本期只读**：退款政策尚未拍板（未使用能否全退、已部分使用如何折算），
> 因此没有退款或作废接口。管理员可以直接改库把卡置为 `REFUNDED`，
> 免单会**立刻停止**（免单判定同时校验状态与有效期）。

### GET /api/orders/me/month-spent

本月累计消费与优惠资格。归在订单模块，但答的是「优惠」的问题。

```json
{
  "code": 0,
  "data": {
    "monthStart": "2026-09-01",
    "monthSpent": 0,
    "threshold": 200,
    "discounted": false,
    "remaining": 200
  }
}
```

口径与结算完全一致：只算**已支付**订单的实付额、按**离场时刻**（`end_time`）
归入自然月、**不含月卡卡费**（月卡本身已是独立优惠，不再叠加）。
月底进店、次日凌晨离店的夜单因此计入离场那个月。

⚠️ 但「一笔钱计入哪个月」与「结算时用哪个月的累计判优惠」是两件事：后者取的是
**订单开始时刻所属月**。于是一笔 8/31 进店、9/1 离店的夜单，享的是 8 月已挣到的
优惠资格，却计入 9 月的累计。

### GET /api/orders/me/stats

我的累计时长与本月时长。**需登录。**

```json
{
  "code": 0,
  "data": { "totalMinutes": 8520, "monthMinutes": 2160, "monthStart": "2026-09-01" }
}
```

与 `/me/month-spent` 并排显示在「我的」页：一个答「玩了多久」，一个答「花了多少钱」。

> **统计的是「在店时长」，不是计费时长。** 包场时段不计费、宽限那 5 分钟也不计入，
> 拿 `dayMinutes + nightMinutes` 汇总的话，一场 2 小时的包场会算成「0 分钟」——
> 人明明待了一下午。
>
> **只算已支付订单**：在店未结账的那一单还没定局，计进去会让数字每次刷新都往上跳。
>
> **归月口径与 `/me/month-spent` 同源**（按**离场时刻**归入自然月，`end_time` 的半开区间）——
> 两个数字在同一个页面上并排，跨月那一刻不能一个算上月、一个算本月。
>
> 分成两个接口而不是合并：一个是时长、一个是金额，且后者还要算优惠资格。
> 前端并发调两个只读聚合即可，合成一个只会让「只想要时长」的调用方白等一次金额查询。

## 十一、公告（不对应论文某一章）

给用户端首页提供一块「店门口的告示牌」。**不对应论文的任何一章** ——
与 `common` 公共层同性质，答辩时讲作「12 个业务包 + 公共层 + 公告包 + 商品包」。

> **公告是一条消息，不是一份状态。** 自动公告只增不改：机台修好不会把
> 「转为维护中」那条改掉或删掉，而是再产生一条「转为良好」。首页公告栏因此
> 读起来是**一段历史**。由此也**没有撤销、没有失效、没有按来源去重、没有生效时刻** ——
> 那些都属于「把公告当成状态的投影」的设计，在那里，机台修好之后那条维护公告
> 就**必须**消失，否则它就在说谎。

| 来源 | 谁写 | 例子 | 能不能改 |
| --- | --- | --- | --- |
| `AUTO` 系统自动 | 业务模块在事件发生时写入 | 机台新增 / 状况变化 / 退役 | **不能**（`PUT` / `DELETE` 返回 40929） |
| `MANUAL` 管理员手写 | 运营后台 | 「明天上午做设备保养」 | 能改能删 |

> **包场与停业都不进公告流**：包场走 `GET /api/store/bookings` 的「包场时间表」
> （它是**未来的安排**，会随改期变动，而消息流只增不改）；停业已有 `GET /api/store/status`
> 在管（那条路径的措辞边界定好了：只说「暂停营业」，不说原因）。

### GET /api/store/notices

查询门店公告栏。**匿名可访问**。

> 未注册的用户恰恰更需要它 —— 看到「本店 3 号机正在维护」才知道换个时间或换台机器。
> 店门口的告示牌不需要注册才能看。

**查询参数**

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `page` | number | 否 | 页码，从 1 开始，默认 1 |
| `size` | number | 否 | 每页条数，默认 4，**最大 20**（超出返回 400） |

**返回 `data`**：`PageResult<NoticeVo>`，**置顶的在前**，其余按时间倒序

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | number | 公告 ID |
| `title` | string | 一句话，公告栏上显示的就是它 |
| `content` | string | 正文，可为 null。**自动公告恒为 null** |
| `publishMode` | string | `AUTO` 系统自动 / `MANUAL` 管理员手写 |
| `publishModeText` | string | 中文，可直接渲染：`系统` / `手写` |
| `pinned` | boolean | 是否置顶。置顶的排在最前，前端画个角标 |
| `createdAt` | string | 这条消息的产生时刻，前端拿它显示「3 分钟前」 |

> **2026-09-30 从「取最近 N 条」改成分页**：首页公告栏只放 4 条
> （`size=4`），右上角「查看全部 ›」进用户端的 `/notices` 页接着往下翻。
> 公告是只增不减的消息流（机台每变一次状况就多一条），
> 只给最近若干条的话，更早的内容就永远看不到了。

> **为什么自动公告要标「系统」**：它的内容长得像**通知**而不像**公告**，
> 用户看到一条没人署名的通知会疑惑「这是谁说的、算不算数」。
> 标一下就回答了这个问题，成本极低。反过来手写公告**不加**标记 ——
> 管理员写的内容本就没有「来源存疑」的问题，加个「人工」标签反而是噪音。

> **`sourceType` / `sourceId` / `createdBy` 不出现在用户端**：顾客看到
> 「拍拍机 1 号 由 良好 转为 维护中」就够了，不需要知道它在库里的主键，
> 也不需要知道是哪个管理员点的按钮。`NoticeVo` 是**白名单**，这几个字段根本没声明。

**错误码**：无（没有公告时返回空数组）

### GET /api/admin/notices

分页查询公告。**仅 ADMIN。**

**查询参数**

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `page` | number | 否 | 页码，从 1 开始，默认 1 |
| `size` | number | 否 | 每页条数，默认 10，最大 100 |
| `publishMode` | string | 否 | 筛选 `AUTO` / `MANUAL`；不传或传空串都表示不筛选 |

**返回 `data`**：分页结构，`records` 内每条为 `AdminNoticeVo`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` / `title` / `content` / `publishMode` / `publishModeText` / `createdAt` | | 同用户端 |
| `sourceType` | string | 来源类型 `DEVICE`；手写公告为 null |
| `sourceTypeText` | string | 中文：`机台`；手写公告为 null |
| `sourceId` | number | 来源记录 ID（机台 ID）；手写公告为 null |
| `createdBy` | number | 发布人（管理员 ID）；自动公告为 null |
| `editable` | boolean | 是否可编辑。**前端据此置灰按钮，但真正的拦截在 Service 层** |

> **为什么列表要分页，而机台列表不分页**：机台是「店里有几台机器」，十几到几十条封顶；
> 而公告是**只增不改的消息流**，机台每变一次状况就多一条，会持续累积。
> 不分页的话，运营几个月后打开列表要在几百条里翻。

**错误码**：`PARAM_INVALID`(40001)

### POST /api/admin/notices

发布一条手写公告。**仅 ADMIN。**

> 请求体里**没有** `publishMode` —— 走到这个接口就是手写，后端硬编码，
> 不让调用方声明（多一个字段就多一个能被传错的东西）。
> 也**没有生效时段**：公告发出来就是可见的，想提前准备就写到点再发。

**请求体**

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `title` | string | 是 | 最长 100 字，就是公告栏上显示的那一句 |
| `content` | string | 否 | 最长 500 字，点开详情才看 |
| `pinned` | number | 否 | 1 置顶 / 0 不置顶。不传按 0 |

> **`pinned` 只有手写公告用得上**：置顶是运营的意图（「这条请大家务必看到」），
> 而自动公告是机台状态变化的事实记录，恒为 0 —— 让自动公告也能置顶的话，
> 一次机台故障就会把首页前几条全占满。`PUT` 同样接收 `pinned`。

**返回 `data`**：`AdminNoticeVo`

**错误码**：`PARAM_INVALID`(40001)

### PUT /api/admin/notices/{id}

修改一条**手写**公告。**仅 ADMIN。**

> ⚠️ **全量替换语义**：`content` 传 null 表示**清空正文**，不是「不修改」。
> 前端提交时要把当前值一起带上。

**请求体**：同 `POST`

**返回 `data`**：`AdminNoticeVo`

**错误码**：`PARAM_INVALID`(40001)、`NOTICE_NOT_FOUND`(40410)、`NOTICE_AUTO_READONLY`(40929)

### DELETE /api/admin/notices/{id}

下架一条**手写**公告（逻辑删除）。**仅 ADMIN。**

**返回 `data`**：null

**错误码**：`NOTICE_NOT_FOUND`(40410)、`NOTICE_AUTO_READONLY`(40929)

> **自动公告为什么改不了也删不了**：它是已经发生的事实的记录 ——
> 改写或删除等于篡改历史。而且消息流里没有「下架」这个动作，后面还会有新的消息
> 盖过它，所以这个拒绝不是拦路，而是指出正确的做法：**去改机台状况**。
>
> **手写公告反过来可改可删**：它不是「已发生的事实」，而是「运营现在想说的话」——
> 说错了、过期了、想换个说法，都该能收回来。

## 十二、商品（不对应论文某一章）

### 购买流程

```
GET  /api/products              →  看有哪些商品、还剩几件
POST /api/product-orders        →  拿到购买单与单号（此时库存还没扣）

线上通道：
POST /api/payments              →  发起支付，targetType 传 PRODUCT
POST /api/payments/mock/pay     →  （模拟模式）完成付款

扫码转账（投产时的路径）：
POST /api/payment-proofs        →  提交付款截图，targetType 同样传 PRODUCT
                                →  库存当场扣、单子当场转已支付

GET  /api/product-orders/me     →  单子变成已支付，商品库存已扣
```

> **商品属于「提交即交付」那一类**：用户提交凭证的那一刻库存就扣了、
> 单子就转已支付了，管理员复核只是留个结论。提交接口返回的 `delivered`
> 字段会说明这一点 —— 前端照着展示即可，不要自己按类型判断。

**付款复用支付模块的统一入口**，不新增支付接口 —— 回调、验签、幂等全部沿用。
与月卡、包场走的是同一套。

> **到店自取，没有核销环节。** 无人值守店里没有店员 —— 付了钱自己去货架拿。
> 代价是系统分不清「货被拿了没有」，争议时只能查监控。这是明知的取舍：
> 将来要追踪，加一个「已交付」状态与核销接口即可，表结构不用动。

### GET /api/products

列出全部上架商品。需要登录。

```json
{
  "code": 0,
  "data": [
    {
      "id": 1,
      "name": "矿泉水 550ml",
      "cover": null,
      "description": "冰柜自取，扫码后到冰柜拿即可",
      "price": 2.00,
      "stock": 48,
      "availableStock": 48,
      "soldOut": false,
      "enabled": true,
      "sortNo": 10
    }
  ]
}
```

**`stock` 与 `availableStock` 不是一回事**，两个都要给：

| 字段 | 含义 |
|---|---|
| `stock` | 实际库存。后台改的就是它 |
| `availableStock` | 可售量 = 库存 − **被未支付的待支付单占掉的部分**。前端展示、下单校验用的都是它 |
| `soldOut` | 后端算好的「是否售罄」（可售量为 0）。**别拿 `availableStock` 自己比** —— 口径要与下单校验一致，只能有一处定义 |

只给 `stock` 的话会出现「页面说还有货、下单却说售罄」——
那个不一致不是竞态造成的，是展示口径偷懒造成的，可以避免。

**已售罄的商品仍在列表里**（带上 `soldOut: true`）—— 直接让它消失
会让顾客以为这东西下架了。前端把卡片置灰即可。

**下架的商品不在这个列表里**，但它的详情仍可打开（见下）。

### GET /api/products/{id}

商品详情。需要登录。

字段与列表相同。**已下架的商品同样能查到**（`enabled: false`）——
用户的订单里可能还指着它，点进去看不了会很莫名其妙。
下架只影响「能不能下单」，不影响「能不能看」。

商品不存在时返回 `40411 PRODUCT_NOT_FOUND`。

### POST /api/product-orders

下单买商品。创建一笔**待支付购买单** —— 此时库存还没有扣，付款成功后才会扣。

**请求**

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `productId` | long | 是 | 商品 ID |
| `quantity` | int | 是 | 数量，1 ~ 99 |

**价格由后端算**，请求里传不了价格 —— 与月卡购买同一条原则。

**响应**

```json
{
  "code": 0,
  "data": {
    "id": 12,
    "orderNo": "PD202609301430251739",
    "productId": 1,
    "productName": "矿泉水 550ml",
    "unitPrice": 2.00,
    "quantity": 3,
    "amount": 6.00,
    "status": "PENDING_PAYMENT",
    "statusLabel": "待支付",
    "paymentMethod": null,
    "paidAt": null,
    "createdAt": "2026-09-30 14:30:25"
  }
}
```

`orderNo` 是商户订单号（前缀 `PD`），发起支付时不用它 —— 传的是 `id`。

**失败**

| 错误码 | 何时 |
|---|---|
| `40411 PRODUCT_NOT_FOUND` | 商品不存在 |
| `40933 PRODUCT_STATUS_INVALID` | 商品已下架 |
| `40932 PRODUCT_SOLD_OUT` | 可售量不够。附加消息里会说明是「已售罄」还是「仅剩 N 件」 |
| `40000 PARAM_INVALID` | 数量不在 1~99 之内。⚠️ Bean Validation 的 `@Min/@Max` 只作用于 Web 入参，
Service 里另有一道 —— 群里的下单指令绕过 Controller 直接调 Service |

> **库存是「支付成功时才扣」，下单时只做一次软检查**（可售量 = 库存 −
> 未支付的待支付单数）。这道检查不锁库存，所以理论上仍有竞态窗口；
> 最后一道防线是支付回调里的条件 UPDATE —— 扣不动就记 error 日志转人工处理。
> 详细权衡见 `开发约定与设计说明.md`。

### GET /api/product-orders/me

我的商品订单，分页。需要登录。

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `pageNum` | int | 否 | 页码，默认 1 |
| `pageSize` | int | 否 | 每页条数，默认 10 |
| `status` | string | 否 | `PENDING_PAYMENT` / `PAID` / `CLOSED`。传非法值返回 40000 |

记录结构同下单响应的 `data`，按最新在前。

### POST /api/product-orders/{id}/cancel

取消一笔待支付的购买单。需要登录。

**这不是退货** —— 那笔钱从来没付过，库存也从来没扣过。取消只是让单子
不再占着可售量，用户可以立刻重新下单。

单子不存在、不归本人、或已不是待支付状态时返回
`40412 PRODUCT_ORDER_NOT_FOUND` / `40933 PRODUCT_STATUS_INVALID`。

### 后台接口

全部要求 `ADMIN` 角色。

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/admin/products` | 分页查商品，**含已下架的**。参数：`pageNum` / `pageSize` / `keyword`（名称模糊）/ `enabled`（1=上架 0=下架）/ `stockAsc`（true 时按库存从少到多排，补货优先） |
| POST | `/api/admin/products` | 新增商品 |
| PUT | `/api/admin/products/{id}` | 修改商品（**全量替换**，见下） |
| PUT | `/api/admin/products/{id}/stock` | **只改库存**。请求体 `{"stock": 5}`。填的是**新的库存值**而不是增减量（0 表示售罄），与 `ProductSaveRequest.stock` 同义。补货与盘点走这条 —— 全量替换那条会把名称、封面一并回传，中间被别人改过的字段会被静默覆盖 |
| DELETE | `/api/admin/products/{id}` | 删除商品（逻辑删除） |
| GET | `/api/admin/products/orders` | 分页查商品订单。参数：`pageNum` / `pageSize` / `userId` / `status` |
| POST | `/api/admin/products/cover` | **上传商品封面**（multipart，字段名 `file`，≤2MB）。返回 `{"cover":"/uploads/product/….jpg"}` |

> ⚠️ **封面上传接口只落盘、只返回路径，不写任何数据库。** 把返回的 `cover`
> 填进表单，随下面的新增 / 修改接口一起提交才落库。三条理由：
> 新增商品时还没有 ID 可写、表单是「填一半可以取消」的语义、传错可以反复换一张。
> 代价是「传了图又取消」会在 `uploads/product/` 下留下一个没人引用的文件 ——
> 只占磁盘，不影响功能。

**新增与修改的请求体相同**：`name`（必填，≤100）、`cover`（≤255）、
`description`（≤500）、`price`（必填，≥0）、`stock`（必填，≥0）、
`enabled`（可空）、`sortNo`（可空，默认 0）。

> ⚠️ **`enabled` 是全量替换（PUT）语义的唯一例外：不传时保持原值。**
> 其余字段不传即清空/归零。改个名字顺手把商品下架了、而管理员毫无察觉，
> 比「多写一个字段」严重得多。

> **`stock` 填的是「新的库存值」，不是「扣减量」。** 后台改库存是
> 「盘点后把数字改成实际数量」，而不是「又卖了几件」。
> 真正按数量扣减的只有支付回调那一条路径。

> **删除 vs 下架**：只想「暂时不卖」的话用 `PUT` 把 `enabled` 置 0 ——
> 那样还能重新上架。删除之后商品从用户端与后台列表双双消失。
> 无论哪种，**历史订单都不受影响**（订单上存的是下单时的名称与价格快照）。

## 十三、前端对接要点

### 首页「开门」按钮的两种语义

```js
const res = await api.get('/api/orders/current')

if (res.data) {
  // 有进行中的订单 → 按钮 = 「查看密码」
  // 调 GET /api/orders/{id}/passcode
} else {
  // 没有 → 按钮 = 「开门并开始计费」
  // 调 POST /api/orders，前端可先弹二次确认
}
```

拿 `ORDER_ALREADY_ACTIVE` 不是错误，是**提示你该切换到「查看密码」了**。

**但「没有进行中的订单」不等于「能开新单」** —— 还欠着费的账号会被
`ORDER_UNPAID_EXISTS` 挡下。首页因此需要两张卡片、两个数据源：

| 卡片 | 数据源 | 何时显示 |
| --- | --- | --- |
| 进行中（计时 + 金额） | `GET /api/orders/current` → `GET /api/orders/{id}/preview` | 有 `IN_USE` 时 |
| 未付款提醒 | `GET /api/orders/me?status=PENDING_PAYMENT&size=1` | 有 `PENDING_PAYMENT` 时 |

两者**可以同时出现**（一笔在玩、另一笔欠着，多见于「上一单忘了付、过几天又来玩」）。
点「开门」前先查一次 `current`：后端有用例挡连点，但先查能把一个错误提示
变成一次正常的页面跳转 —— 若拿到 `ORDER_UNPAID_EXISTS` 则提示并跳「去支付」。

### 支付流程

```js
// 1. 拿可用通道（不要写死），按 UA 预选，用户仍可改
const { data: channels } = await api.get('/api/payments/channels', { params: { targetType: 'ORDER' } })
const preferred = /MicroMessenger/i.test(navigator.userAgent) ? 'WXPAY_JSAPI'
                : /AlipayClient/i.test(navigator.userAgent)  ? 'ALIPAY_WAP'
                : 'WXPAY_H5'
const channel = channels.some(c => c.channel === preferred) ? preferred : channels[0]?.channel
if (!channel) return showTip('本店尚未配置收款方式')   // 投产时一张码都没配就是这样

// 2. 扫码转账：不走网关，转去上传付款凭证
if (channels.find(c => c.channel === channel).needProof) {
  const { data: qrs } = await api.get('/api/payments/qr')   // 收款码，直接给 <img :src>
  return showProofSheet({ targetType: 'ORDER', targetId, qrs })
  // 用户传完图后：POST /api/payment-proofs/image → POST /api/payment-proofs
  // 返回的 delivered 决定文案：「支付完成」还是「等待管理员确认」
}

// 3. 线上通道：发起支付
const { data } = await api.post('/api/payments', { targetType: 'ORDER', targetId, channel })

// 4. 模拟模式：弹自己的收银台
if (data.mockPayUrl) {
  showMockCashier(data.outTradeNo)   // 由它调 POST /api/payments/mock/pay
  return
}

// 5. 真实模式：按通道调起
if (channel === 'WXPAY_JSAPI')       invokeWeixinJSBridge(data.prepayId)
else if (channel === 'WXPAY_H5')     location.href = data.h5Url      // 5 分钟内有效，立刻跳
else                                 document.write(data.formHtml)   // 支付宝表单
```

**支付结果不能只等前端回调** —— H5 支付没有前端回调，支付宝的 `return_url` 在 iOS 上
也可能根本不跳转。**只能靠异步通知或主动查单确认**，所以前端回到页面后
应当调一次 `GET /api/payments/{outTradeNo}`。

### 错误处理

```js
// axios 拦截器
if (err.response.status === 401) {
  // 三种业务码都走这里：未登录 / 凭证失效 / 已过期 → 清凭证、跳登录页
  localStorage.removeItem('token')
  location.href = '/login'
} else {
  // 其余按 message 展示，它已经是中文且面向用户
  toast(err.response.data.message)
}
```

### 已知的接口不一致（不是 bug，但要知道）

| 现象 | 说明 |
| --- | --- |
| `GET /api/access-records/me` 的分页参数没有校验 | 其余接口 `size` 超过 100 会返回 400，这个接口由分页插件静默截断 |
| 只有 `GET /api/admin/access-records` 的 `from`/`to` 收 `yyyy-MM-dd HH:mm:ss` | 查询参数不经过 Jackson，只有显式声明了格式的才能接收带空格的日期串 |
| 两个回调端点的响应体不是 `ApiResult` | 见第九章 |

> **402/409/502 的区分不是随意的**：409 是「用户操作不当」，
> 502 是「上游依赖挂了，错不在我们」，500 是「我们自己出错了」。
> 监控上靠这个区分该找谁。

> **`BOOKING_NOT_PAID`(40930) 与 `ORDER_UNPAID_EXISTS`(40931) 是两回事，别混用**：
> 前者说的是「包场还没付款，所以邀请链接还没生成」，后者说的是
> 「你有普通订单欠着费」。用户看到之后该做的事也不同 —— 一个催包场人去付款，
> 一个催顾客去结账。

> **对账的三个 400 码（40003 / 40004 / 40005）分开也是有原因的**：
> 它们要管理员做的事完全不同 ——「读不出来」要去另存为 CSV 或先解压、
> 「认不出表头」要重新导出一份、「里面没有记录」要检查导出的日期范围。
> 给一句笼统的「格式不对」，他会一直在导出那一步打转。
> 这与 `UPLOAD_FILE_INVALID`(40001) 和 `UPLOAD_FILE_TOO_LARGE`(41300)
> 分开是同一条道理。
>
> 另：`UPLOAD_FILE_TOO_LARGE`(41300) 的文案从「**图片**大小不能超过 2MB」
> 改成了中性的「文件大小超出上限（2MB）」—— 对账的账单文件也会撞到它，
> 而 `spring.servlet.multipart.max-file-size` 是全局的、不分文件类型。
