# 智能门锁方案选型调研

> 本文档用于留档门锁供应商的选型过程，可作为毕业论文「技术选型 / 可行性分析」章节的素材。
>
> - 涂鸦方案：2026-08-11 调研，**可行性已验证但最终弃用**
> - 通通锁方案：2026-09-15 调研，**现采用**

---

## 一、涂鸦（Tuya）方案【已弃用，留档】

调研时间：2026-08-11。当时的结论是「架构可行」，但后续更换供应商，本节内容仅作留档与对比，**不要再照此实施**。

### 当时的实施要点

- **采购**：买 Wi-Fi 版涂鸦生态门锁（**别买纯蓝牙锁** —— 涂鸦 BLE 云服务 API 未开放；Zigbee 需网关）
- **云开发平台**：注册 + 实名认证（个人开发者可用但额度受限），开通「智能门锁开放能力」云服务并授权给云项目
- **设备接入**：涂鸦智能 App 绑定锁 → 云开发后台「关联 App 账号下的设备」扫码授权，拿到 `device_id`
- **Spring Boot 端封装**：HMAC-SHA256 签名 + token 管理（2h 过期）+ password-ticket AES-128-ECB 加密
- **临时密码 API**：创建（7 位数字 Wi-Fi 锁）→ 轮询 `delivery_status`（超时 25s）→ 删除 / 冻结
- **QQ bot**：NapCat（OneBot v11 HTTP 上报，go-cqhttp 已停维护勿用）→ Spring Boot 接口
- **安全**：群内 QQ 白名单 + 限时密码（`invalid_time`）+ 操作 / 开门记录日志

### 当时的接口规格记录

- 创建临时密码：`POST /v1.0/devices/{device_id}/door-lock/temp-password`
- 配套接口：获取密码信息、删除临时密码、修改 / 冻结 / 解冻临时密码、获取动态密码、获取离线临时密码、查询开门记录
- 密码长度：Wi-Fi 门锁 7 位；Zigbee 门锁与蓝牙门锁 6 位
- 传输加密：AES-128/ECB/PKCS7Padding
- **临时密码数量上限：Zigbee 门锁最多 30 组**
- **状态轮询超时 25 秒**，异常流程中网关重试下发 3 次后结束
- **蓝牙门锁的密码不可修改**
- 接口日志仅保留 7 天，需在开发者平台提工单查询，一般 2 小时内答复
- 远程开锁需在手机 APP 中开启后方可远程控制

### 弃用原因

调研阶段**未找到确实在真实项目中使用涂鸦门锁云 API 的案例**，缺乏可参考的落地经验与踩坑记录，风险不可控。

## 二、通通锁（TTLock）方案【现采用】

调研时间：2026-09-15。厂商为杭州赛脑智能科技股份有限公司，产品定位即「酒店 / 民宿 / 公寓无人值守自助入住」，与本课题场景高度重合。

### 开放平台

- 中文开放平台：<https://cnopen.ttlock.com/>
- 文档站：<http://ttlockdoc.ttlock.com/>（另有欧盟站 <https://euopen.ttlock.com/doc/oauth2>）
- **个人开发者可以注册**
- **接口调用免费额度：30,000 次/月**

### 鉴权

- OAuth2 密码模式：`POST /oauth2/token`，`Content-Type: application/x-www-form-urlencoded`
- 参数：`client_id`（开放平台 app_id）、`client_secret`、`username`、`password`（**32 位小写 MD5**）
- 返回：`access_token`、`uid`、`expires_in`（默认 7776000 秒 = **90 天**）、`scope`
- token 应服务端缓存复用，不要每次调用重新换取

### 锁初始化

- `POST /v3/lock/init` —— 服务端初始化锁数据并生成管理员钥匙
- 若锁已通过 APP 添加，则跳过此步直接查锁列表
- 关键参数：`lockMac`、`lockKey`、`aesKeyStr`、`adminPwd`、`pwdInfo`（密码数据，生成密码用）、`timestamp`、`timezoneRawOffset`
- 返回：`lockId`、`keyId`

### 密码接口

- 添加：`/v3/keyboardPwd/add`；修改：`/v3/keyboardPwd/change`
- `addType` 参数：
  - `1` = 先经 APP 蓝牙添加，再调接口同步到云端（默认）
  - `2` = 经网关 / Wi-Fi 锁**远程直接下发**
  - `3` = NB-IoT 锁，需等网络唤醒后下发
- **远程下发密码必须走 `addType=2`** —— 即锁要接入网关，或本身就是 Wi-Fi 锁
- **自定义密码只有三代锁支持，且只能设为限时密码**（不能设成永不过期的一次性码）
- eKey 相关：`/key/send`、`/key/list`；另有 v3 Unlock 端点

### 接口域名

- 国内：`https://api.ttlock.com`
- 欧盟：`https://api.sciener.com`

## 三、选型结论

**采用通通锁（TTLock）**，理由：

1. **场景完全重合**：厂商的产品定位就是「酒店入住自动生成密码 / 电子钥匙」「会议室预定」「分时共享」，与本课题的无人值守共享空间自助开门是同一件事；涂鸦是通用 IoT 平台，门锁只是其众多品类之一
2. **有可查证的实际使用案例**：民宿、公寓、共享会议室等场景大量落地；有第三方 SDK（PHP、Elixir）与第三方对接平台跑通过，说明 API 链路经过真实项目验证
3. **个人开发者准入明确**：可注册，且每月 30,000 次免费调用额度
4. **硬件成本低、生态成熟**：民宿级商用锁市场报价约 ¥150–300，采购与更换都方便

### 需要注意的硬约束（两家共有）

- **远程下发密码必须接网关或使用 Wi-Fi 锁**。纯蓝牙锁只能「先用 APP 蓝牙添加、再调接口同步」，无法远程下发。**采购时必须避开纯蓝牙锁**，这一点在涂鸦方案里同样成立
- 网关到锁之间走蓝牙，远程开锁存在数秒延迟

### 对系统设计的影响

- 模块 5「门禁管理」原设计为「生成**一次性**密码」，受「自定义密码只能设限时密码」约束，应改为**带 `startTime` / `endTime` 的限时密码**
- 免费额度 30,000 次/月是硬约束，按单订单 2~4 次调用计算，约可支撑 10,000~15,000 单/月（333~500 单/天）。**接口设计必须避免轮询**：涂鸦方案中「创建后轮询状态 25 秒」的模式若照搬到通通锁，调用数会膨胀约 4 倍

### 尚未确认的事项

- 达到免费额度上限后的计费方式与降级方案
- 应用创建后的审核所需材料与周期
- `timezoneRawOffset` 时区参数的具体取值规则（影响密码有效期计算）
