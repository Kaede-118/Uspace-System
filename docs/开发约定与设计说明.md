# 开发约定与设计说明

> 本文档面向**阅读本项目代码的人**（指导教师、答辩评委、后续接手者），
> 说明系统的设计决策、模块划分与关键约定。
>
> 每项决策都写明了「为什么这么定」，便于追溯设计意图。
> 论文与答辩中涉及技术选型、架构设计的部分可直接取材于本文。

## 一、系统概述

**无人值守共享娱乐空间管理系统**（系统代号 **uspace**，取自 **U**nattended **Space**），
面向共享娱乐空间（如共享台球室、共享游戏厅）的无人值守运营场景：
用户自助开门进场、系统按使用时长自动计费、管理员远程完成运营管理。

开发分两个阶段，代码设计需同时满足两者：

1. **毕设展示阶段（当前）**：以功能完整、流程可演示为第一优先级，模块边界清晰、注释完整
2. **生产化阶段（后期）**：系统后期将投入商用运营，因此数据模型与接口契约
   从一开始就按生产标准设计（金额用 `DECIMAL` 而非浮点、时间统一时区、状态流转留审计字段）

### 为什么用 Spring Boot 3.x 而不是 4.x

4.x 是建立在 Spring Framework 7 上的「代际更新」，starter 已模块化改名
（`spring-boot-starter-web` → `-webmvc`，测试 starter 拆成多个），
第三方生态仍处于追赶期。毕设期间**中文资料的丰富度**与**第三方库的兼容成熟度**
比「版本最新」重要得多 —— 遇到问题能否搜到答案，直接决定排障效率。

### 为什么选通通锁而不是涂鸦

早期调研过涂鸦（Tuya）生态，最终改用通通锁，理由是**通通锁有可查证的实际使用案例**
（民宿、公寓、共享会议室等场景大量落地，有第三方 SDK 与对接平台验证过 API 链路），
而涂鸦未见确实有人在门锁云 API 上落地。

更关键的是**场景重合度**：通通锁的产品定位就是「酒店入住自动生成密码 / 电子钥匙」
「会议室预定」「分时共享」，与本课题的无人值守共享空间是同一件事；
涂鸦是通用 IoT 平台，门锁只是其众多品类之一。

完整的选型调研过程（含已弃用的涂鸦方案全文）见 `门锁选型调研.md`。

## 三、工程结构

**单体应用 + 按业务分包；前后端同仓库。**

```
Uspace-System/                 一个 git 仓库
├── backend/                   Spring Boot 单体应用，一个 pom.xml
│   └── src/main/java/com/kaede/uspace/
│       ├── BackendApplication.java
│       ├── user/  auth/  space/  device/  lock/  access/
│       └── billing/  order/  promotion/  stats/  qqbot/  log/
├── frontend/                  Vue（脚手架待创建）
└── docs/                      论文素材、数据库脚本、接口与部署文档
```

**设计说明：**

- **12 个业务包与论文十二章一一对应**，答辩时可直接对照讲解
- **不用 Maven 多模块**：单人开发下「编译期强制模块边界」的收益很小，
  多一层 pom 配置反而是负担；将来真需要可渐进拆分
- **前后端同仓库，但仍是前后端分离架构** —— 「分离」说的是运行时
  （Vue 在浏览器里通过 HTTP 调 API，后端不渲染页面），与仓库如何划分无关

| # | 模块 | 包名 | 职责 |

| 7 | 计费管理 | `billing` | 按使用时长、消费时段自动计算费用 |
| 8 | 订单管理 | `order` | 生成、查询及管理消费订单 |

## 五、数据库设计

建表脚本见 **`sql/schema.sql`**，字段级说明以脚本中的注释为准，本节说明整体设计。

### 数据表一览

| 表名 | 对应模块 | 说明 |
|---|---|---|
| `sys_user` | 模块 1 用户管理 | 用户账号与身份信息 |
| `biz_space` | 模块 3 空间管理 | 房间信息与使用状态 |
| `biz_lock` | 模块 5 门禁管理 | 智能门锁及其在门锁云中的标识 |
| `biz_order` | 模块 8 订单管理 | 订单主表，主链路 5→6→7→8 的枢纽 |
| `biz_access_record` | 模块 6 进出记录 | 开门事件记录 |

> 模块 4 设备管理、模块 9 优惠管理、模块 12 系统日志的表待相应模块开发时追加。

### 业务模式对表结构的决定作用

订单表的结构由「**即时制 + 信任制**」这一业务模式决定，而非凭空设计：

- **即时制** —— 用户到店下单即可开门进场，没有预约时段，
  因此订单表**没有** `planned_start` / `planned_end` 这类预约字段
- **进入即计费** —— 计费起点是 `start_time`（首次开门进场时刻），**不是下单时间**。
  下单与进场之间可能间隔任意时长，两者必须分开存储
- **信任制** —— 离场时门锁不拦截，先出门后付款。因此支付相关字段
  （`payment_method`、`payment_proof`、`payment_no`、`paid_at`）
  都在订单**结算之后**才写入，订单可以合法地处于「已离场但未付款」的
  `PENDING_PAYMENT` 状态

**订单状态流转：**

```
CREATED 已创建 ──首次开门──> IN_USE 使用中 ──离场──> PENDING_PAYMENT 待支付 ──付款──> PAID 已支付
    │                                                      │
    └──超时未开门──> CANCELLED                              └──管理员核销──> PAID
```

### 关键设计决策

**为什么表名要加前缀**
`ORDER` 与 `LOCK` 均为 MySQL 保留字，直接用作表名会导致每处 SQL 都需反引号转义，
第三方工具也易踩坑。因此统一加前缀：`sys_` 用于系统级表，`biz_` 用于业务表。

**金额一律 `DECIMAL(10,2)`**
禁止 `FLOAT` / `DOUBLE`。浮点数无法精确表示十进制小数，金额累加会产生误差，
在财务场景中不可接受。

**时间存本地时间而非 UTC**
计费规则本身按本地时钟定义（日场 10:00–22:00）。若存 UTC，每次计费都需来回换算，
反而增加出错机会。本系统面向单一地区运营，不存在跨时区需求。

**逻辑删除而非物理删除**
主要业务表带 `deleted` 标记。订单属于财务数据，即使被取消也必须保留记录以备审计。

**刻意不使用外键约束**
关联完整性由应用层保证。这样便于将来分库分表、数据归档与批量清理，
避免外键带来的锁竞争与迁移困难。

**计费明细内嵌在订单表中**
日场/夜场的时长与金额直接作为 `biz_order` 的列存储，而非独立的计费明细表。
原因：时段固定为两个、结构稳定，用列更简单且查询更快；
同时满足「账单可追溯」的要求 —— 订单结算后金额是否被改动过一目了然。

**订单的人工调整留痕**
字段 `adjusted` / `adjusted_by` / `adjusted_at` / `adjust_reason`。
对应业务场景：用户离场时忘记点「结束使用」，管理员查看开门记录与监控后
手工修正离场时间并重算费用。该操作必须留痕，否则财务上无法解释订单金额的变化。

### 关于「进出记录」的一个说明

`biz_access_record` 记录的是**开门事件**，而非严格意义上的「进」与「出」。

封闭空间的出门通常为机械推杠或按钮（消防要求内部必须能免密自由开门），
**不产生门锁记录**，因此系统只能记录到「进门」这一次开门。
用户的离场时刻由其在应用内手动点「结束使用」确定，
异常情况（忘记点击）由管理员查看开门记录与监控后人工复核。

这是由安全要求反推出的数据模型限制，不是设计疏漏。

## 六、智能门锁接入设计

### 核心约定：按真实规格设计接口，用模拟代码实现

**对外接口按通通锁云 API 的真实规格设计与命名，但当前实现下落为模拟代码，
不连接真实门锁云。** 具体含义：

- **照真实规格的部分**：URL 路径、请求参数名、返回字段名、错误码、鉴权流程。
  将来切换到真实调用时，只需替换 Service 的实现层，Controller、DTO、数据模型均无需改动
- **用模拟实现的部分**：门锁云的 HTTP 调用、token 换取、密码下发

**为什么这样做：** 毕设阶段无法保证有真实门锁硬件与可用的云端账号，
但接口契约必须一次定对 —— 若先用「演示级」接口把流程跑通，后期接入真实门锁时
会牵动上层所有代码，代价远高于现在多写一层实现。

实现的选择由配置项 `uspace.lock.provider` 决定（`mock` / `ttlock`）。
模拟实现位于 `lock/mock/` 包，真实实现预留 `lock/ttlock/`。

### 模拟实现刻意保留的真实约束

模拟实现能脱离外网跑通「下发密码 → 开门 → 记录 → 计费」全流程，
但**不比真实接口宽松**，以免切换到真实实现时才暴露问题：

1. **自定义密码只能是限时密码** —— 不传有效期会被拒绝。
   因此模块 5 的接口设计为「带生效/失效时间的限时密码」而非纯一次性码
2. **远程下发（`addType=2`）需要锁接入网关或本身为 Wi-Fi 锁**，
   可用配置模拟「纯蓝牙锁」，此时远程下发会被拒绝
3. **网络调用可能失败** —— 支持按概率注入失败，用于演练异常处理分支。
   否则异常处理逻辑在演示时永远走不到，而异常处理与数据校验正是考核点

### 通通锁云 API 规格要点

| 项 | 内容 |
|---|---|
| 接口域名 | 国内 `https://api.ttlock.com`；欧盟 `https://api.sciener.com` |
| 鉴权 | OAuth2 密码模式，`POST /oauth2/token`；密码需 32 位小写 MD5 |
| token 有效期 | 90 天，须服务端缓存复用，不可每次调用重新换取 |
| 锁初始化 | `POST /v3/lock/init`（锁已在 APP 添加过则可跳过） |
| 密码接口 | `/v3/keyboardPwd/add`、`/v3/keyboardPwd/change`、`/v3/keyboardPwd/delete` |
| 记录查询 | `POST /v3/lockRecord/list` |
| 免费额度 | **30,000 次/月** |

**接入时容易踩的坑：**

- **开发者账号 ≠ 通通锁 APP 账号**。开发者账号名下没有任何设备，
  换取 token 的 `username` 必须用 APP 登录账号（已授权的管理员账号），
  否则查不到锁状态、无法开锁，报非管理员权限
- **远程开锁通常需要网关**，链路为 锁 → 蓝牙 → 网关 → 互联网 → Cloud API。
  纯蓝牙锁无法远程下发密码，**采购时必须避开**
- 错误码如 `-4043 The function is not supported for this lock`，
  需在 APP 中开启远程开锁后才有远程控制能力
- 时区参数 `timezoneRawOffset` 要对齐，否则密码有效期会算错

### 调用额度约束

30,000 次/月是硬约束，接口设计遵循「省调用」原则：

- **不做轮询**：开门记录按需拉取或批量拉取，不用定时任务反复拉
- 缓存复用 access token，不重复换取
- 单次订单的调用预算控制在 2~4 次（下发密码 + 失效密码 + 可选拉记录）

## 七、计费规则

### 计费公式

**4 元 / 30 分钟**（整点恰好合 8 元/小时）。

```
段费用 = ceil( (段时长分钟 − 10) ÷ 30 ) × 4 元       再与该时段封顶取小
总费用 = 各时段段费用之和
```

公式里每条规则的位置：

- **「−10」是结账误差**：每个整点过后 10 分钟内不涨价，从而保证**恰好整点结算时
  严格是 8 元/小时**（1 小时=8 元、2 小时=16 元、3 小时=24 元）。
  档位边界因此落在 10、40、70、100… 分钟，每档正好覆盖 30 分钟
- **「余数不满 10 分钟舍弃、达到 10 分钟进位」**已包含在公式中：
  玩满 40 分钟仍收 4 元，41 分钟才跳到 8 元
- **「首 10 分钟内免费出场」是公式的自然结果**，不需要额外判断 ——
  段时长为 10 时 `ceil(0÷30) = 0`，费用即为 0

**价格阶梯：**

| 时长 | 费用 | | 时长 | 费用 |
|---|---|---|---|---|
| ≤ 10 分 | 免费 | | 131 – 160 分 | 20 元 |
| 11 – 40 分 | 4 元 | | 161 – 190 分 | 24 元 |
| 41 – 70 分 | 8 元 | | 191 – 220 分 | 28 元 |
| 71 – 100 分 | 12 元 | | 221 – 250 分 | 32 元 |
| 101 – 130 分 | 16 元 | | | |

### 时段划分与封顶

| 时段 | 时间范围 | 封顶 | 触发封顶的时长 |
|---|---|---|---|
| 日场 | 10:00 – 22:00 | 40 元 | 4 小时 41 分起 |
| 夜场 | 22:00 – 10:00（次日） | 30 元 | 3 小时 41 分起 |

### 跨时段处理

**按时段切段分别计算**，各段使用同一公式、各自套各自的封顶，最后相加。

> **已知副作用**：每段各自享有那份「−10」宽限，因此跨时段与不跨时段的同长订单
> 可能算出不同价格，且方向不固定：
> - 21:50–22:10 共 20 分钟（日场 10 分 + 夜场 10 分）→ 两段都落进免费档 → **0 元**，
>   而同样 20 分钟全在日场收 4 元（偏便宜）
> - 21:40–22:20 共 40 分钟（日场 20 分 + 夜场 20 分）→ 各 1 档 → **8 元**，
>   而同样 40 分钟全在日场收 4 元（偏贵）
>
> 这是「分段计算 + 各段独立套公式」的固有结果，属于**已确认接受**的规则形态，
> 不是缺陷。

### 时长精度

时长按**分钟向下取整**。即 40 分 59 秒算 40 分钟、收 4 元而非 8 元。
选向下取整是与整套规则的宽松取向保持一致（宽限、余数舍弃都是在给用户让利）。

### 计费结果的结构

**计费结果必须分段呈现，不能只给一个总价。** 每段同时给出「时长」与「该段价格」：

```
日场   2 小时 30 分     20 元
夜场   1 小时 10 分      8 元
──────────────────────────────
合计   3 小时 40 分     28 元
```

因此计费 Service 返回的是**结构化的分段对象**而非单个金额，
其中还保留了「计费档数」与「封顶前金额」两项中间结果 ——
使账单可追溯：用户质疑金额时能直接看出钱是按几档、有没有被封顶算出来的。

计费参数（单价、单位时长、宽限、封顶、时段起止）全部外置到配置文件，
调整运营规则无需修改代码或重新部署。

## 八、QQ 机器人接入设计

### 数据流

NapCat 是**协议端**，只负责把 QQ 原始事件推给后端、接受后端调用的 Action
（如 `send_group_msg`）。它**不解析** `/开门` 这类业务指令 ——
`raw_message` 原样送过来，解析是后端的事。

```
群消息 "/开门 3号房"
   ↓
NapCat（OneBot v11 协议端）
   ↓  反向 WebSocket
Spring Boot 的 qqbot 包 ← 解析指令、鉴权、办理业务
   ↓  调用 lock / order 等模块的 Service
   ↓  调用 NapCat 的 send_group_msg Action
群消息 "3号房已开门"
```

**这样设计的好处**：业务逻辑全程在 Spring Boot 内，能复用 Service、走事务、
进模块 12 的系统日志。

### 处理链路的三条硬要求

1. **收到事件立刻 ack，业务异步处理** —— OneBot 上报有超时，
   等不到响应会重推；同步处理慢查询或门锁调用会触发重推
2. **幂等** —— 用 `message_id` 去重。`/结账` 这类写订单的操作尤其不能让重推生效两次
3. **来源校验** —— 校验 `access_token` 并限定 `group_id` 白名单，
   否则任何人都能伪造一条「开门」指令

### 不采用 NapCat 插件写业务的原因

NapCat 自带插件机制（在 `plugin_onmessage` 里判断 `raw_message` 再回复），
写关键词回复没问题。但那是跑在 NapCat 进程里的 **JavaScript** ——
用插件做 `/开门` 会把业务逻辑劈成两半、绕开 Service 与事务、
并绕开模块 12 的系统日志。插件只适合纯展示类小功能。

## 九、编码约定

- **所有代码注释用中文**。文件级注释说明文件用途，类/方法级注释说明参数含义、
  返回值与关键逻辑 —— 代码需用于论文撰写与答辩审阅
- **金额一律用 `BigDecimal` / `DECIMAL`**，禁止用 `double` / `float`。
  浮点运算在金额累加时会产生精度误差
- **时间字段统一存储**，注意与门锁云的时区参数对齐
- 代码按 12 个业务包组织，包内再按职责细分子包
  （如 `dto` 放传输对象、`mock` 放模拟实现）

## 十、构建与运行

```bash
cd backend

mvn -B -DskipTests compile     # 编译
mvn spring-boot:run            # 启动开发服务（默认 8080）
mvn test                       # 运行全部测试
mvn -B -DskipTests package     # 打包成可执行 jar
```

**前置条件：**

**1. JDK 17 或以上**

**2. MySQL 8.0**，创建数据库并导入表结构：

```bash
mysql -u root -p -e "CREATE DATABASE uspace DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_general_ci;"
mysql -u root -p uspace < docs/sql/schema.sql
```

> ⚠️ `schema.sql` 含 `DROP TABLE IF EXISTS`，可反复执行以重建表结构，
> 但**会清空表中数据**。仅用于开发与演示环境，生产环境请改用增量迁移脚本。

**3. 数据库凭据通过环境变量注入**，不写入配置文件：

```powershell
[Environment]::SetEnvironmentVariable('MYSQL_USER', 'root', 'User')
[Environment]::SetEnvironmentVariable('MYSQL_PASSWORD', '你的密码', 'User')
```

> Windows 下环境变量**只对新启动的进程生效**，设置后需重开终端。
> 若启动时报 `Access denied`，先检查这两个变量是否已生效。

**关于测试：** 当前单元测试为纯计算与模拟实现测试，**不依赖真实数据库连接**
（Spring Boot 的连接池是懒加载的，上下文启动时不会主动连库）。
将来加入 Mapper 层的集成测试后，跑测试前需先确保数据库可用。
