# 开发约定与设计说明

> 本文档面向**阅读本项目代码的人**（指导教师、答辩评委、后续接手者），
> 说明系统的设计决策、模块划分与关键约定。
> 
> 每项决策都写明了「为什么这么定」，便于追溯设计意图。
> 论文与答辩中涉及技术选型、架构设计的部分可直接取材于本文。

---

## 一、系统概述

**无人值守共享娱乐空间管理系统**（系统代号 **uspace**，取自 **U**nattended **Space**），
面向共享娱乐空间（如共享台球室、共享游戏厅）的无人值守运营场景：
用户自助开门进场、系统按使用时长自动计费、管理员远程完成运营管理。

本系统**计划于 2026 年 12 月投入实际运营**，因此代码设计需同时满足两个场景：

- **可运营** —— 数据模型与接口契约按生产标准设计：金额用 `DECIMAL` 而非浮点、
  时间统一时区、状态流转留审计字段、关键操作留痕
- **可演示** —— 功能完整、流程清晰、模块边界分明、注释完整，便于评审与答辩讲解

两者并不冲突：前者要求数据与契约严谨，后者要求结构与表达清晰。
需要注意的只是**先后顺序是倒过来的** —— 上线在前、答辩在后，
所以「先按演示做、以后再改」这条路走不通，生产标准从一开始就要遵守。

### 为什么用 Spring Boot 3.x 而不是 4.x

4.x 是建立在 Spring Framework 7 上的「代际更新」，starter 已模块化改名
（`spring-boot-starter-web` → `-webmvc`，测试 starter 拆成多个），
第三方生态仍处于追赶期。毕设期间**中文资料的丰富度**与**第三方库的兼容成熟度**
比「版本最新」重要得多 —— 遇到问题能否搜到答案，直接决定排障效率。

### 为什么选通通锁而不是涂鸦

早期调研过涂鸦（Tuya）生态，最终改用通通锁，理由是**通通锁有可查证的实际使用案例**
（民宿、公寓、共享会议室等场景大量落地，有第三方 SDK 与对接平台验证过 API 链路），
而涂鸦未见确实有人在门锁云 API 上落地。

更关键的是**场景重合度**：通通锁的产品定位就是「酒店入住自动生成密码 / 电子钥匙」
「会议室预定」「分时共享」，与本课题的无人值守共享空间是同一件事；
涂鸦是通用 IoT 平台，门锁只是其众多品类之一。

完整的选型调研过程（含已弃用的涂鸦方案全文）见 `门锁选型调研.md`。

### 客户端形态与分工（2026-09-28 修订）

系统对外提供**两个 Web 应用**，**共用同一套后端 API**，业务逻辑不在客户端重复实现：

| 应用       | 面向      | 主要承载                            |
| -------- | ------- | ------------------------------- |
| 用户端 Web  | 顾客      | 浏览空间与店内机台、下单、开门、结算、付款、查看账单（模块 3–9） |
| 运营后台 Web | 管理员     | 公告、机台台账、包场排期、商品维护与商品订单、**付款凭证复核与收款码**（已完成）；订单管理、停业时段、数据统计待做 |
| QQ 机器人   | 顾客 / 店主 | 群内播报与查询，另有三条受限写指令：`/开门`、`/结账`、`/买个商品名`（模块 11，不碰付款） |

> **运营后台的分期**：用户端 17 个页面与后台 5 个页面
> （公告 / 机台 / 包场 / 商品 / 付款与收款码）已完成，都是
> 「投产闭环必须要有人去操作」的那几件事。订单查询与调整时长、进出记录同步、
> 门锁应急发密码、停业时段管理、数据统计这几页**后端接口都已就绪，
> 只是还没做界面** —— 本期定位是「运营后台简版」，统计先手工查库。

#### 用户端：以 Web 为唯一载体

**不做原生 App、不做微信小程序。** 同一套 Web 代码通过多种「外壳」交付给用户：

| 外壳                   | 用户拿到的东西               | 额外代价                         |
| -------------------- | --------------------- | ---------------------------- |
| 手机浏览器直接访问            | 一条链接                  | 无                            |
| 添加到主屏幕（PWA / 网页快捷方式） | 桌面图标，全屏打开，接近原生体验，无地址栏 | 一份 manifest + Service Worker |
| WebView 套壳 App       | 应用商店里的一个 App          | 一个极薄的壳工程，**Web 代码零改造**       |

**为什么走这条路：**

- **一套代码多处复用** —— 三种外壳加载的都是同一个 Web 应用，改一次三处生效；
  用户端与运营后台也共用同一套后端 API 与同一套前端基础组件
- **绕开小程序的资质门槛** —— 小程序若要以 `web-view` 加载现有网页，
  需同时满足**非个人主体**（营业执照）、**已备案域名**、**HTTPS 证书**三个条件，
  毕设阶段均不具备。若改用 uni-app 一套代码编译多端，虽能产出小程序，
  但需额外维护微信开发者工具、提审流程、服务类目与平台差异条件编译，代价高于收益
- **绕开应用商店的审核与更新周期** —— 套壳 App 的界面更新靠服务端推送 Web 资源，
  不必每次提审；而纯原生 App 的每个改动都要走审核
- **支付本来就长在 Web 上** —— 三条线上通道（微信 JSAPI / H5、支付宝 WAP）
  都是「在网页里发起、跳转唤起 App」的形态；**扫码转账同样如此**
  （扫码识别 → 打开微信或支付宝付款 → 回页面传截图，见第九章）。
  原生 App 反而要另开一套 APP 支付，白付一份成本

**对开发的具体约束**（不满足这几条，将来套壳时要返工）：

- **移动端优先布局**，适配安全区（`env(safe-area-inset-*)`，应对刘海屏与手势条）
- **不依赖微信内置浏览器中不可用的浏览器 API** —— 微信内是受限 WebView，
  而它恰恰是 JSAPI 支付的主战场，不能实现成「只在 Chrome 里能跑」
- **API 层独立封装、与视图层解耦**，便于换壳与将来做多端条件编译
- **支付跳转必须在 WebView 里能正常工作** —— 套壳 App 内无论是发起线上支付
  （拉起微信 / 支付宝），还是扫码转账（扫码后跳过去付款），都要能正确唤起外部 App
  并在返回后恢复页面状态。这是套壳方案最容易翻车的一处，
  也是三种外壳中唯一有真实技术风险的地方，实现时要单独验证

**PWA 是三者中最划算的一档** —— 成本只是一份 manifest 与 Service Worker，
却能让用户获得「不装 App 也有桌面图标」的入口，Android 侧体验已接近原生应用。

#### QQ 机器人：从「主力入口」降为「群内播报与查询端」

**2026-09-28 修订**：QQ 机器人**不再承担面向客户的全流程操作**，只做信息播报与查询。

**2026-10-04 再修**：加回**三条受限写指令** —— `/开门`（建单计时）、`/结账`（停止计时）、
`/买个可乐`（下单买商品），
两条都只到「停表出账」为止，**付款仍然只在网页端**，且播报关掉时不执行。
完整的定位、边界与理由见第十章。

这一安排同时意味着**用户端 Web 仍然是唯一能完成用户侧全流程（含付款）的入口** ——
群里的两条指令是它的快捷方式，不是它的替代品。

## 三、工程结构

**单体应用 + 按业务分包；前后端同仓库。**

```
Uspace-System/                 一个 git 仓库
├── backend/                   Spring Boot 单体应用，一个 pom.xml
│   └── src/main/java/com/kaede/uspace/
│       ├── BackendApplication.java
│       ├── common/            公共层：统一返回体、异常处理、实体基类、框架配置
│       ├── notice/            公告包（不对应论文某一章）
│       ├── product/           商品包（不对应论文某一章）
│       ├── user/  auth/  space/  device/  lock/  access/
│       └── billing/  order/  promotion/  stats/  qqbot/  log/
├── frontend/                  Vue 3 + Vite（用户端 Web 18 页 + 运营后台 Web 6 页）
└── docs/                      论文素材、数据库脚本、接口与部署文档
```

**设计说明：**

- **12 个业务包与论文十二章一一对应**，答辩时可直接对照讲解
- **另有 `common` 公共层**，承载统一返回体与错误码、全局异常处理、实体基类
  （审计字段与逻辑删除）、MyBatis-Plus 与 Jackson 配置。它**不对应论文的任何章节** ——
  论文十二章与 12 个业务包一一对应，公共层是它们共同的地基。答辩时讲作
  「12 个业务包 + 1 个公共层」即可
- **另有 `notice` 公告包与 `product` 商品包**，同样**不对应论文的任何章节** ——
  它们与 `common` 公共层同性质，是横跨或独立于那十二条业务线的东西。
  答辩时讲作「**12 个业务包 + 公共层 + 公告包 + 商品包**」：
  - **公告**是横跨设备、包场、门店三条线的**统一信息出口**（店门口的告示牌）。
    独立成包是必须的 —— 公告要展示「机台是否维护中」，而 `device` 已依赖
    `space`，公告落进 `space` 就会成环
  - **商品**是**独立于时长计费之外的第二类收入**（店里卖的饮料、周边）。
    它与 `promotion`（月卡）同形：自己管目录与购买单，收款归模块 8
- **依赖方向是单向的**：`common ← 业务包`。公共层不依赖任何业务包，
  业务包之间也不因共用基础设施而互相耦合
- **不用 Maven 多模块**：单人开发下「编译期强制模块边界」的收益很小，
  多一层 pom 配置反而是负担；将来真需要可渐进拆分
- **前后端同仓库，但仍是前后端分离架构** —— 「分离」说的是运行时
  （Vue 在浏览器里通过 HTTP 调 API，后端不渲染页面），与仓库如何划分无关

## 四、功能模块

| #   | 模块     | 包名          | 职责                          |
| --- | ------ | ----------- | --------------------------- |
| 1   | 用户管理   | `user`      | 用户注册、登录及信息维护                |
| 2   | 权限管理   | `auth`      | 管理员与普通用户权限控制                |
| 3   | 空间管理   | `space`     | 门店信息、停业时段与包场时段管理            |
| 4   | 设备管理   | `device`    | 机台台账：陈列与状况维护（良好 / 待维护 / 维护中） |
| 5   | 门禁管理   | `lock`      | 生成限时密码并调用智能门锁接口             |
| 6   | 进出记录   | `access`    | 记录用户开门及使用时间                 |
| 7   | 计费管理   | `billing`   | 按使用时长、消费时段与月度累计消费自动计算费用；维护免费活动时段 |
| 8   | 订单管理   | `order`     | 生成、查询及管理消费订单                |
| 9   | 优惠管理   | `promotion` | 判定优惠资格（月累计消费、月卡）并维护优惠规则     |
| 10  | 数据统计   | `stats`     | 营业额、订单、空间使用情况统计             |
| 11  | QQ 机器人 | `qqbot`     | QQ 群信息播报与查询，另有三条受限写指令（不碰付款） |
| 12  | 系统日志   | `log`       | 关键业务及管理员操作记录                |

**模块依赖关系：**

模块 5 → 7 → 8 构成一条强耦合主链路
（**门禁 → 计费 → 订单**），改动其中任一环需连带检查其余两环。
**模块 6 进出记录是旁路的记录与审计**（开门记录落库，供人工复核、争议追溯与 QQ 播报），
不参与计费链路 —— 计费起点由订单在用户点击开门时自行记录，无需等门锁记录回来对齐。
模块 9 在订单结算时生效；模块 10 的统计口径依赖模块 8 的订单数据。

**模块 4 的范围（2026-09-30 拍板）**：只做一件事 —— **把店里的机台陈列给顾客看**
（有哪些机器、摆在哪儿、还能不能玩），加上一个供选偏好用的类型列表。
三种状况「良好 / 待维护 / 维护中」由管理员在后台手工维护。

刻意**不做**的三件事，其实是同一件事的三面：**不绑定订单**（用户下单时不选机台，
计费也不看他玩了哪台）、**不参与准入**（机台状况挡不住人，能不能进店只由停业与包场
决定）、**不做设备级使用记录**（「谁正占着哪台」）。根子上是因为本系统的计费与准入
都按「人 + 时段」算，与「他在哪台机器上」无关 —— 这是共享模式（而非包场独占模式）
带来的直接结果。

> **「维护中」的机台照样陈列、不隐藏**：陈列的目的就是让顾客看到「这台在修」，
> 藏起来反而会让人以为机器搬走了。这也是「待维护」单列一态的意义所在 ——
> 它告诉顾客「这台有小毛病，不介意可以玩」，而不是笼统的「异常」。

**模块 7 与模块 9 的分工**：计费规则本身（原价与优惠价两套参数、封顶、时段划分）
属于模块 7，它是**纯计算**、不访问数据库；而「这个用户算不算达到了优惠门槛」
属于模块 9 —— 查询月累计消费、管理月卡、编排将来更多的优惠形态。
两者通过计费 Service 的入参衔接。这样划分的收益是：Web 结算与 QQ 机器人
两条链路能复用同一份计算逻辑，不必各写一遍。

**公告包（`notice`，不对应论文某一章）**：给用户端首页提供一块「店门口的告示牌」，
承载两类内容 —— **系统自动**（机台新增、状况变化、退役）与**管理员手写**
（临时通知、活动说明）。与 `common` 公共层同性质，答辩时讲作
「**12 个业务包 + 公共层 + 公告包 + 商品包**」（商品包见本节末尾）。

**它必须独立成包**：公告要展示「机台是不是在维护中」，而 `device` 包已经单向依赖
`space`（机台按门店陈列）。公告若落进 `space`，就成了 `space → device → space`
的环。独立成包后调用方向只剩单向：`device` / `space` / `order` 可以调公告包，
而 `notice` 只依赖 `common`，不 import 任何业务包 —— 自动公告的文案由调用方
拼好后以字符串传入，公告包本身不认识机台。
**目前真正接入的只有 `device`**（机台新增 / 状况变化 / 退役三处）。

**公告是一条消息，不是一份状态。** 这句话决定了它的全部行为：自动公告**只增不改** ——
机台修好不会把「转为维护中」那条改掉或删掉，而是再产生一条「转为良好」，
首页公告栏因此读起来是**一段历史**。由此也就**没有撤销、没有失效、没有按来源去重**：
那些机制都属于「把公告当成状态的投影」那种设计，在那里，机台修好之后那条维护公告
就**必须**消失，否则它就在说谎；而在消息流里，「刚才它确实维护过」是一条永远成立的事实。

> **披露边界用「结构上写不出来」代替「记得别写」**：自动公告的文案方法
> **刻意不接受运营备注**（如「等屏幕配件到货」）——调用方就算想泄露也没有参数可传。
> 这与「声明成接口方法而非 DTO 字段，是为了漏实现时编译不过」是同一个手法。

**包场不进公告流，走独立的「包场时间表」**（`GET /api/store/bookings`）：
包场是**未来的安排**，公告是**已经发生的事**，混在一条流里用户分不清哪条是通知、
哪条是日程；而且日程会随改期变动，消息流只增不改，改期后旧的那条永远对不上。
时间表只给**时段**、不给包场人 —— 普通顾客只需要知道「这个时段进不去、什么时候能进」，
不需要知道是谁包的场（与营业状态接口遵守同一套披露边界）。

**商品包（`product`，同样不对应论文某一章）**：卖店里的实体商品（饮料、周边），
是**独立于时长计费之外的第二类收入**。它也必须独立成包 —— 商品既不按
「人 + 时段」算钱（那是计费的模型），也不属于门店、设备、订单中的任何一条线。
答辩时讲作「**12 个业务包 + 公共层 + 公告包 + 商品包**」。

**结构上与月卡同形**：自己管目录（`biz_product`）与购买单（`biz_product_order`），
**收款处理器住在 `order` 包**，与包场、月卡共用同一套收款链路 —— 依赖方向固定为
单向的 `order → product`。加这一类收款，支付链路的代码一行未改。

**商品名唯一（2026-10-04 加）**：`biz_product` 上有一条唯一键 `uk_name`。
加它是因为**群里的下单指令按名字找商品**（`/买个可乐`）——
名字一旦能重复，系统就只能猜是哪一件，而猜错的代价是**给顾客下错单、扣错库存**，
当场还没人看得出来。⚠️ 那条键**不含逻辑删除位**（与用户名、QQ 号那两条同一套先例）：
已删除的商品仍然占着名字，查重也因此必须与它同一口径 ——
否则会出现「后台说名字可用、保存时撞唯一键」，用户拿到一句 500。

**库存是「支付到账时才扣」，下单时只做一次软检查。** 严格方案是下单预占、超时释放；
取「到账时才扣」的固有风险是两人同时买最后一件都能下单成功，后到手那个没货可拿。
缓解办法是下单时按「**可售量 = 库存 − 未支付的待支付单件数**」检查一次 ——
它不锁库存，所以理论上仍有竞态窗口；最后一道防线是落账时的条件 UPDATE
（`WHERE stock >= ?`），扣不动就记 error 日志转人工，**绝不让异常冒出去** ——
线上通道那侧会让支付平台不断重推一笔永远处理不了的通知，
凭证那侧则会把用户刚提交的凭证连同落账一起回滚，而钱其实已经付了。

> ⚠️ 那个「件数」很容易被写成「笔数」：一笔「买 5 件」的待支付单占的是 **5 件**库存。
> 写成按单计数不报任何错，只让可售量虚高 ——
> 表现为「明明下单成功了，付款后却说没货」。

**不做核销**：无人值守店里没有店员，付了钱自己去货架拿。代价是系统分不清
「货被拿了没有」，争议时只能查监控。这是明知的取舍而非遗漏 ——
将来要追踪，加一个「已交付」状态与核销接口即可，表结构不用动。

**停业也不进公告流**：停业已有营业状态接口在管，那条路径的措辞边界定好了
（只说「暂停营业」，不说原因，因为「设备维护」「员工休假」属运营内务），
在公告里另开一条说着说着就会说漏。

## 五、认证与权限设计

### 方案选型：JWT 而非 Session

**JWT（`Authorization` 头携带）+ `sys_user.token_version` 字段做撤销。**

选择 JWT 的理由是**多端与跨域**，而非「JWT 更先进」：

- **多端统一** —— 系统有用户端 Web、运营后台 Web，以及用户端将来可能套的 WebView 壳，
  JWT 放请求头对它们一视同仁。若用 Cookie，**微信内置浏览器对跨域 Cookie 限制严格**
  （iOS 的 ITP、Android 的 X5 内核都会拦截第三方 Cookie），且该故障**只在微信内复现** ——
  用 Chrome 调试时一切正常，排查成本极高。而微信内置浏览器恰恰是 JSAPI 支付的主战场，
  绕不开，所以这条不是「万一」而是「必然踩到」
- **跨域零配置** —— 前后端分离下跨域是常态。Cookie 方案需同时配置 `withCredentials`、
  CORS `allowCredentials` 与 `SameSite=None; Secure`，而 `Secure` 要求 HTTPS，
  与本地开发的 HTTP 环境直接冲突
- **诚实的说明** —— JWT 常被宣传的「无状态、便于水平扩展」在本系统单机部署下**并不成立**，
  因此它不是本方案的选型理由

> Session 并非劣选 —— 它更简单、撤销天然、token 不落入 JavaScript 因而抗 XSS。
> 但它适用于「仅有浏览器且同域部署」的场景，本系统的多端形态不满足这个前提。

### 撤销机制：token_version

JWT 的固有短板是**签发后在有效期内无法撤销**。本系统存在两类必须即时生效的场景：
管理员封禁用户（如离场未付款）、用户修改密码。解法是在 `sys_user` 增加 `token_version` 列：

```
登录      → 签发 JWT{userId, role, tokenVersion: 3}
每次请求  → 验签 → 查 sys_user → 比对 tokenVersion 是否仍为 3 → 放行
封禁/改密 → UPDATE sys_user SET token_version = token_version + 1
            → 该用户所有已签发的 token 立即失效
```

选择它而非 Redis 黑名单的原因：**不引入额外组件**。黑名单方案需要部署 Redis，
且每次请求仍要查询，本质上是把「服务端存储」请了回来。`sys_user` 本就是业务表，
查询开销可接受；真到瓶颈时再加本地缓存即可。

### 参数约定

| 项    | 取值                             | 说明                                                             |
| ---- | ------------------------------ | -------------------------------------------------------------- |
| 有效期  | 7 天                            | 共享空间用户可能间隔数周才再次到店，有效期过短会导致反复登录；有 `token_version` 兜底，较长有效期不影响安全 |
| 载荷   | `userId`、`role`、`tokenVersion` | `role` 仅作留痕；**鉴权以数据库中的角色为准**，见下一节                       |
| 签名算法 | HS256                          | 密钥通过**环境变量**注入，与数据库凭据同一处理方式                                    |
| 前端存储 | `localStorage`                 | 代价是理论上可被 XSS 窃取，通过输入转义与有效期控制缓解                                 |

### 权限控制

模块 2 的角色权限由 **Spring Security** 承担，在接口方法上以
`@PreAuthorize("hasRole('ADMIN')")` 声明所需角色，不自行实现注解与拦截器。

> Spring Boot 3 已废弃 `WebSecurityConfigurerAdapter`，配置需改用 `SecurityFilterChain` Bean。
>
> 另一个容易踩的坑：`@PreAuthorize` 生效的前提是配置类上标了 `@EnableMethodSecurity`。
> 漏掉它**不会报任何错**，接口会静默地变成「谁都能访问」—— 集成测试里专门有用例钉住这一点。

### 鉴权用库里的角色，而非载荷里的

载荷中虽然带了 `role`，但**权限判断以 `sys_user.role` 为准**。

原因是 `token_version` 校验**本来就必须每个请求查一次库** —— 不查就发现不了
凭证已被改密或封禁撤销。既然用户记录已经在手上，就没有理由再用一份签发时刻的角色快照：
用快照的话，管理员被降级后仍能凭旧凭证进后台，直到凭证自然过期。

用库里的值还带来一个好处：**改角色立即生效，且不必把用户踢下线**。
这也正是「改角色不升 `token_version`」这条规则的依据
（封禁与改密则会升 —— 它们要的恰恰是「立即失效」）。

### 密码存储

**用户密码使用 BCrypt 哈希**，禁止 MD5 / SHA 等快速哈希。

> 项目中另有一处 MD5：通通锁 API 要求换取 token 时密码传 32 位小写 MD5
> （见「智能门锁接入设计」）。那是**对接协议的既定要求**，与用户密码存储无关，勿混淆。

### 认证层与 QQ 机器人的边界

**QQ 机器人链路不经过 HTTP 认证层** —— 它从群消息中取 `user_id`（QQ 号），
据此在 `sys_user` 中定位用户，然后直接调用 Service。

因此**认证层只负责「HTTP 请求 → 用户身份」的转换，Service 层只接收 `userId` 参数、不感知 JWT**。
这条边界保证 Web 端与 QQ 机器人复用同一套业务逻辑，也是「qqbot 包单向依赖其他模块」的配套约定。

**这条边界有一处必须说清的例外**（2026-10-04）：QQ 机器人多了两条写指令
（`/开门`、`/结账`），它们**同样只带 `userId`、同样走 Service 层** ——
群里那个人的身份完全由「QQ 号 ↔ 用户账号」的绑定关系决定，**没有第二重凭证**。
这正是那两条指令的边界被收紧的原因：**只允许做到「建单 / 停表」为止，绝不触碰付款**
（付款要的是支付平台侧的凭证，而群消息这层给不出）。除此之外它仍是只读的 ——
最坏情况是查到不该查的信息，而不会改坏数据。

### 接口约定（2026-09-28 落地）

**统一返回体。** 所有响应都是同一结构，**包括 401、403、404、500 这些错误出口** ——
前端因此只需写一次统一的错误处理，不必为「万一某个接口挂掉返回的是 HTML 错误页」做兼容。

```json
{ "code": 0,     "message": null,               "data": { … } }   // 成功
{ "code": 40901, "message": "该用户名已被使用",   "data": null }    // 失败
```

`code` 为 0 表示成功，**不用 200** —— HTTP 状态码已经表达了「请求成功」这层含义，
body 里再放一个同名不同义的 200 只会让人混淆。失败时 `code` 是五位业务码，
前三位与 HTTP 状态码对齐（如 `40901` 对应 409），从日志里扫一眼就知道是什么性质的问题。

**HTTP 状态码用真实的，不是一律 200**。这样前端拦截器能靠状态码统一处理登录态失效，
网关与监控也能正确统计错误率：

| 业务码 | HTTP | 场景 |
| --- | --- | --- |
| `PARAM_INVALID` | 400 | 参数校验失败、格式错误 |
| `UNAUTHORIZED` | 401 | 未携带凭证 |
| `TOKEN_INVALID` / `TOKEN_EXPIRED` | 401 | 凭证无效或被撤销 / 已过期 |
| `BAD_CREDENTIALS` | 401 | 用户名或密码错误（**用户不存在也复用它**，避免被枚举账号） |
| `FORBIDDEN` / `ACCOUNT_DISABLED` | 403 | 角色不足 / 账号被禁用 |
| `NOT_FOUND` / `USER_NOT_FOUND` | 404 | 请求的资源不存在 / 目标用户不存在 |
| `USERNAME_EXISTS`、`QQ_ALREADY_BOUND` 等 | 409 | 业务冲突 |
| `ORDER_STATUS_INVALID`、`BOOKING_ACCESS_DENIED` 等 | 409 | 订单状态与包场准入相关的冲突 |
| `ORDER_ALREADY_ACTIVE` / `ORDER_UNPAID_EXISTS` | 409 | 上一单未结清（分别对应「进行中」与「未支付」），引导去「查看密码」/「去支付」 |
| `LOCK_CLOUD_UNAVAILABLE`、`PAYMENT_GATEWAY_UNAVAILABLE` | 502 | 上游依赖不可用（门锁云 / 支付平台），**错不在我们** |
| `INTERNAL_ERROR` | 500 | 服务端异常兜底（堆栈只进日志，不外泄） |

> 502 单独成段是为了让监控上能一眼区分「门锁云挂了」「支付通道挂了」与
> 「用户传错了参数」—— 三者的处置动作完全不同。**不要为了省一个码而把它们混进 409 或 500。**

**注册必须先证明 QQ 号是本人的**（2026-10-01 起）。这不是一道可选的门槛，而是这个
业务形态的要求：**店里没有店员**，顾客是谁、该收多少钱全靠系统；模块 11 的群播报与
查询又都按 `sys_user.qq` 认人。「不绑 QQ 也能进店」等于留一个**出了事找不到主的顾客**，
而「随手填一个号」会让群里的播报认错人。

流程是一次**群内往返**：网页取一个 6 位码 → 用户把它发到 QQ 群 → 机器人看到后
**按发消息那个人的真实 QQ** 查表核对 → 网页轮询到「已验证」→ 提交注册时消费掉这次验证。

> ⚠️ 两个容易忽略的点。其一，**验证码本身不是凭证** —— 群里所有人都看得见它，
> 但只有持有那个 QQ 的人才查得到自己那条记录；若改成「谁拿着码就验证谁」，验证就等于没做。
> 其二，**绑上之后本人改不了 QQ**（改资料接口会返回「QQ 号需要联系管理员修改」）——
> 允许自己改的话，那次群内验证就白做了：先随便填一个号注册，再改成群里某个人的号。
> 要换号得找管理员，管理员改不走群验证（他知道谁是谁），但照样查重。

> **`/api/bookings/**` 这几个接口代码住在 `order` 包而不是 `space` 包** ——
> 它们是模块 8 引入的需求（包场人的付款入口与取链接入口、被邀请者的查看与加入入口），
> 而模块 8 单向依赖 `space`。放进 `space` 会让两个包互相依赖成环。
> 包场的**排期**接口仍在 `space` 包，那部分与收款无关。
>
> 两个列表接口各查各的数据源，这是刻意的：`/host` 按
> `biz_booking.host_user_id` 查（**含待付款的场次** —— 包场人要靠它找到付款入口），
> `/joined` 按参与者表的 `role='PARTICIPANT'` 查。若两个都读参与者表，
> 待付款的场次就会消失，因为 `HOST` 行是付款成功那一刻才写入的。

> **`GET /api/store/instore`（在店名册）是 `/api/store/**` 里唯一的例外：它需要登录**，
> 而且代码同样住在 `order` 包（数据源是订单，`space` 不能反向依赖它 ——
> 与上面 `/api/bookings/**` 是同一个模式的镜像）。
>
> 「店里有谁」与「店开不开门」是两件事：后者是贴在门口的告示，谁路过都能看；
> 前者只有已经成为顾客的人才看得见，是进店之后才有的名册。
>
> **名册里没有任何金额** —— 谁在店里、玩了多久是进门就能看见的事实，
> 谁这一单要付多少是个人消费信息。月卡状态与游玩偏好倒是给，
> 因为同店顾客本来就互相看得见这两样（这也是第十章第 4 条原则被改掉的原因）。
> 名册上的在店时长是**实时算出来的**，不读订单上那一列 ——
> 那一列要结算时才写入，在店期间是空的。

`/api/user/me` 这类路径里**不出现用户 ID**，身份一律从凭证里取 ——
从根上杜绝了「改一下 URL 里的 ID 就能改别人资料」这类越权，因为压根没有那个 ID 可改。

**上传类接口的约定（2026-09-30 补齐）。** 图片一律走**独立的 multipart 端点**，
不并进各模块的「全量替换」接口 —— 比如用户资料那个 `PUT /api/user/me`
传 null 即清空，把图片路径混进去的话，「只改昵称」的表单会因为没带路径而
**把头像清空、且不报任何错**。

| 端点 | 归属 | 上传之后 |
| --- | --- | --- |
| `POST /api/user/me/avatar` | 模块 1 | **立刻写库** —— 用户只有一个头像，不存在「填一半取消」 |
| `POST /api/user/me/banner` | 模块 1 | 同上 |
| `POST /api/admin/products/cover` | 商品包 | **只返回路径、不写库**，随商品的新增 / 修改一起提交 |

- 表单字段名固定 `file`；类型**按文件头判定**（JPG / PNG / WebP），
  不看 `Content-Type`（那是客户端说的，能伪造）；单张上限 2MB。
  大小这一项有**两道闸门**（`uspace.upload.max-image-bytes` 与
  `spring.servlet.multipart.max-file-size`），**两道都要配**
- **文件名完全由服务端生成**，原始文件名一个字符都不采信 ——
  头像用 `{用户名}_{ID}`（用户名被注册校验限死在 `[a-zA-Z0-9_]{3,20}`，可以安全地进文件名），
  商品封面用 UUID（商品名是中文自由文本，清洗规则写不全）
- 扩展名由文件头推出，**调用方连指定它的机会都没有**，
  所以 `.jsp` 这类后缀不可能混进文件名
- 删旧图之前**必须校验路径前缀**，且要 `normalize()` 之后再比 ——
  少了这道，一次换图就能删掉任意文件
- 三段实现共用一个公共层组件 `ImageStorage`，**安全代码全项目只有一份**

**登出语义。** JWT 无状态，服务端没有会话可销毁，登出就是前端删掉 `localStorage`
里的凭证；`POST /api/auth/logout` 只记一条日志便于审计。

> **刻意不用「版本号 +1」来实现登出**：那会让该用户**所有设备**一起下线，
> 那是「强制下线」的语义，应当留给封禁与改密使用。

**游玩偏好的存储（`sys_user.preference`）**

用户喜欢玩哪类机器由**用户自报**，存在 `sys_user.preference`：
`VARCHAR(64)`，**逗号分隔的类型 code**，多选，可为空（没选也是一种合法状态），
例如 `PAIPAI,TAISHOU`。用户在网页端随时可改。

取值来自 `biz_equipment_type`（模块 4 的字典表），当前两条：拍拍机 / 抬手乐。
**做成字典表而不是写死在代码里**，是因为机器类型会随经营调整（进新机、淘汰旧机），
字典化后由运营在后台自行增删，不必改代码重新部署；而且「用户喜欢玩什么」
与「这台机器是什么类型」共用同一份取值，避免两边各维护一套、慢慢漂移。

**为什么用逗号串而不是关联表**：取值只有几个到十几个，属于典型的「小多值属性」；
且没有「按偏好精确筛选用户」这类需要走索引的查询。真要用 SQL 筛选时用
`FIND_IN_SET` 即可 —— 它不走索引，但本店用户量级下无所谓。
这与「不用外键约束」的整体取向也一致。

> **偏好不等于占用事实。** 它说明「某人倾向玩什么」，不说明「他此刻正玩哪台」。
> QQ 群播报里的「张三 · 拍拍机」只能作为判断设施占用的**参考**，
> 不能当账实相符的依据。真要精确到机台占用，需要模块 4 做到设备级使用记录 ——
> 而那**当前明确不做**（见「待定事项」）。模块 4 交付的是一份
> **纯展示的资产台账**：机器叫什么、摆在哪儿、还能不能玩。
> 机台状况是「这台还能不能玩」，**不是**「谁正占着」。

### 业务模式对表结构的决定作用

订单表的结构由「**即时制 + 信任制**」这一业务模式决定，而非凭空设计：

- **即时制** —— 用户到店下单后即可点击开门进场，没有预约时段，
  因此订单表**没有** `planned_start` / `planned_end` 这类预约字段
- **点开门即计费** —— 计费起点是 `start_time`（用户点击「开门」的时刻），**不是下单时间**。
  下单与点开门之间可能间隔任意时长，两者必须分开存储。
  从点击那一刻起算，顾客走到门口输密码的时间也计入使用时长 —— 这是刻意的：
  无需等门锁上报开门记录再对齐时刻，既省下一次门锁云调用（额度 30000 次/月），
  也免去了时刻精度与时区对齐的一整块复杂度
- **信任制** —— 离场时门锁不拦截，先出门后付款。因此支付相关字段
  （`payment_method`、`payment_no`、`paid_at`、`confirmed_by`）
  都在订单**结算之后**才写入，订单可以合法地处于「已离场但未付款」的
  `PENDING_PAYMENT` 状态
- **单门店 + 共享模式** —— 一个场所就是一个共享娱乐空间，多组顾客同时在店内
  各玩各的，各下各的单、各自计费。因此订单不需要处理「换房时时长如何延续」
  「多房间如何排队」这类问题 —— 扩张路径是**开分店**，不是「一个门店内多房间」。
  唯一的排他性是**时间维度**的：某个时段可以被包场（仅被邀请者可进），
  或整店停业；两者各自成表（`biz_booking` / `biz_closure`），
  门店记录本身不带任何时段性状态位

**订单状态流转：**

```
（点击开门 → 创建订单即进入）IN_USE 使用中
         │
      结束使用
         ↓
  PENDING_PAYMENT 待支付 ──支付到账（回调 / 提交付款凭证）──> PAID 已支付
         │                                    ↑
         └────────── 结算为 0 元直通 ──────────┘
```

> **只有两跳，没有 `CREATED` 中转态，也没有 `CANCELLED`**：
> 点一次「开门」就同时完成「创建订单 + 下发密码 + 开始计费」，
> 不存在「已创建但没开门」的挂起订单，自然也没有「下错单要取消」的场景 ——
> 误点一下不想进店，点「结束使用」即可，5 分钟内落在免费档、0 元自动结清。
> 表结构里 `status` 的默认值仍写作 `CREATED`，但业务代码从不产生它。

**一人同时只该有一条未结清的订单**（`IN_USE` 或 `PENDING_PAYMENT`）：

下单入口会先查「这个人有没有未结清的订单」，有就拒绝 ——
`IN_USE` 挡的是**连点两下开门**（点一次就计费，手指抖一下会拿到两个密码、
产生两条并行计费的订单，用户要付两份钱）；`PENDING_PAYMENT` 挡的是
**欠着费接着玩**（结算了但不付款，还能再开一单进场）。

两种情形给**不同的错误码**，因为用户该做的事不同：

| 码 | 用户此刻的处境 | 前端处置 |
| --- | --- | --- |
| `ORDER_ALREADY_ACTIVE`(40919) | 人还在店里玩 | 跳「**查看密码**」 |
| `ORDER_UNPAID_EXISTS`(40931) | 玩完了、账单还欠着 | 跳「**去支付**」 |

合并成一个码的话，前端只能给一句模糊提示，用户不知道自己该点「结束使用」
还是「去支付」。另注意「当前订单」查询（`GET /api/orders/current`，首页据此决定
按钮是「开门」还是「查看密码」）**只认 `IN_USE`** —— 待支付的单已结算、
密码已撤销，返回它会让用户看到一个点不动的「查看密码」。

### 关键设计决策

**为什么表名要加前缀**
`ORDER` 与 `LOCK` 均为 MySQL 保留字，直接用作表名会导致每处 SQL 都需反引号转义，
第三方工具也易踩坑。因此统一加前缀：`sys_` 用于系统级表，`biz_` 用于业务表。

**金额一律 `DECIMAL(10,2)`**
禁止 `FLOAT` / `DOUBLE`。浮点数无法精确表示十进制小数，金额累加会产生误差，
在财务场景中不可接受。

**时间存本地时间而非 UTC**
计费规则本身按本地时钟定义（日场 10:00–22:00）。若存 UTC，每次计费都需来回换算，
反而增加出错机会。本系统面向单一地区运营，不存在跨时区需求。

**逻辑删除而非物理删除**
主要业务表带 `deleted` 标记。订单属于财务数据，即使被取消也必须保留记录以备审计。

**刻意不使用外键约束**
关联完整性由应用层保证。这样便于将来分库分表、数据归档与批量清理，
避免外键带来的锁竞争与迁移困难。

**计费明细内嵌在订单表中**
日场/夜场的时长与金额直接作为 `biz_order` 的列存储，而非独立的计费明细表。
原因：时段固定为两个、结构稳定，用列更简单且查询更快；
同时满足「账单可追溯」的要求 —— 订单结算后金额是否被改动过一目了然。

**订单金额三个列的口径**（容易踩坑，写死在这里）：

| 列                             | 含义                                                  |
| ----------------------------- | --------------------------------------------------- |
| `day_amount` / `night_amount` | 该时段的**实收**金额（已封顶、已含优惠）                              |
| `total_amount`                | 合计 = 日场 + 夜场 = **实收**                               |
| `discount_amount`             | 本单因月度优惠而少收的金额，**说明性字段，已包含在 `total_amount` 里**       |
| `payable_amount`              | 应付金额 = `total_amount`（**不要再减一次 `discount_amount`**） |

三个列都在 `biz_order` 中现有列的基础上直接使用，模块 9 落地时无需改动表结构。
`total_amount` 已经含优惠，若实现时按字面「实付 = 合计 − 优惠」再减一次，
会造成**双重扣减**，且月度累计的口径也会跟着漂。

**订单的人工调整留痕**
字段 `adjusted` / `adjusted_by` / `adjusted_at` / `adjust_reason`。
对应业务场景：用户离场时忘记点「结束使用」，管理员查看开门记录与监控后
手工修正离场时间并重算费用。该操作必须留痕，否则财务上无法解释订单金额的变化。

**「累计实付消费」与「月度累计消费」是两个口径**

库里有两处与「消费额」有关的数，用途不同、口径也不同，实现时不要混用：

|        | 存在哪                                                       | 含义                    | 含月卡充值？ | 用途          |
| ------ | --------------------------------------------------------- | --------------------- | ------ | ----------- |
| 累计实付消费 | `sys_user` 的 `order_paid` / `card_paid` / `total_paid` 三列 | 用户在本店真掏出去的钱（**终生累计**） | **含**  | 前端展示、老客回馈筛选 |
| 月度累计消费 | 由 `biz_order` 按当月聚合得出，**不落字段**                            | 当月已支付订单的实付额（**每月重置**） | **不含** | 判定是否达到优惠价门槛 |

两者对月卡的处理不同，是**刻意的**：月卡本身就是一项独立的优惠政策，
若其卡费还能顶满优惠门槛，等于同一笔钱吃了两次优惠。而「用户掏了多少钱」
是另一回事 —— 那是事实，前台要展示、运营要据此回馈老客。

累计消费为什么拆成**三列**而不是一列：

- `order_paid`（场地消费）与 `card_paid`（月卡充值）分开存，
  便于将来给两类消费各自定政策 —— 例如「续费回馈只认月卡充值」
- `total_paid` 是前两者之和的**冗余列**，专门供前端展示与老客回馈筛选使用。
  这两类查询高频、且往往跨全表（`WHERE total_paid >= 1000`），
  而写成 `order_paid + card_paid` 的表达式是走不了索引的
- 三列同源：只在**订单支付成功**与**月卡支付成功**两处**集中累加**，只增不减，
  不要在别处各自更新。退款是否回冲，待退款政策确定后再定

### 关于「进出记录」的一个说明

`biz_access_record` 记录的是**开门事件**，而非严格意义上的「进」与「出」。

封闭空间的出门通常为机械推杠或按钮（消防要求内部必须能免密自由开门），
**不产生门锁记录**，因此系统只能记录到「进门」这一次开门。
用户的离场时刻由其在应用内手动点「结束使用」确定，
异常情况（忘记点击）由管理员查看开门记录与监控后人工复核。

这是由安全要求反推出的数据模型限制，不是设计疏漏。

**记录怎么采集：手动同步，不做轮询。** 门锁云不提供开门记录的推送回调，
系统只能主动拉取；而免费额度 30000 次/月是硬约束。因此同步设计为
**管理员在运营后台点击触发**，单次同步消耗 1 次额度（拉取结果为空时会再探活一次
确认锁是否在线，变成 2 次）。同步是幂等的 —— 判重键是「门锁 + 开门时刻」，
重复同步同一区间不会写入重复数据。

**拉取失败不会被伪装成「没有记录」。** 门锁云的查询接口在失败时返回空列表而非报错，
若直接采信，就会把「云端没拉到」当成「确实没有开门记录」，系统一声不吭地少记数据 ——
这是最难发现的一类故障。因此拉取为空时会再确认一次锁状态：**锁在线**才下
「确实没有记录」的结论，否则返回错误让管理员重试。

### 关于「公告」的一个说明

`biz_notice` 存的是**一条条消息**，不是「当前有哪些通知」的清单。这个定位推翻了三个
通常会给公告表加上的东西，每一个都是**刻意去掉**的：

| 通常会有 | 这里没有 | 为什么 |
| --- | --- | --- |
| 生效 / 失效时刻 | 没有 | 一条消息的「有效期」是说不通的。「3 号机转维护中」发生在那一刻，它不需要「从明天起生效」，也不会「下周三自动失效」。要提前准备，写到点再发即可 |
| 按来源去重（同一台机器只留最新一条） | 没有 | 去重会把「今天修了两次」抹掉 —— 而那本身就是值得看见的信息 |
| 撤销 / 下架 | **只有手写公告有** | 自动公告是已经发生的事实的记录，改写或删除等于篡改历史；消息流里也没有「下架」这个动作，后面还会有新消息盖过它 |

**手写公告反过来可改可删**，因为它不是「已发生的事实」，而是「运营现在想说的话」——
说错了、过期了、想换个说法，都该能收回来。两类公告靠 `publish_mode` 区分，
`PUT` / `DELETE` 打在自动公告上返回 40929。

**数据库侧还有一道结构约束**（`ck_notice_source`）：手写公告必须没有来源、自动公告
必须有来源，两个来源列要么全空、要么全不空。应用层已经这样保证（Service 方法体里
硬编码，不是「不传就设 null」而是「无论传什么都置空」），约束是第二道防线 ——
将来新增第二条写入路径时，绕过应用层也绕不过它。

**排序是「置顶的最前，其余按主键倒序」**（2026-09-30 修订）。
用 `created_at` 排会因为同秒多条出现不稳定顺序：两条同一秒写入的公告每次查询
可能换个位置，页面看起来像在抖动 —— 所以次序键用自增主键。

> **原先这里写的是「没有置顶」**，理由是「消息流里『我想让这条排前面』
> 不是一个真实需求」。这个判断在**只有自动公告**时成立，加上手写公告之后就不成立了：
> 「今晚临时调整营业时间」这条必须让顾客先看到，而它可能正好被一串机台维护消息
> 挤到看不见的位置。于是加了 `pinned` 一列，并且**只让手写公告能置顶** ——
> 自动公告恒为 0，否则一次机台故障就会占满首页前几条。

**置顶不改变「消息流」这个定位**：它没有让公告变成「状态」，只是在展示顺序上
给了运营一个有限的抓手 —— 置顶的条数天然很少（一屏就那几条位置），
也没有「到点自动取消置顶」那种机制，要取消就手动取消。

## 七、智能门锁接入设计

### 核心约定：按真实规格设计接口，用模拟代码实现

**对外接口按通通锁云 API 的真实规格设计与命名，但当前实现下落为模拟代码，
不连接真实门锁云。** 具体含义：

- **照真实规格的部分**：URL 路径、请求参数名、返回字段名、错误码、鉴权流程。
  将来切换到真实调用时，只需替换 Service 的实现层，Controller、DTO、数据模型均无需改动
- **用模拟实现的部分**：门锁云的 HTTP 调用、token 换取、密码下发

**为什么这样做：** 毕设阶段无法保证有真实门锁硬件与可用的云端账号，
但接口契约必须一次定对 —— 若先用「演示级」接口把流程跑通，后期接入真实门锁时
会牵动上层所有代码，代价远高于现在多写一层实现。

实现的选择由配置项 `uspace.lock.provider` 决定（`mock` / `ttlock`）。
模拟实现位于 `lock/mock/` 包，真实实现预留 `lock/ttlock/`。

### 准入模型：谁在什么时候能进门

系统有**四种时段**，准入规则各不相同：

| 时段 | 谁能进 | 实现方式 |
| --- | --- | --- |
| 平时（默认） | 任何人 | 正常下单，下单即获得密码 |
| 包场预备期（开始前 15 分钟内） | 无人 | 一律拒绝新下单 |
| 包场准备期（开始前 5 分钟内） | 仅包场人与被邀请者 | 其他人下不了单，自然拿不到密码 |
| 包场时段 | 仅包场人与被邀请者 | 同上 |
| 停业时段 | 无人 | 一律拒绝新下单 |

判断顺序是 **停业 → 包场 → 普通**：先看当前时刻是否落在停业区间，
再看是否落在某个已付款包场的**准入窗口**内（比包场本身早 15 分钟开始），
都不命中则按普通订单放行。
三者的数据分别在 `biz_closure`、`biz_booking` 与订单表中。

**「谁是参与者」由 `biz_booking_participant` 一张表说了算**：包场人与被邀请者
各占一行，靠 `role`（`HOST` / `PARTICIPANT`）区分。在这张表之前，「被邀请者」
只是包场人分享出去的一条链接 —— 系统里没有地方记着他是谁，于是准入只能靠
请求里带上令牌才认得出来，而包场开始时的清场与结算时的时长剪切更是完全认不出他。
邀请链接与令牌都保留了下来：被邀请者点开链接时，落地页会自动调一次加入接口
把他记进表里 —— 此后靠账号身份就能被认出来，不必再依赖那条链接。

> ⚠️ **2026-09-30 修正**：这里原先还写着另一层兜底 ——「万一自动加入失败，
> 下单时带上令牌仍然能进场」。**那个入口已经去掉了**，所以这条兜底实际已失效。
> 原因是落地页上那个「现在去开门」按钮**点下去就是创建订单 + 下发密码 + 开始计费**，
> 而点开邀请链接的人多半**不在店里**（在群里翻到、随手点开看看），
> 包场又往往是几天之后的事 —— 误触的代价是真金白银。
> 现在落地页只有一个「返回首页」，到店的入口统一在首页的「开门计时」。
>
> 后端**带令牌下单的能力还在**（`POST /api/orders` 收 `inviteToken`），
> 只是前端不再调它。要恢复这条兜底，得让首页也能带上令牌 —— 那是另一个设计。
> 自动加入失败时，落地页现在提示「刷新页面重试一次」。

**为什么包场要提前挡人**：一局游戏打不完就要被清场，放进来等于让顾客花了钱
却玩不尽兴。开始前 15 分钟就停止接待新顾客 —— 这个时长刚好覆盖「进来打一局」
的最短耗时，更晚进来的必然会被中途打断。参与者另有 5 分钟的提前量，
用来进店放东西、做开场准备；再早的话，店里仍按普通营业安排。

两个提前量是配置项（`uspace.order.booking-lead-duration` 与
`uspace.order.participant-lead-duration`），但**只改窗口宽窄，不改规则结构**：
「谁在哪一档」的判定顺序是固定的。

**包场时段不计费，结算时从计费区间里剪掉。** `biz_order.booking_id` 记下
「这单与哪一场包场有关」，结算时把该包场时段从计费区间里剔除，
只对超出的部分按普通规则收费。三种情形都要认，缺一不可：

- **被邀请者（在准入窗口内进店）**：下单时正处包场时段，`booking_id` 直接指向该场
- **参与者（比准入窗口更早进店）**：下单那一刻包场还没进窗口，准入判定走的是
  「普通」分支。系统会再查一次「他参与的、尚未结束的包场」并把那一场记进订单 ——
  **少了这一步，他会在包场开始时被当散客清场，结算时那个时段还会被重复计费**
  （包场费已经付过一次）
- **包场人提前到店**：与上一条同理，他也占着参与者表里的一行（`HOST`），
  下单时同样会被挂上；`host_user_id` 的回查仍然保留，作为历史数据的兜底

> 剪切这件事**只在服务端做一处**（`OrderService` 里的一个纯函数），
> 结算与人工调整共用同一段逻辑，账单视图把 `billingStart` 一并返回给前端。
> 若前端也各算一份，两边一旦漂移就会展示出与实际收费不符的账单，
> 同样不会报错 —— 这是最难发现的一类缺陷。

#### 包场开始时的清场

准入只挡得住「新订单」，挡不住「已经在店里的人」。包场开始时，仍在店内的
**非参与者**订单会被系统结算离场：账单结算到包场开始时刻，密码一并撤销，
他结算完就进不去了，包场时段只剩参与者在场。

- **计费截止到包场开始时刻**，不是执行结算的那一刻 —— 金额不随系统的执行时机
  浮动，同样的场景重算一遍结果相同。代价是结算任务晚跑几十秒时那几十秒不计费，
  这个偏差对顾客有利
- **参与者不受影响**：包场人与被邀请者都不会被清出去。判定读的是订单上的
  `booking_id` —— 而下单时（哪怕比准入窗口更早）就已经把它挂好了，
  见上一节末尾那三种情形
- 系统**每分钟扫描一次**，发现正在进行的包场就执行。用扫描而不是「到点触发」，
  是因为包场可能提前几天就排好、而系统在这期间重启过 —— 扫描只依赖
  「当前时刻 + 一次查询」，重启不丢、改期也不必重新登记

> 清场是系统里**唯一一处自动结算**。其余结算都由顾客自己发起或管理员人工调整 ——
> 因为「从门锁记录推断顾客何时离开」有可能判断错，而收的是顾客的钱。
> 包场清场不存在这个问题：结算时刻取自包场排期本身，是排期时就定下的确定值。

**准入控制靠「不发密码」实现，不靠门锁的禁止名单。** 非被邀请者拿不到有效密码，
自然进不去 —— 无需在门锁上维护黑名单，也不存在「名单没同步上」这类问题。

#### 门只有一条开启路径：在门口输入密码

**系统不提供「远程直接开锁」**（线上点一下门就开的那种）。用户点「开门」按钮时，
拿到的是**一串密码**，还需走到门口输进去。

这不是实现偷懒，是刻意的：远程开锁一旦存在，账号被误触、被人拿去乱点，
就会**直接把陌生人放进店**；而「拿密码」不会 —— 拿到密码的人必须物理在场。

#### 「点击开门」是展示密码，不是每次下发新密码

密码在**订单创建时**就下发到锁上，点击按钮只是把它**显示出来**。用户看到的行为
与「点一次发一次」完全一致（点击 → 看到密码），但有两个好处：

- **不多花门锁云的调用额度** —— 每次点击都打一次 API 会很快烧完 30,000 次/月
- **不会在锁上堆积密码** —— 否则得再配一套「删旧密码」的流程

已知副作用是密码固定，被截图转发后对方也能用；但转发之后对方仍须人到门口，
风险有限。若将来要求更严，可改为「点一次换一次」，代价是调用额度。

### 模拟实现刻意保留的真实约束

模拟实现能脱离外网跑通「下发密码 → 开门 → 写进出记录」的完整链路
（计费是纯计算，本就与门锁无关），但**不比真实接口宽松**，以免切换到真实实现时才暴露问题：

1. **自定义密码只能是限时密码** —— 不传有效期会被拒绝。
   因此模块 5 的接口设计为「带生效/失效时间的限时密码」而非纯一次性码
2. **远程下发（`addType=2`）需要锁接入网关或本身为 Wi-Fi 锁**，
   可用配置模拟「纯蓝牙锁」，此时远程下发会被拒绝
3. **网络调用可能失败** —— 支持按概率注入失败，用于演练异常处理分支。
   否则异常处理逻辑在演示时永远走不到，而异常处理与数据校验正是考核点

### 通通锁云 API 规格要点

| 项         | 内容                                                                      |
| --------- | ----------------------------------------------------------------------- |
| 接口域名      | 国内 `https://api.ttlock.com`；欧盟 `https://api.sciener.com`                |
| 鉴权        | OAuth2 密码模式，`POST /oauth2/token`；密码需 32 位小写 MD5                         |
| token 有效期 | 90 天，须服务端缓存复用，不可每次调用重新换取                                                |
| 锁初始化      | `POST /v3/lock/init`（锁已在 APP 添加过则可跳过）                                   |
| 密码接口      | `/v3/keyboardPwd/add`、`/v3/keyboardPwd/change`、`/v3/keyboardPwd/delete` |
| 单次密码      | `POST /v3/keyboardPwd/get`（`keyboardPwdType=1`）—— **取一串用一次即焚的密码**，与上面「下发自定义密码」是两条不同的接口。群里的 `/开门` 走它 |
| 记录查询      | `POST /v3/lockRecord/list`                                              |
| 免费额度      | **30,000 次/月**                                                          |

**接入时容易踩的坑：**

- **开发者账号 ≠ 通通锁 APP 账号**。开发者账号名下没有任何设备，
  换取 token 的 `username` 必须用 APP 登录账号（已授权的管理员账号），
  否则查不到锁状态、无法开锁，报非管理员权限
- **远程开锁通常需要网关**，链路为 锁 → 蓝牙 → 网关 → 互联网 → Cloud API。
  纯蓝牙锁无法远程下发密码，**采购时必须避开**
- 错误码如 `-4043 The function is not supported for this lock`，
  需在 APP 中开启远程开锁后才有远程控制能力
- 时区参数 `timezoneRawOffset` 要对齐，否则密码有效期会算错

### 调用额度约束

30,000 次/月是硬约束，接口设计遵循「省调用」原则：

- **不做轮询**：开门记录按需拉取或批量拉取，不用定时任务反复拉
- 缓存复用 access token，不重复换取
- 单次订单的调用预算控制在 2~4 次（下发密码 + 失效密码 + 可选拉记录）。
  **群指令 `/开门` 另计**：每次取一串一次性密码（`keyboardPwd/get`）花 1 次 ——
  不复用旧串是刻意的取舍（判断旧串还在不在同样要花 1 次，却多担一份
  「把已失效的密码发给站在门口的人」的风险），防连点交给冷却时间

## 八、计费规则

> 本章规则于 **2026-09-26** 改版（日夜差异化定价 + 月度累计消费优惠），
> 于 **2026-09-28** 调整档位起点（宽限 7 → 5 分钟）。单价与封顶金额未变。

### 计费公式

**日场 4 元 / 30 分钟，夜场 3.5 元 / 30 分钟**（日场整点合 8 元/小时，夜场合 7 元/小时）。

```
段费用 = ceil( (段时长分钟 − 5) ÷ 30 ) × 单价(时段, 优惠状态)
         再与该时段该优惠状态下的封顶取小
总费用 = 各时段段费用之和
```

公式里每条规则的位置：

- **「−5」是结账误差**：档位边界因此落在 5、35、65、95… 分钟。从整点进场时，
  整点与半点出门恰好都落在整档的末尾 —— 玩 30 分钟收 1 档、玩 60 分钟收 2 档，
  不会因为多玩一两分钟就跳档。这也保证了**恰好整点结算时严格是 8 元/小时**
  （日场 1 小时=8 元、2 小时=16 元、3 小时=24 元）
- **「余数不满 5 分钟舍弃、达到 5 分钟进位」**已包含在公式中：
  玩满 35 分钟仍收 4 元，36 分钟才跳到 8 元
- **「首 5 分钟内免费出场」是公式的自然结果**，不需要额外判断 ——
  段时长为 5 时 `ceil(0÷30) = 0`，费用即为 0

**免费时长为什么是 5 分钟**：一局舞萌（街机音游）的下限约 6 分钟（最低 3 首 × 每首约 2 分钟）。
但**在场时间不等于打机时间** —— 投币、选曲、进出场、离场结算都要花时间，
所以**完整打完一局必然超过 5 分钟，会正常计费**。
关键在于：这 5 分钟**连最短的一局都覆盖不到**，它覆盖的只有「进来看看就走」
「一首都没打完成」这类场景，**彻底没有「送一局」的效果**。
这比早先的 10 分钟、后来的 7 分钟都更严格，刻意套利的空间被进一步压缩。

**为什么用「宽限」而不是「免费时长」**：这 5 分钟在实现上不是一个
「满足条件就减免」的规则，而是公式里的一个减数。它同时决定四件事 ——
**档位边界、免费时长、余数进位线、金额达到封顶所需的时长**。四者同源，
改一个数四个一起动。所以「5 分钟免费」不能当作一条可以单独调整的宣传语，
它在代码里就是 `uspace.billing.grace-minutes` 这一个配置项。

> **已知边界与运营对策**：免费时长理论上可被刻意绕过 —— 打一两首就出场结算（0 元）、
> 再重新下单进场。但这类行为的**特征极其显著**：既然完整打完一局必然超过 5 分钟，
> 那么「订单时长集中在 5 分钟以内、且高频重复」本身就是明晃晃的异常信号，
> 与正常用户的订单分布完全区分得开。
> 
> 对策是**后台检测 → 警告 → 选择性公示 → 拉黑**，而不用技术手段封堵 ——
> 封堵会误伤「真玩了 5 分钟就走、过会儿又来」的正常顾客。
> 该能力归入模块 12 系统日志的延伸，现阶段不实现。

**为什么日场夜场不同价**：夜间（22:00–次日 10:00）是共享娱乐空间闲置率最高的时段，
夜场定价 7 元/小时（比日场低 1 元）是用价格换利用率。

| 1 小时 36 分 – 2 小时 5 分 | 16 元         | 14 元         | 14 元         | 12 元         |
| 2 小时 6 分 – 2 小时 35 分 | 20 元         | 17.5 元       | 17.5 元       | 15 元         |

整点校验：日场原价玩 1 / 2 / 3 / 5 小时 = 8 / 16 / 24 / 40 元，严格 8 元/小时。

### 时段划分与封顶

| 时段  | 时间范围              | 原价封顶 | 优惠价封顶 | 金额达到封顶的时长  |
| --- | ----------------- | ---- | ----- | ---------- |
| 日场  | 10:00 – 22:00     | 40 元 | 35 元  | 4 小时 36 分起 |
| 夜场  | 22:00 – 10:00（次日） | 35 元 | 30 元  | 4 小时 36 分起 |

四组封顶都等于「10 档 × 对应单价」，也就是**5 小时价格** —— 单价与封顶是绑定的
一组参数，调价时四个数字要一起改。优惠是整列降价，封顶随之下降，而不是只降单价。
四组封顶都从第 10 档（4 小时 36 分）起不再增长。

注意「金额达到封顶」与「被标记为超出封顶」是两回事：4 小时 36 分至 5 小时 5 分
（第 10 档）期间金额恰好等于封顶值，程序不把这标记为超出；要到第 11 档
（**5 小时 6 分**起）原始金额才真正超过封顶值。

### 月度累计消费优惠

**用户当月已支付订单的实付额之和达到 200 元后，当月后续订单整单按优惠价计费。**

| 项    | 原价                 | 优惠价          |
| ---- | ------------------ | ------------ |
| 日场单价 | 4 元 / 30 分         | 3.5 元 / 30 分 |
| 日场封顶 | 40 元               | 35 元         |
| 夜场单价 | 3.5 元 / 30 分       | 3 元 / 30 分   |
| 夜场封顶 | 35 元               | 30 元         |
| 门槛   | 当月累计实付额满 **200 元** |              |

判定口径有几条明确约定：

- **只统计已支付订单**（`status = 'PAID'`）的**实付额**：欠着费还不算「消费」，
  口径干净，也避免用户靠不付款堆高累计额
- **判定在订单粒度，不逐档、不追溯**：一单要么全按优惠价、要么全按原价，
  不会出现同一单里前几档原价、后几档优惠的情形。账单上只有一个单价，用户看得懂；
  已经结算过的订单也不会因为后来达标而退款
- **本单自身不计入累计**：结算时本单尚未支付，天然避开了「本单算完之后
  把自己顶过门槛」的循环依赖
- **月卡不计入本门槛**：月卡期间订单免费、金额为 0，按上述口径累计自然是 0；
  购买月卡的卡费也**不计入** —— 月卡本身就是一项独立的优惠政策，不再叠加。
  详见 `月卡设计草案.md` 第七节
- **自然月重置**：每月 1 日零点重新累计
- **按计费起点所属月份归集**：即以订单的 `start_time`（用户点击开门的时刻）
  落在哪个月来计入哪个月，而不是按支付时间。这样跨零点结算的夜单不会莫名其妙
  跳到下个月，管理员事后修正时长也不会让历史订单的优惠判定发生漂移

### 跨时段处理

**按时段切段分别计算**，各段使用同一公式、各自套各自的封顶，最后相加。

> **已知副作用**：每段各自享有那份「−5」宽限，因此跨时段与不跨时段的同长订单
> 可能算出不同价格，且方向不固定：
> 
> - 21:55–22:05 共 10 分钟（日场 5 分 + 夜场 5 分）→ 两段都落进免费档 → **0 元**，
>   而同样 10 分钟全在日场收 4 元（偏便宜）
> - 21:53–22:07 共 14 分钟（日场 7 分 + 夜场 7 分）→ 各 1 档 → **7.5 元**，
>   而同样 14 分钟全在日场收 4 元（偏贵）
> - 21:40–22:20 共 40 分钟（日场 20 分 + 夜场 20 分）→ 各 1 档 → **7.5 元**，
>   而同样 40 分钟全在日场收 8 元（偏便宜）
> 
> 这是「分段计算 + 各段独立套公式」的固有结果，属于**已确认接受**的规则形态，
> 不是缺陷。宽限从 7 分钟缩到 5 分钟后，第一条能落进免费档的跨时段窗口
> 已收窄到 10 分钟（两段各不超过 5 分钟），套利空间比改版前更小。

### 时长精度

时长按**分钟向下取整**。即 35 分 59 秒算 35 分钟、收 4 元，而非按 36 分钟收 8 元。
选向下取整是与整套规则的宽松取向保持一致（宽限、余数舍弃都是在给用户让利）。

### 计费结果的结构

**计费结果必须分段呈现，不能只给一个总价。** 每段给出「时长」「单价」「档数」
与「该段价格」：

```
日场   1 小时 0 分     2 档 × 4 元      8 元
夜场   1 小时 40 分    4 档 × 3.5 元   14 元
──────────────────────────────────────
合计   2 小时 40 分                    22 元
```

若该用户当月累计已满 200 元，同样时长按优惠价计算，账单会明确标出省了多少：

```
日场   1 小时 0 分     2 档 × 3.5 元    7 元
夜场   1 小时 40 分    4 档 × 3 元     12 元
──────────────────────────────────────
合计   2 小时 40 分                    19 元
（已享月度优惠，本单省 3 元）
```

因此计费 Service 返回的是**结构化的分段对象**而非单个金额。每段除时长与金额外，
还保留「计费档数」「所用单价」「封顶值」「封顶前金额」四项中间结果 ——
使账单可追溯：用户质疑金额时，能直接看出钱是按几档、哪个单价算出来的，
以及有没有被封顶压过、压到多少为止。整单另带出「结算前当月累计额」
「是否按优惠价」「本单优惠金额」，便于事后核对优惠判定的依据。

**已结算的订单，详情页同样按段展示**（2026-10-03 加）。做法是**账单快照**：
结算时把这一份分段账单原样存进订单（`biz_order.bill_snapshot`），订单详情直接读 ——
计费规则与价格后来怎么调，已结算订单的明细都不受影响。
这一条不是锦上添花：跨天的长订单会被切成多段、**每段各自封顶**，
只看「日场 34 小时 41 分 ¥120」这样的汇总，没人能算得清 120 是怎么来的。

快照机制之前结算的老订单没有快照，详情接口会**按当前规则重算**一份来兜底，
但只有重算金额与落库金额**完全一致**才展示（活动被删改、包场被撤销、价格调整过，
都会让两者对不上）—— 对不上就回落到日场/夜场汇总行。宁可少展示，
也不给一份与实收金额矛盾的假明细。

计费参数（日夜场单价与封顶、月度优惠的门槛与优惠价、单位时长、宽限、时段起止）
全部外置到配置文件，调整运营规则无需修改代码或重新部署。

### 在店时长与计费时长（2026-09-30）

系统里有两个「时长」，**口径不同、用途不同，不可互相替代**：

| | 在店时长 `stay_minutes` | 计费时长 `day_minutes + night_minutes` |
|---|---|---|
| 含义 | 人在店里待了多久（离场时刻 − 开门时刻） | 其中**按分钟收钱**的那部分 |
| 含包场时段吗 | **含** | 不含（包场时段被剪掉） |
| 含宽限那 5 分钟吗 | 含 | 不含 |
| 用途 | 「我的」页的累计时长、订单展示 | 算钱、账单分段 |

差别可以有多大：一场 2 小时的包场，顾客进店后全程待在包场里，
**计费时长是 0 分钟，在店时长是 2 小时**。拿计费时长当「在店时长」展示，
用户会看到「累计时长 0 分钟」—— 看起来像个 bug，而系统一切正常。

因此订单表同时存这两组值，接口也分别返回（`stayMinutes` 与 `bill.totalMinutes`），
账单页两个都要显示，**标签不能混用**。

### 下一次账单变化的预告（2026-09-30）

用户看着计时器时最想知道的是「现在停，还是再玩一会儿」。首页的进行中卡片与
结账预览页都会显示一句「还有 12:30 进入下一档 ¥20.00」。

**这句话必须由后端算**：档位边界里的「30 分钟一档」与「5 分钟宽限」都是配置项，
前端自己推等于把计费规则复制一份 —— 改配置时前端静默算错，且不报任何错。

后端给出的不是「几点了会变」而是**还有多少秒**：绝对时刻会带上客户端与服务端的
时钟偏差，用户手机时间不准时倒计时会算出荒谬的值。

| 情形 | 提示文案 | 依据 |
|---|---|---|
| 段内跳档 | 「进入下一档 ¥20.00」 | 下一个档位边界落在当前时段**之内** |
| 跨时段 | 「跨入夜场，按夜场重新计价」 | 下一个档位边界落在当前时段**之外**，先发生的是时段边界 |
| 段内不再变化 | 「当前已到封顶价」/「当前时段月卡免费」 | 只给文字，不给倒计时 |

**「跨时段」这一档不能省**：只报「还有 40 分钟进入下一档」的话，21:50 的用户
会以为 22:30 才变，而实际在 22:00 就跨进夜场重新起了一段（夜场更便宜）。
**展示一个错误的时间预期，比不展示更糟。**

### 月卡（模块 9）

与「月度累计优惠」并列的第二项优惠政策。**两种优惠并行存在、互不重叠**：

| | 月度累计优惠 | 月卡 |
|---|---|---|
| 触发条件 | 当月已支付订单实付额满 200 元 | 买了卡且在有效期内 |
| 优惠形式 | 单价降 0.5 元/半小时，封顶随之下降 | 覆盖的时段免费 |
| 生效范围 | 当月后续所有订单 | 有效期内所有订单 |
| 粒度 | **整单** —— 一单要么全优惠价、要么全原价 | **段级** —— 覆盖的段免费，其余照常计费 |

#### 两种卡与免费范围

| 卡种 | 价格 | 覆盖时段 |
|---|---|---|
| 全天月卡 | 600 元 | 全部时段 |
| 夜间月卡 | 320 元 | 只覆盖夜场段（22:00 – 次日 10:00） |

- **有效期按购买日起 30 天计**（含首尾，`end_date = start_date + 29`），不按自然月 ——
  否则月末几天买卡的用户只买到两三天，同样的钱买到的东西差一大截
- **夜场边界沿用计费配置**（`uspace.billing.day-start` / `day-end`），不另设一套 ——
  两套边界迟早漂移，而漂移的后果是顾客账单与月卡权益对不上
- 价格与有效期天数都是配置项（`uspace.promotion.monthly-card.*`），调价不必改代码

#### 有效期边界也是切分线（2026-09-30）

月卡的免费范围**同时在两个维度上生效**：**哪些时段**（全天 / 仅夜场）
与**哪一段日期**（卡的有效期）。后者是后来补上的：

- 在此之前，月卡按**订单的开始日期**整单判定 —— 卡最后一天 23:00 进店、
  玩到次日 01:00，整单都免（等于多送一个多小时）；卡次日才生效时，
  前一天晚上进店的整单也都不免。两头都靠「开始时刻」定，规则不闭合
- 现在**卡的有效期两个端点也是切分线**（前两条是日夜场边界），
  段一律切到卡的边界为止。覆盖到的段免费、没覆盖的照常计价：

```
卡 9/30 到期，9/30 23:00 进店、次日 01:00 离场
夜场  9/30 23:00 – 24:00   1 小时   全天月卡覆盖   → 免费
夜场  10/1 00:00 – 01:00   1 小时   卡已失效       → 2 档 × 3.5 元 = 7 元
──────────────────────────────────────────────────────────
合计                                                    7 元
```

> 上面那条切分线是**日期边界（零点）**，不是时段边界 —— 两段都还在夜场里。

- **切分只在边界真的落在订单区间内时发生**。每多切一段就多享一次那 5 分钟宽限
  （与「跨时段切段」是同一类副作用，见本章开头），所以无卡时一段都不多切，
  卡覆盖整单时也一段都不多切
- **跳档预告同步认这个边界**：当前段被卡覆盖、但卡在本段内失效时，
  界面报的是「月卡即将到期，之后按时长计费」而不是「当前时段月卡免费」——
  否则用户会看着一句静态的「免费」，然后零点金额毫无预兆地开始涨

#### 叠加语义：段级，不是整单

被月卡覆盖的段免费；**未被覆盖的段照常参与月度优惠判定**。以夜间卡用户
21:00–23:30（且当月已满 200 元）为例：

```
日场段 1 小时     2 档 × 3.5 元（优惠价）   7 元
夜场段 1.5 小时   月卡免费                   0 元
──────────────────────────────────────────────
合计                                         7 元
```

若改成「有段被免就整单不打折」，会出现**非单调的价格悬崖**：同样是夜间卡用户，
20:00–21:30 全在日场收 7 元，21:00–23:30 只多玩 30 分钟却收 8 元 ——
进了夜场反而更贵，运营解释不通。

#### 两条不要搞错的口径

- **卡费不计入月度优惠门槛**：月卡期间订单金额为 0（累加自然是 0），
  买卡的 600 / 320 元也不计入 —— 月卡本身已是独立优惠，
  再顶满门槛等于一笔钱吃两次优惠
- **但卡费计入 `sys_user.card_paid`**（累计月卡充值实付）—— 那是用户真掏出去的钱，
  前台要展示、运营要据此回馈老客。两个「累计消费」口径的区别见第六章

#### 账单上的呈现

被月卡覆盖的段**照常算出档数、单价、封顶与封顶前金额，只把实收置 0** ——
用户看到的是「夜场 1.5 小时 · 原价 10.5 元 · 月卡免费」，
而不是一个没有来由的 0 元。

订单上另有一列 `card_free_amount` 记下本单被免掉多少，与 `discount_amount`
（月度优惠省下的）分开存 —— 两者互不重叠，合成一列的话账就没法解释了。

#### 购买与生效

```
POST /api/cards/purchases   落一条待支付购买单（此时还没有卡）
        │
        ├─ 线上通道：POST /api/payments（targetType = MONTHLY_CARD）→ 支付回调
        │
        └─ 扫码转账：POST /api/payment-proofs → 管理员复核通过
        │
   落账（同一事务两跳）
        ├─ 购买单 → 已支付
        └─ 往卡表插一张生效中的卡，生效日 = 支付当日
```

> **月卡是「等复核」的那一类**（见第九章的「交付时机分两层」）：走扫码转账时，
> 凭证提交后卡不会立刻出现，要等管理员确认 —— 卡发出去就收不回来。

**卡与购买单是两张表**：卡是资产（有有效期），购买是交易（可能被放弃）。
合并成一张的话，就得把生效日期放开为可空 —— 而那是「卡」的核心属性。
详见 `月卡设计草案.md` 第五节。

### 免费活动（2026-10-03 新增）

运营者可以排一段**任意起止的活动时间**（如跨年 `12-31 20:00 – 次日 02:00`
全场免费），区间内所有订单的**实收为 0**。粒度是具体时段而不是
「免日场 / 免夜场」那种档位 —— 跨年活动本来就不认日夜场的划分。

> ⚠️ **它与停业是两回事，这是最容易混的一处**：
>
> | | 停业 | 免费活动 |
> |---|---|---|
> | 管什么 | **准入**（能不能进） | **计费**（要不要钱） |
> | 期间进店 | 拒绝新下单 | 照常 —— 人照进、门照开 |
> | 已在店内的人 | 不受影响 | 账单算 0 |
>
> 两者可以同时生效、互不干扰。后台把它们放在「门店」页的两个 tab 里，
> 正是因为它们是同一件事的两面：「哪段时间不营业」与「哪段时间不收钱」。

#### 与包场的关键区别：段保留、金额置零

| | 怎么处理 | 账单上看得见吗 |
|---|---|---|
| **包场** | 把区间**剪掉**，根本不产生分段 | 看不见（那段时间凭空消失） |
| **月卡 / 免费活动** | 段保留、**实收置 0**、记下免了多少 | **看得见**「原价 X 元、活动减免 X 元」 |

办活动就是要让人看见省了多少，剪掉的话账单上什么都看不出来 ——
所以免费活动走的是月卡那条路，不是包场那条。

#### 三种优惠互不重叠

一笔订单可能同时命中几种优惠，各自管各自的范围、各记一列：

| 优惠 | 粒度 | 记在哪一列 |
|---|---|---|
| 月度累计优惠 | **整单**（一单要么全走优惠价、要么全走原价） | `discount_amount` |
| 月卡 | **段**（被覆盖的段免费） | `card_free_amount` |
| 免费活动 | **段**（区间内的段免费） | `activity_free_amount` |

> ⚠️ **月卡与活动落在同一段上时只记前者**：月卡用户本来就免费，
> 活动并没有为他省下什么。两个都记的话，复盘一场活动「送出去多少钱」会虚高，
> 而那种错不会有任何报错。

#### 时段边界

活动的起止时刻是**又一条切分线**（前两条是日夜场边界、月卡有效期边界）：
订单跨到活动边界时切成两段，一段免费、一段照常计费。
切分**只在边界真的落在订单区间内时发生** —— 多切一段就多享一次宽限。

区间是**半开区间** `[startAt, endAt)`，与停业、包场同一口径：
`18:00–20:00` 与 `20:00–22:00` 可以背靠背排，不算重叠。

#### 接口与落点

后台 `GET|POST|PUT|DELETE /api/admin/store/free-periods`（仅 ADMIN），
用户端 `GET /api/store/free-periods`（**匿名**，首页「免费活动」卡与
计费规则页的那一节都读它）。字段级的说明见 `接口文档.md` 第三章。

> **为什么接口挂在 `/api/admin/store` 下、代码却住在 `billing` 包**：
> 它是**计费规则**，归模块 7；但计费包刻意不认识「门店」
>（注入门店 Mapper 会与「门店页反过来调计费包」成环），
> 所以由门店那一侧的 Controller 提供接口、把当前门店 ID 递过去。

## 九、支付接入设计

### 收款方式：扫码转账 + 上传付款截图 + 管理员复核（2026-09-30 改版）

**12 月投产时，这是唯一的收款方式。** 三条线上通道逐条走不通：

| 通道 | 卡在哪 |
| --- | --- |
| 微信 JSAPI | 要**已认证的服务号或小程序**（每年有年费），还要 openid、网页授权域名、备案域名与全链路 HTTPS |
| 微信 H5 支付 | 产品定位是手机浏览器里的**线上**交易，纯线下的到店服务收款不在其受理范围内 |
| 支付宝 WAP | 要**企业支付宝账号**，个人账号不具备手机网站支付能力 |

**共同的根子是「个人主体办不了微信支付商户号」**，而这三条通道都以商户号为前提。

这与第七章的智能门锁是同一种处境：**接口按真实规格设计，投产时先走一条不依赖资质的路径。**
区别在于门锁那条路径是模拟实现（要外网，只能等硬件到位），
支付这条路径是扫码转账 —— 它不需要外网，今天就能收钱。

**完整流程**：顾客扫店里张贴的收款码转账 → 上传付款截图（可填流水号）→
管理员在后台核对到账 → 完成。

截图**默认在网页端上传**；`/结账` 之后**也可以直接把图发到 QQ 群里**
（2026-10-04 加，见第十章）—— 两条路交的是**同一张凭证表、同一套复核**，
所以走哪条都不影响对账。

**上一版否掉这个方案的三条理由，需要逐条重过一遍** —— 它们不是错的，
但都没到「不可用」的程度：

| 当初的理由 | 现在怎么看 |
| --- | --- |
| **破坏「无人值守」** —— 复核要人盯着 | **「无人值守」说的是店里没有店员，不是没有运营者。** 复核是异步的：顾客传完截图该玩玩、该走走，管理员事后在后台批量过一遍即可，没有人在现场等着。真正被放弃的是「零人工」，而这一条本来就做不到 —— 顾客忘点「结束使用」、金额有争议，都得人来处理 |
| **存在伪造风险** —— 截图可以被伪造 | 风险是真的，但它**与经营形态直接相关**：本店做的是本地熟人生意，伪造一张截图的性质与陌生人大市场里不同。系统侧另加了两道防线 —— 截图必须来自本服务的上传接口（挡住外链与别人的图）、同一流水号被多笔凭证引用会被标记 |
| **对账困难** —— 支付流水不在系统内 | **仍然成立，这是这个方案真正的代价。** 缓解手段是让用户填流水号：钱虽然不走系统，但那串号能把系统里的凭证与收款账号里的记录对上 |

**系统的角色因此变了**：不再是「钱的搬运工」（调支付网关、处理回调），
而是**「这笔钱到没到账」的记账处** —— 顾客说「我付了」（截图 + 流水号），
管理员说「收到了」（复核），系统把这两句话记下来，并与订单对上。

### 支付通道（2026-09-30 修订）

**本系统一共四条通道，投产时只启用第一条：**

| 通道 | 是什么 | 投产时的状态 |
| --- | --- | --- |
| `QR_UPLOAD` | 店内收款码 + 上传付款截图 + 管理员复核 | **唯一启用的** |
| `WXPAY_JSAPI` | 微信内置浏览器 → JSAPI 支付 | 实现完整，关闭 |
| `WXPAY_H5` | 微信外的手机浏览器 → H5 支付 | 实现完整，关闭 |
| `ALIPAY_WAP` | 支付宝内置浏览器 → 手机网站支付 | 实现完整，关闭 |

**哪几条出现在收银台上，由 `uspace.payment.enabled-channels` 决定**，前端从
`GET /api/payments/channels` 取，不要在页面里写死 —— 配置改了页面要能自动跟着变，
否则就会出现「选项明明在那里、点下去却报错」。

> **通道是运营决策，不是技术开关。** 它与 `uspace.payment.provider`
> （代码能不能对外调用支付平台）是两件事，不可互相推断：模拟实现还在
> （开发与演示照常能用），而本店不收线上渠道的钱 —— 这个组合完全正常，
> 也正是投产前后的差别。详见「开发策略」一节。

线上三条通道的产品矩阵如下。**它们的实现是完整的，只是投产时关闭** ——
留在这里，供将来资质到位后接入时参考：

**按用户所处的浏览器环境分流到不同支付产品。** 微信支付与支付宝的产品矩阵
都按使用场景划分，名称极易混淆，这里一次讲清：

| 用户所在环境           | 支付产品               | 下单接口                              | 拿到什么              | 怎么调起                                                  |
| ---------------- | ------------------ | --------------------------------- | ----------------- | ----------------------------------------------------- |
| 微信内置浏览器          | **JSAPI 支付**       | `POST /v3/pay/transactions/jsapi` | `prepay_id`       | 前端 `WeixinJSBridge.invoke('getBrandWCPayRequest', …)` |
| 微信外的手机浏览器        | **H5 支付**          | `POST /v3/pay/transactions/h5`    | `h5_url`          | 前端 `location.href = h5_url` 拉起微信 App                  |
| 支付宝内置浏览器 / 支付宝场景 | **支付宝手机网站支付（WAP）** | `alipay.trade.wap.pay`            | 一段自动提交的 form HTML | 前端插入并提交表单，拉起支付宝 App                                   |

**通道由前端按浏览器环境预选，但用户仍可改。** 微信内打不开支付宝、
支付宝内打不开微信（双方互相屏蔽外链），预选错了必然出现「选了却调不起来」的死路。
判断依据是 User-Agent：含 `MicroMessenger` → 微信内；含 `AlipayClient` → 支付宝内；
其余 → 微信外浏览器，此时微信 H5 与支付宝 WAP 都可用，在收银台页上并列给出。

> 做成「**预选 + 可改**」而不是「自动路由且不可改」：「微信里想用支付宝」
> 是常见需求（零钱不够、有支付宝红包），把它锁死在预选结果上会让这种需求无路可走。

### 线上通道的规格（投产时关闭，留待将来接入）

> 下面三部分描述的是**线上通道的接入细节**。投产时它们全部关闭，
> 这些内容留着，是为了将来资质到位、真要接入时不必重新调研一遍。
> **读到这里请记得：当前唯一在用的收款方式是扫码转账**（见本章第一节）。

#### 为什么弃用 Native 扫码（原方案）

**先纠正一个常见混淆：微信内的 H5 页面用不了名为「H5 支付」的产品。**
「H5 支付」是给微信外浏览器用的，微信会拦截它。本项目上一版设计正因这条约束
而选用了 **Native 扫码支付**，2026-09-28 修订后弃用，理由如下。

Native 支付的产品定位是「**PC 端网页浏览器**收款」，流程是网页展示二维码、
用户**掏出手机用摄像头扫**。而本系统的用户端以手机 Web 为主（见第二章
「客户端形态」）—— 用户手机上就只有这一台设备，让他在手机屏幕上看着二维码、
去扫另一台不存在的设备，在逻辑上就走不通。

**这一条有官方文档背书**：微信支付 Native 支付的产品介绍页明确写着
「不支持通过相册识别或长按识别二维码的方式完成支付」——
也就是说二维码必须**用另一台设备的摄像头**去扫，不能靠长按识别绕过。
手机端因此没有 Native 的立足之地。

> Native 仍然适合**收银台有 PC 的场景**（如网吧前台、门店 POS）。
> 本项目是无人值守、纯自助结算，没有这个场景，故整体弃用、不保留该通道。
> 若将来真要做前台代收，按「PC 场景」单独加回来即可，接口本身是现成的。

#### 各通道的硬约束

以下不是「注意事项」，而是会让支付走不通或算错账的硬性行为，接口设计时要预留：

- **JSAPI 的 `prepay_id` 有效期 2 小时**，过期需用原参数重新下单；
  同一 `prepay_id` 在未支付时可多次拉起支付。因此**不要在订单创建时就下单**，
  应在用户点「去支付」时才下单
- **H5 支付的 `h5_url` 有效期只有 5 分钟**（比 Native 的 2 小时短得多），
  且官方明确**严禁篡改、拆分或截断该链接**；要指定支付后跳回的页面，
  **只能**在末尾拼接一个 `redirect_url` 参数，不能再加别的
- **H5 支付没有前端回调** —— 不像小程序 `wx.requestPayment` 那样有 success 回调，
  支付结果只能靠异步通知或主动查单确认
- **支付宝的 `return_url`（前台回跳）不可靠** —— iOS 上从支付宝 App 回来可能
  根本不跳转，官方明确「最终支付结果必须以后台异步通知或查询接口为准」，
  只能拿它当结果页入口
- **支付宝的 `passback_params` 只在异步通知里回传**，同步通知（return_url）不返回 ——
  要往回调里带自定义参数，得走这个字段，而不是拼接到 `return_url` 上

#### 三个通道共用一套订单状态机

微信的两个通道（JSAPI / H5）**共用一个 `notify_url`**；
支付宝的异步通知因协议不同（表单验签 vs. 微信的 RSA 验签 + AES 解密）
单独一个端点。但三者**验签通过后走的是同一段逻辑**：

```
回调到达 → 验签 → 按【商户订单号】幂等去重 → 写支付字段 → 订单流转为 PAID
```

这样加通道不必动订单模块。`payment_method` 列记下具体是走哪条通道的，
对账时能区分来源。

**扫码转账怎么融进这一套**：它不走网关、不产生回调，因此入口完全不同
（凭证的提交与复核，见下一节）；但**最终汇到同一处** —— 同样是
「标记目标已支付 + 按记账品类累加用户消费」。所以四类收款、四条通道
两两组合起来，订单模块里关于「钱到账了」的写法仍然只有一份。

### 付款凭证：钱到没到账的判断（`biz_payment_proof`）

**一张表承载四类收款的凭证** —— 订单、包场、月卡、商品，靠 `target_type` +
`target_id` 指明是哪一笔，加一类收款不必新建表。这与统一支付入口
（`POST /api/payments`）是同一个思路：**若每类收款各建一张凭证表，
「钱到账了」这件事就会有四份写法，迟早分叉。**

**交付时机分两层，这是本节最要紧的一条：**

| 收款类型 | 用户提交凭证时 | 管理员复核时 |
| --- | --- | --- |
| **订单 / 商品** | **当场落账** —— 订单转已支付（欠费拦截随之解除）、商品当场扣库存 | 纯登记 —— 钱早就算收到了，复核只留个结论 |
| **包场 / 月卡** | 只落凭证 | **此刻才交付** —— 生成邀请令牌、发一张卡 |

依据是**「这笔钱买的东西能不能当场交付」**：

- **订单**买的是「已经玩过的那几个小时」—— 人都离场了，东西早就交付完了，没有等的理由
- **商品**买的是货架上的实体商品，付了钱自己取，同样是当场
- **包场与月卡**买的是**一项权益**（一场包场的排他性、一张 30 天的卡），
  而权益一旦发出就收不回来 —— 所以宁可等管理员扫一眼

**代价要说清楚**：订单与商品是「先交付、后复核」。复核若判为不通过，
系统**不做自动回退**（订单已支付、库存已扣、累计消费已加）——
那涉及改状态、退库存、减累计消费三件事，每一件都需要人来判断
（货是不是已经拿走了？钱是不是其实收到了、只是用户传错了图？）。
系统能做的是**把事实喊出来**：后台列表把这类条目标出来，由管理员人工处置。

**提交有五条分支**，不能用一句 upsert 糊过去 —— 用户传错图、重复提交、
被驳回后重交，都是高频事件：

| 目标当前态 | 已有凭证 | 行为 |
| --- | --- | --- |
| 待支付 | 无 / 待复核 / 未通过 | 写凭证，并按类型决定是否当场落账（未通过的要翻回待复核、清掉驳回原因） |
| 已支付 | 待复核 | 只更新凭证（换图 / 改流水号），**不重复落账** |
| 已支付 | 已核对 | 幂等返回，不覆盖 —— 覆盖会把一条已核对的凭证打回待复核 |
| 已支付 | 未通过 | 拒绝并附上驳回原因 —— 让用户自己重传就能翻案的话，驳回这个动作就没有意义了 |
| 已支付（线上通道） | 无 | 拒绝 —— 线上付的款没有凭证可言 |
| 已取消 / 已退款等 | — | 拒绝 —— 没有可付的款 |

**风险标记：同一流水号被多笔凭证引用。**

一张截图付两单，是纯信任制下最省事的作弊手法，而它留下的痕迹只有一个 ——
同一个流水号出现两次。系统**不拦提交**（用户抄错一位、同一笔钱在两个页面都提交了一次，
都是常见情形；静默拒绝一笔可能的正常付款，比让管理员多看一眼糟得多），
而是**把全部相关凭证都标出来**，让它们排到后台列表最前，由人来判断。

用户重交时会先清掉旧标记再重新检测 —— 否则假警报越积越多，
最后管理员干脆就不看这个标记了。

**上传与提交是两个接口**：上传只落盘、只返回路径，提交才写库。
用户传完图要核对流水号、可能还要改一遍再交，合成一个的话，
「传了图又放弃」会留下一条状态不明的凭证记录。

**流水号是选填的，但强烈建议填** —— 它是唯一能把系统里的记录与收款账号里的账对上号的东西。
系统能做的也只有这么多：钱毕竟没有走系统。

### OCR 辅助识别（2026-09-30 新增）

**「钱到没到账」这件事，让机器先替管理员看一遍截图。**

扫码转账是唯一的收款方式，也就意味着**管理员是唯一的对账环节** ——
他要在后台一条条盯着用户的付款截图，看金额对不对、单号有没有。
一单两分钟的话，一天三十单就是一个小时。而这一步机器能替他做完大半：
**把截图里的金额与交易单号读出来**，管理员从「逐条看 100%」降到「只看对不上的那几条」。

#### 照真实规格的部分，与可切换的部分

与第七章的智能门锁、以及本章的支付网关是同一套做法：**接口按真实规格设计，实现可切换**。

| | 内容 |
| --- | --- |
| **照真实规格** | 接口路径（`/rest/2.0/ocr/v1/accurate_basic`）、鉴权流程（OAuth2 换 `access_token`，缓存复用）、请求参数名（`image` 传 Base64）、返回字段名（`words_result[].words`）、错误码 |
| **可切换的实现** | `uspace.ocr.provider` 决定装配哪一个：`mock`（默认，不识别）或 `baidu`（真实调用） |

**为什么默认是不识别**：识别要联网、要账号、按次计费，而它是**搭在收款链路旁边的
增强，不是收款本身的必经之路**。没装引擎时，用户照旧手填交易单号，
整条链路与从前完全一样。真实实现按百度的规格写好了，
申请到 key、填两个凭据即可启用。

> **模拟实现恒返回「未识别出」，不造假的识别结果。**
> 门锁的模拟实现会生成密码、支付的模拟实现会完成支付，它们产出的假数据
> 正是演示时要展示的东西。OCR 不一样：它的产物是「截图里写着 8.00 元、
> 单号 4200…」这样一条**关于事实的陈述**。凭空造一条出来，管理员在后台看到的
> 就是一个不存在的金额 —— 他要么被误导，要么学会不信任这一栏
>（而后者更糟：真识别出来的时候他也不看了）。

#### 识别发生在什么时候

**用户上传截图时，只此一次。**

- 上传时就识别，用户**当场能看到、能核对**，识别出的单号还能直接预填进输入框 ——
  而「用户抄错一位」正是对账困难的主要来源
- **不在提交时再识别一遍**：通用文字识别（高精度版）个人认证有 1000 次/月免费额度，
  一天三十来单恰好是 900 次；改成两次会让额度当月翻倍耗尽，而结果并不会因此更准

识别结果随提交请求回到服务端，落进 `biz_payment_proof` 的 `ocr_payment_no` /
`ocr_amount` / `ocr_text` 三列。**这意味着这三个字段对客户端是可写的** ——
接受它，是因为它们被明确标注为**辅助线索**：复核永远是人做的，
管理员看的始终是那张截图，系统里没有任何自动判断依赖它们。
将来若要加「识别金额相符就自动放行」，**必须先改成服务端自己识别**，
否则等于把放行权交给了请求体。

三列都有列宽（单号 64 字符、金额 `DECIMAL(10,2)`、原文 1000 字符），
服务端在写入前会截断、丢弃越界的值：它们是辅助信息，
不该因为没对上格式而让「提交付款凭证」整个失败 ——
那是用户完全无法自救的一种报错（这三个值不是他填的，他也改不了）。

#### 「哪一行是金额」是系统自己的规则

识别引擎只负责把图上的字读成一行行文本，**「哪一行是金额、哪一行是单号」是本项目的规则**：

- **金额**：找带 `¥` 且金额合理的那一处。只认带货币符号的写法 ——
  微信与支付宝的付款成功页金额都写作 `¥8.00`，放宽到「任何形如 8.00 的独立行」
  会误伤时间戳（`21:45.32` 之类）与各种编号
- **交易单号**：先按「交易单号 → 订单号 → 商户单号 → 交易号 → 流水号」的顺序找关键词，
  一条都找不到时退化为「全文中最长的数字串」。
  **关键词的顺序有讲究**：平台那一侧的号才能与平台账单勾稽上，所以它排在商户单号前面

这套规则独立成一个纯静态的类，不碰 Spring、不碰网络 —— 因为**认错了不会报错**：
认错金额，后台显示一条与截图对不上的提示，而管理员未必分辨得出；
认错单号，那串数字根本没人会逐位核对。它因此是全项目单测覆盖最密的地方之一。

#### 两条纪律

1. **识别失败 = 识别不出，不是错误。** 网络超时、配额耗尽、凭据失效，
   一律记一条 warn 日志、当作「这次没识别出」，**上传与提交都不受它影响**。
   正因如此，这条链路**没有引入任何新的错误码** —— 用户看到的「没识别出」
   与「识别服务不可用」本就该是同一件事
2. **识别原文不进日志。** 付款详情页的截图里有付款人昵称等信息，
   它只出现在两个地方：提交者本人的页面，与后台复核页 ——
   而管理员本来就在看那张截图

### 收款码（`biz_pay_qr`）

**收款码与支付通道是两个概念，刻意没有复用同一个枚举。**

`PaymentChannel` 描述的是「**支付路由**」—— 这笔钱走微信内 JSAPI 还是微信外 H5、
要不要调网关、有没有回调；`PayQrChannel`（微信 / 支付宝）描述的是
「**这笔钱进了哪个收款账号**」。混用的代价很具体：`WXPAY_JSAPI` 与 `WXPAY_H5`
在顾客眼里是同一个微信收款码，而对账时它们又确实不是同一条流水 ——
用一个枚举，就必然要在某处写个 `if` 把它们合并回去，那个 `if` 就是错的开始。

凭证上记着 `pay_qr_id`，于是「这笔钱扫的是哪张码」是可追溯的 ——
店里有多个收款账号时（比如老板与老板娘各自一张微信码），对账能分清钱进了谁的口袋。

**两个查询口径，用错不会有任何报错：**

| 用途 | 接口 | 口径 |
| --- | --- | --- |
| 收银台展示 | `GET /api/payments/qr` | 只取**启用中**的码 —— 把停用的也列出去，顾客会扫到一张不再使用的码 |
| 后台管理 | `GET /api/admin/pay-qrs` | **含停用**的 —— 只列启用中的话，管理员停用一张码之后就再也找不回它了 |

**删除走逻辑删除**：历史凭证上记着 `pay_qr_id`，物理删掉之后那个号就查不出
对应的是哪张码了，对账时说不清「这笔钱当时扫的是哪个账号」。

**门店一张码都没配时返回空列表** —— 那是真实的运营状态（刚部署完还没配），
前端要提示「请联系管理员配置收款方式」，而不是白屏。

### 支付在订单生命周期中的位置

本系统采用**信任制**（见第六章）：用户先离场、后付款。因此支付发生在
**订单结算之后**，而不是开门之前：

```
（点击开门 → 创建订单即进入）IN_USE ──结束使用──> PENDING_PAYMENT ──支付成功──> PAID
                                  └──── 结算为 0 元时直通 ────┘
```

> **状态机只有两跳，没有 `CREATED` 中转态。**
> 用户端只点一次「开门」，这一下同时完成「创建订单 + 下发密码 + 开始计费」。
> 那种「订单已创建但没开门」的中间状态既没有用户价值，又留下
> 「下了单不进门」的垃圾订单需要清理，所以不做。
>
> **也因此没有「取消订单」接口**：误点一下不想进店，点「结束使用」即可 ——
> 五分钟内落在免费档，0 元自动结清。
> （建表脚本里 `status` 的默认值仍保留 `CREATED`，但业务代码从不产生它。）

**结算为 0 元时直接跳到 `PAID`**：0 元单没有任何可支付的通道，
让它卡在待支付只会让用户看到一个「0 元去支付」的按钮。这条规则同时覆盖
「五分钟内免费出场」与「整段时间被包场覆盖」两种情形。

#### 用户端的结账流程

| 用户动作 | 调用 | 结果 |
| --- | --- | --- |
| 点「结账」 | `GET /api/orders/{id}/preview` | 看到当前时长与金额，**计时不停** |
| 点「停止计时」 | `POST /api/orders/{id}/settle` | 定格、转待支付（0 元则直通已支付） |
| 点「去支付」 | `GET /api/payments/channels`、`GET /api/payments/qr` | 拿到本店收哪几种钱、收款码贴出来 |
| 扫码付款后传截图 | `POST /api/payment-proofs/image` → `POST /api/payment-proofs` | 截图落盘、凭证落库；**订单当场转已支付** |
| 管理员复核 | `POST /api/admin/payment-proofs/{id}/confirm` | 留下结论 —— 订单这类，钱在提交那一刻就算收到了 |

> 步骤数取决于走哪条通道：扫码转账比线上支付多「传截图」这一步，
> 线上通道则多一个「等回调」。硬凑一个固定步数反而讲不清。

**第一步的预览页就是那个确认环节。** 它展示的「时长 + 金额 + 是否封顶」
已经足够用户做决定，点「停止计时」即视为确认离场 ——
**没有二次确认弹窗，也没有反悔路径**，停止即定格；想继续玩只能重新开门、重新计费。

**预览不产生任何副作用**：计时继续走、订单状态不变、门锁密码不撤销、
不消耗门锁云额度。它走的是与真实结算**完全同一条计费链路**，
所以预览价与实际价必然一致 —— 唯一的差别是截止时刻（预览用此刻、结算用用户
真正按下按钮的那一刻，中间隔了几秒，跨过档位边界时会跳一档）。
也正因如此，前端要持续轮询这一屏（约 10 秒一次），让屏幕上的数字始终是新的。

**支付字段在「钱到账」那一刻一次性写入**：`payment_method`（走的哪条通道）、
`payment_no`（交易流水号）、`paid_at`（支付时间）、
`confirmed_by`（核销人 —— 线上回调与提交即交付的凭证都为空，表示系统自动确认）。

**两条入口（线上回调 / 付款凭证）写的是同一批字段。** 订单模块因此不必知道
钱是从哪条路进来的，它只知道「这笔到账了」—— 切换收款方式不需要改动数据模型，
这正是「投产时能从线上通道切到扫码转账」的前提。

### 开发策略：模拟实现 + 真实实现

与门锁模块同一思路（见第七章）：**接口按微信支付 API v3 与支付宝开放平台的
真实规格设计，当前下落在模拟实现**。切换靠 `uspace.payment.provider`，
取值有**三档**：

| 取值 | 含义 | 用在哪 |
| --- | --- | --- |
| `mock` | 模拟实现，不访问外网 | 本机开发与答辩演示 |
| `disabled` | 没有线上支付 —— 装配一个所有调用都明确失败的实现 | **12 月投产用这一档** |
| `real` | 真实支付平台（待实现） | 资质到位后 |

> **`disabled` 这一档是必需的，不是可有可无的占位。** 支付服务的构造器依赖
> 一个网关 bean，而模拟实现与将来的真实实现都挂在 `@ConditionalOnProperty` 上 ——
> 少了它，把 provider 改成任何一个非 mock 的值都会让容器装配失败、**应用直接起不来**，
> 而不是「优雅地关掉支付」。
>
> 它失败时返回的是 `PAYMENT_CHANNEL_DISABLED`(40938)，而不是 502 ——
> 这是「本店没开这个业务」，不是「上游挂了」，两者该让用户看到的提示完全不同。

**注意它与「收哪几种钱」是两个开关，不可互相推断**（见「支付通道」一节）。
配置里若出现「网关关了、通道还开着」这种矛盾，启动时会打一条 WARN ——
刻意只警告不抛异常：配置问题不该让服务起不来，而这一档在投产前后切换时
很容易短暂出现。

**扫码转账这条路不需要 provider** —— 它不调网关。所以投产时
`provider=disabled` + `enabled-channels=QR_UPLOAD` 是自洽的组合：
「没有线上支付能力，只收扫码转账」。

模拟实现要能脱离外网跑通**三条线上通道**的完整流程 —— 包括「拿到
`prepay_id` / `h5_url` / form HTML → 模拟用户在微信或支付宝完成支付 →
回调后端 → 订单转 PAID」。演示时可在页面上直接切换通道，把三种环境各演一遍，
不必真的准备三个浏览器环境。

**三条必须设计进去的约束：**

1. **回调验签 + 幂等** —— 支付平台的回调会重推，必须以**商户订单号**做幂等，
   否则同一笔支付会被记账两次。这与 QQ 机器人用 `message_id` 去重是同一模式
2. **回调可能延迟或丢失** —— 模拟实现保留这一语义（可配置注入失败），
   并提供「主动查询订单状态」的补偿路径。支付成功而回调未达，
   是生产环境必然发生的事件，异常分支必须在演示时可走到
3. **三通道共用一套回调处理与订单状态机** —— 见「线上通道的规格」一节。
   加通道不动订单模块

### 实现落地（2026-09-30 修订）

**收款侧是一个统一入口 `POST /api/payments`**，请求体带
`{targetType, targetId, channel}`，而不是挂在订单子路径上。
理由是包场也要收款 —— 若包场付款由 `space` 包提供接口，而模块 8 的支付服务
又依赖 `space` 做准入校验，两个包就成环了。统一入口把依赖方向固定成单向的
`order → space`，将来加月卡也只需多一个 `targetType`。
**付款凭证沿用了同一套结构**：同样靠 `targetType` + `targetId` 指明是哪一笔。

| 端点 | 用途 | 权限 |
| --- | --- | --- |
| **线上通道** | | |
| `POST /api/payments` | 发起支付，按通道返回 `prepayId` / `h5Url` / `formHtml` / `mockPayUrl` | 需登录 |
| `GET /api/payments/{outTradeNo}` | 查询支付状态，必要时向平台补偿 | 需登录 |
| `POST /api/payments/notify/wxpay` | 微信回调（JSAPI 与 H5 共用） | **匿名** |
| `POST /api/payments/notify/alipay` | 支付宝回调（协议不同，单独端点） | **匿名** |
| `POST /api/payments/mock/pay` | 模拟支付，仅 `provider=mock` 时存在 | 需登录 |
| **扫码转账（投产时的主路径）** | | |
| `GET /api/payments/channels` | 列出某类收款当前可用的通道 —— **收银台选项的唯一来源** | 需登录 |
| `GET /api/payments/qr` | 列出启用中的收款码，供扫码转账的收银台展示 | 需登录 |
| `POST /api/payment-proofs/image` | 上传付款截图 —— **只落盘、只返回路径，不写库** | 需登录 |
| `POST /api/payment-proofs` | 提交付款凭证（截图路径 + 可选流水号） | 需登录 |
| `GET /api/admin/payment-proofs` | 后台分页查询凭证，风险与待复核的排在最前 | 仅 ADMIN |
| `POST /api/admin/payment-proofs/{id}/confirm` | 复核通过 | 仅 ADMIN |
| `POST /api/admin/payment-proofs/{id}/reject` | 复核不通过（须填原因，会展示给用户） | 仅 ADMIN |
| `GET` `POST /api/admin/pay-qrs`、`PUT` `DELETE /api/admin/pay-qrs/{id}` | 收款码的增删改查 | 仅 ADMIN |
| `POST /api/admin/pay-qrs/image` | 上传收款码图片（同样只落盘） | 仅 ADMIN |

> **后台的复核端点没有请求体**（通过那条）—— 要填的东西一样都没有，
> 不为对称造一个空对象。驳回那条则必须带原因：用户重交或申诉时要知道「哪里不对」。

> **两个回调端点匿名可达，但鉴权并没有被取消**，而是换了一种 ——
> 改由支付平台的**签名验证**承担，验签不过一律拒绝处理。
> 注意 `requestMatchers(String...)` 是精确匹配，放行这两个路径
> 不会顺带放行 `/api/payments` 本身。

**回调端点的应答必须是平台自己的协议格式**，不能用本系统的 `ApiResult`：
微信认 `{"code":"SUCCESS"}`、支付宝认纯文本 `success`。
给它们一个 `{"code":0,...}`，平台只会当作处理失败并一直重推，而重推依然失败。
所以这两个 Controller 的方法体不是「一行 return」的标准写法，
而是各自 try/catch 把异常翻译成平台协议。

**应答规则**（写在这里是因为答辩会问）：

| 情形 | 应答 | 理由 |
| --- | --- | --- |
| 处理成功 / 重复回调 / 单号不存在 | 成功 | 重推无意义 |
| 金额不符 / 状态冲突 / 验签失败 | 失败 + `error` 日志 | 让平台持续重推，同时引起人工注意 |

**幂等有四道**：状态预检 → 条件 UPDATE 的受影响行数 →
用户累计消费用相对更新 → 商户订单号上的唯一索引。

**凭证路径的幂等另有两条**：

- **提交靠唯一索引**（`uk_target`：一个收款目标只有一条凭证）。
  写入走 `INSERT ... ON DUPLICATE KEY UPDATE` 一条原子语句 ——
  手机上连点两下提交时，两次请求会同时走到「查不到凭证 → 插入」那一支，
  交给数据库处理就不存在竞态：第二次走 UPDATE 分支，
  而落账那一步命中状态守卫返回 0 行，整体表现为幂等成功
- **复核靠状态守卫**（`AND verify_status = 'SUBMITTED'`）。
  两个管理员同时点「确认」时只有一个能改成功，另一个拿到 0 行并收到
  「这条凭证已被处理过」。比「先查状态再更新」可靠 ——
  查与更新之间有竞态窗口，而复核是资金结论，重复处理不能当成成功悄悄放过

**演示线上通道**：前端调 `POST /api/payments` 拿到非空的 `mockPayUrl`
即知当前处于模拟模式，于是弹出自己的模拟收银台，由它调
`POST /api/payments/mock/pay`。该接口**需要登录并校验支付单归属** ——
少了这一步，任何登录用户都能把别人的订单标记成已支付。
演示三条通道时把页面上的通道开关各拨一次即可，不必真的准备
微信与支付宝两个浏览器环境。

**演示扫码转账**（投产时的主路径）：后台「收款码」页传一张收款码图片，
用户端走「去支付 → 扫码 → 传截图」，再回后台「待复核」列表里核对。
几个值得演示的分支：把截图路径改成别人的图（被路径校验挡下）、
填一个已被别的凭证用过的流水号（两条一起被标红并排到列表最前）、
以及「先交付后复核」那类订单在复核不通过时后台如何把它标出来。

**演示异常分支**（改配置后重启即可复现，不必等真实条件）：

| 配置项 | 设为 | 复现的现象 |
| --- | --- | --- |
| `uspace.payment.mock.failure-rate` | `0.3` | 发起支付时返回 502 |
| `uspace.payment.mock.notify-drop-rate` | `1` | 钱付了、回调没到，订单停在待支付；调一次查单接口就补上 |
| `uspace.order.passcode-valid-duration` | `20s` | 门锁密码到期与续期（配合「查看密码」按钮） |

### 线上通道的接入门槛（将来有资质时）

三条线上通道的资质要求不同，真要接入时也不必同时开通：

| 通道       | 主要门槛                                                        |
| -------- | ----------------------------------------------------------- |
| 微信 JSAPI | 门槛最高：微信支付商户号 + **已认证的服务号** + openid + 网页授权域名 + 备案域名 + HTTPS |
| 微信 H5 支付 | 商户号 + **单独申请 H5 支付权限** + 备案域名 + 全链路 HTTPS                   |
| 支付宝 WAP  | **企业支付宝账号**（个人账号不具备手机网站支付能力）                                |

共同点：**需要企业或个体工商户主体，个人主体办不下来**。

**这正是扫码转账成为投产方案的原因**（见本章第一节）。三条通道的实现均已就绪，
届时改两个配置项即可启用、不必改代码 —— 但**那时扫码转账是否保留、
保留多久，是一个经营决策而非技术决策**，不在本文档的范围内。

**两条要提前知道的约束：**

- **合规** —— 个人静态收款码用于经营性收款受监管限制。
  这是当前方案已知的固有代价：本店的规模与形态下可以接受，
  但**规模化运营前需要重新评估** —— 那时该考虑的是转成商户号收款，
  而不是把这条路径继续放大
- **类目限制** —— 经营内容涉及棋牌类时，支付通道可能要求额外资质。
  这属于经营策略问题，技术上无法规避

### 经营模式与接口预留

当前按**单店自营**设计：一个运营方、一个微信支付商户号，不需要分账。

但订单与支付接口**预留 `merchantId` 字段（可空）** ——
将来若扩展为平台模式（多商家入驻 + 分账），需改用服务商模式并引入分账能力，
届时**无需改动表结构与接口签名**。

### 代码组织

支付是**模块 8 订单管理**的组成部分，不新增业务包 ——
12 个业务包与论文十二章一一对应，不应因支付而破坏这一对应关系。
支付相关代码组织在 `order` 包内。

**四类收款共用这一个入口**，各自只提供一个「支付目标处理器」：

| 收款 | 目标类型 | 处理器住在哪 | 付款成功后除了改状态还做什么 |
|---|---|---|---|
| 房间使用费 | `ORDER` | `order` 包 | 记入 `sys_user.order_paid` |
| 包场费 | `BOOKING` | `order` 包 | 生成邀请令牌、产生排他性 |
| 月卡 | `MONTHLY_CARD` | `order` 包 | 往卡表插一张生效中的卡 |
| 商品 | `PRODUCT` | `order` 包 | 条件 UPDATE 扣减库存 |

处理器要回答三个问题，**都是接口方法**：

| 方法 | 回答什么 |
| --- | --- |
| `type()` | 本处理器负责哪一类收款 |
| `paidCategory()` | 这笔钱算哪一类累计消费（`order_paid` 还是 `card_paid`） |
| `deliverOnSubmit()` | 提交凭证时是否当场交付（见「付款凭证」一节） |

> **刻意都声明成抽象方法，而不是给 DTO 加一个可空字段、或给个默认值**：
> 漏实现会编译不过；而漏设字段、漏覆盖默认值只会在运行期静默走另一条路 ——
> 卡费被记进 `order_paid`、或者一笔本该当场交付的钱被当成「等复核」，
> 两种情况都不报任何错。
>
> `supportsChannel()` 是同一个钩子家族里唯一带默认实现的，因为四个处理器
> 当前都受理全部通道。它留着的理由是守着一类真实发生过的故障：
> 人工核销接口曾经是订单专用的，月卡与商品各覆写它挡掉传截图通道 ——
> 少了那道守卫，用户对月卡选「传截图」会拿到一个没有任何支付参数的「成功」，
> 卡永远停在待支付，表现为「买不了卡」且线上零报错。
> 凭证流程建成后「传截图」对四类收款都成立了，覆写因此全部删掉。

### 撤销与退款（2026-09-30 新增）

包场付过款之后要取消，就不能只是「取消」了 —— 钱得退回去。这件事有两个独立的判断。

**一、钱怎么退**（`refundMode`）：

| 方式 | 适用 | 做什么 |
| --- | --- | --- |
| `MANUAL` 人工退 | 顾客当初是传转账截图核销的；商户号还没开通退款权限 | 管理员线下把钱转给顾客，后台只登记这件事 |
| `ONLINE` 原路退回 | 顾客当初走的是线上通道 | 调支付平台的退款接口，钱沿原通道退回，平台侧留有凭证 |

两种都要有，因为**线上退款不是随时能用的**：扫码转账来的钱根本没经过支付平台，
没有可退的流水；新开的商户号也未必立刻有退款权限。只做线上，这两种情况就没有出路；
只做人工，「垫钱 + 手工记账」就成了常态。

> ⚠️ **投产时实际只有 `MANUAL` 这一条可用** —— 扫码转账是唯一的收款方式，
> 那笔钱根本没经过支付平台。`ONLINE` 是给将来接入线上通道预留的。

**二、先占位还是先退钱** —— 这才是这一段真正的要点：

```
先占位（采用）：PAID ──把状态翻成 REFUNDED──> 调平台退款 ──失败则回滚成 PAID
先退钱（否决）：PAID ──调平台退款──> 把状态翻成 REFUNDED
```

按直觉第二种更顺（钱到手了再记账），但它有一个致命窗口：
**两个管理员同时点撤销，两笔退款请求都会到达平台 —— 钱退两次，而本地只记一次。**
第一种则是先用一条带 `WHERE status = 'PAID'` 的 SQL 抢占（并发时只有一个能成功），
抢到的那个才去调平台。代价是有一个几百毫秒的窗口，状态显示「已退款」而钱还没到；
如果失败会当场回滚状态并报错。

**为什么接受这个代价**：状态写着已退款、钱却没出去，管理员会以为事情办完了，
顾客却一直没收到钱 —— 而账面上看一切都是对的；反过来（钱退了、状态还是已付款）
至少一眼看得出来，也好补。**宁可退不成，也不能记成退成了。**

两条附带的设计：

- **退款单号是确定性的**（由包场单号派生，`BK...` → `RF...`）。失败后重试用的还是
  同一个单号，而支付平台**按商户退款单号做幂等** —— 重试落在「同一笔退款」上，
  而不是变成第二笔。随机单号会让每次重试都成为一笔新的退款请求，那正是要防的事
- **已退款（`REFUNDED`）与已取消（`CANCELLED`）是两个状态**：一个说的是「这单没成」，
  一个说的是「钱收过又退回去了」。对账时这是两回事，合成一个就分不清那场有没有
  产生过资金流水。撤销之后**时段重新释放**，可以再排给别人；邀请令牌也随之失效

四个处理器**全部住在 `order` 包**，虽然它们操作的是四张不同模块的表 ——
依赖方向因此固定为单向的 `order → 业务包`，不会形成包级循环。
加一类收款只需新增一个实现类，回调、验签、幂等一行都不用改。

### 凭证被驳回之后（2026-10-04 新增）

订单与商品是**「先交付后复核」**—— 用户一提交付款截图，订单当场转成「已支付」、
商品当场扣库存。管理员事后驳回意味着「这笔钱我不认」，而目标却还停在已支付上，
于是那笔单子成了一个**死结**：用户既不能再付（系统认为不需要）、
也不能重交凭证，管理员那边也没有重开复核的入口。

补法是**三件事一起做**：

| 做什么 | 落在哪 |
|---|---|
| **退回交付** | 订单标成 `REJECTED`（凭证未通过）并清掉支付时间、流水号等四列；商品退回购买单 |
| **冲减累计消费** | 已经记上的那笔消费减回去 —— 这笔钱系统不再认了 |
| **通知本人** | 首页提醒条 + 群里 @ 他本人 |

退完之后目标回到待支付，用户**重新上传走的就是正常的待支付路径** ——
不必为「已支付 + 已驳回」另开一条通道。

**两个刻意的例外，都是为了让账别说谎：**

**一、商品不还库存。** 无人值守店里没有店员，**付了钱自己取** ——
用户提交完凭证的那一刻，货很可能已经从货架上拿走了。而管理员复核往往是
**一两天后**的事（他不会守着凭证看）。这时候把库存加回去，系统里显示「货还在」，
实际上早就没了。**账实不符比少记一件难查得多**，货与账对不上的部分由运营线下处置。

**二、连带恢复欠费拦截。** 标成 `REJECTED` 之后，那笔未结清的单子会挡住他开新单
（下单前的欠费校验查的正是这个状态）。这**不是副作用，是刻意留的** ——
有被驳回的账挂在身上，他就是潜在的欠费者，得先处理掉再进店。

> ⚠️ **提醒文案里必须有一句「已经付过款的话，不要重复支付」**：
> 驳回把订单退回了待支付，用户端看到的是「待支付 ¥8.00」—— 而他明明付过。
> 不说这一句，他很可能再扫一次码，**真的付第二遍**，
> 而那笔多余的款子退起来比提醒一句麻烦得多。

### 对账（2026-09-30 新增）

前面几节解决的是**「这一笔钱到没到账」**。这一节解决的是另一件事：
**「这一天到底收到了多少，跟系统里记的对不对得上」。**

管理员从微信 App 或支付宝 App 导出账单（微信是 xlsx、支付宝是 CSV），
上传到系统；系统把账单里的每一笔收款与系统内的付款凭证勾稽一遍，
把对不上的地方列出来。**目标是把他的工作量从「逐条看 100%」降到「只看差异」。**

这不是锦上添花的功能。**「对账困难」是扫码转账这个方案真正付出的代价** ——
钱没有走系统，系统里只有顾客自己说的「我付了」和管理员看过的截图。
账单是唯一的外部事实来源，不把它与系统对一遍，这套信任制就少了一道校验。

#### 先看总账：这笔账对不对得平（2026-10-04 新增）

打开一个批次，页面顶上先给一个结论 —— **账单里每一笔钱都有凭证认领吗**：

```
✓ 账已对平
账单收款   3 笔 · ¥6.09
已认领     3 笔 · ¥6.09
未认领     0 笔 · ¥0.00
```

**对平了就可以走人，不必再翻下面的逐笔差异。** 这不是偷懒：
逐笔差异永远有杂音 —— OCR 读错一位、顾客当天玩完隔天才想起来传截图 ——
拿它们判断「这个月钱少没少」，等于用人力去消化机器的误差。
而总账只看一件事：**这笔钱在系统里有没有一条有效凭证指着它**，
杂音在这一层全部抵消掉了。

**「未认领」的口径**：系统里**没有一条有效凭证**指着这笔钱。具体是两类 ——

- `BILL_ONLY`：一条凭证都没有
- `REJECTED_IN_BILL`：有凭证指着它，但那条被驳回了（不算数）

⚠️ **金额不符（`AMOUNT_MISMATCH`）与重复认领（`DUPLICATE_CLAIM`）不算未认领。**
那两类钱确实到了、也有凭证指着它，只是有疑点 —— 它们仍然进差异列表，
但不拉低总账。混进来的话，「差 2 元」会被报成「有 8 元没收到」，
而管理员会据此去找一笔并不存在的账。

> **为什么不用「账单合计 − 已匹配金额」现算。** 这两个数口径不同：
> 账单合计是**全部**的，而已匹配金额只是**本批次**认领的。
> 重传同一份账单、或者月中月底各查一次（导出的区间有重叠）时，
> 被跳过的那些笔已经在上一个批次里认领过了，现算会让差额虚高 ——
> 明明全对上了，页面却报「差额 6.09 元」。所以它必须在匹配时算准、存下来。
>
> 也**不能从差异表反推**：差异在写入前会去重（同一处不一致只报一次），
> 差异条数因此不等于实际笔数，拿它算差额会少算。

> 早期建的批次没有这个数据，页面**不显示**总账块 —— 那两列是可空的，
> `NULL` 表示「建于本功能之前、没统计过」，与「统计过、结果是 0」是两回事。

#### 六类差异

| 类型 | 含义 | 处置动作 |
| --- | --- | --- |
| `REJECTED_IN_BILL` | 账单收到了钱，而系统里那条凭证**被驳回了** | 回去改那条凭证的复核结论 |
| `DUPLICATE_CLAIM` | 同一笔账单被多条凭证认领 | 查是不是同一张截图用了两次 |
| `PROOF_ONLY` | 系统有凭证、账单里找不到这笔钱 | 找钱：这笔到底到账没有 |
| `AMOUNT_MISMATCH` | 单号对上了，金额对不上 | 查实际收到了多少 |
| `BILL_ONLY` | 账单里有这笔钱，系统里**任何**凭证都没认领 | 找顾客：钱到了，但没人提交凭证 |
| `NO_PAYMENT_NO` | 凭证没填流水号，无法对账 | 联系顾客补单号，或者不处理 |

**这个顺序就是优先级**，后台列表按它排。两条设计理由值得写下来：

**为什么 `REJECTED_IN_BILL` 要单开一类，而且排在最前。**
它的含义不是「可疑」，而是**「系统当前的结论与事实相反」** —— 一个已知的错误结论，
比「疑似作弊」更该先处理。并进 `BILL_ONLY` 的话它会淹在几十条
「顾客还没交凭证」里被错过，而两者的处置动作恰好相反：一个要去找钱，一个要去找人。

**为什么 `NO_PAYMENT_NO` 与 `PROOF_ONLY` 必须分开。**
流水号是**选填**的（这一节前面写过：「选填，但强烈建议填」）。
把它们合成一类，等于把「用户没填」说成「用户可能骗钱」——
那是在没有任何证据的情况下指控顾客。

#### 三条不做的事，以及为什么

**一、不做「先预览再确认」，一次上传就是对一次账。**

对账的副作用面极小：它**不改任何业务状态** —— 不碰订单、不碰凭证的复核结论、
不扣库存。传错一份「已经对过的」账单，系统走的是「已被认领」那一支、零差异；
传错一份「日期不对的」，可能产生几条「凭证无对应账单」，而那一类**不会写回任何东西**。

而两步方案要引入批次状态、临时文件过期清理、防重复确认、处理「确认时文件已被清掉」——
为了一个小概率的误操作付这么多复杂度，不值得。降险靠的是另外两条：
**上传完直接跳进详情页**，以及**列表上把「未处理差异数」做成显眼列**
（传错文件产生的那种批次，就是一屏差异、一条都没处理，一眼看得出来）。

**二、不做撤销批次。**

批次与差异都是 append-only 的（与付款凭证同一条纪律）。撤销会引出
「差异要不要一起删」的问题，删了就没有审计痕迹了 —— 而对账记录的价值恰恰在于
**它是「当时是这么对出来的」这个事实的留档**。传错文件的后果只是多一条批次
与少量差异，比引入删除语义划算。

**三、不做任何反向操作。**

差异列表里只有「标记已处理 + 备注」一个动作，它**不改动任何业务数据** ——
不改订单状态、不代提交凭证、不撤批次。六类差异的处置动作各不相同，
但没有一个该由这一页代劳，理由与本项目把 QQ 机器人限制在「不碰资金」的范围内、
把订单的人工核销接口删掉是同一条：**资金动作的入口越少越好**。

备注是**选填**的，这一点与凭证驳回的原因（必填）刻意相反：
驳回原因要展示给**顾客**，空着的话他反复重交也猜不出哪里不对；
而对账备注是管理员**写给自己的备忘**。强制填的后果很具体 ——
他会对几十条同类差异逐个打上「已处理」三个字，然后这个功能就没人用了。

#### 账单文件不能落在公开目录下

**这是整个功能里唯一一处安全约束。**

`/uploads/**` 在 `SecurityConfig.PUBLIC_PATHS` 里是**匿名可访问**的 ——
那是必须的，因为用户上传的头像与截图要用 `<img src>` 加载，
而浏览器不会为图片请求带上 `Authorization` 头。

但账单里含**全部交易对手、备注、金额与时间**，是本店最敏感的经营数据。
落在那里等于挂在公网上。

所以账单走一个独立的目录（`uspace.reconcile.bill-dir`），
**不注册静态资源映射、不进 `PUBLIC_PATHS`**，只能通过带鉴权的接口下载。
应用启动时会比较这两个目录，**重叠就拒绝启动** ——
与「`JWT_SECRET` 未设置拒绝启动」同源：配置写错不会有任何报错，
只会悄悄地把经营数据公开出去，而这种事没有任何人会注意到。

> 顺带一提，页面上点「下载原文件」也**不能**用 `<a href>` 直接指向那个接口 ——
> 那样不会带上 `Authorization` 头，拿到的是 401。前端走的是 blob 下载。

#### 匹配怎么做的

**匹配键是交易单号**，两边都归一化之后比对（去掉空白、全角转半角、转大写）——
用户手抄单号时常带空格，而肉眼看上去跟正确的一模一样。

系统侧参与比对的凭证取自一个**时间窗口**：账单里最早与最晚的交易时间，
往前放宽 1 天、往后放宽 2 天。两端不对称是刻意的 ——
下界覆盖「先传图后付款」与时钟漂移，上界覆盖**「当天玩完忘了传、隔天才想起来」**。

窗口的起止会存进批次表，页面上也显示出来。这是为了回答一个问题：
**「为什么这条凭证没被算进来」** —— 那笔账过去之后，光看一条批次记录是推不回去的。

**候选凭证整批取到内存，在代码里分三组**：可匹配的、已被之前批次认领的、被驳回的。
这一条看着啰嗦，但它是整个功能里最容易写错的地方 ——

> 把「跳过已经对过的凭证」写进 SQL 是个很自然的优化，但那样会丢掉
> **「这个单号已经被之前的批次认领过」**这个信息。于是重传同一份账单时，
> 账单里每一笔都找不到「在等的」凭证，全部变成「账单无对应凭证」——
> **一屏假差异，管理员立刻就不看了**。而且这个错误在单元测试里发现不了：
> 假 Mapper 会照着实现写，两边一起错就一起对。

重传同一份账单因此是**幂等**的：已经对过的跳过、已经处理过的差异不重复记，
结果是一条安静的「匹配 0 笔、跳过 N 笔、0 条差异」。
批次上记着「跳过了多少笔」，就是为了让这句话有据可依 ——
没有那两个数字，管理员会以为系统坏了。

#### 三种账单格式

| 格式 | 来源 | 特点 |
| --- | --- | --- |
| 微信 | App 里导出 | **xlsx**（本质是 zip + 一堆 XML） |
| 支付宝 | 导出为 CSV | 无 BOM 的 **GBK** 编码 |
| 系统标准模板 | 管理员手工整理 | 六列，是前两者都读不出来时的退路 |

**读取层与解析层是分开的。** 读取层只管「文件怎么变成格子」（xlsx 走 zip + XML、
CSV 走编码判定 + 切分），产出一律是「行 × 列」的字符串；解析层只管
「哪些格子有意义」，**完全不知道文件原本是表格还是文本**。

两层各有三个必须踩对的坑，都写在代码注释里了，这里只点出两个最危险的：

- **xlsx 里的空单元格是被省略的**，XML 里根本没有那个元素，
  所以必须解析单元格的 `r="B2"` 属性来定位列，**数数是错的**。
  漏了这一条的后果是金额与单号整体串位，而且不报任何错
- **CSV 必须用字符级状态机切，不能 `split(",")`**：账单的「商品」列几乎必然含逗号
  （`游戏币,A 套餐`），用 split 会让每一行的列整体串位——**而行数完全正常**

三个格式的解析器**共用同一份逻辑**（在抽象基类里），子类只提供「列叫什么名字、
哪些取值算收入、哪些算成功、哪些交易类型算本店收款」这四组数据，
而且**不许写 `if`、不许写循环**。
让三个实现各写一份解析，就是三份复制粘贴，而它的失败方式是
「微信的解析对了、支付宝的少认了一列」——同样不报错。

#### 只认「二维码收款」，其余一概不算本店收款

**这一条是拿到真实账单之后才补上的，而它必须补。**

个人收款账号导出的账单里混着大量与本店无关的往来。2026-09-30 实测的那份
40 笔账单是这样的：

| 交易类型 | 笔数 | 金额 | 是什么 |
| --- | --- | --- | --- |
| `二维码收款` | 3 | 6.09 元 | **只有这些是本店收的钱** |
| `转账` | 27 | 46407.35 元 | 个人往来（房租、家人、朋友还钱） |
| `微信红包` | 1 | 10.00 元 | 同上 |
| 各种「-退款」 | 9 | 1340.80 元 | 本人在别处消费的退款 |

后三类每一笔的**「收/支」都是「收入」、状态都是「已存入零钱」这类成功态** ——
看单行根本分不出来，只能靠交易类型。不筛的话，解出来的 31 条记录里 28 条是假的，
每一笔都找不到对应凭证，结果是**一屏「账单有、系统无」的假差异**，
而管理员看一屏假的，第二次就不看了。

选**白名单**而不是黑名单，理由与「状态必须精确匹配」是同一条：
平台哪天新增一个交易类型，白名单默认「不算本店收款」= **少算**
（页面上看得见「未参与对账 N 笔」），黑名单默认「算」= **多算**
（凭空多一笔收款，而没有任何人会注意到）。

被挡下的行**计进 `billExcludedCount`**（连同方向不是「收入」的那些），
并与 `billCount` 并列显示在批次上：一份账单上写着收了多少、系统只认了多少，
差额全在这里。**没有这个数，管理员只看得到「账单 3 笔」，
连那个文件原本有 40 行都不知道** —— 少算看得见，是这一层一路守着的纪律。

> ✅ **真实账单样本已按个人零钱账户那份校准**（2026-09-30）。实测确认了四件事：
> 表头在第 18 行（前面 17 行说明文字）；**空行在 xlsx 的 XML 里被整个省略**；
> 交易时间是 **Excel 日期序列号**而不是文本；金额是**纯数字**，
> `¥#,##0.00` 只是样式表里的显示格式。表头与别名表逐字一致。
>
> ⚠️ **换成经营账户后可能又不一样**，那时要再校准一轮。两条失败路径都是看得见的：
> 表头变了会在报错里原样带出来，只是交易类型变了会在「一条记录都没有」的报错里
> 把账单里出现过的类型列出来 —— 照着往白名单补一行即可。
> 这是刻意的设计：只说一句「格式不对」，管理员那边除了反复重试没有别的动作可做。

#### 页面上在哪

运营后台「收款」页的**第三个 tab「对账」**，内部再分「批次列表 ↔ 批次详情」两个视图。
这一页因此承担了收银台工作的三个层次：**待复核**（逐条看截图）、
**对账**（一整天与账单勾稽）、**收款码**（设置项）。

## 十、QQ 机器人接入设计

### 定位：只读为主 + 三条受限写指令（2026-09-28 定，2026-10-04 修订）

**QQ 机器人以「播报 + 查询」为主体，另有两条受限的写指令。**
写指令的边界写死在三处：受配置项控制、**播报关掉时不执行**、
**绝不触碰任何资金动作**（付款始终只在网页端发生）。

| 方向              | 内容                                                   |
| --------------- | ---------------------------------------------------- |
| **播报**（后端主动推）   | 客户到店 / 离店、在店时长与消费金额、店内当前人数、都有谁、是否月卡、游玩偏好（便于判断设施占用情况）；**新包场生效**与**新公告发布**也会推群（2026-10-04 加）；**商品售出**、**停业与免费时段的新增 / 撤销**、**包场撤销**也各推一条（2026-10-08 加，均不含金额） |
| **查询**（群成员主动发起） | `/在店`（别名 `/看看里面`）、`/包场`、`/营业`、`/价格`、`/菜单`、`/web`、`/看看自己`、`/当前订单`（别名 `/now`）、`/帮助`、`/ping` |
| **写指令**（三条，2026-10-04 加） | `/开门`（建单计时 + 发门锁密码）、`/结账`（停止计时 + 回结算页链接）、`/买个可乐`（下单买商品 + 回付款入口） |

**指令一律要求前缀**：`/` 或 `fw`（`fw开门` 等价于 `/开门`；大小写不敏感、
前缀后可有空格）。没有前缀的一律当闲聊静默 —— 这一条是加写指令时立的规矩，
因为 `/开门` 会**真的建单计费**，群里有人喊一声「开门」绝不能触发它。
唯一带参数的是验证码 `/验证 123456`（注册页提供复制按钮），**纯数字已不再识别**。

「游玩偏好」由**用户自报**（存在 `sys_user.preference`），不靠系统推断 ——
存储设计与理由见第六章。需要留意的是：**偏好是「倾向」，不是「占用事实」**，
群里看到「张三 · 拍拍机」只应作为判断设施占用的参考。

#### 两串密码，两条进门路径

`/开门` 会同时给出两串密码：

- **固定限时密码** —— Web 端「查看密码」可反复查看，并**私聊发一份**；
  有效期覆盖整个订单（可续期，数字不变）。它是**兜底**：
  群里那串被抢先或失效时，本人仍然进得去门
- **一次性密码** —— **只在群里发**，用一次即焚（通通锁的单次密码，
  自生效起 6 小时内可用一次）。它是**快路径**：群里发一下就能进门

两串都在结算时撤销。**每次 `/开门` 都重新取一串一次性密码**，
不复用 —— 判断旧串是否还在（查密码列表或拉开门记录）同样要花一次门锁云调用，
与直接生成成本相同，却多担一份「把已经失效的密码发给站在门口的人」的风险。

#### ⚠️ 一条纪律：执行必有回响（2026-10-04 定）

**凡是被执行的指令，群里必须看到一条消息。** 允许的「没有任何回应」只有两种，
且都不是静默执行：① **确实没调用**（闲聊、未授权群、重复消息、验证码不匹配）；
② **NapCat 挂了**（连接断了，消息发不出去）。

因此每条失败分支都必须回话，**中间态尤其不能漏** —— 比如
「订单建好了但门锁云取不到密码」：那时人正在被计费，群里静悄悄的话
他只会站在门口等一串永远不来的密码。

#### 群内下单买商品（2026-10-04）

群里可以买店里的东西。两种写法，**都显式写着数量**：

| 写法 | 含义 |
| --- | --- |
| `/买个可乐` | 1 件 —— 量词「个」本身说明了数量 |
| `/买2个可乐` | 2 件（中文数词也认：`/买两个可乐`） |
| `/可乐-2` | 2 件，简写变体 |

**⚠️「只写商品名」这条路刻意没有。** 早先设计成「`/可乐` 就买一件」，
而那意味着**任何带前缀的未知文本都得当商品名查一遍** —— 于是「`/在店铺`」
这种打错的指令会得到一句「没有叫「在店铺」的商品」，而群里天天有人在打字。
改成关键词开头之后，指令重新是个**封闭集合**：不认识就说「没认出这条指令」，
一个字都不会被错怪成商品。同一天还删掉了 `/买单` 这个别名 ——
它与商品下单共用「买」字开头，两条语法摆在一起容易被误用
（看到 `/买单` 能结账，就会以为 `/买可乐` 也能下单）。

**商品名必须唯一**，所以 `biz_product` 上加了唯一键 `uk_name`：
名字一旦能重复，「`/买个可乐`」到底是哪一件就只能靠猜，而猜错的代价是
**给顾客下错单、扣错库存**，当场还没人看得出来。
⚠️ 那条键**不含 `deleted`**（与 `uk_username`、`uk_qq` 同源），
逻辑删除过的名字会被一直占着；查重也因此必须与它<b>同一口径</b> ——
否则会出现「后台说名字可用、保存时撞唯一键」，用户拿到一句 500。

**数量范围（1~99）由商品模块判**，不在解析器里判 —— 放在那里的话，
「单次最多买 99 件」这句提示就没有地方可写了。另外，群里的下单
**绕过了 Web 层的 Bean Validation**（那些注解只作用于 Controller 入参），
所以 `ProductService#createOrder` 里补了一道范围校验：少了它，
`/买0个可乐` 会建出一笔 0 元的单，而负数量会算出一笔**负金额**的订单。

下单成功后同样**撑起「等他发付款截图」那道闸**，付款入口群里与网页端各给一份
（网页端在「商品订单」页）。那条路与房间订单**共用同一套凭证提交与复核** ——
见下一节。

#### 群内传付款截图（2026-10-04）

**`/结账`（房间计时）或 `/买个可乐`（商品）之后，这个人发的下一张图**
就当付款截图收下 —— 由后端取图、识别、提交凭证。
**付款本身仍然不在群里发生**，这条路交的只是**凭证**。

**为什么值得开这条路**：扫码转账要在网页端上传截图，而顾客付款时人就在群里
（`/结账` 也是从群里发的），为了传张图再打开一次网页是白费一道手续。

**⚠️ 为什么必须有「等一张图」这道闸**：绝不能让「群里发图」直接等于「提交付款凭证」。
群里的图绝大多数是闲聊 —— 表情包、随手拍的照、发错群 —— 而订单与商品的凭证是
**提交即落账**的（订单当场转已支付、商品当场扣库存）。任何一张无关的图被当成凭证，
就是把一笔**没收到钱**的账标成已收，事后只能靠管理员人工发现。
**那两条写指令就是那道闸**：它们同时说明「这个人有意传凭证」与「这笔账正等着付」。

**闸认的是「哪一类收款 + 那笔的主键」**，所以它同时管房间订单与商品，
而且加第三类收款时本机制一行都不用改 —— 状态的回查交给支付模块既有的
收款处理器（四类收款各有一个）。**同一时刻只等一张图**：连下两单时以最近那笔为准。

**三道失效条件：**

| 条件 | 处置 |
| --- | --- |
| **网页端付过了** | 每次受理前回查目标状态，不再是待支付就丢弃。**不靠通知，靠惰性校验** |
| **等了太久** | 超过 5 分钟作废，并回一句说明（太短来不及翻相册，太长会把「几分钟前的表情包」误收） |
| **一次发了多张** | 只认第一张，不做「多图 = 多张凭证」这种猜测 |

这条链路**与网页端走的是同一套服务**（上传落盘与凭证提交都是既有组件），
所以两条路不会分叉出两套规则；图片落盘也共用公共层的同一个组件 ——
文件头判类型、路径越界防御那些安全代码**不能有第二份**。

> **静默只允许出现在这一处。** 没在等的时候，群里发来的图**一个字都不回** ——
> 每张图都答一句「这不是付款截图」只会把群刷爆。除此之外，
> 这条路每一条分支都必须有回话（图取不到、订单找不到、提交失败各有一句），
> 见上面那条「执行必有回响」。

**⚠️ 两个 ID 不是一回事（落地当天真踩到过）**：群事件里唯一给得出的身份是
**QQ 号**，而查订单与提交凭证要的是 **`sys_user.id`**。等待表一度一边用后者写、
一边用前者查，两边永远对不上 —— 表现是「`/结账` 之后发图**毫无反应**」，
而且**一行日志都没有**（查不到就走「没在等」的静默分支）。
约定是：**等待表以 QQ 号为键**，`sys_user.id` 随记录一起存着。
API 那一侧也据此收口 —— 登记方法收的是**用户实体**而不是两个长整型，
免得「两个同类型的参数写反了」再次编译通过。

**`/结账` 有两种情形**：还在计时就停表出账；**已经停过表**（网页端结的、
或截图等超时了）就把待付金额与入口重新给一遍，并**重新撑起等图那道闸**。
少了后一半，「截图超时 → 重新发一次 `/结账`」那句提示就成了**死胡同** ——
那时订单已不是「进行中」，按原分支走只会回「你没有在计时的订单」，
用户再发多少张图都不会有反应。

> 图片是后端按 NapCat 给的地址**主动取回**的（同机 HTTP）。
> 取不到（地址失效、超限、NapCat 没在跑）时回一句「这张图没取到」——
> 仍然是回话，不是静默。

#### 为什么当初全只读、现在放回两条

原定「全只读」的三条理由，逐条看现在是否还成立：

- ~~**支付流水统计会乱**~~ —— **已不成立**：`/结账` 只停表出账、回一条结算页链接，
  **付款仍然只在网页端完成**，支付方式 / 流水号 / 时刻照旧由 Web 侧写入，对账不受影响
- ~~**资金动作不该由群消息触发**~~ —— **仍然成立**，所以两条写指令**都不碰钱**：
  它们产生的只是「应收」与一条去付款的链接，资金动作一步都没挪进群里
- **播报恰恰是它的长处** —— 群是常驻的、推送免费、用户不必打开任何界面。
  这是 Web 端做不到的，把它用在这里收益最大（这条从未变过）

**由此新增的一条约束**：**播报关掉时不执行写指令** ——
群里的公示正是这两条指令敢放进群里的依据，看不到播报就等于一次没人看见的账。

> 与「先离场后付款」的信任制仍然配套：机器人播报「谁离店了、该付多少」，
> 付款动作本身始终在 Web 端完成 —— 它在多帮顾客做「开始计时」与「停止计时」
> 两件事，但**始终不是支付的入口**。

### 数据流

NapCat 是**协议端**，只负责把 QQ 原始事件推给后端、接受后端调用的 Action
（如 `send_group_msg`）。它**不解析** `/在店` 这类业务指令 ——
`raw_message` 原样送过来，解析是后端的事。

**查询链路：**

```
群消息 "/在店"
   ↓
NapCat（OneBot v11 协议端）
   ↓  反向 WebSocket
Spring Boot 的 qqbot 包 ← 解析指令、鉴权、查询
   ↓  调用 space / order / promotion 等模块的 Service（查询为常态；两条写指令只经订单模块）
   ↓  调用 NapCat 的 send_group_msg Action
群消息 "当前 3 人在店，已玩 2 小时 15 分"
```

**播报链路**（事件驱动，发起方不是群消息而是业务事件）：

```
用户点击开门 / 离场结算（order 模块）
   ↓  发布 Spring 事件
qqbot 包通过 @EventListener 监听
   ↓  查在店状态、组装文案
   ↓  调用 NapCat 的 send_group_msg Action
群消息 "张三已到店，当前 2 人在店"
```

**为什么播报用事件而不是让业务模块直接调用 qqbot**：保持包依赖单向。
业务模块只发布事件，不 import `qqbot` 的任何类；`qqbot` 包主动监听。
编译期 `order` 不认识 `qqbot`，运行时靠事件解耦 ——
将来真要把机器人拆成独立服务，整个包拎出去即可。

### 处理链路的四条硬要求

1. **别把处理堵在连接的 IO 线程上**（2026-10-01 更正）—— 早先写的是
   「收到事件立刻 ack，业务异步处理 —— OneBot 上报有超时，等不到响应会重推」，
   那是 **HTTP 上报模式**的行为：那种模式下服务端要回一个 200，超时平台就重推。
   **反向 WebSocket 下没有 ack 这一步**，NapCat 也不会因为处理慢而重推，
   帧只是排队、不会丢。顾虑本身没错（一条慢查询会拖住该连接上的后续事件），
   但理由要换。实现上入站指令是同步处理的（都是一次索引查询），
   真正挪出去异步的是播报 —— 它在事务提交后跑在用户的请求线程上
2. **幂等** —— 用 `message_id` 去重。反向连接下 NapCat 不会因为处理慢而重推，
   但断线重连的窗口、人工重放都仍可能让同一条消息回来两次。
   ⚠️ **加了写指令之后，这条从「体验问题」重新变回「正确性问题」**：
   `/开门` 重放两次就是两笔白扣的钱。真正的防线在订单模块
   （上一单没结清不给开新单），但去重是更前面的一道 —— 而且它顺带挡住刷屏
3. **来源校验** —— 校验 `access_token` 并限定 `group_id` 白名单，
   否则任何人都能在任意群里查本店的经营数据（在店人数、消费金额属于经营信息，
   不该外泄）

**另加一条（播报这条链路带来的要求）：**

4. **播报内容按群分级** —— 群消息对所有群成员可见。**消费金额**只推到
   **店主 / 管理员群**；顾客群推到店离店、在店人数，以及**谁有月卡**这类不含金额的概况。
   ⚠️ **月卡状态不再算隐私（2026-09-30 改）**：它只说明「这人今天免单」，
   不含任何金额，而同店顾客本来就互相看得见 —— Web 端的在店名册
   （`GET /api/store/instore`）也把它给已登录用户看。原先这条写的是
   「消费金额、月卡状态这类信息只推到店主群」，与在店名册的做法正好相反；
   **两份文档写着相互矛盾的约定，比哪一条对更危险**，所以改掉的是这条原则

### 不采用 NapCat 插件写业务的原因

NapCat 自带插件机制（在 `plugin_onmessage` 里判断 `raw_message` 再回复），
写关键词回复没问题。但那是跑在 NapCat 进程里的 **JavaScript** ——
用它实现查询会把逻辑劈成两半、绕开 Service 与模块 2 的权限约束、
并绕开模块 12 的系统日志。插件只适合纯展示类小功能。

### 实现落地（2026-10-01，2026-10-04 扩充写指令与群内传图）

**接入方式**：反向 WebSocket（NapCat 作客户端主动连后端），端点 `/onebot/v11/ws`。
握手阶段校验 `Authorization: Bearer <令牌>`，令牌不对直接拒绝连接；
URL 上的 `access_token` 查询参数作为兜底（规范允许，但优先用请求头）。
⚠️ 比对时两边都不裁剪空白 —— 这是协议明确要求的，顺手加 `trim()` 会让
「配置里带了个尾空格」变成永远连不上。

**为什么选反向而不是正向**：正向要后端自己配置 NapCat 的地址、自己管重连；
反向则由 NapCat 负责重连，后端只需开一个端点。收事件与发消息共用这一条连接。

**指令与它们的落点**（整条精确匹配，不做「包含关键词」；一律要带 `/` 或 `fw` 前缀）：

| 指令 | 落点 |
| --- | --- |
| `/ping` | 连通性自检，回 `pong`。它把「链路通不通」与「业务逻辑对不对」分开 —— 不回就说明问题在连接 / 鉴权 / 白名单那几环 |
| `/在店` | 在店名册（复用 Web 端同一个 `InstoreService`，所以两处口径必然一致，且**不含任何金额**）|
| `/包场` `/营业` `/价格` `/看看自己` `/菜单` | 各自复用 `space` / `billing` / `order` / `product` 的既有 Service —— 群里报的数与网页上看到的必然一致 |
| `/web` `/网址` | 网页端地址，原文取自 `uspace.web.base-url`（与包场邀请链接同一项，**换域名只动那一处**）。⚠️ 本机开发时把它写成局域网地址，留 `localhost` 的话别人点开只会看到自己的手机 |
| `/当前订单` `/now` | **正在计时的这一单现在多少钱** —— 报进场时刻、已玩时长、当前应付、还有多久跳下一档。⚠️ **只看，不停表**：数据源是网页端「结账」点进去那一屏（`OrderPreviewVo`，纯查询、零副作用），想真结账要再发 `/结账`。两个动作分开是为了防「只想看一眼多少钱，结果把表停了」|
| `/帮助` | 指令列表。三条写指令只在**确实可用**时才列出来（列出来却发不动，用户只会以为机器人坏了）|
| `/开门` `/结账` `/买个可乐` `/买2个可乐` `/可乐-2` | 三条受限写指令，只经订单与商品模块，见上 |
| `/验证 123456` | QQ 验证码确认，见下。注册页给的是**整条可复制的指令**，用户不必理解它 |

**文案集中在一处**：所有回复文本由 `QqReplyText` 组装 —— 纯静态、可脱离 Spring 单测。
它守的是一类**不会报错的错**：写错了只会答非所问或把数字说错
（比如 `stripTrailingZeros` 之后忘了 `toPlainString`，群里就会冒出「封顶 4E+1 元」，
而它会一直躺在群聊记录里，直到有人翻到才发现）。

**八个播报时机**（2026-10-04 扩、2026-10-08 再扩）：订单开门成功、结算完成、
**包场生效**、**包场撤销**、**公告发布**、**商品售出**、
**停业新增 / 撤销**、**免费活动新增 / 撤销**。
它们由各业务模块发布 Spring 事件、本模块监听实现，**编译期那些模块完全不认识 qqbot**
（将来拆包时整包拎走即可）。
⚠️ 监听器必须是「事务提交之后」才执行：订单此刻才真正落库可见，
提前跑会播报出「张三到店，当前 0 人在店」这种自相矛盾的话，且不报任何错。

**几条播报各有一条边界**：

- **商品只在「落账」那一刻播**（`ProductPaymentTargetHandler#markPaid`，2026-10-08 加）——
  网页扫码付款（上传付款截图即落账）与线上回调两条路都汇聚在那里，
  所以两种时机天然各播一次、不重不漏。⚠️ **只在库存扣减成功之后播**：
  扣减失败意味着「钱收了但没货」，那一笔已转入人工处理，
  播报它只会给出一个没减过的库存数（商品被删时更是查不到）。
  「还剩多少」报的是**可售量**（库存 − 未支付的待支付单），
  与商城页、`/菜单` 同一口径 —— 报实际库存会造出「群里说还剩 5 件、下单却说卖完了」。
- **包场撤销也播**（`BookingRevokedEvent`，2026-10-08 加）：生效时说过
  「该时段仅限包场人与被邀请者入场」，撤销之后那条消息就成了假消息，
  而群消息不会自己消失。发布点在 `BookingRefundService#revoke`，
  ⚠️ 且它**刻意没有 `@Transactional`**（占位靠 SQL 的状态守卫，不靠事务锁），
  所以那个监听器必须带 `fallbackExecution = true` —— 否则事件在
  「发布时没有事务」的情况下被静默丢弃，表现是「撤销成功、群里一条不播、零报错」。
  退款失败回滚（`revertRefund`）刻意不播：那次撤销没成功，包场仍有效。
- **停业与免费时段都「新增 + 撤销」成对播**（2026-10-08 加）：理由是同一个 ——
  群里那条消息不会自己消失，说过「明天 10:00 不营业」之后撤销不播，
  顾客就照着过期的消息安排行程。两个事件各带一个 `*ChangeAction`
  （`CREATED` / `DELETED`）区分动作；**撤销播报带的是删除前查到的那一份时段**，
  否则没人知道撤的是哪一段。改期（PUT）暂不播，要播时两个枚举各加一个
  `UPDATED` 即可。
- **包场只播已生效的场次**（付款成功、或 0 元场次的建单那一刻）——
  待付款的包场随时可能取消，提前说就成了空头安排。事件因此有**两个发布点**
  （`space` 的 0 元建单、`order` 的付款成功），而事件类住在 `space` 包 ——
  `space → order` 是禁止方向，一个类住这边才能被两处共用。
- **公告手写与自动都播**。自动公告由 `NoticeService#publishAuto` 发布，而它
  **刻意不标 `@Transactional`**（契约是「与调用方同事务」而非「自己开事务」），
  所以公告那个监听器多写了 `fallbackExecution = true` —— 少了它，将来任何在
  事务外调用 `publishAuto` 的模块都会遇到「公告落库成功、群里一条不播、零报错」。
  有事务时它与另外几个监听器完全一样（提交后才跑、回滚不跑）。

这几条播报都**不含金额**（包场播报也不含包场人；与在店名册同一条披露边界），
所有群收到同一份文本。

**与注册的联动**：QQ 号验证是一条**群内往返** ——
注册页取 6 位码 → 用户把它发到群里 → 机器人按「发消息那个人的真实 QQ」查表核对 →
注册时消费掉。机器人是这条链路里唯一能让验证生效的一环，
所以它和注册页必须一起上线（少任何一头，另一端都会变成死路）。

**权益边界**：群消息对所有人可见，所以**播报里的消费金额只推到店主群**；
顾客群收到的是到店 / 离店、在店人数、以及在店名册这类不含金额的概况。
名单里连金额字段都没有 —— 那道边界画在数据对象上，不是靠「记得别说」。

**但「本人自查询」不在这条边界之内**（2026-10-04 明确）：`/看看自己`、`/结账`
以及群内传图的受理回执里**会出现金额**，因为那些都是**本人主动查自己的账**，
与「系统把某人的消费推给全群」是两回事。它由单独一项配置控制
（`self-amount-visible`）——关掉它关掉的是「连本人的金额也不显示」，
**不是**「只显示给店主」，两者各管一边，不要互相推断。

## 十一、编码约定

- **所有代码注释用中文**。文件级注释说明文件用途，类/方法级注释说明参数含义、
  返回值与关键逻辑 —— 代码需用于论文撰写与答辩审阅
- **金额一律用 `BigDecimal` / `DECIMAL`**，禁止用 `double` / `float`。
  浮点运算在金额累加时会产生精度误差
- **时间字段统一存储**，注意与门锁云的时区参数对齐
- **参数错误抛异常，业务失败走返回值**：前者如「游玩偏好格式不对」，
  属于调用方给错了数据，抛 `IllegalArgumentException` 由全局异常处理器转成 400；
  后者如「用户名已被占用」，属于业务规则不接受，用 `BizResult.fail(错误码)` 表达，
  调用方一眼能看出哪些失败是可预期的
- **HTTP 层用 `ApiResult`，Service 层用 `BizResult`**，两者不混用。
  Controller 通过 `ApiResult.of(bizResult)` 一步转换，
  **HTTP 状态码只在这一处决定** —— 不会出现「同一个错误码在不同接口返回不同状态码」的漂移
- 代码按 12 个业务包组织，包内再按职责细分子包
  （如 `dto` 放传输对象、`mock` 放模拟实现、`entity` 放实体、`mapper` 放数据访问接口）
- 另有 `common` 公共层承载统一返回体与错误码、全局异常处理、实体基类与框架配置。
  它**不对应论文的任何章节**，是 12 个业务包共同的地基（见「工程结构」一节）

## 十二、构建与运行

```bash
cd backend

mvn -B -DskipTests compile     # 编译
mvn spring-boot:run            # 启动开发服务（默认 8080）
mvn test                       # 运行全部测试
mvn -B -DskipTests package     # 打包成可执行 jar
```

**前置条件：**

**1. JDK 17 或以上**

**2. MySQL 8.0**，创建数据库并导入表结构：

```bash
mysql -u root -p -e "CREATE DATABASE uspace DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_general_ci;"
mysql -u root -p uspace < docs/sql/schema.sql
```

> ⚠️ `schema.sql` 含 `DROP TABLE IF EXISTS`，可反复执行以重建表结构，
> 但**会清空表中数据**。仅用于开发与演示环境，生产环境请改用增量迁移脚本。

**3. 数据库凭据通过环境变量注入**，不写入配置文件：

```powershell
[Environment]::SetEnvironmentVariable('MYSQL_USER', 'root', 'User')
[Environment]::SetEnvironmentVariable('MYSQL_PASSWORD', '你的密码', 'User')
```

> Windows 下环境变量**只对新启动的进程生效**，设置后需重开终端。
> 若启动时报 `Access denied`，先检查这两个变量是否已生效。

**4. JWT 签名密钥同样通过环境变量注入**：

```powershell
[Environment]::SetEnvironmentVariable('JWT_SECRET', '至少 32 字节的随机字符串', 'User')
```

> 密钥要求**至少 32 字节**（HS256 的强度下限，注意是按**字节**而非字符计算）。
> 未设置或长度不足时，应用会在启动阶段直接报错退出，**不会带着弱密钥继续跑** ——
> 一个「看起来有签名」的弱密钥比明摆着没有签名更危险，因为没人会去怀疑它。
>
> 生成一个够长的随机字符串：
> ```powershell
> -join ((1..48) | ForEach-Object { '{0:x}' -f (Get-Random -Max 16) })
> ```

**关于测试。** 测试分两类：

- **单元测试** —— 不启动 Spring、不连数据库，测业务规则与计算逻辑
  （计费、门锁模拟、JWT 的签发与解析、用户服务的各项校验、认证过滤器的判定）。
  这类测试随 `mvn test` **无条件执行**
- **集成测试** —— 连真实 MySQL，验证只有真库才能确认的东西
  （列名映射、审计字段自动填充、逻辑删除、唯一索引、过滤器链与授权规则）。
  用 `@Transactional` 在每个用例后回滚，**不会在开发库里留下数据**

集成测试带 `@EnabledIfEnvironmentVariable` 门控：**没配置 `MYSQL_PASSWORD` 的机器
（如刚 clone 下来还没配置的环境）会整体跳过，而不是报错失败**。
本机跑 `mvn test` 前请确保 MySQL 正在运行。
