**接口**：

| 方法 | 路径 | 鉴权 |
|---|---|---|
| POST | `/api/user/me/avatar` | 登录（multipart，字段名 `file`） |
| POST | `/api/user/me/banner` | 登录（同上） |
| GET | `/uploads/**` | **匿名**（已加入 `SecurityConfig.PUBLIC_PATHS`） |

**新增错误码**：`UPLOAD_FILE_INVALID`(40001)、`UPLOAD_FILE_TOO_LARGE`(41300)

**文件名**：`{url-prefix}/{avatar|banner}/{用户名}_{用户ID}.{扩展名}`
→ 如 `/uploads/avatar/xiaofeng_12.png`。

> **不分日期目录**（原设计是 `{yyyyMMdd}/{userId}_{UUID}.{ext}`，实现时按用户要求改简）：
> 用户名与 ID 都已唯一，拼起来天然不重名，日期目录起不到去重作用；
> 单店量级下用户数在千级，一个目录放得下。用户名能安全进文件名，
> 是因为注册校验把它限死在 `[a-zA-Z0-9_]{3,20}` —— **换成昵称就不行了**，这条别想当然。

> ⚠️ **文件名固定带来的一个坑，必须记住**：同一用户重传**同一种格式**会落到**同一个路径**上。
> 此时若还按「写完新图就删旧图」去做，**删掉的正是刚写进去的那张** ——
> 用户既没有新图也没有旧图，而接口返回 200 说成功了。
> `ImageUploadService.store` 里那行 `if (!url.equals(oldUrl))` 就是挡它的，
> 只有**扩展名变了**（png → jpg）才真的需要删旧文件。
> 两条用例钉住：`upload_sameFormatTwice_overwritesInPlace`（原地覆盖、文件还在）
> 与 `upload_differentFormat_deletesOldFile`（换格式才删）。

**安全上的四条纪律**（都有对应用例）：

1. **按文件头（magic bytes）判类型，不看 `Content-Type`** —— 后者是客户端说的，能随手伪造
   （JPEG `FF D8 FF`｜PNG `89 50 4E 47 0D 0A 1A 0A`｜WebP `RIFF` + 偏移 8 处 `WEBP`）
2. **文件名完全由服务端生成，原始文件名一个字都不用** —— 路径穿越与 `.jsp` 扩展名同时失效；
   扩展名从 MIME 白名单映射，不从原文件名截取
3. **删旧图前必须 `Path.normalize()` 之后再校验前缀** —— 只比字符串开头的话，
   `/uploads/../etc/passwd` 能通过检查，一次换头像就能删掉任意文件**且不报错**
4. **删旧图失败只记日志，不阻断上传** —— 换头像这件事已经完成了

**`GlobalExceptionHandler` 补了三个分支**（前两个是计划内，第三个是实测发现的）：

| 异常 | 返回 | 为什么必须有 |
|---|---|---|
| `MaxUploadSizeExceededException` | 413 `UPLOAD_FILE_TOO_LARGE` | 不加就落到兜底变 500「服务异常，请稍后重试」，而事实是「你的图太大了」 |
| `HttpMediaTypeNotSupportedException` + `MultipartException` | 400 `PARAM_INVALID` | **实测才发现的缺口**，见下 |
| （已有）`AccessDeniedException` 等 | — | — |

> ⚠️ **第三个分支的来龙去脉值得记一笔，因为它暴露了 MockMvc 的一个盲区**：
> 接口上声明了 `consumes = MULTIPART_FORM_DATA_VALUE`，于是一个**不带请求体、
> 不带 Content-Type 的 POST** 会在映射阶段被 `HttpMediaTypeNotSupportedException`
> 挡下。这个异常原先不在名单里 → 落到兜底 → **500**。
>
> 而**集成测试全绿**，因为 `MockMvc` 的 `multipart()` 构造器**永远**会造出一个合法的
> multipart 请求，走不到「压根不是 multipart」这条路上。是**起真实服务用 `curl` 实测**
> 才把它逮出来的（`HTTP 500`）。
>
> 补分支的同时补了一条用例 `nonMultipartRequest_returns400`，
> 它**刻意用普通的 `post()` 而不是 `multipart()`**，并且**断言具体的提示文案**而不是
> 只断 400 —— 只断状态码的话，它在修复前可能因为别的原因变绿，等于没测。

**三处必须同时改，漏一处功能就是坏的**（这是本节最要紧的一段）：

| 位置 | 作用 | 漏掉的症状 |
|---|---|---|
| `WebMvcConfig`（本次新增） | 把目录映射成 URL | 图片 404，**后端日志里一行都没有** |
| `SecurityConfig.PUBLIC_PATHS` 加 `/uploads/**` | 放行图片路径 | **页面上头像与背景图全裂**，日志里同样看不到 —— 图是 `<img src>` 加载的，浏览器不会为图片请求带 `Authorization` 头 |
| `backend/.gitignore` 加 `uploads/` | 不把用户上传的图提交进仓库 | 仓库体积只增不减 |

**另外两处注释也顺手补了**（都是「两份文档写着相反的话」的隐患）：

- `SecurityConfig` 的 `PUBLIC_PATHS` 注释原先写着「`requestMatchers(String...)` 是精确匹配」，
  容易被后来者读成「这个重载不支持通配符」而不敢写 `/uploads/**`。
  已改写清楚：**字面路径只匹配它自己（没有前缀语义），但 `*` 与 `**` 是支持的**，两件事不矛盾
- 该数组的计数注释（原写「七个」）早已与实际条目数对不上，一并改成按用途列举

### 3.4 在店时长

**建表**（增量执行 + 写回 `schema.sql`，已在开发库建好）：

```sql
ALTER TABLE `biz_order`
  ADD COLUMN `stay_minutes` INT DEFAULT NULL
    COMMENT '在店时长（分钟）= end_time − start_time，【不参与计费】，仅展示与聚合用。'
            '与 day_minutes + night_minutes（计费时长）的区别：前者含包场时段、含宽限那 5 分钟'
  AFTER `end_time`;
```

> ⚠️ **执行这条 DDL 时踩了一个编码坑，值得记一笔**：
> 用 `mysql -e "...− ..."` 把语句写在**命令行参数**里，注释中的 `−`（U+2212）
> 会被 Windows 的命令行编码转换吃掉，**落库变成 `?`**，且不报任何错。
> 核对办法：`SELECT HEX(SUBSTRING(COLUMN_COMMENT, ...))`，正确的字节是 `E2 88 92`。
> 改正的办法是**把 SQL 走 stdin 传进去**（heredoc 或 `< file.sql`），不走命令行参数。
> 项目里 `schema.sql` 一直是文件形式，所以从没碰到过这个问题。

**改动**：`Order` 加 `stayMinutes` 字段 · `OrderMapper` 的 `updateSettlement` 与
`updateAdjustment` 各加一个 `stayMinutes` 参数（`FakeOrderMapper` 的 `applyAmounts`
下标随之整体平移）· `OrderVo` 加 `stayMinutes`（订单列表与详情都要展示它）。

**写入点**：`OrderService.applySettlement` —— **与人工调整共用同一段**，
两条路径不会一个写、一个不写。

```java
// 起点取 order.getStartTime()（真正的开门时刻），不是 bill.getStartTime()（实际计费起点）——
// 包场人提前到店时后者晚几小时，用它会少算那段时间，而那正是「他明明在店里」的证据。
// 终点取 endTime 而非 now()：包场清场的 endTime 是包场开始时刻，取 now() 会与
// end_time 列不自洽（看着像「离场时刻比在店时长算出来的还早」）。
int stayMinutes = (int) Duration.between(order.getStartTime(), endTime).toMinutes();
```

**新增接口** `GET /api/orders/me/stats`（需登录）：

```json
{ "totalMinutes": 8520, "monthMinutes": 2160, "monthStart": "2026-09-01" }
```

- 新增 `OrderStatsVo` + `OrderMapper` 的 `selectTotalStayMinutes` / `selectMonthStayMinutes`
- **两个数字都只算 `PAID`**，与消费口径一致 —— 把在店未结账的那一单算进去，
  数字每刷新一次就往上跳一次，而它还没定局
- **抽出 `currentMonthRange()`（配一个 `MonthRange` record），`monthSpent` 与 `stats` 共用**。
  各自算一遍的话，跨月那一刻会出现「消费算上月、时长算本月」的错位 ——
  而这两个数字在「我的」页是并排显示的
- **没有合并进 `/me/month-spent`**：一个是时长、一个是金额，且后者还要多两次优惠判定
- 📌 **加列之前的老订单 `stay_minutes` 是 NULL，不会计入统计**（SQL 的 `SUM` 跳过 NULL）。
  这是刻意的：那些订单确实没有这个信息，编不出来。开发库里的几条联调订单现在就是这个状态，
  「我的」页会显示「累计时长少于累计消费对应的时长」—— **不是 bug**，
  生产库首次上线时是空表，不存在这个问题

|---|---|---|
| `unitsOf(minutes)` | `billSegment` 里内联的档数公式 | 「还有 12 分钟进入下一档」与账单上的档数对不上 |
| `isFreeByCard(period, coverage)` | `billSegment` 里的月卡免费判定 | 「月卡段还会不会涨价」在某个卡种上给出相反答案 |

**三种结果的判定顺序**：月卡覆盖 → 已封顶 → 段内档位边界 vs 时段边界。

> ⚠️ **与 3.5 节表格的一处出入，已在实现里定稿**：表格第三行写的是
> 「当前段已 `capped`，**且不会再跨段** → `null` / 「当前已到封顶价」」。
> 实现时发现「不会再跨段」这个条件**恒为假** —— 时间一直往后走，下一个时段边界总会来。
> 于是把这一档落实为：**已达封顶就给文字「当前已到封顶价」、不给秒数**
> （`inSeconds = null`）。
>
> 不给倒计时的理由：跨段那一刻旧段定格、新段从 0 分钟起算，**金额并不跳变**；
> 而那个跨段时刻可能在十余小时之后，给一个「还有 11 小时跨入夜场」的倒计时没有意义。
> 真到了跨段那一刻，预览接口会重新算出新段的预告（前端本来就在 10 秒轮询）——
> **信息不会漏，只是不在段内提前十几小时报**。

**「已封顶」用的是「原始金额 ≥ 封顶」而不是段上的 `capped` 标志** ——
后者要到第 11 档（5 小时 6 分）才为 true，而金额不再增长从第 10 档
（4 小时 36 分）就开始了，靠它会漏报。与 `OrderService.allSegmentsCapped` 同一条口径。

**`OrderService` 侧的接线**多了一道判断：**只在「此刻真有一段在计费」时才给预告**。
判据是账单最后一段的结束时刻是否就是此刻 —— 包场挡在中间时它会更早，
那时若照常算，会得出一个只对「包场前那段」成立、而那段早已结束的时刻。

## 2.3 任务 4 具体做了什么（✅ 2026-09-30）

**一句话**：上一单没结清就不要再开新单 —— 把「欠着费还能接着玩」这个口子补上。

| 文件 | 改了什么 |

### 为什么必须拆成两个查询

`selectActiveByUser` 原先**同时被两处用**，而它们要的语义正好相反：

| 调用点 | 用途 | 能否包含 `PENDING_PAYMENT` |
|---|---|---|
| `createOrder` 第 ④ 步 | 防连点 + 欠费拦截 | **要包含** —— 这正是本次补的规则 |
| `GET /api/orders/current` | 首页判断「开门 / 查看密码」 | **不能** —— 待支付的单密码已撤销，返回它会让用户看到一个点不动的「查看密码」 |

**不拆的后果是「改一边、坏另一边」，而且不报任何错**：直接给原方法加上 `PENDING_PAYMENT`，
首页就会在订单结算后仍然显示「查看密码」；反之则欠费拦截永远不生效。

### 为什么是两个错误码而不是一个

| 码 | 用户此刻的处境 | 前端处置 |
|---|---|---|
| `ORDER_ALREADY_ACTIVE`(40919) | 人还在店里玩 | 跳「**查看密码**」 |
| `ORDER_UNPAID_EXISTS`(40931) | 玩完了、账单还欠着 | 跳「**去支付**」 |

合并成一个码的话，前端只能给一句模糊提示，**用户不知道自己该点「结束使用」还是「去支付」**。
两个动作的后果完全不同 —— 一个把人留在店里继续玩，一个把人引到收银台。

> 40931 而非 40930：**40930 已预留给任务 5 的 `BOOKING_NOT_PAID`**（见 3.10 节），
> 照那个预留往下排即可。`ErrorCodeTests` 只钉唯一性与 HTTP 对齐，**不查连续性** ——
> 跳号不会被任何测试发现，别以为有测试看着。

### 三个容易写错的点（都有用例钉住）

1. **必须按 `user_id` 过滤** —— 漏了就把别人的欠费算到自己头上，**所有人都下不了单**
   （`createOrder_rejectsWhenUnpaidOrderExists` 里同时 seed 了一条 `OTHER_USER` 的待支付单）
2. **`PAID` 必须排除** —— 算进去的话**所有老顾客都进不了门**
   （`createOrder_allowsWhenPreviousOrderPaid`）
3. **`current` 的行为一个字都不能变** —— 它仍只认 `IN_USE`
   （集成测试 `selectUnsettledByUser_coversPendingPayment` 同时断言了两条查询的差异）

> **顺带修掉的一个老隐患（2026-09-30 追加）**：`OrderStatus.isUnpaid` 原先写作
> `Set.of(...).contains(name)`，而 JDK 的不可变集合对 null 查询会抛 NPE ——
> 与它自己「null 返回 false」的契约正好相反。同一批写法还有
> `BookingStatus.occupiesSlot` 与 `PaymentChannel.isOnline`（后者的入参
> `payment_method` 确实可能为空），三处一并改成了「`equals` 逐个比」，
> 各自补了测试类钉住。**因此假 Mapper 里那层 `status != null` 的守卫也去掉了** ——
> 留着它反而有害：万一 `isUnpaid` 又被改回会抛 NPE 的写法，
> 守卫会把问题盖住、测试照样全绿。

## 2.4 任务 5 具体做了什么（✅ 2026-09-30）

**一句话**：把「被邀请者」这个身份**落库**了。在此之前，他只是包场人分享出去的
一条链接 —— 系统里没有任何地方记着他是谁，于是准入只能靠请求里带令牌才认得出来，
清场与结算更是完全认不出他。新增关联表 `biz_booking_participant`，
包场人与被邀请者各占一行，靠 `role` 区分。

### 两处偏离原设计的地方（都让改动变小了，理由记在这里）

**① 清场与计费剪切没有改成读参与者表，而是「下单时就把 `booking_id` 挂上」**

3.6 节原本的设计是三处判定统一读参与者表（准入 + 清场 + 计费剪切）。
动手前重新核对代码，发现清场与计费剪切读的**都是订单上的 `booking_id`**
（`OrderService.isBookingParticipant` 与 `findCoveringBookings`），
而准入之所以认不出被邀请者，根子是**那张单从来没挂上过包场 ID** ——
他的身份只活在链接里，链接进不了 SQL。

于是改动收缩成一句：**下单时，如果他参与了某场尚未结束的包场，就把那一场挂上去**。
挂上之后，清场与计费两条链路**一行都不用改** —— 它们本来就认 `booking_id`。

> 挂上一场**还没到时间**的包场是无害的：`billableRanges` 会先把包场区间夹到订单
> 区间内，夹完为空就整段跳过，不会少收一分钱（`OrderService.java:973-978`）。
> 这条思路是用户提的（「没到时间的话不会剪切时长」），核对代码确认属实。

**② `/api/bookings/host` 仍按 `host_user_id` 查，没有按 3.8 节写的「两个列表都从参与者表出发」**

文档那句有个盲点：**`HOST` 行是付款成功那一刻才写入的**。改读参与者表会让包场人
看不到自己**待付款**的场次 —— 而付款入口恰恰在那个列表上，功能会断在
「排期 → 付款」这一步。所以两个列表各查各的：`/host` 按 `biz_booking.host_user_id`
查（含待付款），`/joined` 按参与者表的 `role='PARTICIPANT'` 查。

### 三个容易写错的点（都有用例钉住）

1. **`markPaid` 里插 `HOST` 行的异常必须自己吞掉** —— 外层那个
   `catch (DuplicateKeyException)` 是给「令牌撞索引 → 换一个重试」用的。
   异常一旦冒到那里，整条 UPDATE 会重试一遍，而那时状态已不是 `PENDING_PAYMENT`、
   受影响行数为 0，于是**整笔付款被当作「已处理」返回，而 `HOST` 行永远没插上**，
   且不报任何错
2. **名单排序不能只按 `joined_at`** —— 包场人付款若晚于别人点链接，发起人就会掉到
   名单中间去。SQL 用 `CASE WHEN role = 'HOST' THEN 0 ELSE 1 END` 把他钉在最前，
   而不是依赖「HOST 的字母序在前」这个巧合（将来加一个 `GUEST` 就破了）
3. **「重复加入」不是错误** —— 刷新页面、从聊天记录里再点一次都会走到 `join`。
   唯一键冲突是**答案**不是异常，那条 catch 分支必须返回 `alreadyJoined=true`。
   它只在并发下走到，所以假 Mapper 专门留了 `failNextInsertWithDuplicateKey()`
   把这条路径逼出来 —— 否则并发下唯一正确的那段代码没有任何用例看着

### 与 3.9 节当初的设计有三处偏离

**① 软检查统计的必须是「件数」而不是「笔数」** —— 那一节的 SQL 写的是
「可售量 = stock − 未支付的待支付单数」，没写明那个"数"是 `SUM(quantity)` 还是
`COUNT(*)`。第一版实现写成了 `COUNT(*)`，被一条用例逮住：
一笔「买 5 件」的待支付单只占掉 1 件库存，可售量因此虚高 4 件。
**这个错误不报任何错**，只在有人真的买走那 4 件、付款后无货可拿时才暴露。
现在单测与集成测试各有一条专门钉着它。

**② 超时的待支付单不再占库存，但不会被自动关闭** ——
原设计只说了「可售量 = 库存 − 未支付的待支付单数」，没考虑那些单子会一直躺着。
用户下单后不付款就把商品永久占住了，而商品单**没有**月卡那样的
「下次购买时顺手关掉」这个触发点（商品可以买多笔，没有那个时机）。
解法是让软检查按 `created_at > now − pendingTimeout` 过滤 ——
超时的单不再占位，但**用户仍然可以把它付掉**（那时库存多半已被买走，
扣减会失败并转人工，这是可接受的）。

> 与月卡的 `pending-timeout` **语义刻意不同**：月卡那边超时会被关单、不能再付。
> 因为月卡是「一人一卡」，未关闭的旧单会把用户自己卡死；
> 商品关掉旧单反而是替用户做了「不买了」的决定。

**③ 多了一个取消接口**（`POST /api/product-orders/{id}/cancel`）——
原接口表里没有。没有它，用户误下单之后只能干等超时，
而超时又不关单，界面上会一直挂着一笔「待支付」。

### 顺带完成：月卡有效区间逐段覆盖（模块 7 + 9）

不在本文件的十项任务里，是同一轮顺手做完的。规则与理由见
`docs/月卡设计草案.md` 第四节末尾，这里只记落地形状：

- `CardCoverage` 从枚举变成对象：时段那一半拆成新的 `CardScope`（`ALL` / `NIGHT`），
  另一半是卡的有效区间。计费侧「不认识月卡这个业务名词」这条边界不变
- **卡的有效期边界成了第三条切分线**（前两条是日夜场边界）。
  切分只在边界真的落在订单区间内时发生 —— 多切一段就多享一次宽限，
  无卡与卡覆盖整单时一段都不多切，各有一条守门用例
- `nextChange` 多一种结果：卡在本段内失效时报「月卡即将到期，之后按时长计费」
- `promotion` 包只动了一处：`findCoverageAt` 的返回值多了有效期，

| 决策 | 选择 | 为什么 |
|---|---|---|
| 构建 | **Vite** | 热重载 —— 改样式不用刷新、组件状态保留。本机 Node 24.14.1 |

### 3.1 公告模块（新包 `notice`）—— **消息流，不是状态投影**

> ⚠️ **这一节 2026-09-30 改过一次定位**，改动很大。原先按「状态的投影」设计：
> 按来源幂等（同一机台只有一条公告）、机台修好要撤销公告、公告有生效/失效时刻。
> 后来的结论是**那套设计错了** —— 公告就是一块**消息播报牌**，
> 记的是「什么时刻发生了什么事」，不是「现在是什么状态」。

**由这个定位推出的四条硬约束**（每一条都与「状态投影」的做法相反）：

| 约束 | 为什么 |
|---|---|
| **只增不改** | 机台每次状况变化<b>各产生一条</b>。先坏后好是两条消息，读完能看出「今天修过」这段过程 |
| **没有唯一键** | 原先的 `uk_source` 必须去掉 —— 它恰恰会阻止同一台机台发第二条公告。同一来源反复出现正是要的 |
| **没有生效/失效时刻** | 一条消息的「有效期」是说不通的。「3 号机转维护中」发生在那一刻，不会「下周三自动失效」 |
| **最新的在最上面** | 靠主键倒序。没有置顶、权重、排序值 —— 消息流里「让这条排前面」不是真实需求 |

**建表**（增量执行 + 写回 `schema.sql`，**已在开发库建好**）：

```sql
CREATE TABLE `biz_notice` (
  `id`           BIGINT        NOT NULL AUTO_INCREMENT COMMENT '主键',
  `title`        VARCHAR(100)  NOT NULL                COMMENT '公告标题，一句话。首页公告栏显示的就是它',
  `content`      VARCHAR(500)  DEFAULT NULL            COMMENT '公告正文。自动公告恒为 NULL，只有手写公告才有',
  `publish_mode` VARCHAR(20)   NOT NULL                COMMENT '发布方式：AUTO 系统自动 / MANUAL 管理员手写',
  `source_type`  VARCHAR(20)   DEFAULT NULL            COMMENT '来源类型：DEVICE 机台；手写公告为 NULL',
  `source_id`    BIGINT        DEFAULT NULL            COMMENT '来源记录 ID（机台 ID）；手写公告为 NULL。用来追溯是哪台机器产生的',
  `created_by`   BIGINT        DEFAULT NULL            COMMENT '发布人（管理员 ID）；自动公告为 NULL',
  `created_at`   DATETIME      NOT NULL                COMMENT '创建时间，同时也是这条消息的发生时刻',
  `updated_at`   DATETIME      NOT NULL,
  `deleted`      TINYINT       NOT NULL DEFAULT 0       COMMENT '逻辑删除：只有手写公告会被删',
  PRIMARY KEY (`id`),
  KEY `idx_source` (`source_type`, `source_id`),   -- 普通索引，不是唯一键
  CONSTRAINT `ck_notice_source` CHECK (
      (`publish_mode` = 'MANUAL' AND `source_type` IS NULL     AND `source_id` IS NULL)
   OR (`publish_mode` = 'AUTO'   AND `source_type` IS NOT NULL AND `source_id` IS NOT NULL)
  )
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COLLATE = utf8mb4_general_ci COMMENT = '公告（消息流）';
```

**已有的类**（`backend/src/main/java/com/kaede/uspace/notice/`）：
`Notice` · `NoticePublishMode`(AUTO/MANUAL) · `NoticeSourceType`(只有 DEVICE) ·

**同步钩子**（已在 `DeviceService` 挂好）：

| 触发 | 位置 | 记什么 |
|---|---|---|
| 新增机台 | `DeviceService.java` `createDevice` | 「新增机台 X（良好）」 |
| 状况变化 | `updateStatus` **与** `updateDevice` **两处都要挂** | 「X 由 良好 转为 维护中」 |
| 机台退役 | `deleteDevice` | 「机台 X 已退役」 |

> ⚠️ **`updateDevice` 那一处最容易漏**：`AdminDeviceController.update` 的 `status` 字段也生效

>
> ⚠️ **状况没变时不记**：对着已经在维护中的机器再点一次「维护中」什么都没发生，
> 反复点几下会把公告栏刷满，把要紧信息挤下去。

**文案工厂 `NoticeContents` —— 用「结构上写不出来」代替「记得别写」**

每个方法都**刻意不接受 `biz_device.remark`**（运营备注，如「等屏幕配件到货」）——
连匿名的 `DeviceDisplayVo` 都不含它，公告更不该含。调用方想泄露也没参数可传。

**三条硬纪律**：① **停业不生成公告**（那条路径的措辞边界 `StoreStatusVo` 已经定好了）；
② 设备公告不带 remark；③ 公告文案用**事件描述**（「由 A 转为 B」）而非状态断言
（「A 现在是 B」）—— 后者被翻到时状态可能早就又变了，而事件描述永远不过期。

**接口**：

| 方法 | 路径 | 鉴权 | 说明 |
|---|---|---|---|
| GET | `/api/store/notices?limit=5` | **匿名** | 只按 id 倒序取最近 N 条，**无任何时间条件**。limit 1–20 |
| GET | `/api/admin/notices` | ADMIN | 分页；可按 `publishMode` 筛 |
| POST | `/api/admin/notices` | ADMIN | 手写发布（**无 `publishMode` 入参**，方法体内硬编码 MANUAL + `source_*` 无条件置 null） |
| PUT | `/api/admin/notices/{id}` | ADMIN | 只允许改 title/content |
| DELETE | `/api/admin/notices/{id}` | ADMIN | 逻辑删除 |

**自动公告只读**：`PUT` / `DELETE` 遇 `publishMode == AUTO` 返回 `NOTICE_AUTO_READONLY`(40929)。
理由不是权限，而是**改写或删除等于篡改历史**。手写公告可改可删 ——
它不是「已发生的事实」，而是「运营现在想说的话」，说错了该能收回来。

`NoticeVo` 是**白名单**，**不出 `sourceType` / `sourceId` / `createdBy`**。

> **放匿名**的理由与 `/api/store/status` 的既有注释完全对齐：
> 「门店名称、地址与『此刻是否营业』是面向公众的信息，相当于店门口挂的牌子」——
> **店门口的告示牌不需要注册才能看**。

**已删除的东西**（不要再加回来）：`NoticeExpiryScheduler`、`NoticeMapper` 的
`upsertAuto` / `revokeAuto` / `expireOverdue` / `selectVisibleForUser`、
表上的 `effective_from` / `effective_to` 两列、`NoticeSourceType.BOOKING`。

### 3.1.1 包场时间表（取代了原来的「包场公告」）

**包场不进公告流**：它是「未来的安排」，公告是「已发生的事」。混在一条流里，
用户分不清哪条是通知、哪条是日程；而且日程会随改期变动，
消息流只增不改，改期后旧的那条就永远对不上了。

**已有实现**：`GET /api/store/bookings?limit=10`（**匿名**，配在 `SecurityConfig.PUBLIC_PATHS`）

- `BookingMapper.selectUpcoming(now, limit)`：`status='PAID' AND end_at > now`，
  按 `start_at` **升序**（时间表从近到远读，与公告的倒序正好相反）
- `BookingScheduleVo` —— **只有 `startAt` / `endAt` / `ongoing` 三个字段**，
  连 `hostUserId` 都没有。与 `StoreStatusVo`「包场时也不披露包场人是谁」同一条边界
- `ongoing` 由后端算（`!startAt.isAfter(now) && endAt.isAfter(now)`），
  不让前端拿两个时间比当前时刻 —— 客户端时钟不可信，且口径只能有一处定义
- 挂在 `space` 包的 `StoreController` 上（`/api/store` 前缀）；它现在注入了
  `BookingService`，**`StoreServiceTests` 不受影响**（测的是 Service 不是 Controller）

> **「进行中」那一行要标出来**：用户当场进不去时，看到时间表上那行亮着就知道原因，
> 而不是以为门坏了。

### 3.5 「下一次账单变化」预告

**必须后端算，不能让前端拿 `bill.segments` 自己推**：档位边界 = `units × 30 + 5 + 1` 分钟，
其中的 **30（档位单位）与 5（宽限）都是 `BillingProperties` 的配置**。
前端算等于把计费规则复制一份 —— 改配置时前端静默算错，且不报任何错。
CLAUDE.md 的定论是「日夜场边界仍然只有计费侧一处定义」；月卡文档也写过
「**不必自己拿状态和日期去判断，那样等于在客户端再实现一遍判定的口径**」。同一条道理。

**`OrderPreviewVo` 新增两个字段**：

| 字段 | 类型 | 说明 |
|---|---|---|
| `nextChangeInSeconds` | Integer | 距下一次账单变化的**剩余秒数**；`null` 表示当前不会再变 |
| `nextChangeText` | String | 变化性质的说明，**不含时间**，前端拼成「还有 12:30 进入下一档 ¥20.00」 |

**用剩余秒数而不是绝对时刻**：绝对时刻会带上客户端与服务端的时钟偏差，
用户手机时间不准时倒计时会算出荒谬的值，而秒数是后端算好的。

**要判定的三种情况**（这才是「下次跳档」真正的难点）：

| 情形 | 触发条件 | `nextChangeText` 示例 |
|---|---|---|
| **TIER** 段内跳档 | 下一个档位边界落在当前时段**之内** | 「进入下一档 ¥20.00」 |
| **PERIOD** 跨时段 | 下一个档位边界落在当前时段**之外** —— 先发生的是时段边界 | 「跨入夜场，按夜场重新计价」 |
| 不再变化 | 当前段已 `capped`，且不会再跨段 | `null` / 「当前已到封顶价」 |

> ⚠️ **PERIOD 这一档不能省。** 只做 TIER 的话，21:50 的卡片会写「还有 40 分钟进入下一档」，
> 而用户实际在 22:00 就跨进夜场重新起了一段（**夜场更便宜**）。
> 前端展示一个错误的时间预期，比不展示更糟。

```java
/**
 * <p>档位边界推导：{@code units = ceil((minutes - grace) / unit)}，
 * 下一个档位出现在 {@code minutes = units * unit + grace + 1}。
 * 注意取时长是<b>向下取整</b>的（{@code toMinutes()}），所以边界落在整分钟上，
 * {@code nextChangeAt} 是精确的，不是估算。
 *
 * @param startTime 计费起点（已剪掉包场）
 * @param now       计算截止时刻
 * @param monthSpent 当月累计，用于取正确的单价（优惠价还是原价）
 * @return 剩余秒数与说明；已封顶且不跨段时返回 null
 */
public NextChange nextChange(LocalDateTime startTime, LocalDateTime now,
                             BigDecimal monthSpent, CardCoverage coverage)
```

**结账预览页同时受益** —— `OrderPreviewVo` 是首页与结账页共用的，
结账页可以顺手显示「再玩 12 分钟会跳到 ¥20」，正好给「该不该现在停」提供依据，
与「预览页就是确认环节」的设计是一致的。

**库存扣减 —— 你选了「支付成功时才扣」，这里加一道缓解**

```java
/**
 * <p>⚠️ <b>本系统选择「支付成功时才扣库存」，这不是最严格的方案。</b>
 * 严格方案是下单时预占、超时释放（月卡的购买单就是这么做的）。
 * 支付时才扣的固有风险是：两人同时买最后一件，都能下单成功，
 * 后付款的那个会扣成负数 —— 钱收了却没货。
 *
 * <p><b>缓解办法是下单时做一次软检查</b>：可售量 = {@code stock − 未支付的待支付单数}，
 * 为 0 就拒绝下单。它不锁库存，所以理论上仍有竞态窗口，
 * 但把「已经有人在下单但还没付」这段最容易撞的时间差挡掉了 ——
 * 单店量级下这已经足够，且实现成本只有一条 SQL。
 *
 * <p><b>扣减用条件 UPDATE</b>：{@code WHERE id=? AND stock >= ?}。
 * 受影响行数为 0 表示确实卖光了，此时记一条 error 日志并让该笔支付进入人工处理 ——
 * 不要在回调里抛异常，那会让支付平台不断重推一笔永远处理不了的通知。
 */
```

**接口**：

| 方法 | 路径 | 鉴权 | 说明 |
|---|---|---|---|
| GET | `/api/products` | 登录 | 上架商品列表（**卡片式**：封面/名称/价格/是否售罄） |
| GET | `/api/products/{id}` | 登录 | 商品详情 |

| GET | `/api/admin/products` | ADMIN | 后台列表（分页） |
| POST/PUT/DELETE | `/api/admin/products/**` | ADMIN | 商品 CRUD |

> **为什么不做核销**（你已定）：无人值守店里没有店员，付了钱自己取。
> 代价是分不清「货被拿了没有」，争议时只能查监控、库存与实物的差异无法追踪。
> **这是明知的取舍，不是遗漏** —— 若将来要追踪，加一个 `FULFILLED` 状态与核销接口即可，
> 表结构不用动（状态列是 VARCHAR，加一个取值就行）。

## 四、最容易写错的交互

### 1. 首页「开门」按钮的双语义

```js
const resp = await getCurrentOrder()
// ⚠️ 两层 .data：第一层 axios 的 response.data，第二层 ApiResult.data。
// 少写一层会得到一个恒为真的对象，于是「开门」按钮永远不出现。
// 用 == null 而不是 !order —— !order 对 0/''/false 也为真
if (resp.data == null) showOpenDoorButton()
else                   showSettleButton(resp.data)
```

点击前**先查一次 `current`**：后端有用例挡连点，但用户会先看到一个错误提示，
而他的真实处境可能是「我已经开过门了」。**先查一次能把一个错误提示变成一次正常的页面跳转。**
若拿到的是 40931（欠费），则提示并跳「去支付」而不是「查看密码」。

### 2. 结算预览的 10 秒轮询（`usePreviewPolling`）

三个坑，每个都不是理论问题：

- **乱序响应**：网络抖动时第 20 秒的响应可能先于第 10 秒的到达，
  页面会先显示新数据再**倒退**（金额变小），用户以为系统算错了。
  用响应里的 `previewAt` 比较，比已渲染的更早则**整个丢弃**。用 `previewAt` 而不是本地时间戳
  —— 本地时钟可能被用户改过
- **停止后仍在途的响应**：用户点了「停止计时」，上一个 preview 还在路上，
  它回来会把页面从「已结束」刷回「计时中」，用户以为没停成功又点一次。**停止时置标志，响应回来先查标志**
- **停止后的 409 不是错误**：订单变成 `PENDING_PAYMENT` 后再请求 preview 会返回 409，
  这是**预期内**的（接口文档明写「那个 409 不是错误，而是本页使命结束」），不能弹提示

```js
// 【先停轮询再发 settle】：反过来的话，settle 期间的 preview 会返回 409，
// 而那是个预期内的错误，却会因为 stopped 还是 false 被当成真错误弹出来
async function onStop() {
  stopPolling()
  const resp = await settleOrder(orderId)
  router.replace(`/orders/${orderId}`)   // 金额与状态一律以 settle 的返回为准
}
```

**用递归 `setTimeout` 而不是 `setInterval`** —— 某次请求耗时 3 秒时，
`setInterval` 会在它还没返回时又发一个。`onUnmounted` 必须清理。
**首页那个 30 秒的进行中卡片复用同一个 composable**，只是间隔不同。

### 3. 模拟收银台

```js
// ⚠️【先判 mockPayUrl，再判 h5Url】顺序不能颠倒。
// mock provider 下后端为了让流程逼真，两个字段可能同时有值。
// 先判 h5Url 并 location.href 跳过去，会跳到一个真实支付网关的沙箱地址（或 404）。
if (payInfo.mockPayUrl)       showMockCashier(payInfo)   // 绝不动 location.href
else if (payInfo.jsapiParams) invokeWechatJsapi(...)
else if (payInfo.h5Url)       location.href = payInfo.h5Url
```

收银台**不需要用户输入金额** —— 金额由后端决定，前端只传 `outTradeNo`。
必须放一个显眼的「模拟支付」水印，防止有人以为这是真收银台。

### 4. 按 UA 自动选通道

```js
export function defaultChannel() {
  if (/MicroMessenger/i.test(navigator.userAgent)) return 'WXPAY_JSAPI'
  if (/AlipayClient/i.test(navigator.userAgent))   return 'ALIPAY_WAP'
  return null   // 其余：H5 与 WAP 并排给出，都不预选
}
```

> **这只是「默认勾选」，用户仍可手动切换。** 不要做成自动跳转且不可改 ——
> 微信里想用支付宝是常见需求（零钱不够、有红包），强制跳转会让这类用户完全没法付款。

### 5. 支付结果必须主动查单

`application.properties` 里有 `uspace.payment.mock.notify-drop-rate`，
`MockPaymentController` 会**按概率故意丢掉回调** —— 这是刻意造的，
因为真实支付平台的回调确实会丢。

```js
// ⚠️【mock/pay 返回成功 ≠ 支付成功】它只是「把支付模拟提交了」，
// 真正的确认在于后端的 applyNotify 有没有走到，而那取决于回调有没有被丢。
// 依赖回调的后果：用户付了钱、回调丢了、前端一直显示「支付中」，
// 用户以为没付成功又付一次 —— 重复扣款。
const result = await pollPaymentStatus(outTradeNo, channel)   // 15 次 × 2 秒

// channel 必传（后端签名是 required=false，但不同通道查单实现不同）。
// 建议顺手把 docs/接口文档.md 里这个参数从「可选」改成「必填」，
// 让契约与实现一致，比让前端记住「虽然标着可选但一定要传」可靠得多。
```

### 6. 分段账单展示（`BillSegmentList`）

```js
// ❌ const finalPay = bill.totalAmount - bill.discountAmount - bill.cardFreeAmount
// ✅ const finalPay = bill.payableAmount
```

**`payableAmount` 是唯一权威的「要付多少」**，它已包含优惠与月卡抵扣。
`discountAmount` / `cardFreeAmount` 是**说明性字段** —— 它们解释「为什么便宜了」，
**不是「还要再减多少」**。再减一次会让页面金额小于实际应付，用户按页面数字去付款。
**这个 bug 不报任何错**，只在付款时表现为金额对不上。

其余两点：**`unitPrice` 与 `capAmount` 必须逐段展示**（日夜场不同价、优惠与否又不同价，
只显示总价的话用户拿总时长去乘会对不上）；**`stayMinutes` ≠ `bill.totalMinutes`**
（前者是在店时长、后者是计费时长，扣了包场与宽限），两个都要显示，标签绝不能混用。

### 7. 格式化工具的两个坑

```js
/**
 * ⚠️ 不要 new Date("2026-09-30 19:00:00") —— 后端返回的是不带时区的本地时间串，
 * Safari 只认 ISO 8601 的 "2026-09-30T19:00:00"，会返回 Invalid Date；
 * Chrome 按本地时区解析。同一份代码在 iOS 上白屏、安卓正常。
 * 本项目要真机调试，必然会在 iOS 上跑。直接字符串切分，不经过 Date。
 *
 * ⚠️ 金额绝不用 parseFloat().toFixed() —— 那会引入浮点误差，
 * 而钱是差一分都要说清楚的。只做字符串层面的展示格式化。
 */
```

### 8. Banner 卡片的兜底

```js
// banner 未设置时不能是破图 —— 回落到纯色底
// 设了但加载失败时也要回落（用户传的图后来被删了、或网络抖动）

<div :class="{'card-banner': true, 'card-banner--fallback': !banner || bannerFailed}">
```
