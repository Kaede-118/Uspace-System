## 月卡有效区间逐段覆盖（2026-09-30，模块 7 + 9）

月卡的免费判定从
  「按订单开始日期整单判定」改成「**按卡的有效区间逐段覆盖**」。
  改动前卡最后一天 23:00 进店、次日 01:00 离场是整单都免（多送一个多小时），
  卡次日才生效时前一天晚上的整单也都不免 —— 两头都靠「开始时刻」定，规则不闭合。
  - **`CardCoverage` 从枚举变成对象**：原来只表达「免哪些时段」（`ALL` / `NIGHT`），
    现在同时带上卡的有效区间。时段那一半拆成新的 `CardScope` 枚举，
    计费侧「不认识月卡这个业务名词」这条边界不变
  - **卡的有效期边界成了第三条切分线**（前两条是日夜场边界）：
    `BillingService.splitByPeriod` 现在收 `CardCoverage`，段一律切到卡的边界为止。
    切分**只在边界真的落在订单区间内时发生** —— 多切一段就多享一次宽限，
    无卡与卡覆盖整单时一段都不多切（各有一条守门用例）
  - **`nextChange` 多一种结果**：当前段被卡覆盖但**卡在本段内失效**时，报
    「月卡即将到期，之后按时长计费」而不是「当前时段月卡免费」——
    少了这一支，23:50 的用户会看着一句静态的「免费」，然后零点金额毫无预兆地开始涨
  - **`findCoverageAt` 的返回值语义变了**：它仍按订单开始日期**查**卡，
    但带回来的是那张卡的**完整有效期**（查询用的那一天只决定取哪张卡）

      本来相同的值仍算 1 行）—— 若将来给 JDBC URL 加 `useAffectedRows=true`，
      同值更新会回一句「商品不存在」，注释里已点明
    - 测试：`ProductServiceTests` 32 → 37（含一条**幂等用例**钉住 SET 语义：

    **只落盘、只返回路径，不写任何数据库** —— 前端把 `cover` 填进表单，
    随商品的新增 / 修改一起提交。三条理由：新增商品时还没有 ID 可写、
    表单是「填一半可以取消」的语义、传错可以反复换一张。
    代价是「传了图又取消」会留下没人引用的文件（只占磁盘、不影响功能）——
    这是那条语义的固有结果，不是 bug
  - **`ProductCoverService` 的构造器只有一个依赖、没有 Mapper** —— 这不是巧合，
    它就是「上传不写库」这条语义的结构性证明
  - **文件名用 UUID，不采信商品名**：商品名是中文自由文本（含空格、斜杠，
    Windows 下还有 `CON` / `PRN` 这类保留名），想清洗成安全文件名的那套规则
    没有任何测试能穷尽；而头像能用 `{用户名}_{ID}`，是因为注册校验把用户名
    限死在 `[a-zA-Z0-9_]{3,20}` —— 商品名没有这个前提。
    顺带买到两件事：不会重名（所以不存在「重传覆盖同一路径」，也就没有删旧图那套判断），
    以及 **URL 每次都变 → 前端不需要 `bumpImageVersion()` 防缓存**
  - **落盘走公共层的 `ImageStorage`**，与头像 / 背景图共用同一份安全代码 ——
    见「工程结构」一节的公共层说明
  - **两张表与月卡同构**（资产与交易分开）：`biz_product` 放「卖什么」，
    `biz_product_order` 放「买过什么」。`product_name` / `unit_price` 是**快照**，
    商品改名或调价不影响已售出的单
  - **收款复用模块 8 的统一入口**：`ProductPaymentTargetHandler` **住在 order 包**
    （与月卡、包场同理，依赖方向 `order → product`），回调、验签、幂等**一行未改**，
    只是 `targetType` 多一个 `PRODUCT`
  - **库存是「支付成功时才扣」+ 下单时软检查**：严格方案是下单预占、超时释放；
    取「支付时才扣」的固有风险是两人同时买最后一件都能下单成功。
    缓解办法是下单时按「**可售量 = 库存 − 未支付的待支付单数**」做一次软检查
    （不锁库存，所以仍有竞态窗口）；最后一道防线是支付时的**条件 UPDATE**
    （`WHERE stock >= ?`），扣不动就记 error 日志转人工 —— **绝不在回调里抛异常**，
    那会让支付平台不断重推一笔永远处理不了的通知
  - **「是否售罄」在列表与下单两处是同一个口径**（都算上未支付的占用），
    所以不会出现「页面说还有货、下单却说售罄」
  - ⚠️ **软检查统计的是「件数」不是「笔数」**：SQL 必须是 `SUM(quantity)`
    而不是 `COUNT(*)` —— 一笔「买 5 件」的待支付单占的是 5 件库存。
    写成后者不报任何错，只让可售量虚高，表现为「明明下单成功了，付款后却说没货」。
    这个 bug 是写测试时被一条更宽的用例顺带发现的，现在单测与集成测试各有一条守着
  - **超时的待支付单不再占库存，但不会被自动关闭**（用户仍可付款）——
    与月卡刻意不同：月卡是「一人一卡」，未关闭的旧单会把用户自己卡死；
    商品可以买多笔，关掉旧单反而是替用户做了「不买了」的决定。
    这样也就**不必为商品再引入一个调度器**
  - **商品消费记进 `order_paid`**（与房间使用费同类），不进 `card_paid` ——
    后者是月卡的预付卡费，两个口径的用途不同
  - **不做核销**（已拍板）：无人值守店里没有店员，付了钱自己取。
    代价是分不清货被拿了没有。**这是明知的取舍，不是遗漏** ——
    将来要追踪，加一个「已交付」状态与核销接口即可，表结构不用动
  - **凭证被驳回时只退状态、不还库存（2026-10-04 加）**：购买单转
    `ProductOrderStatus.REJECTED`（与订单那个同义，不复用 `PENDING_PAYMENT` ——
    后者会让用户以为要再下一次单）。**货不还**：付了钱自己取，而驳回发生在
    管理员有空复核时（往往隔了一两天），那时货多半已被拿走，还回去是记假账。
    顺带一处容易漏的：`ProductOrderMapper.markPaid` 的守卫原本只写
    `status = 'PENDING_PAYMENT'`，加了这个新状态之后**必须改成 `IN (...)`** ——
    否则用户重传凭证时提交接口返回成功、落账那一步被 SQL 悄悄挡掉，
    单子永远停在「凭证未通过」上（这个 bug 是被测试逮住的）
  - **`supportsChannel` 的覆写已全部删掉（2026-09-30）**：凭证流程建成之后
    「传截图」对四类收款都成立了，四个处理器当前都受理全部通道。
    **钩子留着**，因为它守着一类真实发生过的故障：人工核销接口曾是订单专用的，
    月卡与商品各覆写它挡掉传截图通道 —— 少了那道守卫，用户对月卡选「传截图」
    会拿到一个没有任何支付参数的「成功」，卡永远停在待支付，且线上零报错
  - **详情接口对下架商品照常返回**（带 `enabled = false`）：用户的订单里可能还
    指着它，点进去看不了会很莫名其妙。下架只影响「能不能下单」
  - **`enabled` 是全量替换（PUT）语义的唯一例外**：不传时保持原值。

  - ⚠️ **后台改商品走 `ProductMapper.updateProduct`（显式 SQL），不用 `updateById`** ——

    走了 `updateById` 的话，撤封面、清描述都做不到，且**不报任何错**

## QQ 号验证 `QqVerifyService`（2026-09-30 建，2026-10-01 接线完成）

17 个测试
  - **它解决的问题**：模块 11 靠 `sys_user.qq` 把群消息的发送者对应到系统用户，
    而注册页填的那个 QQ 号本身没有任何可信度 —— 他随手填别人的也行，
    那样「群里来的人是谁」就永远对不上。这是一条**群内的往返**：
    取 6 位码 → 发到群里 → 机器人把「发消息那个人的真实 QQ」与码回执给后端 →
    后端**按发送者 QQ 查表**核对 → 注册接口再消费掉
  - **基石是「按发送者 QQ 查表」**：验证码本身不是凭证（群里所有人都看得见它），
    但只有持有该 QQ 的人才查得到自己那条记录。改成「遍历所有记录找匹配的码」
    就变成「谁拿着码就验证谁」，验证等于没做 —— **而那种写法一样能跑通全部演示**
  - **存一张以 QQ 为键的内存表**（`ConcurrentHashMap`），不落库。代价要如实说：
    **进程一重启，正在验证的人全部作废**，只能重新取一次码；
    换来的是不必为一份一次性的临时状态建表
  - **6 位数字不做限流不是疏忽**：猜对了也只能查到自己那条，真正的防线是查表键。
    这与 `InviteTokenService` 的「256 位熵够了所以不用限流」**不是一回事，别照搬**
  - **2026-10-01 接线完成，两端齐了**（2026-09-30 拍板的就是「与模块 11 一起接」，
    免得留下「注册要求先过群验证、而群里没人应答」的死路）：
    - **群侧**（模块 11）：`QqCommandService` 收到 6 位数字就调 `confirm`，
      回执文本为空时**保持沉默** —— 群友随口发的数字不会换来一句「验证码不正确」
    - **Web 侧**（模块 1）：新增 `QqVerifyController`，两个接口
      `POST /api/user/qq-verify`（签发）与 `fwstatus`（轮询），都在
      `SecurityConfig.PUBLIC_PATHS` 里（注册前没有凭证）
    - ⚠️ **两个接口都走 POST + 请求体，`status` 虽然是纯查询也不破例** ——
      `challengeId` 是能换取账号绑定的凭证，放进 URL 查询参数会落进访问日志，
      看到日志的人就能在那个 QQ 完成群内验证之后抢先注册
    - **注册时消费**：`RegisterRequest` 加了 `challengeId`；`UserService#register` 里
      「填了 QQ 就必须先过验证」。⚠️ 顺序是**先查重、再 consume** ——
      consume 用完即焚，反过来会让「QQ 已被占用」这种完全可预期的失败
      白白烧掉一次验证，用户得重新取码重新发群
    - 前端 `RegisterView`：加「获取验证码」按钮、验证码展示与 3 秒轮询；
      `challengeId` 存 sessionStorage（用户要切到 QQ 粘贴，页面可能已被回收）
    - ⚠️ **代价要如实说**：机器人没配好（或 NapCat 没跑）时，**用户就注册不了带 QQ 的账号** ——
      这是「硬门槛」的应有之义，不填 QQ 仍然能注册
  - **QQ 号绑定后本人不得修改（2026-10-01 加，用上了早就存在的 40937）**：
    `UserService#updateProfile` 里，只要 `qq` 与当前值不等就返回
    `QQ_CHANGE_REQUIRES_ADMIN`(40937)。⚠️ **清空也算变更，一并拒绝** ——
    只挡「改成别的号」是不够的，先清空、再设成别人的，正好绕过去。
    - **为什么不能松**：QQ 号是机器人在群里认人的唯一依据，而注册时它经过一次
      群内验证；允许本人改，那次验证就等于白做（先随便填一个号注册，
      再改成群里某个人的号，此后那个人的群消息就会被当成他的）
    - **它是「PUT 全量替换」语义的第二个例外**（第一个是机台的 `status`）：
      前端要原样带上当前值，否则会被拒。`ProfileEditView` 的输入框已置灰
    - **管理员改 QQ 的入口在运营后台的「用户管理」页**（`PUT /api/admin/users/{id}`，
      2026-10-01 同日补上）—— 就是 40937 文案里说的「联系管理员」那个地方。
      管理员改不走群内验证（他知道谁是谁），但**照样查重**
    - ⚠️ **注册时 QQ 也是必填的（2026-10-01 改）**：原先允许留空，理由是
      「注册每多一个必填项就多一分流失」—— 那条对普通产品成立，对这个系统不成立：
      **店里没有店员**，顾客是谁、该收多少钱全靠系统，「不绑 QQ 也能进店」
      等于留一个**出了事找不到主的顾客**。`RegisterRequest.qq` 上的
      `@NotBlank` 与 `UserService#register` 里的判空各拦一道
      （后者是给「直接调 Service」的路径兜底）

## 模块 6 进出记录：订单口径的到店 / 离店与名册快照（2026-10-16）

**背景与口径**：后台一直缺「进出记录」界面（后端接口与前端封装都在，只是没页面消费）。
补的时候由使用者定死了口径：**到店 = 开始计时（`start_time`），离店 = 停止计时（`end_time`）**
—— 也就是**读订单，不读门锁开门记录**。理由是封闭空间的出门是机械推杠、
不产生门锁记录（`biz_access_record` 的表注释就写着这一条），
拿门锁记录当「离店」会永远等不到那一条。门锁记录仍在同页另一个 tab，定位是**旁证**：
它只证明「有人在门口输对了密码」。

**为什么落在 order 包**：数据源是 `biz_order`，而 `access` 与 `order` 两个包互不依赖 ——
读订单的代码只能住在 `order` 包，路径却按业务挂在 `/api/admin/instore/*`
（与 `InstoreController` 住在 order 包、路径 `/api/store/instore` 是同一条理由）。

  - 代码：`InstoreService` 加 `listTraffic` / `snapshotAt`；`AdminInstoreController`
    两个端点（`GET /api/admin/instore/traffic`、`GET /api/admin/instore/snapshot`）；
    DTO `OrderTrafficVo` / `InstoreSnapshotVo`；`OrderMapper` 加三条查询
    （`selectOverlappingWindow`、`selectTrafficPageByArrive`、`selectTrafficPageByLeave`，
    可选条件照项目惯例写 `(#{x} IS NULL OR ...)`，假 Mapper 因此不必模拟动态 SQL）
  - **名册是推算的，不是当时存下来的**：`start_time <= at AND (end_time IS NULL OR end_time > at)`。
    好处是历史任意时刻都能还原、一条都不用补录；代价是人工调整过离店时刻的单子，
    受影响的快照会跟着变 —— 页面上如实写明，别让读的人以为它是现场录像
  - ⚠️ **半开语义是这套东西的要点**：判离店用 `end_time > at` 而不是 `>=`，
    所以「离店之后剩余名单」不把刚走的那位算进去 —— 他要是留在名单里，
    「某人走了、还剩 3 人」就变成了「还剩 4 人，含他自己」
  - ⚠️ **名册必须向窗口外取人**：算本页快照时，窗口取「本页所有时刻的最小 / 最大值」，
    再查**与窗口相交**的全部订单（不是「开始时刻落在窗口内」）——
    19:00 到店、次日 02:00 离店的人必须出现在 23:00 那份名册上。
    只查窗口内会静默漏人且不报错，用例 `listTraffic_keepsCrossWindowVisitorInSnapshot` 钉住
  - ⚠️ **按离店排序时，本页最早离店那条不在窗口查询结果里**：它的 `end_time` 恰好等于
    窗口起点，会被 `end_time > from` 排除 —— 这是口径的直接结果，不是缺陷。
    所以本页订单要单独并进「查昵称」的集合，否则它自己的名字会回落成「用户{ID}」
  - **前端**：后台第九个 tab「进出」（`views/admin/AccessManageView.vue`，路由 `/admin/access`），

    门锁开门记录（此前 `api/admin.js` 里那批封装一直没有页面消费，这次一并接上：
    同步 / 补录 / 模拟开门）
  - **⚠️ 同日晚改成事件流**（使用者反馈）：最初做的是「一行一单、到店与离店两端并排」，

  - ⚠️ **播报必须是 `@TransactionalEventListener(AFTER_COMMIT)`**：发布点在
    `createOrder` / `applySettlement` 的事务里，普通 `@EventListener` 会在提交前跑，
    那时回查在店名册**读不到刚插入的订单** —— 播报会说「张三到店，当前 0 人在店」，且不报任何错
  - ⚠️ **监听器方法体整个包在 try/catch 里**：Spring 的 `processCommit` 触发 afterCommit
    回调时**没有针对单个监听器的保护**，异常会沿着 `publishEvent` 冒回 `createOrder` 的调用方 ——
    用户看到「开门失败」，而**订单已落库、密码已下发**，他再去点一次得到的是「已有进行中的订单」。
    这是本模块最严重的一个坑
  - ⚠️ **监听器里绝对不能写库**：AFTER_COMMIT 时事务已提交但**连接还没归还**，
    `DataSourceUtils` 会把那条连接再借给你，写入**既不在事务里、也不会被提交**，
    归还时被 rollback 且一声不吭。本模块只读所以天然安全 —— 但这正是「只读」的技术依据，
    不是一句写在文档里的口号
  - **一个点覆盖三条离店路径**（用户自助 / 包场清场 / 管理员补录）——
    但 `applySettlement` 为此加了第 5 个参数 `OrderLeftEvent.Source`：
    只看 `operatorId` 分不出「用户自助」与「包场清场」（两者都传 null），
    而**管理员补录的是「昨晚忘了点结束使用」的单子，群里发一句「刚离店」就是假消息**
  - **离店播报刻意不报「还有几人在店」**：包场清场在一个事务里循环结算 N 单，
    N 个事件都在提交后触发，此时所有人都已结算完 —— 逐条读会得到 N 条一模一样的
    「还有 0 人在店」。少说一句没损失，多说一句错的会让人以为系统坏了
  - **自己发的消息**（运营者用同一个 QQ 在手机上发指令）：NapCat 要开 `reportSelfMessage`，
    事件类型是 `message_sent`。⚠️ 它与「机器人自己刚发出去的回复」在**协议字段上无法区分**
    （`user_id == self_id` 两者都成立），所以判据只能落在内容上 ——
    **解析结果不是「闲聊」就处理**。回环仍然被切断：机器人发出去的那几种文本
    （`pong`、在店名册、帮助、验证结果）没有一种能解析成指令
  - ⚠️ **那个判据【不能】写成「带不带 `/` 前缀」** —— 这是实测踩到的坑：
    6 位验证码不带斜杠，同号登录 bot 时它会被当成「机器人自己发的话」挡掉，
    表现是**取码正常、发到群里也正常，但验证永远通不过，而后端与群里都没有任何报错**。
    判据换成「解析结果是不是 `IGNORE`」之后，验证码与 `fwping` 都放行，

## 指令回复的发送队列与 @ 调用者（2026-10-10 深夜，模块 11）

**起因**：指令处理得快（毫秒级）、回复也就发得快 —— 连着刷屏正是 QQ 风控盯的特征
（用户原话：「回复的太快了 qq 容易风控」）。两个要求：给回复限速、所有回复 @ 调用者。

### `QqReplyQueue`：回复不再「算完即发」

- 新组件 `QqReplyQueue`（qqbot 包）：回复进队，**单线程 worker 取一条、等一段随机时长、
  再发**。每条发出前都等（**含第一条** —— 秒回同样是被盯的特征，
  所以「队列空时立即发」那种常见写法在这里是刻意反着写的）
- 节奏 **3~10 秒随机**（`reply-min-interval` / `reply-max-interval`，默认 3s / 10s）——
  固定间隔本身也是可识别的特征。上限配 0 = 关闭限流直发（测试与排障用）
- 队列上限 100 条，满了丢弃 + error 日志（不无限堆积）
- 队列在内存、重启即丢（与等待表同性质）；`@PreDestroy` 停 worker
- **回复一律 @ 发指令的人**：发送统一走 `sendGroupMessageAt`（段数组的 @，
  防昵称注入）—— `QqReplyQueue.submit(groupId, qq, text)` 的 qq 就是干这个的

### 两类不走队列

- **`fw开门` 与 `fw结账`**（含 `replyPendingIfAny` 那条回头路、以及 `checkAllowed`
  的三条前置拒绝）：人站在门口等密码、等结账结果，压队列等十秒不可接受 ——
  这 12 处直接用 `client.sendGroupMessageAt`（直发 + @），见
  `QqWriteCommandService` 里那几处与 `QqReplyQueue` 类注释的说明
- **播报**（到店 / 离店 / 包场生效……）：不是指令回复，频率天然低，不经过队列

### @ 之后换行（同日追加，全站统一）

`OneBotAction#sendGroupMessageWithAt` 在 at 段与 text 段之间加一个 `\n` ——
**所有 @ 都走这里**（指令回复与播报提醒一起生效）。@ 与正文挤在同一行时，
群消息窗口里名字与内容连成一片，长文案读不清哪句是回谁的。
退化情形（没 QQ 可 @）不加换行。连带改掉一处旧写法：
`QqReplyText.proofRejected` 原本以空格开头（那是给 @ 留的缝），
换行统一之后成了多余缩进，去掉。

**测试**：新增 `QqReplyQueueTests`（6 条：第一条也等、顺序与间隔、带 @、
无 QQ 退化、关闭限流、空正文丢弃）+ 协议层两条守卫改钉换行行为；
两个 `RecordingClient` 补覆写 `sendGroupMessageAt`（不补的话队列发的消息
会落到父类真实实现、断言全看不到）。

### 0 元结账单不再撑「等付款截图」闸（模块 11）

现场撞到：`fw结账` 结出一笔 0 元（首 5 分钟免费），群里随手发了个表情，
机器人回「该订单已不是待支付状态（可能已在网页端完成付款）」—— 而那笔本来就无需付。

- 根因：`QqWriteCommandService.settle` 撑闸时没看金额，0 元单也登记了等图
  （订单已自动结清、状态直通 PAID，用户随后发的任何图必然撞上状态检查那句）
- 修法：只在金额 > 0 时撑闸；判据与 `QqReplyText#settleDone` 的「无需支付」
  共用同一份 `isFreeOfCharge` —— 两处各写一份的话，
  将来改一处就会出现「群里说账目已结清、系统却还在等他发图」
- 守门用例在 `QqReplyTextTests#isFreeOfCharge_alignsWithSettleDone`：
  判据本身（null / 0 / 0.00 / 正数）与文案的对应关系逐项对齐
- 修掉之后，0 元结账后发图走「根本没在等」的静默分支 —— 群里的休闲图本就不该被搭理

### STAFF 卡（模块 9）

给店员自己人的免单卡：`MonthlyCardType.STAFF`（中文名「STAFF 卡」，
2026-10-10 由用户定名 —— 我先写的「员工卡」被否），
`CardScope.ALL`、`isOnSale() = false`（不可购买，只在后台发放）。

- **「无到期日」用远期日期 2099-12-31 表达**（`MonthlyCardType.STAFF_END_DATE`），
  **不是**把日期列放开为可空。大日期方案让 SQL 的日期条件、`CardCoverage`、
  计费切段与跳档预告**一行不改**；放开可空则那条链路上每一处都要加 null 分支，
  漏判一处不是「少免一次」而是 NPE、结不了账 —— 这个取舍 2026-10-10 由用户拍板
  （原话：「填很大的日期就行了」；我最初的无日期方案被否）
- **起始日同样是远古日期 2000-01-01**（`STAFF_START_DATE`），**不是开卡当日** ——
  ⚠️ 2026-10-10 晚现场踩到（猫头鹰十七的卡不显示在在店列表）：在店名册与结算
  按**订单开始日期**判卡（两者必须同口径，见 `InstoreService`），而订单可能是
  昨天开的、人一直挂到现在 —— 拿昨天的日期去查今天才开的卡，
  `start_date <= 昨天` 不成立，卡片就显示不出来（「先开门、后开卡」同理）。
  填远古日期后这个坑整个不存在；开卡时刻不丢，它记在 `paid_at` 里。
  真库已有 4 张 STAFF 卡的 `start_date` 已随之 UPDATE 前移
- 计费侧零特判：2099 的区间天然覆盖所有订单（`nextCardBoundary` 不会切段、
  `nextChange` 不会误报到期），员工卡直接走 `CardCoverage.of(...)` 那条老路
- 与月卡**允许并存**（`issueCard` 对 STAFF 卡不校验已有卡）：给已有月卡的店员
  发卡是正常操作，挡住他只会让 STAFF 卡永远发不出来（月卡不能退）。
  并存时计费取 STAFF 卡 —— `selectActiveAt` 改为 `ORDER BY end_date DESC`，
  2099 最晚、天然胜出
- 收回走 `MonthlyCardStatus.REVOKED`（「已停用」，本批新增）——
  与 REFUNDED 分开，因为「卡停了」与「钱退了」是两个可以各自成立的结论
  （STAFF 卡没有钱的问题，报「已退款」是误导）
- 展示层两处按**卡种**特判（不是按日期大小 —— 后者会在 2099 年之后静默失效）：
  `MonthlyCardVo.remainingDays` 对 STAFF 卡返回 null（不报「还剩两万多天」），
  前端的卡包与后台弹层按卡种显示「长期有效」，不摆出 2099-12-31
- `cardTypes()`（在售列表）与 `purchase()` 都按 `isOnSale()` 拒绝 STAFF 卡 ——
  它出现在商城里的话，顾客能买到一张只该由店主发出去的卡

### 后台开卡 / 停卡（模块 9，面对面收款）

`POST /api/admin/cards`（开卡）与 `POST /api/admin/cards/{id}/revoke`（停卡）；

- 开卡补的是「用户自己线上购买」之外的那条路：顾客当面付了钱，管理员一次点完，

`biz_trade_log` 是 **2026-10-10** 才建的表（append-only，记四类事件）——**在那之前发生的到账没有流水**。
于是「前端累计收入」（取自流水的 `PAY_RECEIVED` 合计）只有 **112 元**，而订单 / 商品 / 月卡三张业务表里
躺着 2000 多元的已支付单。**两者对不上不是算法不同，是流水表的时间覆盖不全** ——
页面上又没有任何提示，谁看都会以为账算错了。

**做法**：一次性从三张业务表把「已支付且有到账时刻」的记录补成 `PAY_RECEIVED`：

- 逐条按 `(target_no, event_type)` **防重**（`NOT EXISTS` 子查询）—— 语句可重复执行，不会补第二遍
- ⚠️ `created_at` 取业务表上的 **`paid_at`**，不是补记时刻 —— 否则所有历史到账都会挤在补记那一天，
  「上月 / 本月收入」立刻失真
- `source` 记 `SYSTEM`、`remark` 写「历史补记：流水表上线前的到账（2026-10-10 建表）」，
  与真实事件一眼可辨
- 只补 `deleted = 0` 的单：有一笔 4 元的已支付订单是**软删**的，dry-run 时算进去了、实际没补
  —— 这正是「按 2144 核对会差 4 元」的原因，不是漏账

**结果**：补 **33 笔 / 2032 元**后，累计收入 **2140** ＝ 业务表四类已支付合计（未软删），逐分吻合。
月度分布：2026-09 = 665、2026-10 = 1475（合计 2140）。

**刻意没补的两类**：

- **包场**：`biz_booking` 里「已付款」的 0 笔（那 20 笔是**已退款**）。而流水表**没有退款事件**
  （`TradeEventType` 只有提交凭证 / 到账 / 驳回 / 取消未付款四类），补一条 `PAY_RECEIVED` 会让收入**虚增 311 元**。
  ⚠️ 也就是说**包场退款目前不落流水**（`BookingRefundService` 只改业务表）—— 这是个已知空档，
  将来要给包场做退款对账，得先补一个退款事件类型
- **`paid_at` 为空的单**（37 笔，全是 0 元单）：没有到账时刻，落不进时间线；金额为 0 也不影响合计

## 包场清场：追溯包场下的漏清（2026-10-10 深夜，模块 8）

**现象**：管理员设了一场覆盖当前时段的包场（10:00–22:00，20:20 才创建并付款），
店内两名非参与者，只有一人被清场结算，另一人（10:55 进店、晚于包场开始）还留着。

**根因**：`OrderService.settleNonParticipants` 有一条守卫 —— 跳过「订单开始时间
不早于包场开始时间」的订单，理由写的是「包场开始后非参与者已下不了单、这类单
不该存在；真出现（比如管理员补录）也不能按包场开始时刻倒着结算」。该前提只对
**提前排好的包场**成立：包场在本时段已经开始之后才创建/付款时，下单那一刻准入
还拦不住人，这类订单不但存在、而且完全合法 —— 被静默跳过了。

**修法**：结算时刻分两种取法 —— 订单在包场开始前就开着的，截止到包场开始时刻
（行为不变）；订单晚于包场开始的，**结算到当前时刻**（绝不能倒着填，那会算出
负时长，`applySettlement` 的 `stayMinutes` 与区间查询都不接受）。

**测试**：改写 `OrderServiceTests#settleNonParticipants_settlesLateStartedOrderAtNow`
（原名 `skipsOrdersStartedAfterBooking`，钉的正是旧行为）。全量 1358 个全绿。

**不扩大范围**：包场的计费区间剪切（`findCoveringBookings`）只认「订单挂 bookingId」
与「本人是包场人」两个来源，被清的散客两者都不是，不会被误剪成 0 元 —— 修之前
确认过这一条，所以只动清场、没动计费。

## 客户端形态：最小可安装 PWA（2026-10-10，前端）

### 只取「可安装」那一半，不做离线缓存

目标是让手机浏览器能弹「添加到桌面」。而**唯一**能弹出那个原生窗口的时机是
`beforeinstallprompt` 事件，浏览器只在判定「站点可安装」时才给 —— 判定条件恰好是
**manifest + 一个带 fetch 处理器的 Service Worker + HTTPS**，三条里没有一条与离线有关。
于是「PWA」被拆成两半取用：可安装条件必须凑齐，缓存策略一点不做。

| 文件 | 作用 |
|---|---|
| `public/manifest.webmanifest` | name / short_name / start_url / `display: standalone` / theme_color / 三个图标 |
| `public/sw.js` | **空的** —— 只有一个不调 `respondWith` 的 fetch 监听器，对请求完全透明 |
| `public/icons/icon-{180,192,512}.png` | 主题紫底 + 白色音符，PowerShell + `System.Drawing` 生成（`any` + `maskable`，内容画在中心安全区内） |
| `index.html` | manifest 链接、`apple-touch-icon`、iOS 的三个 `apple-mobile-web-app-*` meta |
| `src/main.js` | `load` 之后注册 SW，**失败静默**（非 HTTPS 必然失败，而它只影响能否装桌面） |
| `src/composables/useInstallPrompt.js` | 环境判定 + 存住事件 + 触发安装 |
| `src/components/InstallGuide.vue` | 提示条，挂 App.vue，`/admin` 路由不显示 |

### 四种环境、三条路

| 环境 | 提示条 | 为什么 |
|---|---|---|
| Android / 桌面 Chromium | 「添加」→ **系统原生安装窗** | 拦下 `beforeinstallprompt` 存住，用户点按钮时才调 `prompt()` |
| iOS（**所有**浏览器） | 「点底部分享 → 添加到主屏幕」 | iOS 至今没有对应事件，任何网站都一样（全 WebKit，苹果不给） |
| 微信 / QQ 内置浏览器 | 「点右上角 ⋯ → 在浏览器打开」 | 两家的 WebView 既没有添加到桌面能力，也**没有任何从网页侧唤起外部浏览器的接口** |
| 其他（Firefox、夸克……） | **不显示** | 没有可用路径；对做不到的事给提示只会让人白点一遍 |

### 非显然的几条

- **必须拦 `beforeinstallprompt`**：Chromium 早已不再自动弹那条小横幅；而事件是
  一次性的，不在事件里 `preventDefault()` 存下来，之后就没有任何办法触发安装了
- **微信 / QQ 里自动跳浏览器做不到**：Android 的 `intent://`、iOS 的自定义 scheme
  都被两家专门拦掉，硬绕有被封域名的风险 —— 这不是「没研究透」，是唯一解
- **UA 判断收进 `utils/ua.js`**（新增 `isQqInApp()` / `isInAppBrowser()` / `isIOS()`）：
  那里本来就是全站 UA 判断的出处（`isWechat()` 早已存在），散开写会变成几份略有
  出入的正则，而它们的失败方式是静默的
- **iOS 检测必须带 `maxTouchPoints`**：iPadOS 13+ 的 UA 伪装成 macOS，只看 UA
  会把 iPad 当成桌面 Mac —— 而这两类在「能不能弹原生窗」上处境完全相反

### 验证时踩的坑（Windows headless）

用 `chrome --headless --screenshot --window-size=390,760` 截窄视口**截不准**：
Windows 下 Chrome 窗口有最小宽度（约 500px），请求 390 会被抬高到 500，于是页面
按 476 的视口**正确居中**、截图却只裁了左边 390 —— 看起来像「内容偏右被切」，
而**代码完全没问题**。这一度让人以为提示条布局坏了，实际是量尺坏了。
（`tools/screenshots.mjs` 没这个问题，它走 CDP 的设备模拟绕开了窗口尺寸。）

## 后台订单流水：卡片上的优惠与订单详情页（2026-10-16 晚，模块 8 + 后台前端）

**改了什么**：计时订单的每张卡片上直接给出「计价 ¥40.00 → 实付 ¥35.00」，
以及月度优惠 / 月卡抵扣 / 活动减免**各**免了多少；点卡片进 `/admin/orders/:id` 看订单详情。

- **明细只能摊开写**：三种优惠的出资方不是同一个（月度累计优惠 / 月卡 / 活动），
  后端的 `discount_amount` / `card_free_amount` / `activity_free_amount` 本就是三列。
  合成一句「共减 ¥23.50」的话，月卡免掉的钱会被读成活动送的 —— 而那种错不报任何错
- ⚠️ **「计价」是反推出来的**：订单上没有原价列（`total_amount` 与 `payable_amount`
  存的都是**实收**，三项减免只是说明性字段），所以计价 = 实收 + 三项减免。
  有一处刻意不精确：**半场累计封顶**削掉的钱不在三项里，于是会被算进「计价」——
  这个数字的口径就是「没享受到这些优惠与额度时要付多少」，逐段解释仍在详情页账单里
- 没优惠的单子**不显示**那一行：九成订单没有优惠，每行都印一遍「计价」纯属噪音
- **商品订单的卡片不跳详情**：它的「详情」是商品与数量，卡片上已经写全；
  订单详情那一页讲的是时长与分段账单，对它是另一回事
- **卡片上印用户 ID，而且能点**（同日补）：筛选栏是按「用户 ID」查的，而管理员
  既背不下每个人的 ID、昵称又可能重名。点那个 ID 就**就地按他筛一遍**
  （`filterByUser`），省掉「看一眼详情、回来手抄一串数字」那一步。
  `@click.stop` 是必须的 —— 整张卡片本身可点，不拦住就会顺带跳进订单详情。
  商品流水那边同理（`filterProductByUser`），但**不切 tab**：
  在商品流水里点 ID 就把商品流水按他筛一遍，跳到计时流水反而违背「我正在看什么」

- **账单金额区排成一个算式**（同日补）：`优惠前 → 各项减免 → 合计 → 应付` ——
  多一行「优惠前」，并把三项减免挪到合计**之前**。原先是「合计 ¥21 / 月度优惠 -¥3」，
  读起来像「21 还要再减 3」，而实际是 24 减掉 3 才是 21。
  口径与后台卡片上的「计价」逐字同源（`合计 + 三项减免`，订单上没有原价列），
  没优惠的订单不显示这一行。⚠️ `BillSegmentList` 是**用户端与后台共用**的组件，
  所以顾客看到的账单同步变了 —— 这一条是用户明确点头后才动的（2026-10-16）

**同日还加了一条开发期便利**：后端启动完成时弹一条 Windows 桌面通知
（`common/dev/StartupToastNotifier`）—— `mvn spring-boot:run` 起完、以及 devtools
因改代码热重启完都会弹一条「后端启动完成喵」，省掉「盯着一大片日志猜什么时候能点页面」。

### 流水页的筛选与页码写进 URL

tab、筛选、页码经 `router.replace` 落到 URL 的 query 上；从详情页返回时由
`OrderDetailView#goBack` 原样带回来 —— 筛出某个用户后连看几单，不必每单重填一次筛选。
顺带得到「刷新不丢筛选、URL 可直接发给同事」。

- ⚠️ 用 `replace` 不用 `push`：筛选是「同一屏的不同看法」，每改一次压一条历史的话，
  后退键要按很多次才退得出这一页
- ⚠️ **不监听 `route.query`**（监听 + replace 容易写成死循环）：query 只在挂载时读一次。
  页码只接受正整数 —— URL 是手可以改的，`?page=abc` 要回落到第 1 页而不是带着 `NaN` 去请求

**验证**：`npm run build` 通过（含新页面与共享组件）、后端 `mvn -DskipTests compile` 通过。

> ⚠️ 这一段当时写的是「**没能起真后端跑一遍**，只到构建层」—— **那条后来被推翻了**。
> 当时看到的是「MySQL 没在跑、`MYSQL_PASSWORD` / `JWT_SECRET` 未设置」，其实三样全都在：
> MySQL 服务是 Running（沙箱里读不到 TCP 表，把空结果当成了「没开」），
> 两个变量也早配在**用户级注册表**里、只是没继承给当前进程。注入之后端到端一次跑通 ——
> 教训是「进程环境里没有」不等于「机器上没有」，查环境变量要连注册表一起看。

### 计费时长与在店时长：什么时候它们不一样（同日实测）

用户问「这两个不是语义重复吗」—— 实测结论：**语义不重复，但 59 单里 58 单数值相同**。

- **在店时长** = 离场时刻 − 开门时刻（整段一次截断到分钟）→ 回答「他**待了多久**」
- **计费时长** = 各计费段时长之和 → 回答「按**多久收的钱**」
- 全库 59 单里只有 **1 单**两者不同（id 3274：`5366` vs `5006` 分钟，**差 360 分钟 = 6 小时**，
  正是被包场剪掉的那一段）；其余 58 单两者完全相等 —— 所以日常看起来确实像重复
- 另有一种理论上的分叉：跨时段切段时**每段各自向下取整**，合计最多比整段一次取整
  少 0~1 分钟（现实中没出现过这个量级）
- **结论：两个都要留**。少了「在店时长」，包场单上「待了 2.5 小时只收 30 分钟的钱」
  就成了一桩说不清的事 —— `freeByBooking` 那句「包场时段不计费…」正是为它准备的
- 待定的显示优化（用户还没拍板）：**两者相同时只显示一行**，只有分叉时才把两行都列出来

### 端到端是怎么验的（可复用的做法）

这一轮的界面改动是**真跑后端 + 真浏览器**验过的（20/20 项断言通过、零控制台错误），
做法记在这儿，以后照抄：

1. **起后端前先把环境变量补上**：`MYSQL_PASSWORD` / `JWT_SECRET` / `BAIDU_OCR_API_KEY` /
   `BAIDU_OCR_SECRET_KEY` 都配在**用户级**环境里，而运行进程未必继承得到 ——
   `[Environment]::GetEnvironmentVariable($n,'User')` 取出来再 `Set-Item Env:$n` 注入。
   少任何一个的表现都很具体：缺 `JWT_SECRET` 直接拒绝启动，缺 OCR 凭据则是
   `uspace.ocr.provider=baidu 但未配置凭据`
2. **前端要用 `vite preview --mode tunnel`**：只有 tunnel 构建的产物才走相对路径、
   由 preview 反代 `/api`；用普通构建的产物会去找 `http://<hostname>:8080`，
   表现为「一直说后端未启动」（`vite.config.js` 里有 `requireTunnelBuild` 拦这一条）
3. **登录用本机调试管理员**：账号在 `CLAUDE.md`（不进版本库），**随用随开、用完立刻禁回去**
4. **浏览器用 `tools/cdp.mjs`**（零依赖、自起无头 Chrome）驱动；
   硬指标是**零控制台错误** —— 页面渲染对了但底下报错，往往意味着某个分支已经坏了
5. **特殊用例不必造整条业务链路**：想验「2.5 小时里插 2 小时包场」这种账单，
   直接插一条**带合法 `bill_snapshot` 的订单**即可。⚠️ 前提是
   `OrderService#attachBill` **优先读快照**、只有快照缺失才重算，
   所以手写一份 JSON（字段照抄真实快照、时间格式 `yyyy-MM-dd HH:mm:ss`）就走到真实渲染了，
   **不用真去排一场包场**。造出来的测试单跑完**逻辑删除**（`deleted=1`），别留在流水里
6. **截图之后要看图**，不能只靠 DOM 文本断言：文字断言能证明「那几行在」，
   证明不了「排版有没有被挤坏」。用户端与后台各截一张（414px 手机 / 1280px 桌面），
   同一张订单对比着看，才能确认「同一个组件、两端一致」这句话是真的

## 桌面端整体等比放大（2026-10-16，前端）

用户反馈：同一套界面，在他的机器（1920×1080 屏 + Windows **125% 缩放**）上看着正合适，
在 **100% 缩放**的机器上「界面元素特别小」。这不是样式写错了 —— Windows 显示缩放
只决定「1 个 CSS 像素占几个物理像素」，而窄列是写死的 360px：

| 机器（同一块 1920×1080 屏） | 窗口最大化后的视口宽 | 360px 窄列的物理宽度 |
|---|---|---|
| @125% 缩放 | 1536 CSS px | 450 px（看着正合适） |
| @100% 缩放 | 1920 CSS px | 360 px（**小 20%**） |

**做法：把布局宽度钉在 1536 这一档，再整体等比放大填满窗口** ——
`--ui-scale = 视口宽 ÷ 1536`（夹在 `[1, 2]`），手机 / 平板 / 没最大化的窗口恒为 1（原样）。

| 文件 | 作用 |
|---|---|
| `src/utils/uiScale.js`（新增） | 算倍数 + 写 `:root` 的 `--ui-scale` + 跟 `resize` 重算 |
| `src/assets/styles/tokens.css` | `--ui-scale: 1`（默认值，全站唯一出处） |
| `src/assets/styles/base.css` | **唯一的落点**：`#app { zoom: var(--ui-scale) }` |
| `src/main.js` | `mount` **之前**调用 `installUiScale()` —— 此时页面上还没有内容，不会跳一下 |

四条不显然的取舍：

- **用 `zoom` 而不是 `transform: scale`**：`transform` 会成为 `position: fixed` 后代的
  包含块，底部 TabBar、各种弹层、请求遮罩会**跟着页面滚走**（fixed 变成相对被变换的祖先
  定位）；`zoom` 不动包含块，fixed 仍锚在视口上，只是整体一起被画大
- **不按窗口宽度另做一套尺寸**（放大字号、加宽栅格）：那正是 2026-10-03 否掉的
  「两套规则」，会与 `--page-max` 那条「手机与电脑一模一样」直接打架。
  zoom 是整体画大，栅格仍是写死的两列 —— 也因此**不会引起任何回流**
- **不拿 `devicePixelRatio` 反推**：它把「系统缩放」与「浏览器页面缩放（Ctrl+加号）」
  乘在一起，看不出哪个是哪个；而**视口宽度是两者共同作用后的结果**，用它不会跟用户的
  浏览器缩放对着干（窄列占窗口宽度的比例恒定）
- **重算用 `setTimeout` 防抖，不用 `requestAnimationFrame`**：页面被隐藏（后台标签页）时
  rAF 回调**根本不执行**，而 resize 事件照来 —— 用 rAF 的话第一次隐藏期间的 resize
  就会把「已排队」的标记永远留在那里，之后所有 resize 都被吞掉，
  界面大小从此定格在旧值上（且不报任何错）

**媒体查询不受影响**（zoom 不改变它看到的视口宽度）：全项目只剩 `AdminSheet` 一处
768px 查询，而倍数 > 1 只在视口 ≥ 1536 时出现，两者不会打架。

验证（跑的是真页面，不是示意图）：同源 iframe 模拟不同宽度的窗口，读回真实几何，
并核对 `#app` 的 computed `zoom` 确实等于变量值：

| 视口宽 | `--ui-scale` | `.login` 宽 | 登录按钮高 |
|---|---|---|---|
| 393（手机） | 1 | 393 | 46 |
| 1536 | 1 | 420 | 46 |
| 1920 | 1.25 | 525（＝420×1.25） | 57.5 |
| 2560 | 1.67 | 701.4 | 76.8 |

再按「同一块 1920×1080 屏」截两张图对比（`--force-device-scale-factor` 模拟两种缩放，
两张 PNG 都是 1920×1080）：**125% 缩放 + 1536 窗口**与**100% 缩放 + 1920 窗口**里，
登录卡片都落在 x≈748~1172（宽约 425 物理像素）—— **物理观感一致**，也正是这次改动的目的。

## Phase 3 付款凭证（核心）

`biz_payment_proof` 一张表承载**四类收款**的凭证
  （订单 / 包场 / 月卡 / 商品），`PaymentProofService` 统一受理提交与复核
  - **交付时机分两层**，由 `PaymentTargetHandler.deliverOnSubmit()` 声明：
    **订单与商品提交即交付**（当场落账、库存当场扣、欠费拦截当场解除），
    **包场与月卡等复核**。依据是「这笔钱买的东西能不能当场交付」——
    对包场与月卡来说「放行」与「落账」**是同一件事**（邀请令牌与卡都产生在
    `markPaid` 里），所以它们不能只改一个查询条件就放行
  - ⚠️ **由此带来的风险与处置（2026-10-04 改）**：订单与商品是「先交付后复核」，
    复核不通过时目标已经落账。**驳回会把这一步退回去**（`revertDelivery`）：
    订单标记为 `REJECTED`（凭证未通过）并清掉支付四列、商品退回购买单、累计消费冲减；
    **商品不退库存**（货多半已被取走，还回去是记假账）。
    退回去顺带恢复了欠费拦截 —— 有被驳回的账在，他开不了新单
  - **`PaymentService.settleByProof` 取代了原先的 `confirmPayment`**，
    与线上回调写的是同一批字段、同一套累计分派。**传播行为取 MANDATORY** ——
    它必须跑在调用方的事务里，否则会出现「凭证落了库、钱没落账」的半成品状态
  - **提交有两条新接口**（`POST /api/payment-proofs` 提交、
    `POST /api/payment-proofs/image` 上传截图），**提交时没有金额参数** ——
    凭证金额取自目标本身，不由请求体决定
  - **五条分支**（见 `PaymentProofService` 的类注释）：待支付 / 已支付 + 待复核 /
    已核对 / 未通过 / 线上通道付过。**执行顺序是「先读目标 → 再 upsert 凭证 →
    最后落账」**，反过来时并发的第二次会撞 `uk_target` 抛异常，
    用户重试看到的是「当前状态不支持该操作」这种完全指错方向的提示
  - **同一流水号被多笔凭证引用会被标记风险**（走 `idx_payment_no` 的一条 SQL）——
    一张截图付两单是纯信任制下最省事的作弊手法，而它留下的痕迹只有这一个。
    **不拦提交**，只在后台把相关条目排到最前并标红 —— 静默拒绝一笔可能的
    正常付款（用户抄错一位、同一笔在两个页面都交了一次）比让管理员多看一眼糟得多。
    重交时旧标记会被清掉（否则假警报越积越多，管理员干脆不看了）
  - **`proof_url` 一定校验前缀**（`{url-prefix}/proof/` + 不含分隔符 + 不含 `..`）：
    请求体是客户端给的，不校验就能塞外链（管理员的浏览器会去加载别人的服务器，
    等于泄露「谁在什么时候付款」）或塞别的 kind 的图
  - **后台 `/admin/payments` 扩成两 tab**：「待复核」（默认）与「收款码」。
    一打开先看到最该处理的
  - 新增错误码六个：`PAYMENT_PROOF_IMAGE_INVALID`(40002)、
    `PAYMENT_PROOF_NOT_FOUND`(40415)、`PAYMENT_PROOF_REJECTED`(40939)、
    `PAYMENT_PROOF_STATUS_INVALID`(40940)、`PAYMENT_PROOF_TARGET_INVALID`(40941)、
    `PAYMENT_ALREADY_PAID`(40942)。`PAYMENT_PROOF_REQUIRED`(40921) 保留但**已无调用方**
  - **删除**（已获批准）：`POST /api/orders/{id}/payment-proof`、

    **`biz_order.payment_proof` 那一列保留**（DROP 不可逆），只把注释标了废弃
  - ⚠️ **`PaymentProofMapper.upsert` 是手写的 `@Insert`，MyBatis 不回填主键**
    （`useGeneratedKeys` 只配在 MyBatis-Plus 自带的 `insert` 上）。
    需要 ID 时用 `selectByTarget` 再查一次 —— **刻意不加 `@Options`**：
    加了的话插入路径能拿到 ID、冲突路径拿到的却是 `ON DUPLICATE KEY UPDATE` 下
    不可靠的值，一个「有时对有时错」的 ID 比恒为 null 的更危险
  - ⚠️ **`Order.paymentProof` 字段是刻意删掉的、不是遗漏**：映射了就会有人写它，
    而 `updateById` 跳过 null 的语义会让一次普通的订单更新把凭证静默清空

## Phase 4 识别（OCR）

`order/ocr/` 子包，7 个类 + 1 个配置类
  - `OcrService`（接口，`OcrResult recognize(byte[])`）、`OcrResult`
    （`success` / `errcode` / `errmsg` / `List<String> lines`，照 `PasscodeResult`
    的形状）、`OcrFields`（record：单号 / 金额 / 原文）、`OcrTextParser`
    （纯静态解析规则）、`OcrProperties`、`mock/MockOcrServiceImpl`、
    `baidu/BaiduOcrServiceImpl` + `baidu/BaiduOcrConfig`
  - ⚠️ **`order/ocr/` 是子包，与 `order/mock/` 那个先例不完全一致** —— 理由是
    OCR 有 7 个类（接口、配置、两个 DTO、解析器、两个实现），摊进已经有四十来个
    文件的 `order/` 根下只会让它更难找。两个实现仍按先例放在 `mock/` 与 `baidu/` 子包里
  - **`OcrFields.isEmpty()` 只看单号与金额，不看原文**：原文是给管理员看的，
    用户端看不到，因此不能拿它当「识别出了东西」的依据（传一张风景照也能
    识别出一堆无关的字）
  - **`BaiduOcrConfig` 单独存在**：`RestClient` 的 baseUrl 与超时在那里配，
    服务类注入的是**造好的 `RestClient`**。服务若自己去动 `RestClient.Builder`，
    就会覆盖掉单测里 `MockRestServiceServer` 设下的拦截工厂，
    让测试静默地打真网络并**照样全绿**
  - **token 缓存复用（30 天）+ 110/111 时清缓存重试一次**：后者是「防 OCR
    从某天起永久静默失效」的阀 —— 百度控制台轮换密钥会让 token 提前作废，
    此后每个请求都稳定失败而表现只是「识别不出」
  - **NFKC 归一化**：OCR 只认字形不认宽度，`８．００` 与 `8.00` 是同一张图
  - 新增配置 `uspace.ocr.provider`（`mock`/`baidu`）、`uspace.ocr.timeout-millis`、
    `uspace.ocr.baidu.api-key` / `secret-key`（走环境变量 `BAIDU_OCR_API_KEY` /
    `BAIDU_OCR_SECRET_KEY`）。**没有新增错误码**
  - 前端三处：`ProofSubmitSheet`（上传后预填单号、展示识别到的金额、
    **三个字段每次上传都无条件覆盖**）、`api/payment.js` 的 `submitProof`、
    后台 `PaymentManageView`（补 `ocrPaymentNo` 与折叠的 `ocrText`）
